# CrossTrialLog: история Sharpe-значений по всем прогонам

**TL;DR:** CrossTrialLog — это накопительный журнал результатов всех тестовых прогонов бота, сохранённый в файле `data/cross_trial_sharpes.json`. Он нужен для честного расчёта DSR — особой метрики качества стратегии, которая учитывает, сколько раз мы «примерили» разные варианты на одних и тех же данных.

---

## Простыми словами

Представьте, что вы тестируете рецепт торта. Если вы приготовили его один раз и получилось вкусно — это один результат. Но если вы уже испробовали 50 рецептов на тех же гостях, а потом выбрали лучший — гостям уже нельзя доверять как объективным судьям: они «привыкли» к вашим экспериментам.

То же самое в трейдинге. Если бот тестировал 30 вариантов стратегии на одних и тех же исторических данных и выбрал самый прибыльный — часть этой прибыли объясняется простой случайностью, а не реальным преимуществом. Это явление называется **переподгонкой** (по-английски — overfitting) и относится к [[dsr-and-mc|проблеме множественного тестирования]] (см. также [[tstat-oos-is-metrics|OOS/IS Sharpe]]).

Чтобы честно оценить, насколько хороша стратегия, нужно знать:
1. Насколько сильно «прыгает» её результат от прогона к прогону (разброс Sharpe-ратио).
2. Сколько всего прогонов было проведено за всю историю.

**CrossTrialLog — это блокнот**, где бот после каждого завершённого тестового прогона записывает итоговое значение **OOS Sharpe** (результата на «невиданных» данных) вместе с тем, какая именно стратегия тестировалась, на каком инструменте и в каком спринте (цикле разработки). Блокнот хранится на диске, не теряется между перезапусками, и из него позднее вычисляется разброс — **sigma_SR**.

> **OOS Sharpe** (Sharpe вне выборки) — это показатель качества стратегии, посчитанный на данных, которые стратегия «не видела» во время обучения. Подробнее: [[03-индикаторы-и-расчёты/sharpe-sortino-metrics]].

> **Sigma_SR** — стандартное отклонение OOS Sharpe по прогонам. Это мера разброса: насколько сильно результат стратегии колеблется от прогона к прогону. Используется в формуле DSR для поправки на многократное тестирование.

## Как это работает у нас

### Структура данных

Журнал хранится в файле `data/cross_trial_sharpes.json`. Каждая запись называется **TrialEntry** и содержит четыре поля:

```python
class TrialEntry(TypedDict):
    sprint: int           # номер спринта разработки (S13, S15, S44...)
    symbol: str           # торговый инструмент + параметры (например "BTCUSDT_9_2.5")
    strategy_class: str   # семейство стратегии ("supertrend", "atr_breakout"...)
    oos_sharpe: float     # итоговый OOS Sharpe этого прогона
```

Пример реального содержимого файла:

```json
{
  "trials": [
    {"sprint": 44, "symbol": "BTCUSDT_9_3.0",  "strategy_class": "atr_breakout", "oos_sharpe": -14.41},
    {"sprint": 44, "symbol": "ETHUSDT_9_3.0",  "strategy_class": "atr_breakout", "oos_sharpe": -89.49},
    {"sprint": 44, "symbol": "BTCUSDT_9_?",    "strategy_class": "volume_breakout", "oos_sharpe": -0.28},
    {"sprint": 50, "symbol": "BTCUSDT_7_3.0",  "strategy_class": "supertrend",   "oos_sharpe": -9.38}
  ]
}
```

`(src/analytics/cross_trial_log.py:73-88)`

### Метод `append_trial()` — добавление записи

Когда бот завершает прогон бэктеста, он добавляет результат в журнал:

```python
trial_log.append_trial(
    sprint=sprint_int,
    symbol=f"{symbol}_{params.get('atr_period', '?')}_{_mult}",
    strategy_class=strategy_class,
    oos_sharpe=trial_mean_fold_oos_sharpe,
)
```

`(src/backtest/research_wfa.py:272-276)`

Метод работает **идемпотентно** — это значит, что повторный вызов с теми же `(sprint, symbol)` не добавит дубликат, а заменит существующую запись. Это важно, потому что дашборд мог раньше дублировать записи при каждом перерасчёте. Исправлено в S45 B1.

Логика идемпотентности:
1. Загрузить все записи из файла.
2. Поискать существующую запись с тем же `(sprint, symbol)`.
3. Если нашли — заменить `oos_sharpe` на новое значение (позиция в списке сохраняется).
4. Если не нашли — добавить в конец.
5. Записать обратно на диск.

`(src/analytics/cross_trial_log.py:150-195)`

**Ключ идемпотентности — только пара `(sprint, symbol)`.** Поле `strategy_class` является метаданными и не входит в идентификатор записи: если вы перезапустите прогон с другим классом стратегии, но теми же спринтом и символом — `strategy_class` обновится, но запись не задублируется. `(src/analytics/cross_trial_log.py:179-189)`

---

### Атомарная запись — защита от потери данных

Файл никогда не перезаписывается напрямую. Вместо этого:

1. Данные записываются во временный файл `cross_trial_sharpes.json.tmp`.
2. Затем временный файл переименовывается в основной одной операцией (`rename`).

Переименование на уровне операционной системы — атомарная операция: либо файл целый, либо старый. Никакого «полузаписанного» промежуточного состояния. `(src/analytics/cross_trial_log.py:193-195)`

### Метод `n_trials()` — глобальный счётчик прогонов

```python
def n_trials(self) -> int:
    return len(self._load())
```

`(src/analytics/cross_trial_log.py:142-148)`

`n_trials()` возвращает **суммарное количество всех записей** — без фильтрации по классу стратегии или инструменту. Если в одном спринте тестировали три разных инструмента (BTC, ETH, SOL) — это три отдельные записи, `n_trials()` вернёт 3. Методологически это правильно: три теста = три независимые возможности подобрать «удачный» результат случайно.

> Это **намеренное решение** (протокол (a) по Bailey & López de Prado): каждая пара `(спринт, инструмент)` считается независимым испытанием. Один спринт с тремя инструментами — это три испытания, не одно. `(src/analytics/cross_trial_log.py:10-12)`

### Метод `sigma_sr()` — разброс Sharpe по прогонам, с двумя режимами

```python
def sigma_sr(self, strategy_class: str | None = None) -> float | None:
```

`(src/analytics/cross_trial_log.py:197-232)`

Это главный метод журнала. Он считает **стандартное отклонение** (разброс) всех OOS Sharpe-значений. Чем больше разброс — тем менее стабильна стратегия и тем более суровой будет поправка DSR.

Метод имеет два режима:

**Режим 1 — глобальный пул** (`strategy_class=None`):
Берёт все записи без разбора, считает stdev по всему списку. Использовался до S51 D5, сохранён для обратной совместимости. `(src/analytics/cross_trial_log.py:219-220)`

**Режим 2 — пул по классу стратегии** (`strategy_class="supertrend"`):
Берёт только записи указанного класса, считает stdev внутри него. Введён в S51 D5. `(src/analytics/cross_trial_log.py:221-226)`

Зачем нужен режим 2? Рассмотрим реальный пример из журнала: стратегия `atr_breakout` на ETHUSDT в спринте 44 получила OOS Sharpe = **-89.49** — аномальное значение. Если бы мы считали sigma_SR по всему пулу (включая записи `supertrend`), этот выброс увеличил бы «кажущийся разброс» supertrend и неоправданно занизил бы её DSR. Бот выглядел бы плохим там, где он работает нормально. `(src/analytics/cross_trial_log.py:13-20)`

---

### Три ветки результата `sigma_sr()`

| Количество записей в пуле | Что возвращает | Что это значит |
|---|---|---|
| 0 записей | `None` | Журнал пуст, прогонов ещё не было |
| 1–2 записи | `float("nan")` (не-число) | Математически недопустимо (степени свободы < 2) |
| ≥ 3 записи | число (stdev) | Нормальный результат, используется в DSR |

`(src/analytics/cross_trial_log.py:227-232)`

Почему 1–2 записи возвращают NaN, а не просто маленькое число? Потому что стандартное отклонение по двум точкам имеет **одну степень свободы** — оценка крайне ненадёжна. Учёные Bailey & López de Prado 2014 указывают это явно как недопустимое. ADR 0056 закрепил этот порог: нужно минимум три честных независимых прогона, чтобы sigma_SR стала статистически обоснованной. `(src/analytics/cross_trial_log.py:200-203, 216-217)`

---

### Два уровня поправки в DSR: sigma_SR и N_trials

Это принципиально важное разграничение, введённое в S51 D5. Оба числа затем подставляются в формулу [[deflated-sharpe-ratio|DSR]] (Bailey & López de Prado 2014).

**sigma_SR** — разброс Sharpe-значений — считается **по классу стратегии**. Каждая семья стратегий имеет свою характерную нестабильность, и смешивать их было бы некорректно.

**N_trials** (счётчик прогонов) — считается **глобально** по всему журналу. Логика: общий «бюджет» тестирования — единый для проекта. Новая семья стратегий не «сбрасывает» счётчик. `(src/analytics/cross_trial_log.py:15-21)`

Пример: если бот провёл 5 прогонов atr_breakout и 3 прогона supertrend, то:
- `n_trials()` = 8 (все вместе)
- `sigma_sr(strategy_class="supertrend")` = stdev трёх результатов supertrend (только они)
- `sigma_sr(strategy_class="atr_breakout")` = stdev пяти результатов atr_breakout (только они)

### Статусы sigma_scope_status в research_wfa

Когда `research_wfa` (ядро исполнения пробойных стратегий, см. [[research-kernel-execution-model]]) использует журнал при расчёте DSR, он присваивает один из трёх статусов:

| Статус | Когда возникает | Что делает DSR |
|---|---|---|
| `SINGLE_TRIAL` | Передан `n_trials=1` | Поправки нет, один прогон |
| `INSUFFICIENT_CLASS_HISTORY` | `sigma_sr()` вернул None или NaN | `effective_n_trials=1`, поправка не применяется |
| `CLASS_SCOPED` | sigma_sr готова (≥3 записей) | Полная поправка с n_trials и sigma_SR |

`(src/backtest/research_wfa.py:295-312)`

Статус `INSUFFICIENT_CLASS_HISTORY` означает: «класс стратегии новый, прогонов ещё меньше трёх — мы честно говорим, что поправка не применяется, а не подставляем сомнительное число». Первые 1–2 прогона любого нового класса стратегий всегда попадают в этот статус. Это намеренно: DSR тогда опирается на другие ворота (T5, [[mc-permutation-test|Монте-Карло]], fold-Sharpe). `(src/analytics/cross_trial_log.py:27-31)`

### Обратная совместимость — backfill старых данных

Журнал несколько раз менял схему:

- **До S33** — поля `symbol` не было. При загрузке старых записей поле заполняется значением `"BTCUSDT"` по умолчанию (все исторические прогоны до S33 были на одном инструменте — BTC). `(src/analytics/cross_trial_log.py:122-123, 91)`
- **До S51** — поля `strategy_class` не было. При загрузке таких записей поле заполняется значением `"unknown"`. `(src/analytics/cross_trial_log.py:123-126, 94)`

Никакого скрипта миграции запускать не нужно: backfill происходит автоматически при каждом чтении файла через метод `_load()`. `(src/analytics/cross_trial_log.py:109-129)`

## Формулы и расчёты

### sigma_SR (стандартное отклонение Sharpe-ратио)

Формула (Bailey & López de Prado 2014, уравнение 13):

```text
sigma_SR = stdev([oos_sharpe_1, oos_sharpe_2, ..., oos_sharpe_N])
```

Расшифровка простыми словами: берём все OOS Sharpe-значения, накопленные в журнале для данного класса стратегии, и считаем, насколько они разбросаны вокруг среднего. Это **выборочное стандартное отклонение** (делим на N-1, не N) — именно его возвращает `statistics.stdev()` в Python.

Реализация:

```python
return float(statistics.stdev(sharpes))
```

`(src/analytics/cross_trial_log.py:232)`

Условие применения: N ≥ 3. Иначе — NaN (1–2 записи) или None (0 записей).

## Примеры / сценарии

### Сценарий 1: первый прогон (журнал пуст)

Ситуация: мы впервые запускаем бэктест стратегии `supertrend` на BTCUSDT. В журнале ничего нет.

1. `append_trial(sprint=50, symbol="BTCUSDT_7_3.0", strategy_class="supertrend", oos_sharpe=-9.38)` — добавляем первую запись.
2. `n_trials()` → 1
3. `sigma_sr(strategy_class="supertrend")` → `float("nan")` (N=1, статистически недопустимо)
4. В `research_wfa` срабатывает ветка `INSUFFICIENT_CLASS_HISTORY` → DSR считается с `n_trials=1`, поправки нет.

### Сценарий 2: накоплено три прогона одного класса (гипотетический пример)

Ситуация: представим, что в журнале ровно три записи стратегии `atr_breakout` — по одному прогону на трёх разных наборах параметров. (Реальный журнал может содержать больше записей, и тогда sigma_SR будет другой — метод всегда использует все записи указанного класса.)

| Запись | sprint | symbol | strategy_class | oos_sharpe |
|---|---|---|---|---|
| 1 | 10 | BTCUSDT_9_3.0 | atr_breakout | -14.41 |
| 2 | 10 | BTCUSDT_9_2.5 | atr_breakout | 0.37 |
| 3 | 10 | ETHUSDT_9_3.0 | atr_breakout | -89.49 |

`sigma_sr(strategy_class="atr_breakout")` → `stdev([-14.41, 0.37, -89.49])` ≈ 48.2

Это огромный разброс. Это значит, что DSR получит жёсткую поправку на нестабильность atr_breakout, что честно отражает реальность: стратегия очень нестабильна.

### Сценарий 3: защита от перезаписи дубликата

Ситуация: дашборд вызывает `append_trial(sprint=44, symbol="BTCUSDT_9_2.5", oos_sharpe=1.55)` повторно (например, при перерисовке страницы).

- Метод находит существующую запись `(44, "BTCUSDT_9_2.5")`.
- Заменяет `oos_sharpe` с прежнего значения на `1.55`.
- `n_trials()` остаётся прежним — дубликата нет.

`(src/analytics/cross_trial_log.py:179-191)`

### Сценарий 4: загрузка старого журнала без поля `strategy_class`

Старый файл (до S51):

```json
{"trials": [{"sprint": 13, "symbol": "BTCUSDT", "oos_sharpe": -44.46}]}
```

После `_load()` запись получает `strategy_class = "unknown"`. Никаких ошибок, никакого ручного вмешательства. `(src/analytics/cross_trial_log.py:123-126)`

## Подводные камни / что важно понимать

**N_trials — глобальный, sigma_SR — по классу.** Это принципиальное разграничение S51 D5. Не путать: `n_trials()` всегда возвращает полное число записей по всему журналу, а `sigma_sr(strategy_class=...)` смотрит только внутрь указанного класса.

**Порог N=3 — жёсткий.** При 1 или 2 записях метод возвращает `float("nan")`, а не «маленький стdev». Это не ошибка — это намеренная защита от статистически бессмысленных оценок. Новые стратегии первые два прогона будут получать `INSUFFICIENT_CLASS_HISTORY`.

**Ключ идемпотентности не включает `strategy_class`.** Если в одном прогоне стратегия называлась `"atr_breakout"`, а в повторном вы передали другое имя — запись обновится (включая `strategy_class`), но не задублируется. Это означает, что класс стратегии определяется последним вызовом для данной пары `(sprint, symbol)`.

**Журнал не потокобезопасен.** Класс работает в режиме одного писателя — один CLI-вызов за раз. Параллельные запуски могут конкурировать за файл. `(src/analytics/cross_trial_log.py:101-103)`

**Тесты не трогают реальный журнал.** Переменная окружения `CROSS_TRIAL_LOG_PATH` перенаправляет путь во временную директорию. Если вы запускаете тесты и потом видите, что в `data/cross_trial_sharpes.json` что-то изменилось — это баг в тестовом окружении, а не штатное поведение.

**Symbol в записи — это не просто торговый инструмент.** В `research_wfa` символ формируется как `{ticker}_{atr_period}_{multiplier}` (например `"BTCUSDT_9_2.5"`), что делает его уникальным по параметрам. Это позволяет хранить несколько прогонов с одним инструментом, но разными параметрами, в рамках одного спринта. `(src/backtest/research_wfa.py:274)`
