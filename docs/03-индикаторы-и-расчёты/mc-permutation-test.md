# Монте-Карло: тест статистической значимости стратегии

**TL;DR:** бот проводит 2000 испытаний, в каждом из которых случайно «переворачивает» знак каждой сделки: из прибыли в убыток и обратно. Если реальный результат стратегии лучше, чем хаотичные перестановки в 95% случаев, стратегия считается незакономерно прибыльной — и это называется статистически значимым результатом. Порог: `p ≤ 0.05`.

---

## Простыми словами

Представьте, что вы подбрасываете монету 100 раз и выигрываете 60. Может быть, монета нечестная — а может, просто повезло? Как проверить?

Идея: сыграть ту же игру ещё 2000 раз, но уже с **честной** монетой (которая не знает «куда» упасть). Если честная монета хотя бы в 5% случаев даёт результат не хуже вашего — значит, ваши 60 выигрышей вполне могли оказаться случайными. Если нет — значит, что-то в вашем подходе действительно работает.

Именно это делает тест Монте-Карло с перестановкой. «Монте-Карло» здесь — это название метода: многократно повторять случайный эксперимент и смотреть на распределение результатов. «Перестановка знаков» — конкретный способ сымитировать «честную» случайную стратегию.

**P-value (уровень значимости)** — это вероятность получить такой же или лучший результат при условии, что стратегия ничем не лучше монеты. Чем меньше p-value, тем увереннее можно сказать «это не везение».

**Нулевая гипотеза** — исходное предположение, которое тест пытается опровергнуть: «доходности симметричны вокруг нуля, то есть у стратегии нет направленного преимущества». Наша задача — набрать достаточно свидетельств против этой гипотезы.

**Sign-flip (переворот знака)** — технический приём: умножаем каждую доходность на случайное +1 или −1. Это эквивалентно вопросу: «а что если бы каждая сделка случайно оказалась убыточной или прибыльной?». Если реальный средний результат всё равно выше большинства таких «перетасованных» вариантов — значит, у стратегии есть устойчивое преимущество.

## Как это работает у нас

### Шаг 0. Откуда берутся данные

Тест получает на вход массив `returns` — процентные доходности по каждой сделке из OOS-фолдов [[walk-forward-analysis|walk-forward analysis]]. Это реальные результаты по уже завершённым сделкам: не цены, не индикаторы, а итог каждой конкретной позиции в процентах.

Все три основных запускателя бэктеста вызывают `sign_flip_p_value` именно с агрегированными OOS-доходностями и одинаковыми параметрами `n_iterations=2000, seed=42` — это [[single-symbol-wfa-and-data-loading|загрузчик данных одного символа]] и эталонный [[donchian-runner-and-reference-run|Donchian runner]].
(src/backtest/research_wfa.py:224, src/backtest/data_loading.py:170, src/backtest/donchian_runner.py:135)

### Функция `sign_flip_p_value()` — основной тест (L2 gate)

Это главная функция, которая определяет, пройдёт ли стратегия ворота допуска к торговле.

```python
def sign_flip_p_value(
    returns: npt.NDArray[np.float64],
    *,
    n_iterations: int = 2000,
    seed: int | None = 42,
) -> float:
```
(src/backtest/mc_permutation.py:28-33)

**Что делает, шаг за шагом:**

1. **Защитная проверка.** Если массив пуст — возвращает `NaN` (не ноль и не единицу, а «нет данных»). Пустой массив означает, что в OOS не было ни одной сделки. (src/backtest/mc_permutation.py:51-52)

2. **Вычисляет наблюдаемый показатель.** Берёт `abs(mean(returns))` — абсолютное значение средней доходности по всем сделкам. Это «планка», которую должны превысить случайные перестановки. Модуль нужен потому, что тест двусторонний: нас интересует любое отклонение от нуля. (src/backtest/mc_permutation.py:54)

3. **Инициализирует генератор случайных чисел** с фиксированным `seed=42`. Это критично: без фиксации одни и те же данные давали бы разные p-значения при каждом запуске, что делает аудит невозможным. До S27 seed был `None`, и это реально приводило к нестабильным результатам в `formulas_audit_v1.json`. (src/backtest/mc_permutation.py:55)

4. **Цикл 2000 итераций.** В каждой:
   - Генерирует массив случайных знаков: каждый элемент независимо равен +1 или −1 с вероятностью 50/50.
   - Умножает исходные доходности на эти знаки — это и есть «перевёрнутая» стратегия.
   - Если `|mean(перевёрнутой стратегии)| ≥ observed` — увеличивает счётчик `count_extreme`.
   (src/backtest/mc_permutation.py:57-62)

5. **Вычисляет p-value** по формуле с поправкой. (src/backtest/mc_permutation.py:67)

### Формула p-value и поправка Phipson & Smyth 2010

Наивная формула была бы: `p = count_extreme / n_iterations`. Проблема: если ни одна перестановка не превысила наблюдаемое значение, получается `p = 0`. Но `p = 0` физически означает «невозможно», что логически неверно при конечном числе экспериментов — мы просто не видели такого события, это не значит, что его не существует.

Поправка Phipson & Smyth 2010, которую использует наш код (S33 T2 fix):

```
p = (count_extreme + 1) / (n_iterations + 1)
```
(src/backtest/mc_permutation.py:67)

**Что это даёт:**
- Минимально возможное p-value = `1 / (2000 + 1) ≈ 0.000499` — даже при нуле «экстремальных» перестановок.
- Максимально возможное p-value при `count_extreme = n_iterations`: `(2000 + 1) / (2001) = 1.0`.
- Это «честное» байесовское поведение: с конечным числом перестановок нельзя быть уверенным на 100%.

### Функция `block_bootstrap_p_value()` — вторичная диагностика

```python
def block_bootstrap_p_value(
    returns: npt.NDArray[np.float64],
    *,
    n_iterations: int = 2000,
    block_size: int = MC_BLOCK_SIZE,  # = 20
    seed: int | None = 42,
) -> float:
```
(src/backtest/mc_permutation.py:70-76)

**В чём разница от sign-flip?**

Sign-flip перемешивает знаки произвольно — каждая сделка независима. Но в реальной торговле соседние сделки часто «связаны»: если рынок трендит, несколько сделок подряд могут быть прибыльными просто потому, что рыночный тренд длится. Эта связь называется **автокорреляцией доходностей**.

Block bootstrap сохраняет эту связь: вместо перемешивания отдельных сделок он случайно выбирает блоки по 20 сделок подряд (`MC_BLOCK_SIZE = 20`), и из них составляет новую последовательность. Так структура «серий» сохраняется, и тест честнее оценивает вариабельность именно для нашего рынка.

(src/backtest/mc_permutation.py:24-25, 104-111)

**Важное предупреждение из кода:**

Block bootstrap — это НЕ тест наличия эджа. Он оценивает разброс выборки вокруг наблюдаемого среднего, а не то, является ли это среднее ненулевым при случайной стратегии. Поэтому он используется только как информационная вторичная диагностика, но никогда не как ворота допуска. Единственный gate — `sign_flip_p_value`. (src/backtest/mc_permutation.py:83-89)

**Механика block bootstrap:**

1. Вычисляет число блоков: `n_blocks = ceil(n / block_size)`.
2. В каждой итерации случайно выбирает `n_blocks` стартовых позиций (с заменой), нарезает блоки по 20 сделок и склеивает их в новую последовательность, обрезая до длины исходного массива.
3. Сравнивает `|mean(склеенного)| ≥ observed` и считает счётчик.
4. p-value по той же формуле `(count + 1) / (N + 1)`.

(src/backtest/mc_permutation.py:104-117)

### Ворота допуска: как MC входит в решение о стратегии

Функция `evaluate_acceptance_gate()` проверяет стратегию через четыре уровня [[acceptance-gates-t1-t6|ворот допуска]]:

| Уровень | Условие | Источник |
|---------|---------|---------|
| L1 | [[tstat-oos-is-metrics\|OOS/IS Sharpe ratio]] ≥ 0.7 на каждом фолде | ADR 0014 |
| **L2** | **MC p-value ≤ 0.05** | **ADR 0015, ADR 0052** |
| L3 | n_eff ≥ порог (если передан) | ADR 0052 |
| L4 | n_trades_raw ≥ 50 (если передан) | ADR 0052 |

Все уровни объединены условием AND: провал любого одного — общий вердикт FAIL.

```python
mc_gate_passed = mc_p_value <= p_threshold  # p_threshold = 0.05 по умолчанию
```
(src/backtest/walk_forward.py:199)

Порог `p_threshold = 0.05` — значение по умолчанию, которое использует `evaluate_acceptance_gate()`. До S34 (ADR 0052) порог был `0.10`; S34 его ужесточил. Старые вызовы, явно передающие `p_threshold=0.10`, остаются обратно совместимыми.
(src/backtest/walk_forward.py:160, 175, 184)

### Адаптивный запуск в живом режиме

В `live_trade_reporter.py` реализован дополнительный уровень защиты: MC запускается только при достаточном числе сделок (`compute_mc_with_gating()`).

| Число сделок | Поведение |
|---|---|
| < 20 | Оба теста не запускаются, статус `MC_INSUFFICIENT_N` |
| 20 – 39 | Только `sign_flip_p_value` |
| ≥ 40 | Оба: `sign_flip_p_value` + `block_bootstrap_p_value` |

(src/analytics/live_trade_reporter.py:38-39, 108-133)

Причина: `block_bootstrap` требует хотя бы `block_size = 20` сделок, а ниже 40 нарезка блоков даёт слишком мало вариантов для надёжной оценки. Sign-flip при n=20 уже даёт достаточно перестановок.

## Формулы и расчёты

### Sign-flip p-value

```
observed = |mean(returns)|

для i = 1..2000:
    signs_i = случайный массив ±1, каждый элемент с P=0.5
    permuted_i = returns × signs_i
    если |mean(permuted_i)| ≥ observed: count_extreme += 1

p = (count_extreme + 1) / (2000 + 1)
```

**Расшифровка простыми словами:** считаем, сколько из 2000 случайных «бессмысленных» версий стратегии дали средний результат не хуже реального. Плюс единица в числителе и знаменателе (поправка Phipson & Smyth) не позволяет получить математически невозможное `p=0`.

**Минимальное значение** при 2000 итерациях: `1 / 2001 ≈ 0.0005`. Это значит, что даже самая «убедительная» стратегия не может получить p=0.

(src/backtest/mc_permutation.py:54-67)

### Block bootstrap p-value

```
n_blocks = ceil(n / block_size)  # block_size = 20

для i = 1..2000:
    starts_i = n_blocks случайных стартовых позиций в [0, n - block_size]
    sampled_i = склейка блоков starts_i..starts_i+20, обрезанная до длины n
    если |mean(sampled_i)| ≥ observed: count_extreme += 1

p = (count_extreme + 1) / (2000 + 1)
```

(src/backtest/mc_permutation.py:104-117)

## Примеры / сценарии

### Сценарий A: стратегия проходит (p = 0.018)

Представьте, что у стратегии 100 OOS-сделок со средней доходностью +1.25% на сделку. Запускаем 2000 перестановок. Из них только 36 перестановок дали `|mean| ≥ 1.25%`.

```
p = (36 + 1) / (2000 + 1) = 37 / 2001 ≈ 0.0185
```

`0.0185 ≤ 0.05` — ворота L2 пройдены. Вывод: с вероятностью ~98% такой результат не случаен.

### Сценарий B: стратегия не проходит (p = 0.12)

Та же стратегия, но на более шумных данных, со средней +0.3% на сделку. Перестановки дали превышение в 239 случаях из 2000.

```
p = (239 + 1) / (2000 + 1) = 240 / 2001 ≈ 0.12
```

`0.12 > 0.05` — ворота L2 НЕ пройдены. Статус `mc_gate_passed = False`, общий [[verdict-and-warnings|вердикт]] `passed = False`. Стратегия не допускается к торговле, даже если все остальные метрики в порядке.

### Сценарий C: пустой массив сделок

Если OOS-фолды не дали ни одной сделки (например, стратегия не открывала позиций), функция вернёт `NaN`. В `research_wfa.py` это обрабатывается отдельно: при `n_trades_raw == 0` p-value принудительно устанавливается в `1.0` (максимально плохое значение — стратегия точно не проходит). (src/backtest/research_wfa.py:220-221)

### Сценарий D: живая торговля, 25 сделок

В `live_trade_reporter.py` с 25 сделками запустится только `sign_flip_p_value` (n=25 ≥ 20, но < 40), `block_bootstrap` пропускается. Статус `"OK"`, `block_bootstrap = None`. (src/analytics/live_trade_reporter.py:117-133)

## Подводные камни / что важно понимать

**1. Sign-flip — это тест эджа. Block bootstrap — нет.**

Это самое важное: `block_bootstrap_p_value` измеряет не то, есть ли у стратегии преимущество, а то, насколько стабилен средний результат по выборке. Он может дать низкое p-value даже для стратегии без реального эджа. Поэтому ворота L2 используют только `sign_flip_p_value`. Использование block bootstrap как gate прямо запрещено комментарием в коде. (src/backtest/mc_permutation.py:83-89)

**2. p ≤ 0.05 — это не «стратегия точно прибыльная».**

p-value говорит только одно: «маловероятно, что этот результат случаен». Он не гарантирует, что стратегия будет прибыльной в будущем. Реальный рынок может измениться; тест только оценивает, реален ли паттерн на исторических данных.

**3. Seed=42 обязателен для воспроизводимости.**

До S27 T5 seed был `None` — каждый аудитный запуск давал разные p-value. Это делало невозможным сравнение результатов разных прогонов. Теперь seed=42 зафиксирован как дефолт во всех вызовах. Если нужен нефиксированный (случайный) результат при каждом запуске — передавайте `seed=None` явно. (src/backtest/mc_permutation.py:43-46)

**4. Порог изменился в S34 с 0.10 до 0.05.**

Это ужесточение. Стратегии, которые проходили ворота при старом пороге 0.10, при новом пороге 0.05 могут не пройти. Ни один пороговый параметр в коде не заменяется автоматически — старые вызовы, передающие `p_threshold=0.10` напрямую, работают по-прежнему. (src/backtest/walk_forward.py:160, 175, 184)

**5. Минимальное p = 0.0005, а не 0.**

При 2000 итерациях физически невозможно получить p < `1/2001`. Это важно понимать при интерпретации: очень низкое p (`p = 0.001`) говорит «экстремально сильное свидетельство», но не «математически невозможно быть случайным».

**6. Block size = 20 выбран намеренно для крипто.**

ADR 0015 допускал диапазон 20–50 блоков. Значение 20 зафиксировано как `MC_BLOCK_SIZE = 20` (S39 T11 F8) потому, что маленькие блоки дают больше перестановок, что повышает точность p-value при малом числе сделок. Это важно для 4H-стратегий, у которых бывает немного OOS-сделок. (src/backtest/mc_permutation.py:24-25)

**7. n < 20 сделок — тест не запускается.**

В живом режиме (`live_trade_reporter`) при менее 20 сделках оба теста возвращают `None` и статус `MC_INSUFFICIENT_N`. Это не ошибка — это защита от статистически бессмысленного результата. (src/analytics/live_trade_reporter.py:38, 117-123)
