# HaltGate: заранее оговорённые правила полной остановки (демо-режим)

**TL;DR:** Бот работает на тестовой бирже по заранее согласованным «красным линиям». Если любая из четырёх линий пересечена — бот немедленно останавливается и зовёт оператора. Линии записаны в конфиге ДО запуска, чтобы решение «когда остановиться» не принималось под влиянием паники в моменте.

---

## Простыми словами

Представьте, что вы договорились с другом: «Если я в казино проиграю 20% за один день — ты обязан меня увести, что бы я ни говорил». Это и есть **pre-committed criteria** (по-русски: заранее зафиксированные правила) — соглашение, принятое *до* начала игры, когда голова холодная.

Бот работает в специальном режиме боевого тестирования (**демо-режим**, или [[01-как-работает-бот/run-modes-testnet-live-reconcile|testnet]] — тестовая биржа, где деньги ненастоящие). Чтобы эксперимент был честным и не превращался в «подождём ещё чуть-чуть», мы зафиксировали четыре конкретных ситуации, при которых бот **обязан** полностью остановиться и ничего не делать до прихода оператора:

1. **Слишком большой обвал за день** — внутридневная просадка ≥ 20% от сегодняшнего пика капитала.
2. **Слишком большие потери с начала эксперимента** — суммарная просадка от исторического максимума ≥ 15%.
3. **Длинная серия убытков** — пять и более убыточных сделок подряд.
4. **Бот долго не торгует** — шесть и более месяцев без закрытых сделок (сигналов нет, а значит, что-то идёт не так).

Именно этот механизм называется **HaltGate** — буквально «шлюз остановки». Когда шлюз закрывается, бот больше не принимает никаких торговых решений.

Важно: HaltGate — это **не** аварийный тормоз на случай технической поломки. Для поломок есть отдельные механизмы ([[04-риск-менеджмент/circuit-breakers-drawdown-flash|circuit breakers]]), а для мгновенной ручной остановки оператором — [[04-риск-менеджмент/kill-switch-emergency-stop|аварийный стоп (kill-switch)]]. HaltGate — это именно честное условие завершения эксперимента, принятое заранее. Полную карту всех механизмов остановки бота см. в [[01-как-работает-бот/safety-stops-and-halts|обзоре тормозов и предохранителей]].

## Как это работает у нас

### Шаг 0. Активация только в демо-режиме

HaltGate работает **только** если в настройках (`settings.s35_demo_active = True`). На реальных деньгах (`live_trading = True`) это поле невозможно включить одновременно — конфиг запрещает это явно. По умолчанию флаг выключен (`default=False`).

При запуске в демо-режиме бот сразу печатает в лог стартовый баннер со всеми четырьмя порогами (`src/runtime/manager.py:123-134`), чтобы оператор видел, с какими правилами работает сессия.

(src/platform/config.py:124-131)

### Шаг 1. Белый список символов — защита от случайного запуска

Перед любой проверкой метрик бот сверяет торговый инструмент (например, `BTCUSDT`) со списком разрешённых символов (`s35_demo_approved_symbols`, по умолчанию `["BTCUSDT"]`). Если символ не в списке — бот немедленно останавливается с кодом `HALT_UNKNOWN_SYMBOL`. Это принцип **fail-closed** (отказ в безопасную сторону): неизвестное лучше остановить, чем разрешить.

```python
# src/runtime/manager.py:199-208
symbol = getattr(self._coordinator, "symbol", None)
if symbol is None or symbol not in self._settings.s35_demo_approved_symbols:
    logger.error("runtime.halt_gate_unknown_symbol", ...)
    self._coordinator.request_halt(ReasonCode.HALT_UNKNOWN_SYMBOL)
    self._stopping = True
    return True
```

### Шаг 2. Метка активации с защитой от подмены (HMAC)

Для критерия «многодневная просадка» нужно знать точку отсчёта — момент, когда эксперимент начался. Эта метка называется **activation timestamp** (метка активации).

При первом запуске бот записывает текущее время в базу данных под ключом `runtime:halt_gate:activation_ts`. При последующих запусках читает эту же метку.

Чтобы никто не мог «перемотать» начало эксперимента вперёд и тем самым скрыть потери, метка хранится с **HMAC-подписью** (цифровая подпись на основе секретного ключа — как пломба на письме: если вскрыли, сразу видно). Тот же секретный ключ (`risk_override_hmac_key`) используется и в механизме [[04-риск-менеджмент/manual-override-resume|ручного снятия предохранителя]]. Если подпись не совпадает — бот считает данные скомпрометированными и останавливается (`fail-closed`).

```python
# src/runtime/manager.py:213-236
activation_record = self._state_repo.get_signed(
    "runtime:halt_gate:activation_ts",
    hmac_key=self._settings.risk_override_hmac_key,
)
# ValueError при несовпадении HMAC → halt fail-closed
```

(src/risk/state_repo.py:97-140)

### Шаг 3. Сбор четырёх показателей

Перед каждым тиком ([[01-как-работает-бот/main-loop-tick|главного цикла]], т.е. на каждой новой свече цены) `_check_halt_gate()` вычисляет четыре числа:

**3.1. Внутридневная просадка (`intraday_dd`)**

Запрашивается из `EquityTracker.intraday_dd_pct()` (см. [[04-риск-менеджмент/equity-tracking|учёт капитала]]). Метод берёт максимальный капитал за последние 24 часа и сравнивает с текущим:

```
intraday_dd = (пик за 24ч - текущий капитал) / пик за 24ч
```

Если текущий капитал не ниже пика — возвращает 0 (нет просадки). Результат — дробь: 0.20 означает 20% просадки.

(src/risk/equity_tracker.py:101-113)

**3.2. Многодневная просадка (`multiday_dd`)**

Берётся исторический максимум капитала (`HWM` — High Water Mark, «отметка прилива») начиная с момента активации (`activation_ts`), и сравнивается с текущим капиталом:

```
multiday_dd = (HWM с начала эксперимента - текущий) / HWM
```

Метод `equity_tracker.hwm_since(since_ts=activation_ts)` возвращает максимальное значение капитала за всё время эксперимента.

(src/runtime/manager.py:241-246, src/risk/equity_tracker.py:115-127)

**3.3. Серия убытков (`consecutive_losses`)**

Метод `TradeHistoryRepository.consecutive_losses(symbol=symbol)` читает все закрытые сделки по данному инструменту (из [[04-риск-менеджмент/trade-fill-history|истории сделок]]) в обратном хронологическом порядке и считает сделки с отрицательным результатом подряд. Как только встречается прибыльная сделка — счёт обнуляется и цикл прерывается.

```python
# src/risk/trade_history.py:132-148
for (pnl_str,) in rows:  # DESC по exit_ts
    if Decimal(str(pnl_str)) < Decimal("0"):
        streak += 1
    else:
        break
return streak
```

(src/risk/trade_history.py:132-148)

**3.4. Месяцы без сделок (`months_since_last_trade`)**

Метод `TradeHistoryRepository.last_trade_ts(symbol=symbol)` возвращает время последней закрытой сделки. Разница в днях делится на 30 (целочисленно), что даёт «месяцы».

Важный нюанс: если сделок ещё не было вообще (бот только что запустился), счёт ведётся **от даты активации**, а не от нуля. Это предотвращает ситуацию, когда бот молчит полгода и при этом никогда не срабатывает этот критерий.

```python
# src/runtime/manager.py:248-254
if last_ts is not None:
    months_since = (self._clock() - last_ts).days // 30
else:
    # Нет сделок — считаем от даты старта эксперимента
    months_since = (self._clock() - activation_ts).days // 30
```

(src/runtime/manager.py:248-254)

### Шаг 4. Оценка критериев — функция `HaltGate.evaluate()`

Все четыре числа передаются в `HaltGate.evaluate()`. Функция проверяет критерии **сверху вниз** и возвращает первый сработавший. Если ни один не сработал — возвращает `None`.

```python
# src/risk/halt_gate.py:53-73
def evaluate(self, *, intraday_dd, multiday_dd, consecutive_losses, months_since_last_trade):
    if intraday_dd >= self.dd_intraday_threshold:
        return HaltTrigger.DD_INTRADAY
    if multiday_dd >= self.dd_multiday_threshold:
        return HaltTrigger.DD_MULTIDAY
    if consecutive_losses >= self.consecutive_losses_threshold:
        return HaltTrigger.CONSECUTIVE_LOSSES
    if months_since_last_trade >= self.no_trade_months_threshold:
        return HaltTrigger.NO_TRADE_TIMEOUT
    return None
```

Порядок — не случаен: внутридневной обвал самый срочный (деньги тают прямо сейчас), поэтому идёт первым. Серия убытков и «голодание» по сигналам менее острые, они стоят последними.

### Шаг 5. Остановка бота

Если `evaluate()` вернул триггер — бот:

1. Переводит код триггера в стандартный [[04-риск-менеджмент/reason-codes-assessment-output|код остановки (`ReasonCode`)]] через таблицу `_HALT_TRIGGER_TO_REASON`:

| Триггер | Код остановки |
|---|---|
| `DD_INTRADAY` | `HALT_S36_DD_INTRADAY` |
| `DD_MULTIDAY` | `HALT_S36_DD_MULTIDAY` |
| `CONSECUTIVE_LOSSES` | `HALT_S36_CONSECUTIVE_LOSSES` |
| `NO_TRADE_TIMEOUT` | `HALT_S36_NO_TRADE_TIMEOUT` |

(src/runtime/manager.py:44-49)

2. Вызывает `coordinator.request_halt(reason)` — [[05-исполнение-ордеров/coordinator-orchestration|координатор]] записывает причину остановки в базу данных (см. [[05-исполнение-ордеров/execution-state-persistence-and-halt-audit|журнал аварийных остановок]]) и переводит [[05-исполнение-ордеров/execution-state-machine|FSM]] в состояние `HALTED` (тупиковое состояние без исходящих переходов). **Активные биржевые ордера (например, [[05-исполнение-ордеров/oco-bracket-emulation|TP/SL ноги OCO]]) при этом НЕ отменяются автоматически** — они остаются висеть на бирже. Отменить их должен оператор вручную. (src/execution/coordinator.py:1001-1031)
3. Устанавливает `self._stopping = True` — главный цикл прекращает тиковую обработку.

```python
# src/runtime/manager.py:271-283
reason = _HALT_TRIGGER_TO_REASON[trigger]
logger.error("runtime.halt_gate_fired", trigger=..., reason=..., ...)
self._coordinator.request_halt(reason)
self._stopping = True
return True
```

## Формулы и расчёты

### Внутридневная просадка

```
intraday_dd = (peak_24h - current_equity) / peak_24h
```

Где:
- `peak_24h` — максимальный суммарный капитал (реализованный + нереализованный) за последние 24 часа, по всем снимкам в базе
- `current_equity` — последний зафиксированный суммарный капитал

Простыми словами: «насколько мы упали от сегодняшней вершины». Если вершина была 1 000 USDT, а сейчас 800 USDT — просадка 20%.

Срабатывает при: `intraday_dd >= 0.20` (≥ 20%)

(src/risk/equity_tracker.py:101-113, src/platform/config.py:132-137)

### Многодневная просадка

```
multiday_dd = (hwm_since_activation - current_equity) / hwm_since_activation
```

Где:
- `hwm_since_activation` — исторический максимум капитала начиная с даты активации HaltGate
- `current_equity` — последний зафиксированный суммарный капитал

Простыми словами: «насколько мы упали от самой высокой точки за всё время тестирования». Если на пике было 1 000 USDT, а сейчас 850 USDT — просадка 15%.

Срабатывает при: `multiday_dd >= 0.15` (≥ 15%)

(src/runtime/manager.py:241-246, src/platform/config.py:138-143)

### Серия убытков

```
consecutive_losses = количество убыточных сделок подряд в конце истории
```

«Убыточная» сделка — `pnl_quote < 0` (отрицательный финансовый результат в котируемой валюте, например USDT). Счёт сбрасывается как только встречается прибыльная сделка.

Срабатывает при: `consecutive_losses >= 5`

(src/risk/trade_history.py:132-148, src/platform/config.py:144-149)

### Голодание по сигналам

```
months_since_last_trade = (сейчас - последняя_сделка).days // 30
```

Если сделок ещё не было — вместо `последняя_сделка` берётся `activation_ts` (дата старта эксперимента).

Срабатывает при: `months_since_last_trade >= 6`

(src/runtime/manager.py:248-254, src/platform/config.py:150-155)

## Примеры / сценарии

### Сценарий 1: обвал за день — DD_INTRADAY

Утром капитал бота составлял 1 000 USDT. К вечеру из-за резкого движения рынка капитал упал до 790 USDT.

```
intraday_dd = (1000 - 790) / 1000 = 0.21 = 21%
```

Порог: 20%. Результат: `21% >= 20%` — сработал `DD_INTRADAY`. Бот останавливается и пишет в лог `HALT_S36_DD_INTRADAY`. Остальные три критерия даже не проверяются.

### Сценарий 2: накопленные потери — DD_MULTIDAY

Эксперимент идёт две недели. На пятый день капитал достигал максимума 1 200 USDT (`hwm_since_activation`). Сегодня капитал 1 010 USDT.

```
multiday_dd = (1200 - 1010) / 1200 ≈ 0.158 = 15.8%
intraday_dd = пусть 3% (в течение сегодняшнего дня упали незначительно)
```

Внутридневная просадка: 3% < 20% — проходим. Многодневная: 15.8% >= 15% — сработал `DD_MULTIDAY`. Бот останавливается с `HALT_S36_DD_MULTIDAY`.

### Сценарий 3: серия убытков — CONSECUTIVE_LOSSES

Пять последних сделок закрыты с убытком (например, рынок стал трендовым, а стратегия настроена на боковик). Все метрики просадки в норме.

```
consecutive_losses = 5
```

Порог: 5. Результат: `5 >= 5` — сработал `CONSECUTIVE_LOSSES`. Бот останавливается с `HALT_S36_CONSECUTIVE_LOSSES`. Это сигнал для оператора проверить, не сломалась ли логика сигналов.

### Сценарий 4: молчание — NO_TRADE_TIMEOUT

Бот запущен в тестовой сети, но за 6 месяцев стратегия не дала ни одного сигнала на вход (рынок был в неподходящей фазе). Ни одной сделки не закрыто.

```
last_trade_ts = None → months_since = (сейчас - activation_ts).days // 30 = 6
```

Порог: 6. Результат: `6 >= 6` — сработал `NO_TRADE_TIMEOUT`. Бот останавливается с `HALT_S36_NO_TRADE_TIMEOUT`. Это не значит, что бот «ломался» — просто за шесть месяцев стратегия не дала ни одной закрытой сделки, и продолжать бессмысленно.

Важно: таймер — **чисто календарный** (`(now - last_trade_ts).days // 30`, src/runtime/manager.py:249-250). Количество сделок этот критерий **не проверяет** — срабатывает исключительно по прошедшему времени. Число n ≥ 30 упомянуто в комментариях кода как мотивировка дизайна, но не реализовано как условие.

### Сценарий 5: приоритет — все четыре критерия одновременно

Теоретически возможна ситуация, когда нарушены сразу несколько критериев. Проверка идёт сверху вниз, побеждает первый.

```
intraday_dd=0.25, multiday_dd=0.20, consecutive_losses=10, months_since=7
→ возвращает HaltTrigger.DD_INTRADAY (самый острый, проверяется первым)
```

(tests/unit/test_halt_gate.py:78-86)

### Сценарий 6: неизвестный символ — fail-closed

Оператор случайно указал в белом списке `["BTCUSDT"]`, но бот запущен для `ETHUSDT`. Ещё до любых рыночных проверок:

```
symbol = "ETHUSDT"
whitelist = {"BTCUSDT"}
→ HALT_UNKNOWN_SYMBOL
```

Бот останавливается немедленно, не совершив ни одной сделки.

## Подводные камни / что важно понимать

**HaltGate работает только в демо-режиме.** Когда `s35_demo_active = False` (режим по умолчанию), функция `_check_halt_gate()` просто возвращает `False` и не делает никаких вычислений. На mainnet этот механизм не активен — для боевой торговли существуют отдельные circuit breakers.

**Пороги — включительно.** Все четыре условия используют оператор `>=` (больше или равно). Это значит, что ровно 20% внутридневной просадки — уже стоп, не нужно чуть-чуть переступить черту. То же для 15%, 5 убытков, 6 месяцев. Это подтверждено тестами: `Decimal("0.15")` при пороге `0.15` срабатывает (`tests/unit/test_halt_gate.py:129`).

**Месяцы считаются грубо.** Формула `days // 30` — целочисленное деление. Это приближение: в реальности месяцы имеют разное число дней. 180 дней = 6 месяцев, 181 день = 6 месяцев, 210 дней = 7 месяцев. Для порогового инструмента такой точности достаточно, но знайте об этом при интерпретации логов.

**Серия убытков — per symbol.** Счётчик убытков ведётся отдельно для каждого торгового инструмента (например, BTCUSDT и ETHUSDT — разные счётчики). Это не ошибка: проигрыши на биткоине не должны учитываться при подсчёте серии по эфиру.

**HMAC-ключ должен быть не короче 32 символов (≥ 32).** Если `risk_override_hmac_key` в настройках содержит менее 32 символов — при первой проверке `_hmac_sign()` выбросит `ValueError` (src/risk/state_repo.py:92-93). Ключ ровно из 32 символов является допустимым. Это намеренная защита: слишком короткий ключ небезопасен.

**Подмена метки активации = немедленная остановка.** Если кто-то изменил запись `runtime:halt_gate:activation_ts` в базе данных вручную (например, чтобы «перезапустить» отсчёт многодневной просадки) — HMAC подпись не совпадёт, и бот остановится с `HALT_UNKNOWN_SYMBOL`. Да, это несколько контринтуитивный код ошибки для случая подмены метки — исторически выбрано для единообразия, не отражает причину (`src/runtime/manager.py:219-226`).

**Инициализация только один раз.** После первого успешного чтения метки активации (`self._activation_ts`) она кешируется в памяти (`_activation_ts: datetime | None`). При последующих тиках база данных не запрашивается — экономия на операциях чтения (src/runtime/manager.py:98-99, 212).

**`__post_init__` — защита от бессмысленной конфигурации.** При создании объекта `HaltGate` автоматически проверяется: все пороги просадки > 0, оба счётчика (убытков и месяцев) ≥ 1. Нельзя случайно создать объект с нулевыми порогами, который останавливал бы бота при первом же тике. (src/risk/halt_gate.py:43-51)

## Связанные документы

Другие механизмы остановки и защиты (риск-менеджмент):

- [[04-риск-менеджмент/circuit-breakers-drawdown-flash]] — аварийные тормоза при технических сбоях и рыночных аномалиях (отдельный механизм от HaltGate; работают в том числе на mainnet)
- [[04-риск-менеджмент/kill-switch-emergency-stop]] — «красная кнопка» оператора: мгновенная ручная остановка через файл-сигнал (контраст: ручная vs автоматическая по критериям)
- [[04-риск-менеджмент/manual-override-resume]] — ручное снятие предохранителя с криптоподписью; использует тот же `risk_override_hmac_key`, что и метка активации HaltGate
- [[04-риск-менеджмент/risk-overview-decision-pipeline]] — главный компонент управления рисками, в котором HaltGate является одним из слоёв защиты
- [[04-риск-менеджмент/reason-codes-assessment-output]] — каталог кодов причин; HaltGate выдаёт коды `HALT_S36_*` и `HALT_UNKNOWN_SYMBOL`

Источники данных для четырёх критериев:

- [[04-риск-менеджмент/equity-tracking]] — учёт капитала: снимки equity для внутридневной и многодневной просадки (HWM)
- [[04-риск-менеджмент/trade-fill-history]] — хранилище истории сделок, откуда читается серия убытков и время последней сделки

Как HaltGate останавливает исполнение (слой ордеров):

- [[05-исполнение-ордеров/coordinator-orchestration]] — координатор, которому HaltGate шлёт `request_halt(reason)`
- [[05-исполнение-ордеров/execution-state-machine]] — FSM ордера; при остановке переходит в тупиковое состояние `HALTED`
- [[05-исполнение-ордеров/execution-state-persistence-and-halt-audit]] — куда записывается причина остановки: неизменяемый журнал аудита халтов в базе
- [[05-исполнение-ордеров/oco-bracket-emulation]] — брекет TP/SL, ноги которого при халте остаются висеть на бирже (снимать вручную)
- [[05-исполнение-ордеров/emergency-flatten-and-residual]] — контраст: аварийное закрытие отменяет ордера и продаёт, тогда как HaltGate позицию НЕ закрывает
