# Учёт капитала: как бот измеряет свой счёт и просадку

**TL;DR:** Бот регулярно делает «снимки» своего капитала в SQLite-базе и по этим снимкам вычисляет текущее состояние счёта, максимум за последние 24 часа и просадку (насколько счёт просел от пика). Эти три числа питают все защитные механизмы — от автоматической остановки торговли до расчёта размера позиции.

---

## Простыми словами

Представьте, что вы ведёте личный финансовый дневник: каждый вечер записываете, сколько у вас денег, и можете в любой момент посмотреть, какой максимум был за последние сутки и насколько счёт провалился от этого максимума.

Бот делает ровно то же самое, только автоматически:

- **Что записывается.** После каждого закрытия свечи (бара) бот делает «снимок» (snapshot) счёта. Снимок содержит три числа: реализованный капитал, бумажная прибыль/убыток по открытой позиции и их сумма — итоговый капитал (equity). В продакшн-коде `source` всегда равен `"BAR_CLOSE"` (захардкожено в единственном вызове `update_equity`, `src/risk/manager.py:171`).

- **Зачем нужна история.** Одного числа «сколько сейчас» недостаточно. Важно знать — был ли счёт выше, и если да, то насколько просел. Именно из этой истории вычисляется **просадка** (drawdown) — насколько счёт упал от своего пика. Если просадка превышает заданный порог, бот автоматически останавливается (подробнее в [[circuit-breakers-drawdown-flash]] и [[halt-gate-precommitted-criteria]]).

- **Аналогия.** Это как спидометр и одометр в машине: спидометр показывает скорость сейчас (текущий капитал), а одометр хранит историю пробега (снимки за 24 часа). Без одометра нельзя понять, «разогнались» вы или «тормозили».

## Как это работает у нас

### Класс EquityTracker — журнал снимков

Весь учёт капитала сосредоточен в одном классе — `EquityTracker`. Он работает с SQLite-базой через уже открытое соединение `conn` (нет собственного соединения, нет шанса рассинхронизироваться). (`src/risk/equity_tracker.py:11-15`)

Снимки хранятся в таблице `equity_snapshots`. Схема (из миграции `002_risk.sql:23-31`):

```text
snapshot_id      — уникальный номер снимка (автоинкремент)
ts               — момент времени (ISO-8601, UTC)
realized_equity  — реализованный капитал (TEXT, хранится как строка Decimal)
unrealized_pnl   — бумажный P&L по открытой позиции (TEXT, может быть отрицательным)
total_equity     — итог: realized + unrealized (TEXT)
source           — кто создал снимок: BAR_CLOSE / POSITION_CLOSE / MANUAL
```

Три значения `source` — допустимые метки, объявленные в типе `SnapshotSource` (`src/risk/equity_tracker.py:8`):
- **BAR_CLOSE** — снимок в конце свечи. **Единственное значение, которое бот записывает в продакшн** — захардкожено в `src/risk/manager.py:171`.
- **POSITION_CLOSE** — предусмотрено типом для снимка при закрытии сделки, но ни одного продакшн-вызова с этим значением в `src/` нет (встречается только в тестах).
- **MANUAL** — для тестовых и ручных записей.

Любое другое значение SQLite отклоняет с ошибкой — CHECK-ограничение в схеме.

### Почему все суммы хранятся строками, а не числами

**Капитал (equity)** — это денежная величина. В Python есть два способа хранить дробные числа: обычный `float` (число с плавающей точкой) и специальный `Decimal` (десятичная дробь с заданной точностью).

`float` даёт ошибки округления: например, `0.1 + 0.2` в Python равно `0.30000000000000004`, а не `0.3`. Для торговых расчётов это недопустимо.

`Decimal` вычисляет точно, как на калькуляторе. Но SQLite не умеет хранить `Decimal` напрямую — только числа или строки.

Поэтому договорились: на запись `Decimal → str` (строка), на чтение `str → Decimal`. Точность не теряется. (`src/risk/equity_tracker.py:37`, `src/risk/equity_tracker.py:87,99`)

### record() — запись снимка с немедленным коммитом

```python
def record(self, *, realized, unrealized, ts, source) -> int:
    if realized < 0:
        raise ValueError("realized must be >= 0")
    total = realized + unrealized
    cursor = self._conn.execute(...)
    self._conn.commit()
    return int(cursor.lastrowid)
```
(`src/risk/equity_tracker.py:17-42`)

Метод:
1. Проверяет, что реализованный капитал не отрицательный. Реализованный капитал (деньги, уже зафиксированные на счёте) не может быть меньше нуля — это физически невозможно для спот-счёта. Бумажный P&L (`unrealized`) может быть отрицательным — открытая позиция в убытке.
2. Считает `total = realized + unrealized`.
3. Сохраняет все четыре значения в базу.
4. **Сам коммитит транзакцию** — изменение сразу становится постоянным.
5. Возвращает `snapshot_id` — номер записи.

### record_no_commit() — запись без коммита (для атомарных операций)

```python
def record_no_commit(self, *, realized, unrealized, ts, source) -> int:
    # ... то же, кроме self._conn.commit() ...
```
(`src/risk/equity_tracker.py:44-68`)

Иногда нужно записать снимок капитала и одновременно обновить состояние автоматического выключателя ([[circuit-breakers-drawdown-flash|circuit breaker]]) — и сделать это как **одну неделимую операцию**: либо обе записи прошли, либо ни одна. Это называется атомарностью.

Для этого вызывающий код оборачивает обе записи в один блок `with conn:` и управляет коммитом сам. Внутри этого блока `record_no_commit` просто делает INSERT без коммита.

Именно так работает `RiskManager.update_equity`:

```python
# src/risk/manager.py:169-182
with self._conn:                                    # одна транзакция
    self._equity.record_no_commit(...)              # снимок капитала
    self._state.update_many_no_commit({             # состояние CB
        "risk:cb:current_level": { ... }
    })
```

Если что-то упало посередине — оба изменения откатятся. Нет риска ситуации «капитал записан, но CB-уровень устарел».

### peak_equity_24h() — максимум капитала за 24 часа

```python
def peak_equity_24h(self, *, now=None) -> Decimal | None:
    cutoff = (now or datetime.now(UTC)) - timedelta(hours=24)
    rows = self._conn.execute(
        "SELECT total_equity FROM equity_snapshots WHERE ts >= ?",
        (cutoff.isoformat(),)
    ).fetchall()
    values = [Decimal(r[0]) for r in rows if r[0] is not None]
    if not values:
        return None
    return max(values)
```
(`src/risk/equity_tracker.py:70-90`)

Метод возвращает наибольшее значение `total_equity` среди всех снимков за последние 24 часа (считая от `now`). Если снимков нет — возвращает `None`.

**Почему максимум ищется в Python, а не через SQL `ORDER BY`?**

Казалось бы, проще написать `ORDER BY total_equity DESC LIMIT 1` прямо в SQL. Но есть ловушка: SQLite не знает типа `Decimal` — он видит текстовую строку. Чтобы отсортировать как числа, пришлось бы применить `CAST(total_equity AS REAL)`. А `REAL` в SQLite — это IEEE-754 double (64-битный float), который хранит максимум ~15 значащих цифр.

Два снимка с суммами `12345.67890123450001` и `12345.67890123450002` (отличаются на 16-й значащей цифре) превратятся в одно и то же число после CAST — и SQL выберет «победителя» произвольно. Python с `Decimal` видит разницу точно.

Это задокументировано как аудит-находка I1 в ADR 0007 (Decimal-strict) и ADR 0018 (sub-decision 9). Тест `test_peak_equity_24h_decimal_precision_beyond_double` явно воспроизводит этот сценарий. (`tests/unit/test_risk_equity_tracker.py:191-219`)

### current_total() — текущий капитал

```python
def current_total(self) -> Decimal | None:
    row = self._conn.execute(
        "SELECT total_equity FROM equity_snapshots ORDER BY ts DESC LIMIT 1"
    ).fetchone()
    return Decimal(row[0]) if row else None
```
(`src/risk/equity_tracker.py:92-99`)

Самый свежий снимок по времени (`ts DESC`) — это и есть «текущий» капитал. Если таблица пуста — `None`. Используется при расчёте размера позиции (sizing) и как входной параметр для просадки.

### intraday_dd_pct() — внутридневная просадка

**Просадка ([[max-drawdown-winrate-rr|drawdown]])** — это насколько счёт упал от своего пика. Простая аналогия: если у вас было 11 000 рублей, а сейчас 10 000, то просадка = (11 000 − 10 000) / 11 000 = ~9%.

```python
def intraday_dd_pct(self, *, now=None) -> Decimal:
    peak = self.peak_equity_24h(now=now)
    current = self.current_total()
    if peak is None or current is None or peak <= Decimal("0"):
        return Decimal("0")
    if current >= peak:
        return Decimal("0")
    return (peak - current) / peak
```
(`src/risk/equity_tracker.py:101-113`)

Формула: `DD = (peak_24h − current) / peak_24h`.

Метод возвращает `Decimal("0")` в трёх защитных случаях:
- нет снимков вообще (таблица пуста),
- пик равен нулю или отрицателен (аномалия),
- текущий капитал не ниже пика (роста нет — просадки нет).

Результат `intraday_dd_pct()` — это главный вход для проверки внутридневной просадки в [[halt-gate-precommitted-criteria|HaltGate]]. (`src/runtime/manager.py:240`)

---

### hwm_since() — высшая точка с момента активации

**High-Water Mark (HWM)** — «высшая водная отметка», то есть максимум, которого достигал счёт за весь период отслеживания. Аналогия: отметка на стене, куда доходила вода во время паводка.

```python
def hwm_since(self, *, since_ts: datetime) -> Decimal | None:
    rows = self._conn.execute(
        "SELECT total_equity FROM equity_snapshots WHERE ts >= ?",
        (since_ts.isoformat(),)
    ).fetchall()
    values = [Decimal(r[0]) for r in rows if r[0] is not None]
    return max(values) if values else None
```
(`src/risk/equity_tracker.py:115-127`)

Отличие от `peak_equity_24h`: здесь окно не фиксировано на 24 часа — оно начинается с произвольного момента `since_ts` и идёт до сейчас. Это позволяет вычислить **многодневную просадку** — насколько счёт просел от максимума за всё время наблюдения (с момента включения режима HaltGate).

`hwm_since()` вызывается в `RuntimeManager._check_halt_gate()` с аргументом `activation_ts` — временем первого запуска HaltGate. (`src/runtime/manager.py:241`)

## Формулы и расчёты

### Итоговый капитал (total equity)

```text
total_equity = realized_equity + unrealized_pnl
```

- **realized_equity** — деньги, реально зафиксированные на счёте: депозит минус потери и комиссии, плюс прибыль от закрытых сделок.
- **unrealized_pnl** (бумажный P&L) — текущая стоимость открытой позиции относительно цены входа. Может быть положительным (позиция в плюсе) или отрицательным (позиция в минусе).

Реализация: `total = realized + unrealized` — одна строка до INSERT. (`src/risk/equity_tracker.py:32,59`)

### Внутридневная просадка (intraday drawdown)

```text
DD_intraday = (peak_24h − current) / peak_24h
```

Где `peak_24h` — максимальный `total_equity` за скользящие 24 часа, `current` — последний снимок.

Пример: пик за 24 часа = 11 000 USDT, текущий капитал = 10 000 USDT.  
`DD = (11 000 − 10 000) / 11 000 ≈ 0.0909` → просадка ~9.1%.

Реализация: `src/risk/equity_tracker.py:112-113`

### Многодневная просадка (multiday drawdown)

```text
DD_multiday = (hwm_since(activation_ts) − current) / hwm_since(activation_ts)
```

Вычисляется не в `EquityTracker`, а в `RuntimeManager._check_halt_gate()` прямо по результатам `hwm_since()` и `current_total()`. (`src/runtime/manager.py:243-246`)

## Примеры / сценарии

### Сценарий 1 — обычный день, счёт растёт

| Время  | realized | unrealized | total_equity | source       |
|--------|----------|------------|--------------|--------------|
| 10:00  | 10 000   | 0          | 10 000       | BAR_CLOSE    |
| 11:00  | 10 000   | +200       | 10 200       | BAR_CLOSE    |
| 12:00  | 10 200   | 0          | 10 200       | POSITION_CLOSE |
| 13:00  | 10 200   | +150       | 10 350       | BAR_CLOSE    |

Вызов `current_total()` в 13:00 → `10 350`.  
Вызов `peak_equity_24h()` в 13:00 → `10 350` (максимум за сутки).  
Вызов `intraday_dd_pct()` → `0` (просадки нет, текущий = пику).

### Сценарий 2 — просадка после пика

Добавляется снимок в 14:00: realized=10 200, unrealized=−500, total=9 700.

Вызов `intraday_dd_pct()` в 14:00:
- `peak_24h = 10 350` (снимок 13:00)
- `current = 9 700` (снимок 14:00)
- `DD = (10 350 − 9 700) / 10 350 ≈ 0.0628` → ~6.3%.

Если порог автовыключателя (например) 5%, бот получает сигнал остановиться.

### Сценарий 3 — снимок за пределами 24 часов

В 10:00 прошлого дня был снимок с peak=15 000. Сейчас 10:01 следующего дня.  
`peak_equity_24h()` не включит вчерашний снимок — он уже за пределами скользящего окна (SQL условие `ts >= cutoff`, где `cutoff = now − 24h`). Этот снимок не повлияет на внутридневную просадку. (`src/risk/equity_tracker.py:82-86`)

## Класс StateRepository — хранилище состояния системы

Помимо снимков капитала, боту нужно где-то хранить текущее состояние своих компонентов: уровень автоматического выключателя, параметры [[position-sizing-kelly|Kelly-размера позиции]], метку времени активации HaltGate. Для этого служит `StateRepository`.

**Аналогия:** это как блокнот с именованными страницами. Каждой странице дано имя (ключ), и на ней записан JSON-объект (значение). Можно читать и перезаписывать отдельные страницы, или обновить несколько страниц за один раз — атомарно.

Таблица `state` в SQLite (`migrations/001_initial.sql:66-70`):

```text
key        — имя ключа (уникальный, TEXT PRIMARY KEY)
value_json — JSON-значение
updated_at — когда обновлялось
```

### Известные ключи в системе

| Ключ | Что хранит | Где пишется |
|------|------------|-------------|
| `risk:cb:current_level` | Текущий уровень автовыключателя (L0 / L1 / L2 / L3 / FLASH) | `src/risk/manager.py:173-182` |
| `risk:cb:prev_close` | Цена закрытия предыдущей свечи (для flash-детектора) | `src/risk/manager.py:196` |
| `runtime:halt_gate:activation_ts` | Момент первой активации HaltGate (HMAC-подписанный) | `src/runtime/manager.py` |

> **Примечание.** Ключи `risk:kelly:phase` и `risk:kelly:params` упомянуты в docstring `src/risk/state_repo.py:16-17`, но нигде в `src/` не записываются. Kelly вычисляется динамически из настроек и истории сделок при каждом вызове `assess()` (`src/risk/manager.py:65-69`), а не читается из базы. Считать эти ключи «активными» нельзя.

(`src/risk/manager.py:131-196`)

### set() / get() — чтение и запись одного ключа

```python
repo.set("risk:cb:current_level", {"level": "L1"})
value = repo.get("risk:cb:current_level")   # → {"level": "L1"}
```
(`src/risk/state_repo.py:23-39`)

`set()` использует upsert (INSERT ... ON CONFLICT DO UPDATE) — если ключ уже есть, перезапишет; если нет — создаст. Каждый `set()` открывает и коммитит собственную транзакцию.

### update_many() и update_many_no_commit() — пакетное обновление

```python
repo.update_many({
    "risk:cb:current_level": {"level": "L1"},
    "risk:cb:prev_close":   {"value": "10500.00"},
})
```
(`src/risk/state_repo.py:41-58`)

`update_many()` — вспомогательный метод: обновляет несколько ключей в одной транзакции (все или никто). В текущем `src/` он напрямую **не вызывается** ни из одного продакшн-пути — это инструмент, доступный для будущих вызывающих, которым нужно обновить несколько ключей атомарно.

`update_many_no_commit()` — то же, но без коммита (внешний `with conn:` управляет транзакцией). **Единственный реально используемый вариант** в основном потоке: `RiskManager.update_equity` вызывает его для записи только `risk:cb:current_level` в рамках одной транзакции вместе со снимком капитала. (`src/risk/state_repo.py:60-77`, `src/risk/manager.py:173-182`)

### set_signed() / get_signed() — HMAC-подписанное состояние

Некоторые значения критичны: если их подменить (например, сдвинуть `activation_ts` назад — бот «забудет» многодневную просадку), система будет вести себя неправильно. Для таких значений используется **HMAC-подпись**.

**Что такое HMAC.** Это алгоритм, который берёт данные и секретный ключ (минимум 32 символа) и вычисляет уникальный «цифровой отпечаток». Если данные изменить даже на один символ — отпечаток станет другим. Без знания секретного ключа подделать отпечаток невозможно.

Схема хранения подписанного значения в базе:

```json
{
  "payload": {"value": "2026-06-01T10:00:00+00:00"},
  "sig": "a3f1b2c4..."
}
```

(`src/risk/state_repo.py:97-140`)

Алгоритм при записи (`set_signed`):
1. Сериализовать `payload` в канонический JSON (ключи отсортированы, нет лишних пробелов) — это гарантирует одинаковую строку независимо от порядка ключей в Python-словаре.
2. Вычислить HMAC-SHA256 от байтов этой строки.
3. Записать `{"payload": ..., "sig": <hex-digest>}`.

При чтении (`get_signed`):
1. Прочитать запись.
2. Пересчитать ожидаемый `sig` по `payload` и секретному ключу.
3. Сравнить через `hmac.compare_digest` (защита от атаки по времени).
4. Если подписи не совпадают — выбросить `ValueError`. Вызывающий код обязан остановить бота, потому что «безопасное значение по умолчанию» неизвестно. (`src/risk/state_repo.py:135-140`)

Единственный ключ, подписанный таким образом: `runtime:halt_gate:activation_ts`. При обнаружении подмены `RuntimeManager._check_halt_gate()` немедленно останавливается. (`src/runtime/manager.py:218-226`)

## Подводные камни / что важно понимать

**Снимок создаётся на момент закрытия свечи, а не в реальном времени.**  
В течение открытой свечи `current_total()` возвращает значение из предыдущего снимка. Это означает, что внутридневная просадка, вычисленная между двумя свечами, отражает состояние на конец предыдущей свечи, а не прямо сейчас. Для 1-часовых свечей задержка — до часа.

**Отрицательный `unrealized_pnl` — нормальное состояние.**  
Если позиция в минусе, бумажный P&L отрицательный и `total_equity` может быть ниже `realized_equity`. Проверка `realized >= 0` стоит в коде, но нет проверки на `total >= 0` — технически возможна ситуация `total < 0` при огромном открытом убытке. На практике circuit breaker остановит бота до наступления такого сценария. (`src/risk/equity_tracker.py:30-31`)

**`peak_equity_24h` и `current_total` читают разные данные.**  
`peak_equity_24h()` читает только снимки в окне `[now − 24h, now]`. `current_total()` читает самый последний снимок по `ts DESC LIMIT 1` — он может быть старше 24 часов (если бот не делал снимков долго). При вычислении `intraday_dd_pct()`: если нет снимков в 24-часовом окне, `peak` = `None`, и метод вернёт `0` (защитный дефолт). Это означает, что после долгого простоя бот не будет считать просадку от «давнего пика» — только от свежих снимков. (`src/risk/equity_tracker.py:101-113`)

**Атомарность нарушается при смешении `record()` и `record_no_commit()`.**  
`record()` сам коммитит. Если вызвать его внутри внешнего `with conn:`, транзакция зафиксируется досрочно — принцип «всё или ничего» сломается. В коде `RiskManager.update_equity` используется исключительно `record_no_commit()`. (`src/risk/manager.py:170-173`)

**HMAC-ключ должен быть не короче 32 символов.**  
Это жёсткое требование кода (`src/risk/state_repo.py:92-93`). Передача более короткого ключа вызывает `ValueError` на стадии запуска — бот не стартует. Ключ берётся из настроек `risk_override_hmac_key` (тот же ключ, что используется для файла [[manual-override-resume|ручного переопределения]]). (`src/risk/state_repo.py:90-95`, `src/platform/config.py:207`)

**Подмена `activation_ts` — критическая угроза.**  
Если бы злоумышленник или сбойная программа могла сдвинуть `activation_ts` вперёд (ближе к текущему моменту), многодневное HWM «обнулилось» бы — бот потерял историю просадки. Именно для предотвращения этого введена HMAC-подпись: любое несоответствие = немедленная остановка. (`src/runtime/manager.py:218-226`, ADR 0057 SD-4)
