# Автоматические предохранители: остановка при просадке и обвале

**TL;DR:** Бот сам выключает торговлю в двух опасных ситуациях — когда капитал упал слишком сильно от недавнего максимума (просадка L1/L2/L3) и когда цена резко скакнула за один бар (flash-crash). Обе проверки — чистые математические функции без побочных эффектов. Возобновить торговлю после L2/L3/FLASH может только оператор через override; L1 в работающем процессе не снимается ни автоматически, ни через override.

> **СТАТУС РЕАЛИЗАЦИИ (важно):** методы `on_bar_close` и `update_equity` определены в `src/risk/manager.py`, но ни один из них **не вызывается** в `src/runtime/manager.py` — единственном файле, управляющем [[main-loop-tick|live-циклом]] бота. Это означает, что оба механизма (flash-CB и drawdown-CB) в настоящее время **не активны в production**: `self._prev_close` всегда остаётся `None`, ветка flash-проверки в `assess()` никогда не выполняется; `self._current_halt` всегда остаётся `L0` после старта. Код реализован и протестирован изолированно, но интеграция с live runtime ещё не завершена.

---

## Простыми словами

Представьте, что в вашей розетке стоит автоматический предохранитель (те самые «автоматы» в электрощитке). Пока ток нормальный — всё работает. Появился опасный скачок — автомат щёлкнул и разомкнул цепь. Сам, без вашего участия. Чтобы снова включить свет, нужно вручную поднять рычажок.

В боте ровно та же идея. Есть два типа «опасных ситуаций», на которые реагируют предохранители:

**Просадка (drawdown)** — это когда капитал постепенно падает от своего недавнего пика. Представьте, что у вас было 1000 долларов, стало 850 — это [[max-drawdown-winrate-rr|просадка]] 15%. Бот отслеживает максимум капитала за последние 24 часа и сравнивает с текущим значением. Если разница превышает порог — торговля останавливается.

**Flash-crash (мгновенный обвал)** — это когда цена резко прыгнула или рухнула за одну свечу. Например, биткоин стоил 60 000 долларов, а за час упал до 54 000 — это движение на 10% за один бар. Торговать в такой ситуации очень рискованно: цена нестабильна, стоп-лоссы могут не исполниться по ожидаемой цене.

Предохранители работают **автоматически и молча**: они не записывают файлы, не отправляют запросы на биржу — просто вычисляют математику и возвращают ответ. Всё это называется «чистыми функциями» (pure functions): дал входные данные — получил результат, никаких скрытых эффектов.

## Как это работает у нас

### Архитектура: чистый детектор без состояния

Весь механизм предохранителей реализован в классе `CircuitBreakerDetector` (src/risk/circuit_breakers.py:20-57). Класс принимает конфигурацию при создании и предоставляет два метода:

- `check_drawdown` — проверяет просадку капитала
- `check_flash` — проверяет резкий скачок цены

Важная деталь: **оба метода не сохраняют никакого состояния**. Дайте им одинаковые числа — получите одинаковый ответ. Это делает их легко тестируемыми и предсказуемыми.

```python
# src/risk/circuit_breakers.py:20-24
class CircuitBreakerDetector:
    """Pure functions — no I/O, no state. Stateless detector over inputs."""

    def __init__(self, config: CircuitBreakerConfig) -> None:
        self._cfg = config
```

### Шаг 1. Откуда берётся «пик» капитала

Прежде чем проверять просадку, нужно знать: от какого максимума считать падение? Бот берёт **скользящий максимум за последние 24 часа** из базы данных (класс `EquityTracker`, см. [[equity-tracking]]).

Метод `peak_equity_24h` (src/risk/equity_tracker.py:70-90) выбирает все снимки капитала за последние 24 часа и возвращает наибольший из них. Максимум ищется в Python, а не в SQL — чтобы избежать ошибок округления при работе с точными денежными числами (Decimal).

```python
# src/risk/equity_tracker.py:82-90
cutoff = (now or datetime.now(UTC)) - timedelta(hours=24)
rows = self._conn.execute(
    "SELECT total_equity FROM equity_snapshots WHERE ts >= ?",
    (cutoff.isoformat(),),
).fetchall()
values = [Decimal(r[0]) for r in rows if r[0] is not None]
if not values:
    return None
return max(values)
```

В риск-менеджере (src/risk/manager.py:153-156) при обновлении капитала пик дополнительно сравнивается с текущим значением: если текущий капитал выше всех предыдущих снимков, он и становится новым пиком.

```python
# src/risk/manager.py:153-157
peak = self._equity.peak_equity_24h(now=ts) or current
# Include the about-to-write current snapshot in the peak comparison.
if current > peak:
    peak = current
new_halt = self._cb.check_drawdown(peak=peak, current=current)
```

> **Статус реализации:** вся эта логика находится внутри метода `update_equity` (src/risk/manager.py:142). Метод реализован и покрыт тестами, но в live runtime (`src/runtime/manager.py`) не вызывается — drawdown-CB сейчас не активен в production.

### Шаг 2. Проверка просадки: `check_drawdown`

Метод получает два числа: `peak` (пик за 24 часа) и `current` (текущий капитал). Вычисляет процент падения и сравнивает с тремя порогами.

```python
# src/risk/circuit_breakers.py:26-43
def check_drawdown(self, *, peak: Decimal, current: Decimal) -> HaltState:
    if peak <= 0:
        return HaltState.L0
    if current >= peak:
        return HaltState.L0
    dd = (peak - current) / peak
    if dd >= self._cfg.l3_dd:
        return HaltState.L3
    if dd >= self._cfg.l2_dd:
        return HaltState.L2
    if dd >= self._cfg.l1_dd:
        return HaltState.L1
    return HaltState.L0
```

Два защитных случая возвращают L0 (норма):
- `peak <= 0` — пик капитала нулевой или отрицательный (такого не бывает, но защита от деления на ноль)
- `current >= peak` — текущий капитал не ниже пика, просадки нет

Метод всегда возвращает **наивысший сработавший уровень**: если просадка 25%, это L2, а не L1 (хотя порог L1 тоже превышен).

---

### Шаг 3. Проверка мгновенного обвала: `check_flash`

Метод получает цену закрытия текущего бара (`bar_close`), цену закрытия предыдущего бара (`prev_close`) и значение [[atr-indicator|ATR]] — индикатора волатильности (среднего истинного диапазона цен за последние 14 периодов).

```python
# src/risk/circuit_breakers.py:45-57
def check_flash(
    self, *, bar_close: Decimal, prev_close: Decimal, atr: Decimal
) -> bool:
    if prev_close <= 0:
        return False
    delta_pct = abs(bar_close - prev_close) / prev_close
    atr_pct = (self._cfg.flash_atr_mult * atr) / prev_close
    threshold = max(self._cfg.flash_abs, atr_pct)
    return delta_pct > threshold
```

Метод вычисляет, насколько цена сдвинулась в процентах от предыдущего закрытия (в любую сторону — рост или падение). Затем сравнивает с **динамическим порогом**: берётся максимум из фиксированных 8% и `3 × ATR / prev_close`.

Если `prev_close <= 0` — возвращает False (защитная проверка: нет предыдущей цены — нет и обнаружения).

В `assess()` flash-проверка вызывается только если предыдущая цена закрытия уже известна (src/risk/manager.py:234-243):

```python
# src/risk/manager.py:234-243
if self._prev_close is not None:
    is_flash = self._cb.check_flash(
        bar_close=mark_price,
        prev_close=self._prev_close,
        atr=signal.atr_14,
    )
    if is_flash and self._halt_severity(HaltState.FLASH) > self._halt_severity(
        self._current_halt
    ):
        self._current_halt = HaltState.FLASH
```

Предыдущая цена закрытия предназначена для сохранения в методе `on_bar_close` и восстановления при перезапуске из базы данных — чтобы первый бар после перезапуска не пропустил flash-обнаружение (src/risk/manager.py:188-196). **Важно:** `on_bar_close` определён в `src/risk/manager.py:188`, но в live runtime (`src/runtime/manager.py`) не вызывается — см. раздел «Статус реализации» выше.

### Шаг 4. Лестница серьёзности: HaltState

Все возможные состояния предохранителей описаны в перечислении `HaltState` (src/risk/models.py:17-23):

```python
class HaltState(StrEnum):
    L0 = "L0"      # норма — торговля разрешена
    L1 = "L1"      # лёгкая просадка
    L2 = "L2"      # серьёзная просадка
    L3 = "L3"      # критическая просадка
    FLASH = "FLASH" # мгновенный обвал цены
```

Уровни имеют чёткий числовой приоритет — больше число, серьёзнее ситуация (src/risk/manager.py:344-351):

| HaltState | Приоритет (severity) |
|-----------|----------------------|
| L0        | 0                    |
| L1        | 1                    |
| L2        | 2                    |
| L3        | 3                    |
| FLASH     | 4                    |

Важный принцип: уровень может **только расти**, но не снижаться сам по себе. Обновление происходит только при строгом `>`: `if self._halt_severity(new_halt) > self._halt_severity(self._current_halt)` (src/risk/manager.py:159). Если просадка сначала достигла L1, а потом капитал немного вырос, это **не** означает автоматического возврата к L0 — понижающего пути в коде нет.

Важно понимать различие по уровням:

- **L2, L3, FLASH** — снять может оператор через механизм override (см. [[manual-override-resume]]). `OverrideLevel = Literal["L2", "L3", "FLASH"]` (src/risk/override.py:24).
- **L1** — override для L1 **не предусмотрен**: тип `OverrideLevel` его не включает, поэтому ни CLI, ни структура данных не позволяют выдать пропуск. Понижающего автоматического пути тоже нет. В работающем процессе L1 не снимается никак.

---

### Шаг 5. Что происходит при срабатывании

Когда предохранитель срабатывает, любой новый торговый сигнал получает отказ в методе `assess()` (src/risk/manager.py:246-255). Отказ возвращается как `RiskAssessment` с `approved=False` и соответствующим кодом причины:

| HaltState | Код причины (ReasonCode)  |
|-----------|---------------------------|
| L1        | `HALT_DRAWDOWN_L1`        |
| L2        | `HALT_DRAWDOWN_L2`        |
| L3        | `HALT_DRAWDOWN_L3`        |
| FLASH     | `HALT_FLASH_CRASH`        |

Коды определены в src/risk/reason_codes.py:78-81 и src/risk/manager.py:354-359.

Состояние предохранителя и текущая цена закрытия сохраняются в базу данных атомарно, вместе со снимком капитала (src/risk/manager.py:168-182) — чтобы перезапуск бота не потерял информацию о том, что предохранитель уже сработал.

## Формулы и расчёты

### Формула просадки (Drawdown, DD)

```text
DD = (peak − current) / peak
```

Простыми словами: на сколько процентов текущий капитал ниже своего недавнего максимума.

**Пример:** пик был 1000 USDT, сейчас 780 USDT.
DD = (1000 − 780) / 1000 = 0.22 = 22% → сработает L2 (порог L2 = 22%).

Реализация: src/risk/circuit_breakers.py:36 — `dd = (peak - current) / peak`.

### Пороги просадки (из конфига)

| Уровень | Порог (по умолчанию) | Источник конфига             |
|---------|----------------------|------------------------------|
| L1      | ≥ 15%               | `risk_cb_l1_dd = 0.15` (src/platform/config.py:167) |
| L2      | ≥ 22%               | `risk_cb_l2_dd = 0.22` (src/platform/config.py:168) |
| L3      | ≥ 30%               | `risk_cb_l3_dd = 0.30` (src/platform/config.py:169) |

### Формула порога flash-crash

Процент изменения цены за бар:
```text
delta_pct = |bar_close − prev_close| / prev_close
```

Динамический порог (берётся большее из двух значений):
```text
threshold = max(flash_abs, flash_atr_mult × atr / prev_close)
           = max(8%, 3.0 × ATR / prev_close)
```

Срабатывание: `delta_pct > threshold`

Простыми словами: порог в 8% — это защита от очевидных обвалов. Порог `3 × ATR` — адаптивная часть. На спокойном рынке ATR мал, и условие `3 × ATR` даёт небольшой процент — тогда управляет фиксированная граница 8%. На волатильном рынке ATR велик, и динамический порог поднимается выше 8% — это предотвращает ложные срабатывания: «нормальное» движение для волатильного рынка не считается обвалом.

Параметры по умолчанию (src/platform/config.py:170-171):
- `risk_cb_flash_abs = 0.08` (8%)
- `risk_cb_flash_atr_mult = 3.0`

Реализация: src/risk/circuit_breakers.py:54-57.

## Примеры / сценарии

### Сценарий 1. Постепенная просадка, L1

Начало дня: пик капитала (за последние 24 часа) = 10 000 USDT.

Вечером текущий капитал = 8 400 USDT.

DD = (10 000 − 8 400) / 10 000 = 0.16 = 16%.

- 16% ≥ 15% → L1 срабатывает
- 16% < 22% → L2 не срабатывает

Результат: `check_drawdown` возвращает `HaltState.L1`. Новый торговый сигнал получает `approved=False, reason_code=HALT_DRAWDOWN_L1`.

### Сценарий 2. Резкая просадка, L3

Пик = 10 000 USDT, текущий = 6 800 USDT.

DD = (10 000 − 6 800) / 10 000 = 0.32 = 32%.

- 32% ≥ 30% → L3 срабатывает (метод проверяет L3 первым и возвращает сразу)

Результат: `HaltState.L3`, код `HALT_DRAWDOWN_L3`.

### Сценарий 3. Мгновенный обвал (flash-crash)

Предыдущее закрытие: 60 000 USDT (биткоин).
Текущее закрытие: 54 200 USDT.
ATR = 800 USDT (рынок был относительно спокоен).

```text
delta_pct = |54 200 − 60 000| / 60 000 = 5 800 / 60 000 ≈ 9.67%
atr_pct   = 3.0 × 800 / 60 000 = 2 400 / 60 000 = 4.0%
threshold = max(8%, 4.0%) = 8%
```

9.67% > 8% → flash-crash обнаружен. `check_flash` возвращает `True`.

Результат: `self._current_halt` повышается до `HaltState.FLASH`, код `HALT_FLASH_CRASH`.

### Сценарий 4. Волатильный рынок — ложное срабатывание предотвращено

Предыдущее закрытие: 60 000 USDT.
Текущее закрытие: 64 800 USDT (рост 8%).
ATR = 3 500 USDT (рынок очень волатильный).

```text
delta_pct = |64 800 − 60 000| / 60 000 = 4 800 / 60 000 = 8.0%
atr_pct   = 3.0 × 3 500 / 60 000 = 10 500 / 60 000 = 17.5%
threshold = max(8%, 17.5%) = 17.5%
```

8.0% < 17.5% → flash-crash НЕ обнаружен. Движение в 8% считается обычным для такого волатильного рынка.

### Сценарий 5. Первый бар после перезапуска (проектный замысел)

> **Примечание:** описанный ниже сценарий — проектный замысел, который будет работать после интеграции `on_bar_close` в live runtime. Пока `on_bar_close` не вызывается из `src/runtime/manager.py`, `_prev_close` всегда `None` и flash-ветка не срабатывает.

Бот перезапускается. Метод `load_state` восстанавливает `_prev_close` из базы данных (src/risk/manager.py:134-136). На следующем баре flash-проверка работает нормально — значение предыдущего закрытия не потеряно.

Если бы `_prev_close` не восстанавливался, первый бар после перезапуска пропускал бы flash-обнаружение (условие `if self._prev_close is not None` в assess() вернуло бы False для flash-ветки).

## Подводные камни / что важно понимать

**1. Уровень halt не снижается автоматически — и для L1 нет пути выхода в работающем процессе.**
Если просадка была 25% (L2), а потом капитал вырос обратно и просадка стала 10%, уровень L2 остаётся. Это сделано намеренно: автоматическое снятие halt создаёт риск «пилы» — бот мог бы постоянно включаться и выключаться на границе порога. Код реализует это через строгое `>` при обновлении (src/risk/manager.py:159) — понижающей ветки нет.

Для **L2, L3 и FLASH** оператор может снять уровень через механизм override (см. [[manual-override-resume]]). Для **L1** это невозможно ни автоматически, ни вручную: тип `OverrideLevel = Literal["L2", "L3", "FLASH"]` (src/risk/override.py:24) не включает L1, а автоматического понижения нет. L1 остаётся до перезапуска бота.

**2. Flash-срабатывание имеет наивысший приоритет (severity=4) — и переводит в FLASH даже с L3.**
Flash поднимает halt только если текущий уровень строго ниже FLASH по числу приоритета. Проверка (src/risk/manager.py:240-243):

```python
if is_flash and self._halt_severity(HaltState.FLASH) > self._halt_severity(self._current_halt):
    self._current_halt = HaltState.FLASH
```

По таблице приоритетов FLASH=4, L3=3. Значит: **если уже стоит L3, flash переводит в FLASH** (4 > 3 = True) — оба уровня серьёзны, но flash имеет более высокий приоритет. Если уже стоит FLASH — повторное flash-событие ничего не меняет (4 > 4 = False). Если стоит L1 — flash переводит в FLASH (4 > 1 = True).

**3. Все пороги живут в конфиге, а не в коде.**
Ни одного «магического числа» в `circuit_breakers.py` нет. Все значения (15%, 22%, 30%, 8%, 3.0) приходят через `CircuitBreakerConfig`, который заполняется из [[configuration-and-settings|Settings]] (src/platform/config.py:167-171). Изменить порог — значит изменить переменную окружения и перезапустить бота. Это важно: при выдаче оператором override-а система проверяет хэш конфига — чтобы никто не мог тихо изменить порог уже после выдачи разрешения.

**4. Flash-проверка — «закрытие к закрытию» (close-to-close).**
Метод сравнивает `mark_price` (цена текущего момента в `assess()`) с `prev_close` (ценой закрытия предыдущего бара). Это не внутрибаровый скачок, а движение от одного закрытия к другому. Резкие движения внутри бара, которые «залечились» к закрытию, предохранитель не поймает.

**5. Детектор — чистая математика, управление состоянием — в менеджере.**
`CircuitBreakerDetector` ничего не сохраняет. Он просто считает. Всё управление состоянием (какой текущий halt, когда он изменился, сохранение в базу данных) — в `RiskManager`. Это разделение намеренно: детектор легко тестировать изолированно, передавая любые числа.

**6. Атомарность записи.**
Снимок капитала и состояние предохранителя сохраняются в одной SQLite-транзакции (src/risk/manager.py:169-182). Если запись состояния предохранителя не удалась — снимок капитала тоже откатывается. Это гарантирует, что после перезапуска бот не прочитает «старый» halt-уровень против «нового» пика капитала.

- [[equity-tracking]] — как именно накапливаются снимки капитала и откуда берётся 24-часовой пик (EquityTracker)
- [[manual-override-resume]] — как оператор снимает halt и возобновляет торговлю после срабатывания предохранителя
- [[halt-gate-precommitted-criteria]] — расширенный набор halt-условий для тестнет-демо (S35 HaltGate): падение за день, падение за несколько дней, серия убытков
- [[reason-codes-assessment-output]] — полный справочник кодов причин, включая все HALT_* коды
- [[risk-overview-decision-pipeline]] — общая картина: как circuit breaker встраивается в цепочку принятия решений (assess → sizing → исполнение)
- [[kill-switch-emergency-stop]] — аварийная остановка по файлу-флагу, отдельный механизм от circuit breakers
- [[safety-stops-and-halts]] — общий обзор всех тормозов бота (стоп-файл, halt-пороги, аварийный выход) с точки зрения runtime — сюда встраиваются оба предохранителя
- [[main-loop-tick]] — главный цикл бота: где именно на каждом тике должны бы вызываться `on_bar_close` и `update_equity` (пока не интегрированы)
- [[position-sizing-kelly]] — следующий шаг конвейера: если предохранитель пропустил сделку (approved=True), дальше вычисляется размер позиции
- [[max-drawdown-winrate-rr]] — определение и расчёт просадки (drawdown) по equity-кривой — метрика, на пороги которой опираются уровни L1/L2/L3
- [[atr-indicator]] — что такое ATR и как он считается; ATR входит в динамический порог flash-crash (`3 × ATR / prev_close`)
- [[configuration-and-settings]] — откуда берутся пороги предохранителей (`risk_cb_*`) и почему override сверяет хэш конфига
- [[execution-state-persistence-and-halt-audit]] — как состояние halt и предыдущее закрытие сохраняются/восстанавливаются при перезапуске и журнал аварийных остановок

За техническими деталями: `llm-wiki/wiki/project/components/risk-manager.md`
