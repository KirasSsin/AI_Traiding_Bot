# История сделок и исполнений: данные, на которых бот учится

**TL;DR:** Каждый раз, когда бот закрывает позицию, он записывает итог в свою «тетрадь» — базу данных. Из этой тетради он потом считает, насколько успешно торгует, какой размер ставить на следующую сделку ([[position-sizing-kelly|формула Келли]]) и когда пора остановиться (серия убытков, просадка).

## Простыми словами

Представьте профессионального игрока в покер, который после каждой партии записывает в блокнот: когда начал, когда закончил, сколько поставил, сколько выиграл или проиграл, и почему ушёл из-за стола. Через месяц он открывает блокнот и считает: «За последние 90 дней я выигрывал в 55% партий, средний выигрыш в 1.8 раза больше среднего проигрыша — могу чуть поднять ставку». Если же он проиграл 5 партий подряд — самодисциплина говорит: «Стоп, сегодня хватит».

Наш бот делает то же самое, только автоматически и с математической точностью.

Данные хранятся в двух «тетрадях»:
1. **Тетрадь закрытых сделок** (`trade_history`) — итог каждой позиции целиком: вошёл по такой-то цене, вышел по такой-то, заработал/потерял столько-то.
2. **Тетрадь исполнений** (`trade_fills`) — дробные подробности: каждый частичный «тик» покупки или продажи на бирже, чтобы потом анализировать, насколько точно исполнился приказ (слиппедж — разница между ожидаемой и реальной ценой исполнения).

Из первой тетради напрямую питаются два ключевых механизма:
- **[[position-sizing-kelly|Формула Келли]]** — сколько ставить на следующую сделку.
- **[[halt-gate-precommitted-criteria|HaltGate]] (аварийный тормоз)** — сколько убытков подряд и как давно была последняя сделка.

## Как это работает у нас

### Запись закрытой сделки

#### Модель `TradeRecord` — что именно сохраняется

Каждая закрытая сделка — это неизменяемый (frozen=True) объект `TradeRecord` со следующими полями (`src/risk/trade_history.py:17–35`):

| Поле | Тип | Что значит |
|---|---|---|
| `symbol` | строка | Торговая пара, например `BTCUSDT` |
| `entry_signal_id` | UUID | Уникальный идентификатор [[signal-architecture|сигнала входа]] — связывает сделку с её «командой на покупку» |
| `entry_ts` / `exit_ts` | AwareDatetime UTC | Время открытия и закрытия позиции в формате ISO-8601 UTC |
| `qty` | Decimal | Объём позиции (всегда > 0) |
| `entry_price` / `exit_price` | Decimal | Цены входа и выхода (всегда > 0) |
| `pnl_quote` | Decimal | **PnL (Profit and Loss)** — прибыль или убыток в котируемой валюте (USDT), со знаком: положительное = прибыль, отрицательное = убыток |
| `pnl_pct` | Decimal | PnL в процентах от суммы позиции (например, `0.012` = +1.2%) |
| `fees_paid` | Decimal | Комиссия биржи, уплаченная за сделку (всегда ≥ 0) |
| `reason_code` | ReasonCode | Код причины закрытия (подробнее — ниже) |
| `kelly_phase` | 1, 2, 3 или 4 | Фаза Келли в момент сделки — зафиксирована «как было» для аудита |
| `recorded_at` | AwareDatetime UTC | Момент записи в базу данных |

Все денежные поля — `Decimal` (точная арифметика), а не float, чтобы избежать ошибок округления при финансовых расчётах. (`src/risk/trade_history.py:17–36`)

#### `insert_closed_trade(record)` — защита от дублей

Когда бот сохраняет закрытую сделку, он вызывает `insert_closed_trade()` (`src/risk/trade_history.py:44–76`). Главная особенность — **идемпотентность**: если сделку попытаться записать дважды с одним и тем же `entry_signal_id`, база данных тихо проигнорирует дубликат и вернёт уже существующий `trade_id`.

Это реализовано через SQL-команду `INSERT OR IGNORE` с уникальным индексом по полю `entry_signal_id` (`src/risk/trade_history.py:47–52`). Зачем это нужно: биржевые события могут прийти дважды (так называемая «доставка at-least-once» — «хотя бы один раз»). Без этой защиты одна и та же сделка попала бы в статистику дважды и исказила расчёт Келли.

```python
# INSERT OR IGNORE — если запись с этим entry_signal_id уже есть, она останется нетронутой
cursor = self._conn.execute(
    "INSERT OR IGNORE INTO trade_history (...) VALUES (?...)",
    ...
)
# Если rowcount == 0 — дубликат, читаем существующий trade_id
```

(src/risk/trade_history.py:47–76)

#### Хранение в базе данных

Decimal-числа сохраняются как строки (`str(record.qty)`, и т.д.) и при чтении обратно восстанавливаются через `Decimal(row[5])` — это стандартный способ сохранить точность в SQLite, который не имеет встроенного Decimal-типа. Дата-время хранится в формате ISO-8601. (`src/risk/trade_history.py:55–67`, `src/risk/trade_history.py:164–180`)

### Чтение данных для Келли

#### `load_recent(window_days=90, symbol)` — скользящее окно

Для расчёта Келли бот читает только **последние 90 дней** закрытых сделок (`src/risk/trade_history.py:78–114`). Это называется скользящим окном (window_days): старые сделки уже не учитываются, потому что рыночные условия меняются и прошлая статистика двухлетней давности может быть неактуальна.

Важный нюанс: метод принимает опциональный параметр `symbol`. Если символ указан (например `BTCUSDT`), возвращаются только сделки по этому активу. Это **изоляция Келли по символу** (S15, ADR 0030): выигрыши на ETH не раздувают долю ставки по BTC, и наоборот. Если символ не указан — возвращаются все сделки (для совместимости). (`src/risk/trade_history.py:85–114`)

Отсечка по времени:
```python
cutoff = (now or datetime.now(UTC)) - timedelta(days=window_days)  # по умолчанию 90 дней
# Запрос: WHERE exit_ts >= cutoff AND symbol = ?
```
(src/risk/trade_history.py:93–103)

[[risk-overview-decision-pipeline|Риск-менеджер]] вызывает этот метод так (`src/risk/manager.py:329`):
```python
recent = self._trades.load_recent(window_days=90, now=self._clock(), symbol=self._symbol)
```

#### `count()` — определяет фазу Келли

Метод `count()` возвращает общее число закрытых сделок в базе (без ограничения по времени). Это число используется для определения **фазы Келли** — см. ниже в разделе формул. (`src/risk/trade_history.py:116–117`)

### Данные для [[halt-gate-precommitted-criteria|HaltGate]] (аварийный тормоз)

#### `consecutive_losses(symbol)` — серия убытков

Метод читает все сделки по символу, отсортированные от новых к старым, и считает, сколько подряд **убыточных** сделок в хвосте (до первой прибыльной) (`src/risk/trade_history.py:132–148`):

```python
rows = self._conn.execute(
    "SELECT pnl_quote FROM trade_history WHERE symbol = ? ORDER BY exit_ts DESC",
    (symbol,),
).fetchall()
streak = 0
for (pnl_str,) in rows:
    if Decimal(str(pnl_str)) < Decimal("0"):
        streak += 1
    else:
        break  # первая прибыльная — стрик сбрасывается
return streak
```

Убыток определяется как `pnl_quote < 0`. Как только встречается хоть одна прибыльная сделка — счётчик останавливается. Этот результат передаётся в `HaltGate.evaluate()`. При `consecutive_losses >= 5` (порог по умолчанию, `src/platform/config.py:144–148`) HaltGate требует остановки и проверки оператором.

#### `last_trade_ts(symbol)` — когда была последняя сделка

Метод возвращает время последней закрытой сделки по символу (`src/risk/trade_history.py:150–161`). Используется для расчёта `months_since_last_trade`: если бот работает, но 6+ месяцев не закрыл ни одной сделки (сигнальное голодание) — это тоже стоп-сигнал. (`src/runtime/manager.py:248–254`, `src/platform/config.py:150–154`)

### Запись исполнений (fills)

#### `FillRecord` — отдельный тик на бирже

Если `TradeRecord` — это итог всей сделки, то `FillRecord` — это каждый отдельный «тик», когда биржа исполняла приказ (`src/risk/fill_history.py:19–33`):

| Поле | Что значит |
|---|---|
| `parent_trade_id` | Ссылка на родительскую сделку в `trade_history` |
| `exec_id` | Уникальный идентификатор исполнения от Bybit V5 — ключ идемпотентности |
| `fill_qty` / `fill_price` | Объём и цена частичного исполнения |
| `fill_fee` / `fee_currency` | Комиссия за этот тик и в какой валюте |
| `is_partial` | `True`, если `leavesQty > 0` — ордер исполнен не полностью (частичное исполнение) |
| `fill_ts` | Время исполнения на бирже (из метки биржи, не нашего сервера) |

**Частичное исполнение (partial fill)** — это когда ордер на покупку, скажем, 1 BTC, биржа исполняет частями: сначала 0.4 BTC по одной цене, затем ещё 0.6 BTC по другой. Каждая часть — отдельный FillRecord. (`src/risk/fill_history.py:26–31`)

Идемпотентность — через `exec_id`: повторный `INSERT OR IGNORE` по уникальному индексу на `exec_id`. (`src/risk/fill_history.py:42–69`)

### FillRecorderAdapter — мост от биржи к базе данных

`FillRecorderAdapter` перехватывает события от Bybit в режиме реального времени (через [[bybit-private-websocket|приватный WebSocket]] — постоянное соединение, по которому биржа сама присылает уведомления об исполнениях) и пытается записать их в базу (`src/risk/fill_recorder_adapter.py:49–158`).

#### Двухслойный паттерн «best-effort»

**Слой 1 (всегда):** каждое событие исполнения логируется в audit-лог (`logger.info("fill_event_received", ...)`) — независимо от того, удастся ли сохранить в базу. (`src/risk/fill_recorder_adapter.py:83`)

**Слой 2 (по возможности):** попытка сохранить в базу через цепочку разрешения идентификаторов (`bracket_id` — идентификатор [[oco-bracket-emulation|OCO-брекета]], хранится в таблице [[execution-state-persistence-and-halt-audit|execution_state]]):
```text
Bybit orderId → execution_state.bracket_id → entry_signal_id → trade_id
```
Если хотя бы один шаг цепочки не разрешается — запись пропускается с предупреждением в лог, но адаптер **не падает с ошибкой**. (`src/risk/fill_recorder_adapter.py:91–138`)

Главный инвариант: WS-колбэк (функция обратного вызова, которую вызывает библиотека pybit при получении биржевого события) **никогда не должен завершаться с исключением** — иначе поток WebSocket-соединения упадёт. Поэтому весь код обёрнут в `try/except Exception` с логированием ошибки. (`src/risk/fill_recorder_adapter.py:86–89`)

#### Текущее ограничение (отложено к S13+)

На момент текущей реализации (S12) в таблице `execution_state` нет поля `entry_signal_id` — только `bracket_id`. Из-за этого цепочка разрешения всегда обрывается на втором шаге, и fill-записи в БД не попадают. Это осознанное техническое решение (Q7-ограничение на S12 запрещало миграцию схемы). Данные не теряются — они всегда есть в audit-логе (слой 1). Исправление запланировано на S13+. (`src/risk/fill_recorder_adapter.py:9–22`)

#### Потокобезопасность

WS-события приходят в отдельном потоке, а основная логика бота работает в главном потоке. Чтобы одновременная запись в SQLite не вызывала конфликт, критическая секция разрешения и вставки защищена `threading.Lock` (`src/risk/fill_recorder_adapter.py:63–73`, `src/risk/fill_recorder_adapter.py:103–104`).

### Коды причин ([[reason-codes-assessment-output|ReasonCode]]) — зачем закрылась сделка

Каждая закрытая сделка содержит `reason_code` — код, объясняющий, почему она закрылась. Это перечисление (`StrEnum`) из 67 значений в `src/risk/reason_codes.py`. Коды разбиты на пять групп по префиксу:

| Группа | Кодов | Примеры | Что означают |
|---|---|---|---|
| **Входы** (`ENTRY_*`, 11 кодов) | 11 | `ENTRY_LONG_TREND_FOLLOWING`, `ENTRY_LONG_KRONOS` | По какой стратегии вошли в позицию |
| **Масштабирование** (`SCALE_*`, 3 кода) | 3 | `SCALE_IN_LONG`, `SCALE_OUT_PARTIAL` | Добавили к позиции или уменьшили её частично |
| **Выходы** (`EXIT_*`, 20 кодов) | 20 | `EXIT_SL_HIT`, `EXIT_TP_HIT`, `EXIT_FLAT_KRONOS` | Как вышли: стоп-лосс, тейк-профит, сигнал стратегии, трейлинг-стоп и др. |
| **Отказы** (`REJECT_*`, 9 кодов) | 9 | `REJECT_RISK_EXCEEDED`, `REJECT_MIN_NOTIONAL` | Почему бот отверг сигнал, не открыв позицию |
| **Остановки** (`HALT_*` + `KILL_SWITCH_REQUESTED`, 24 кода) | 24 | `HALT_DRAWDOWN_L1`, `HALT_S36_CONSECUTIVE_LOSSES`, `KILL_SWITCH_REQUESTED` | Системные аварийные остановки и принудительный сигнал выключения ([[kill-switch-emergency-stop|kill-switch]]) |

(`src/risk/reason_codes.py:45–153`)

**Внутри группы «Выходы»** есть важное разделение: из 20 кодов ровно 10 имеют подпрефикс `EXIT_FLAT_*` — это выходы, инициированные самой торговой стратегией (например, `EXIT_FLAT_KRONOS`, `EXIT_FLAT_ATR_STOP`, `EXIT_FLAT_SUPERTREND_FLIP`). Остальные 10 кодов без `FLAT_` — это системные выходы, инициированные не стратегией, а другими механизмами: `EXIT_SL_HIT` (стоп-лосс), `EXIT_TP_HIT` (тейк-профит), `EXIT_TRAILING_STOP` (трейлинг-стоп), `EXIT_SIGNAL_FLIP` (смена сигнала на уровне исполнения), `EXIT_TIME_STOP` (тайм-аут), `EXIT_MANUAL_OVERRIDE` ([[manual-override-resume|ручное вмешательство оператора]]), `EXIT_CIRCUIT_BREAKER` ([[circuit-breakers-drawdown-flash|предохранитель просадки/обвала]]), `EXIT_OCO_PARTIAL_TIMEOUT`, `EXIT_STOP_RESIDUAL_FLATTEN` ([[emergency-flatten-and-residual|аварийное закрытие остатка]]) и `EXIT_RECONCILE_DETECTED` ([[reconcile-as-truth|сверка с биржей]]). (`src/risk/reason_codes.py:55–101`)

Коды **неизменяемы** — переименование требует поправки ADR. Это важно: исторические записи в базе должны оставаться читаемыми, даже если через год появятся новые стратегии.

## Формулы и расчёты

### Четыре фазы Келли — как торговая история влияет на размер ставки

**Что такое фаза Келли:** формула Келли вычисляет оптимальную долю капитала для ставки исходя из вероятности выигрыша и соотношения выигрыша к проигрышу. Но эта формула работает только при наличии достаточной статистики. Пока сделок мало — используются консервативные фиксированные значения.

**Определение фазы** — функция `phase_from_trade_count(n)` (`src/risk/kelly.py:20–40`):

```text
n < 30   → Фаза 1 (мало данных)
n < 100  → Фаза 2 (накапливаем)
n < 200  → Фаза 3 (достаточно для Четверть-Келли)
n ≥ 200  → Фаза 4 (полная статистика, Полу-Келли)
```

Здесь `n` — результат `TradeHistoryRepository.count()` (общее число закрытых сделок).

**Размер ставки по фазе** — функция `phase_adjusted_fraction()` (`src/risk/kelly.py:95–128`):

| Фаза | Условие | Правило | Ограничение (cap) |
|---|---|---|---|
| 1 | n < 30 | Фиксированная ставка | 1% капитала (`risk_kelly_phase1_cap = 0.01`) |
| 2 | 30 ≤ n < 100 | Фиксированная ставка | 2% капитала (`risk_kelly_phase2_cap = 0.02`) |
| 3 | 100 ≤ n < 200 | Четверть-Келли: `0.25 × f*` | не более 3% (`risk_kelly_phase3_cap = 0.03`) |
| 4 | n ≥ 200 | Полу-Келли: `0.5 × f*` | не более 5% (`risk_kelly_phase4_cap = 0.05`) |

Значения по умолчанию: `src/platform/config.py:172–175`.

**Что такое `f*`:** базовая формула Келли:

```text
f* = (p × b − q) / b
```

где:
- `p` — вероятность выигрыша ([[max-drawdown-winrate-rr|доля прибыльных сделок, Win Rate]])
- `q = 1 − p` — вероятность проигрыша
- `b` — соотношение среднего выигрыша к среднему проигрышу (Risk-Reward)

Простыми словами: если в 55% сделок выигрываешь, и средний выигрыш в 1.5 раза больше среднего проигрыша — формула говорит, какую долю капитала ставить, чтобы рост был максимальным без риска разорения.

В фазах 1 и 2 `f*` не вычисляется — используется фиксированный cap. В фазах 3 и 4 для `p` используется не просто доля побед, а **нижняя граница доверительного интервала Вильсона 95%** — консервативная оценка, которая защищает от переоценки удачи при небольшой выборке. (`src/risk/manager.py:325–341`)

### Консервативная оценка `p` через доверительный интервал Вильсона

Формула (`src/risk/kelly.py:43–70`):

```text
p_hat  = wins / total
z      = 1.96  (95% доверительный интервал)
center = p_hat + z² / (2 × total)
spread = z × √(p_hat × (1 − p_hat) / total + z² / (4 × total²))
denom  = 1 + z² / total
lower  = (center − spread) / denom
upper  = (center + spread) / denom
```

Бот использует `lower` — нижнюю границу. Это значит: «даже если нам немного не повезло с выборкой, мы не переставим ставку слишком высоко». Если в последние 90 дней меньше 30 сделок (даже в фазе 3+) — формула не применяется, возвращается дефолт `(p=0.5, b=1.0)`. (`src/risk/manager.py:325–341`)

## Примеры / сценарии

### Сценарий 1: первые 15 закрытых сделок

Бот только начал торговать. `count()` возвращает 15. `phase_from_trade_count(15)` → Фаза 1. Размер ставки фиксирован: 1% капитала (`risk_kelly_phase1_cap = 0.01`). Никакой статистики из истории сделок не нужно — просто осторожно.

### Сценарий 2: 120 закрытых сделок, хорошая статистика

`count()` = 120 → Фаза 3 (n < 200). Бот вызывает `load_recent(window_days=90, symbol="BTCUSDT")` и получает 45 сделок за последние 90 дней. Из них: 26 прибыльных, 19 убыточных. Средний выигрыш = 15 USDT, средний проигрыш = 10 USDT.

- `p_hat = 26/45 ≈ 0.578`
- `b = 15/10 = 1.5`
- `f* = (0.578 × 1.5 − 0.422) / 1.5 ≈ 0.297`
- Нижняя граница Вильсона `p_lower ≈ 0.432` (консервативнее p_hat)
- `f*` с `p_lower = (0.432 × 1.5 − 0.568) / 1.5 ≈ 0.054`
- Четверть-Келли: `0.25 × 0.054 ≈ 0.0135`
- Ограничение cap3 = 0.03 → итоговая ставка = **1.35% капитала** (в cap вписываемся)

### Сценарий 3: серия из 5 убытков подряд

`consecutive_losses("BTCUSDT")` → 5. Порог в конфиге (`s35_halt_consecutive_losses`) = 5. Условие `>= 5` выполнено. `HaltGate.evaluate()` возвращает `HaltTrigger.CONSECUTIVE_LOSSES`. Runtime-менеджер вызывает `coordinator.request_halt(HALT_S36_CONSECUTIVE_LOSSES)`. Бот останавливается до проверки оператором. (`src/risk/halt_gate.py:69–70`, `src/runtime/manager.py:247–283`)

### Сценарий 4: попытка записать сделку дважды

Событие о закрытии сделки с `entry_signal_id = "abc-123"` пришло от биржи дважды (сбой сети, повторная доставка). Первый вызов `insert_closed_trade()` записывает сделку и возвращает `trade_id = 42`. Второй вызов встречает `INSERT OR IGNORE` — БД игнорирует дубликат, метод читает существующую запись и также возвращает `trade_id = 42`. Дубликата в статистике нет. (`src/risk/trade_history.py:44–76`)

### Сценарий 5: fill-событие от Bybit в реальном времени

Bybit присылает по WebSocket событие исполнения с `orderId = "XYZ"`. Адаптер:
1. Логирует в audit-лог («fill_event_received») — всегда.
2. Пытается разрешить: `order_id="XYZ"` → ищет в `execution_state` → находит `bracket_id="B1"`.
3. Пытается получить `entry_signal_id` из `state_row` — поле отсутствует (текущая схема S12).
4. Логирует предупреждение «bracket_id↔trade_id schema link missing (deferred к S13)» и пропускает вставку в БД.
5. Fill остаётся в audit-логе, но не в таблице `trade_fills` — до исправления схемы в S13+.

(`src/risk/fill_recorder_adapter.py:106–138`)

## Подводные камни / что важно понимать

**1. Все денежные поля — Decimal, не float.** Это принципиально: float в Python имеет погрешность (например, `0.1 + 0.2 ≠ 0.3`). При финансовых расчётах накопленная погрешность может исказить PnL или Kelly-ставку. Все суммы в TradeRecord и FillRecord — `Decimal`. (`src/risk/trade_history.py:18`)

**2. `load_recent` читает по `exit_ts`, не `entry_ts`.** Для скользящего окна важен момент закрытия, а не открытия сделки: сделка, открытая 95 дней назад, но закрытая 3 дня назад — попадёт в окно 90 дней. (`src/risk/trade_history.py:85–101`)

**3. Изоляция Kelly по символу — обязательна.** Если не передать `symbol`, Kelly-расчёт смешает статистику разных активов. Это режим совместимости (backward-compat), а не рекомендуемый вариант. Каждый `RiskManager` передаёт свой символ. (`src/risk/trade_history.py:85–89`, `src/risk/manager.py:329`)

**4. В фазах 1 и 2 `_compute_p_b` не вызывается.** В фазах 1 и 2 статистика сделок для Келли вообще не читается из базы — возвращаются заглушки `(0.5, 1.0)`, которые `phase_adjusted_fraction` игнорирует, применяя фиксированный cap. `load_recent` вызывается только начиная с фазы 3. (`src/risk/manager.py:325–341`)

**5. Fill-записи сейчас не попадают в БД.** Из-за отсутствия `entry_signal_id` в схеме `execution_state` (S12) цепочка разрешения всегда обрывается. Это известное ограничение, зафиксированное в коде и запланированное к исправлению в S13+. Для аналитики fills пока нужно читать audit-лог. (`src/risk/fill_recorder_adapter.py:9–22`, `src/risk/fill_recorder_adapter.py:116–127`)

**6. `months_since_last_trade` считается целыми месяцами через `days // 30`.** Нет ни одной сделки — отсчёт идёт от момента активации бота, не от нуля. Это намеренно: если бот включён и 6 месяцев не торгует — это тревожный знак сигнального голодания. (`src/runtime/manager.py:249–254`)

**7. `kelly_phase` в `TradeRecord` — исторический снимок.** Это фаза в момент сделки. С ростом числа сделок фаза растёт, и старые записи с фазой 1 останутся с фазой 1 — это нормально и используется только для аудита, а не для текущего расчёта.

**8. ReasonCode — неизменяемый контракт.** Коды нельзя переименовывать — исторические записи в базе сломаются. Новые коды добавляются только через поправку ADR. (`src/risk/reason_codes.py:1–10`)
