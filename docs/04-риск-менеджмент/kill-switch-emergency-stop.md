# Аварийный стоп (kill-switch): как оператор мгновенно глушит бота

**TL;DR:** Оператор запускает одну команду — `python -m src kill` — и бот при ближайшей же проверке (раз в 5 секунд) замечает сигнал и полностью останавливает торговлю. Никакой сетевой зависимости: механизм работает через обычный файл на диске.

---

## Простыми словами

Представьте, что у торгового бота есть большая красная кнопка аварийного отключения. Пока кнопка не нажата — бот работает. Как только кнопка нажата — бот при первой же возможности останавливается.

В нашем случае «красная кнопка» — это специальный пустой файл на диске с именем `.kill_switch`. Оператор пишет этот файл одной командой. Бот в своём торговом цикле (так называемом «тике» — проверке раз в 5 секунд) первым делом смотрит: есть ли этот файл? Если есть — всё, торговля прекращается.

**Зачем файл, а не, например, кнопка в интерфейсе?** Файловый механизм работает независимо от сети, от состояния дашборда, от базы данных. Даже если всё остальное зависло — файл на диске можно создать мгновенно из любого места: из другого терминала, по SSH, через скрипт. Это простой и надёжный канал управления извне процесса бота.

**Что происходит с деньгами после нажатия?** Бот переходит в состояние HALTED («заморожен»): торговля прекращается, открытые ордера остаются в том положении, в котором они были на момент остановки. Бот не снимает ордера автоматически — он просто перестаёт делать новые действия. Это осознанное решение: принудительное снятие ордеров в панике может оказаться опаснее, чем оставить их в работе.

## Как это работает у нас

### Шаг 1. Оператор записывает файл-сигнал

Команда запускается из командной строки:

```bash
python -m src kill
```

За этим стоит функция `_cmd_kill` в `src/__main__.py:459–484`. Вот что она делает:

1. Читает из настроек путь к файлу-сигналу: `settings.runtime_kill_switch_path` — по умолчанию это просто `.kill_switch` в текущей директории (src/platform/config.py:222–224).
2. Создаёт родительскую папку, если её нет.
3. Пишет **пустой файл** атомарно: сначала во временный файл `.kill_switch.tmp`, затем переименовывает его в `.kill_switch`. Этот приём называется **атомарной записью** — он гарантирует, что бот никогда не прочитает файл в «полусозданном» состоянии.
4. Выводит на экран подтверждение: `kill switch written: .kill_switch` и завершается с кодом 0.

```python
# src/__main__.py:472–481
tmp = sentinel.with_suffix(sentinel.suffix + ".tmp")
flags = os.O_WRONLY | os.O_CREAT | os.O_TRUNC
fd = os.open(tmp, flags, 0o600)
try:
    with os.fdopen(fd, "wb") as f:
        f.write(b"")
    os.replace(tmp, sentinel)
finally:
    if tmp.exists():
        tmp.unlink(missing_ok=True)
```

Файл создаётся с правами `0o600` (только владелец может читать и писать) — базовая мера безопасности, чтобы случайный процесс не мог прочитать или изменить сигнал.

**Важно:** функция не использует `os.fsync` (принудительный сброс на диск). Docstring объясняет: kill-switch — операторский сигнал, не финансовые данные; накладные расходы fsync здесь не оправданы. `os.replace` (атомарное переименование) защищает от частичного файла — это достаточная гарантия надёжности.

### Шаг 2. Бот обнаруживает файл на очередном тике

Каждые `runtime_bar_poll_cadence_seconds` секунд (по умолчанию 5.0, src/platform/config.py:210–212) бот выполняет один [[main-loop-tick|«тик»]] — функцию `_tick()` в `src/runtime/manager.py:162–178`.

Порядок проверок внутри тика строго определён:

```
kill_switch → check_alive → halt_gate → reconcile_ttl → poll_bar → strategy → risk → bracket
```

**Kill-switch проверяется самым первым** — это наивысший приоритет оператора. Если сигнал обнаружен, весь остаток тика пропускается.

Проверку выполняет метод `_maybe_kill_switch()` (src/runtime/manager.py:286–296):

```python
def _maybe_kill_switch(self) -> bool:
    if self._kill_switch_path.exists():
        logger.info(
            "runtime.kill_switch_detected",
            sentinel_path=str(self._kill_switch_path),
        )
        self._coordinator.request_halt(ReasonCode.KILL_SWITCH_REQUESTED)
        self._stopping = True
        return True
    return False
```

Метод просто проверяет, существует ли файл. Если да — три действия:
1. Записывает в лог событие `runtime.kill_switch_detected` с путём к файлу.
2. Вызывает `coordinator.request_halt(KILL_SWITCH_REQUESTED)`.
3. Устанавливает флаг `self._stopping = True` — это сигнал главному циклу (`_main_loop`) прекратить итерации.

### Шаг 3. [[coordinator-orchestration|Координатор]] переводит FSM в состояние HALTED

**FSM** (Finite State Machine — конечный автомат) — это механизм, который отслеживает текущее состояние бота: торгует ли он сейчас, ждёт ли исполнения ордера, остановлен ли. Подробнее об FSM — в [[05-исполнение-ордеров/execution-state-machine]].

Метод `coordinator.request_halt()` (src/execution/coordinator.py:1001–1031) делает следующее:

1. Захватывает блокировку (RLock) — гарантия, что WS-поток (поток получения обновлений с биржи) не изменит состояние одновременно.
2. Записывает причину остановки в [[execution-state-persistence-and-halt-audit|базу данных]]: `halt_reason = "KILL_SWITCH_REQUESTED"`.
3. Проверяет текущее состояние FSM. Если бот ещё не в состоянии HALTED — применяет FSM-событие `KILL_SWITCH_REQUESTED`.
4. Это событие переводит FSM в состояние **HALTED** из любого возможного состояния работы: FLAT, ENTRY_PENDING, LONG_OPEN, OCO_ARMING, OCO_ARMED, EXIT_PENDING и других (src/execution/state_machine.py:174–191).

Если бот уже находится в состоянии HALTED — функция ничего не делает (идемпотентность: повторный вызов безопасен).

**Почему HALTED, а не KILLED?** В FSM есть два «стоповых» состояния. `HALTED` — управляемая пауза; теоретически бот может быть возобновлён вручную. `KILLED` — терминальное состояние, переход в него происходит через другое FSM-событие (`KILL_SWITCH`, без суффикса `_REQUESTED`). Kill-switch через файл-сентинел переводит именно в HALTED — это намеренно, чтобы оставить возможность инспекции перед финальным завершением (src/execution/state_machine.py:174, комментарий «operator HALT (NOT terminal)»).

### Шаг 4. Главный цикл останавливается

После того как `_maybe_kill_switch()` вернула `True` и установила `self._stopping = True`, главный цикл `_main_loop` (src/runtime/manager.py:153–160) видит флаг и выходит из `while not self._stopping`. `_main_loop` завершается **без исключения**, поэтому `run()` (src/runtime/manager.py:150–151) попадает в ветку `else:` и вызывает `_shutdown(reason="NORMAL_EXIT")` — корректное завершение: останавливается WS-потребитель, фиксируется количество незавершённых ордеров. Строка `"KILL_SWITCH"` не передаётся `_shutdown` ни в каком пути — причина остановки в значении «kill-switch» хранится отдельно в БД в колонке `halt_reason = "KILL_SWITCH_REQUESTED"` (записывается ранее, на Шаге 3).

### Шаг 5. Очистка устаревшего сигнала при следующем старте

Если бот был остановлен через kill-switch, а файл `.kill_switch` так и остался на диске — при следующем запуске `rm.run()` первым делом удаляет его (src/runtime/manager.py:116–118):

```python
# Sub-decision 5: clean stale .kill_switch from previous session
if self._kill_switch_path.exists():
    self._kill_switch_path.unlink()
```

Это гарантирует, что старый сигнал не помешает новому запуску бота. Сделано по ADR 0022 sub-decision 5.

## Примеры / сценарии

### Сценарий 1. Штатная остановка

Оператор замечает, что рынок ведёт себя необычно, и хочет остановить бота:

```text
[Терминал 1 — бот работает]
runtime.bar_tick   bar_close_ts=2026-06-26T14:00:00Z
runtime.bar_tick   bar_close_ts=2026-06-26T14:05:00Z
...

[Терминал 2 — оператор вводит команду]
$ python -m src kill
kill switch written: .kill_switch

[Терминал 1 — бот при следующей проверке через ≤5 секунд]
runtime.kill_switch_detected   sentinel_path=.kill_switch
runtime.shutdown               reason=NORMAL_EXIT   in_flight_orders=0
```

Итог: бот остановлен, состояние FSM = HALTED, причина в БД = `KILL_SWITCH_REQUESTED`.

### Сценарий 2. Kill-switch застал бота с открытой позицией

Бот находится в состоянии `OCO_ARMED` (позиция открыта, ордера стоп-лосс и тейк-профит выставлены на бирже). Оператор пишет kill-switch.

Событие `KILL_SWITCH_REQUESTED` применяется к состоянию `OCO_ARMED` → переход в `HALTED` (src/execution/state_machine.py:179). Ордера на бирже остаются активными. Бот перестаёт обрабатывать новые тики. Оператор вручную решает, что делать с открытой позицией — через дашборд или Bybit-интерфейс.

### Сценарий 3. Повторный запуск после остановки

После анализа ситуации оператор решает перезапустить бота:

```bash
python -m src run --symbol BTCUSDT
```

При старте `run()` автоматически удаляет `.kill_switch` (если он есть), затем продолжает нормальный bootstrap. Бот начинает работу с чистого листа.

## Подводные камни / что важно понимать

**Kill-switch НЕ снимает открытые ордера.** Переход в HALTED означает «бот перестал торговать», но не «ордера на бирже отменены». Если в момент нажатия у бота была открытая позиция с выставленными стоп-лоссом и тейк-профитом — они продолжат работать на бирже. Это не баг: убирать ордера в панике может стоить больше денег, чем оставить их работать по плану.

**Путь к файлу задаётся в настройках.** По умолчанию `.kill_switch` — это относительный путь к текущей директории, из которой запускается бот. Если нужна другая папка, её нужно явно указать в `RUNTIME_KILL_SWITCH_PATH` в переменных среды. Командная строка `python -m src kill` всегда читает тот же `Settings`, что и `python -m src run` — они всегда указывают на один файл.

**HALTED — это не KILLED.** После HALTED бот может быть теоретически возобновлён оператором вручную. KILLED — финальное состояние из другой ветки FSM (событие `KILL_SWITCH`, не `KILL_SWITCH_REQUESTED`). Kill-switch через файл-сентинел всегда даёт HALTED, не KILLED. Это сделано специально: оставить время на инспекцию прежде чем принимать финальное решение.

**Идемпотентность.** Можно запустить `python -m src kill` несколько раз подряд — ничего страшного. Если бот уже HALTED, повторный вызов `request_halt` просто ничего не делает (guard на строке coordinator.py:1022–1023). Файл будет перезаписан пустым (флаг `O_TRUNC`), что безвредно.

**Kill-switch — это ручной операторский сигнал, не автоматика.** Его нельзя спутать с автоматическими остановками бота:

| Причина остановки | Код | Кто инициирует |
|---|---|---|
| Файл `.kill_switch` обнаружен | `KILL_SWITCH_REQUESTED` | Оператор вручную |
| Необработанное исключение в боте | `HALT_RUNTIME_CRASH` | Бот автоматически |
| 24 подряд неудачных опроса биржи | `HALT_BAR_POLL_STALL` | Бот автоматически |
| Аномальная цена бара (>0.5% отклонение) | `HALT_DATA_QUALITY` | Бот автоматически |
| Превышение порога просадки ([[halt-gate-precommitted-criteria|HaltGate]]) | `HALT_S36_DD_INTRADAY` и другие | Бот автоматически |

`KILL_SWITCH_REQUESTED` — единственный код, где инициатива принадлежит человеку. Остальные коды начинаются с `HALT_` и срабатывают автоматически по внутренним правилам. Полный [[reason-codes-assessment-output|словарь кодов причин]] — на отдельной странице. (src/risk/reason_codes.py:104–116)

**Порядок проверок в тике критичен.** Kill-switch проверяется первым в `_tick()`, до любых других проверок — сети, стратегии, риска. Это гарантирует, что сигнал оператора не может быть «перекрыт» автоматикой или замедлен обработкой биржевых данных.
