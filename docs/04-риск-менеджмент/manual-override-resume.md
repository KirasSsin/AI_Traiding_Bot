# Ручное снятие предохранителя: override с криптоподписью

**TL;DR:** Когда автоматический предохранитель остановил торговлю, оператор может осознанно выдать разовый «пропуск» — специальный файл с криптографической подписью, который позволяет боту совершить одну сделку в обход остановки. Файл защищён от подделки, привязан к текущим настройкам рисков и «сгорает» ровно после одного использования.

---

## Простыми словами

Представьте, что в вашем офисе сработала пожарная сигнализация — замки на всех дверях автоматически заблокировались. Это правильная реакция: чрезвычайная ситуация. Но охранник, осмотрев здание и убедившись, что тревога ложная (задымился тостер), принимает осознанное решение: он достаёт специальный ключ из сейфа, открывает именно ту дверь и ровно на один проход — после чего ключ автоматически сбрасывается и требует перевыпуска.

В боте работает та же логика:

- **Предохранитель** — это автоматический остановщик торговли при просадке или обвале цены (уровни L2, L3, FLASH). Подробнее — [[circuit-breakers-drawdown-flash]].
- **Override (переопределение, или ручной пропуск)** — разрешение оператора возобновить одну сделку, несмотря на то что предохранитель сработал.
- Это не «выключить сигнализацию насовсем» — это «пройти один раз под ответственность оператора».

**Зачем это вообще нужно?** Предохранитель иногда срабатывает ложно: рынок резко упал, но уже восстановился, а стратегия даёт хороший сигнал. Оператор, проанализировав ситуацию, может решить, что торговать разумно. Без механизма override ему пришлось бы перезапускать бота или менять настройки, что опаснее.

**Почему нужна криптоподпись (cryptographic signature)?** Потому что файл override живёт на диске сервера. Без защиты его можно было бы подделать: написать в нём «разрешить торговлю» и подложить вместо настоящего. Криптоподпись — это математический замок: никто не может создать правильный файл, не зная секретного ключа.

## Как это работает у нас

### Шаг 0: что такое уровни предохранителей и какие из них поддерживают override

У бота пять состояний halt (останова): L0 (норма), L1 (мягкая просадка), L2 (сильная просадка), L3 (критическая), FLASH (мгновенный обвал). Тип `OverrideLevel` (src/risk/override.py:24) допускает override только для **L2, L3 и FLASH** — именно эти три уровня:

```python
OverrideLevel = Literal["L2", "L3", "FLASH"]
```

L1 — это уровень мягкой просадки. Override для L1 не предусмотрен вообще: ни CLI, ни структура данных его не поддерживают (`OverrideLevel` не включает "L1", src/risk/override.py:24). При этом в `src/risk/manager.py:159` уровень halt обновляется только при строгом `>` — понижающего пути нет. Это значит, что L1, однажды установленный, **не снимается автоматически при восстановлении капитала**: даже если `check_drawdown()` вернёт L0 (капитал восстановился, просадки нет), проверка «новый уровень L0 строго серьёзнее текущего L1?» даст «нет» — L0 менее серьёзен, чем L1, а уровень движется только вверх. Бот остаётся в L1. Не помогает и обычный перезапуск: метод `load_state()` при старте читает сохранённый halt-уровень из базы данных и восстанавливает L1 (src/risk/manager.py:131-133; про хранение halt-состояния — [[execution-state-persistence-and-halt-audit]]). Единственный способ сбросить L1 — перезапуск бота **с предварительной очисткой таблицы состояния** в базе данных (удаление записи `risk:cb:current_level`). Никакого автоматического или override-пути выхода из L1 в коде нет.

### Шаг 1: структура разрешения — CbOverride

Разрешение на обход предохранителя описывается неизменяемой (frozen) структурой `CbOverride` (src/risk/override.py:27-36):

```python
class CbOverride(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")

    level: OverrideLevel          # L2, L3 или FLASH
    reason: str                   # объяснение оператора, 1..500 символов
    config_hash: str              # SHA-256 хеш текущих риск-настроек (64 hex-символа)
    created_at: AwareDatetime     # момент выдачи
    expires_at: AwareDatetime     # до когда действует
```

Каждое поле важно:

- **`level`** — с каким конкретным уровнем останова боремся. Override действует только если этот уровень совпадает с тем, что сейчас активен в боте (проверка в manager.assess, см. ниже).
- **`reason`** — текстовое обоснование. Оператор обязан его написать (минимум 1 символ), максимум 500 символов. Это журнальная запись: «рынок восстановился после новости X, сигнал по стратегии Y подтверждён».
- **`config_hash`** — «отпечаток» текущих риск-параметров (порогов просадки, [[position-sizing-kelly|Kelly-капов]] и т.д.). Если оператор после выдачи override изменит настройки — этот хеш не совпадёт, override станет недействительным. Смысл: нельзя выдать разрешение «при одних правилах», а потом тихо поменять правила (см. Шаг 4).
- **`created_at` / `expires_at`** — время жизни. Просроченный override бот не принимает.

### Шаг 2: криптографическая подпись — функция `_sign` и HMAC-SHA256

Прежде чем сохранить файл, система вычисляет подпись над содержимым. Функция `_sign` (src/risk/override.py:39-41):

```python
def _sign(payload: bytes, key: str) -> str:
    return hmac.new(key.encode("utf-8"), payload, hashlib.sha256).hexdigest()
```

**HMAC-SHA256** (Hash-based Message Authentication Code на базе SHA-256) — это криптографическая функция, которая берёт два входа: данные и секретный ключ, и возвращает «контрольную сумму» длиной 64 символа (hex). Главное свойство: без знания секретного ключа невозможно создать правильную подпись. Именно это защищает от подделки файла (CWE-345/306).

Ключ для подписи — `risk_override_hmac_key` из настроек (src/platform/config.py:207):

```python
risk_override_hmac_key: str = Field(..., min_length=32)
```

Это **отдельный ключ**, никак не связанный с API-ключами биржи. Почему отдельный? Если оператор меняет API-ключи (например, из-за подозрения на утечку), это не должно «сбрасывать» уже выданные override-разрешения. И наоборот — смена HMAC-ключа автоматически делает все старые override-файлы недействительными.

**Канонический JSON** (`sort_keys=True`): перед вычислением подписи JSON-поля сортируются по ключу (src/risk/override.py:71-73). Это гарантирует стабильность подписи: `{"a":1,"b":2}` и `{"b":2,"a":1}` — это один и тот же JSON, и подпись должна быть одинаковой независимо от порядка полей в файле.

### Шаг 3: запись файла — атомарная и с правами доступа

Метод `OverrideStore.write()` (src/risk/override.py:61-95) сохраняет подписанный файл следующим образом:

**Формат файла на диске:**
```json
{
  "payload": { <поля CbOverride> },
  "sig": "<64-символьная HMAC-SHA256 подпись>"
}
```

**Последовательность записи (5 шагов):**

1. Создать родительскую директорию с правами `0o700` — только владелец может читать/писать/просматривать содержимое (CWE-276 M1, src/risk/override.py:67).
2. Сериализовать `CbOverride` → JSON → канонический вид (sort_keys) → вычислить подпись.
3. Сформировать «конверт» (envelope) с полями `payload` и `sig`.
4. Записать во **временный файл** (`cb_override.json.tmp`) с правами `0o600` (только владелец читает и пишет) через `os.open(..., 0o600)` (src/risk/override.py:85).
5. Переименовать временный файл в финальный через `os.replace` (src/risk/override.py:91).

**Зачем временный файл и `os.replace`?** Это называется «атомарная запись файла» (atomic file write). `os.replace` — это одна неделимая операция на уровне операционной системы: читатель никогда не увидит файл «наполовину записанным». Либо старая версия, либо новая — третьего не дано. Это защита от ситуации, когда бот читает файл точно в момент записи (CWE-367 M2).

Перед вызовом `os.replace` вызывается `os.fsync` (src/risk/override.py:90), чтобы данные физически попали на диск и не остались в буфере операционной системы. Только после этого происходит атомарное переименование.

По умолчанию файл хранится по пути `./state/cb_override.json` (src/platform/config.py:203).

### Шаг 4: привязка к хешу конфигурации — `config_hash()`

Метод `Settings.config_hash()` (src/platform/config.py:308-321) вычисляет SHA-256 только над «списком» (allowlist) параметров риска. Полный список того, что входит в хеш (src/platform/config.py:22-42):

```python
_HASH_ALLOWLIST = frozenset({
    "risk_max_position_pct_cap",
    "risk_sl_atr_multiplier",
    "risk_tp_atr_multiplier",
    "risk_cb_l1_dd",
    "risk_cb_l2_dd",
    "risk_cb_l3_dd",
    "risk_cb_flash_abs",
    "risk_cb_flash_atr_mult",
    "risk_kelly_phase1_cap",
    "risk_kelly_phase2_cap",
    "risk_kelly_phase3_cap",
    "risk_kelly_phase4_cap",
    "s35_halt_dd_intraday",
    "s35_halt_dd_multiday",
    "s35_halt_consecutive_losses",
    "s35_halt_no_trade_months",
})
```

В хеш **не входят**: API-ключи, пути к файлам, настройки логирования, параметры стратегий. Только риск-пороги. Почему такое разделение?

- Если включить секреты в хеш — они попадут в логи при отладке (CWE-532).
- Если включить пути или флаги логирования — оператор не сможет изменить место хранения лога, не «сломав» override.
- Только риск-пороги важны для решения об override: именно на эти числа смотрит оператор, принимая решение «при таких правилах я разрешаю торговать».

В allowlist входят три семейства параметров: пороги [[circuit-breakers-drawdown-flash|предохранителей]] (`risk_cb_l1_dd`…`risk_cb_flash_atr_mult`), капы [[position-sizing-kelly|Kelly-сайзинга]] по фазам (`risk_kelly_phase1_cap`…`phase4_cap`), [[atr-indicator|ATR]]-множители стопов (`risk_sl_atr_multiplier`, `risk_tp_atr_multiplier`) и критерии [[halt-gate-precommitted-criteria|HaltGate]] (`s35_halt_*`). Все они берутся из [[configuration-and-settings|настроек бота]].

**Практическое следствие:** если после выдачи override поменять хотя бы один из 16 параметров (например, порог L2 с 22% на 25%) — override автоматически становится недействительным. Нужно выдавать заново.

### Шаг 5: чтение и валидация — `read_active()`

Метод `OverrideStore.read_active()` (src/risk/override.py:97-138) возвращает `CbOverride` только если **все** условия выполнены:

| Проверка | Что делает при провале |
|---|---|
| Файл существует | возвращает `None` |
| JSON корректен, есть поля `payload` и `sig` | возвращает `None` |
| HMAC-подпись совпадает | возвращает `None` + **WARNING в лог** («possible tampering») |
| `config_hash` в файле == текущий хеш настроек | возвращает `None` |
| `now < expires_at` (не истёк срок) | возвращает `None` |

Проверка подписи использует `hmac.compare_digest` (src/risk/override.py:124) — специальную функцию, которая сравнивает строки за константное время. Это защищает от атаки по времени (timing attack): обычное сравнение строк возвращает быстрее, если строки расходятся в начале, что позволяет угадывать подпись побайтно.

**Принцип fail-closed (закрыть при ошибке):** при любом сомнении (неверная подпись, неправильный JSON, несовпадение хеша) функция возвращает `None`. Бот **не торгует** по умолчанию — торгует только если override прошёл все проверки. Это противоположность «fail-open», когда при ошибке всё разрешается.

### Шаг 6: применение override в `manager.assess()`

Когда стратегия даёт сигнал на покупку, `RiskManager.assess()` (src/risk/manager.py:202-312) — центральный узел [[risk-overview-decision-pipeline|риск-пайплайна]] — делает следующее:

1. **Читает** активный override (строки 228-231):

```python
override = self._override.read_active(
    now=assessed_at,
    expected_config_hash=self._settings.config_hash(),
)
```

2. **Проверяет уровень halt** (строки 246-255):

```python
if self._current_halt != HaltState.L0:
    if override and override.level == self._current_halt.value:
        self._override.consume(override=override)
        # Bypass succeeded — proceed to sizing.
    else:
        return self._reject(signal, assessed_at, ...)
```

Важный нюанс: `override.level == self._current_halt.value` — это проверка точного совпадения. Если бот стоит в состоянии L3, а override выдан для L2 — он **не сработает**. Оператор должен выдать override именно для того уровня, который сейчас активен.

3. Если override прошёл — немедленно вызывается **`consume()`** (разовое использование). Сделка в итоге разрешается и уходит на расчёт размера ([[position-sizing-kelly|Kelly-сайзинг]]), но следующий сигнал снова упрётся в предохранитель. Если override не прошёл — `assess()` возвращает reject с соответствующим [[reason-codes-assessment-output|кодом причины]] (`HALT_DRAWDOWN_L2/L3/FLASH`).

### Шаг 7: разовое использование — `consume()`

Метод `OverrideStore.consume()` (src/risk/override.py:140-147) переименовывает файл:

```
cb_override.json  →  cb_override.consumed.<unix-timestamp>.json
```

Пример: `cb_override.consumed.1719398400.json`. После переименования оригинальный файл `cb_override.json` исчезает. Следующий вызов `read_active` вернёт `None` — файла больше нет.

Это реализует **single-use semantics (разовое использование)** (ADR 0018 H3, CWE-672): даже если злоумышленник каким-то образом скопировал подписанный файл — первое же реальное использование «сжигает» оригинал. Повторно воспользоваться нельзя.

Consumed-файлы остаются на диске как журнал аудита — можно проверить, сколько раз и когда выдавались override-разрешения.

### Шаг 8: CLI для выдачи override — `resume_cb.py`

Оператор создаёт override через командную строку (src/risk/resume_cb.py):

```bash
python -m src.risk.resume_cb \
    --level L2 \
    --reason "Flash-recovery confirmed, RSI 42 + volume normal" \
    --expires-in 1h
```

Параметры:

| Параметр | Обязателен | Значение по умолчанию | Допустимые форматы |
|---|---|---|---|
| `--level` | да | — | `L2`, `L3`, `FLASH` |
| `--reason` | да | — | строка 1-500 символов |
| `--expires-in` | нет | `1h` | `NNh` (часы), `NNm` (минуты), `NNd` (дни) |

Допустимые форматы срока (`parse_duration`, src/risk/resume_cb.py:13-22): `1h`, `30m`, `2d`. Другие форматы вызывают ошибку аргументов.

CLI печатает в stdout подтверждение вида:
```
Override written: level=L2 expires_at=2026-06-26T15:30:00+00:00
```

**Важно:** путь к файлу override **намеренно не печатается** в stdout (src/risk/resume_cb.py:46-48, CWE-532 L3). Оператор, запускающий команду, и так знает, где настроен путь. Показывать путь в терминале означало бы включить его в логи систем мониторинга, что нежелательно.

После вызова CLI происходит:
1. `Settings()` — загрузка текущих настроек (чтение `.env`).
2. Вычисление `settings.config_hash()` — «отпечаток» текущих риск-параметров.
3. Создание `CbOverride` с `expires_at = now + expires_in`.
4. `OverrideStore.write(override=override)` — атомарная запись подписанного файла.

## Примеры / сценарии

### Сценарий A: нормальный обход flash-crash

**Ситуация:** Биткоин резко упал на 9% за один час из-за новости, через 20 минут восстановился. Бот остановился (FLASH). Стратегия даёт сигнал на покупку в зоне восстановления.

**Действие оператора:**
```bash
python -m src.risk.resume_cb \
    --level FLASH \
    --reason "False flash: BTC recovered +8% in 20min, RSI 38, volume spike normalized" \
    --expires-in 30m
```

**Что происходит:**
1. Файл `./state/cb_override.json` создан, подписан, срок действия 30 минут.
2. Стратегия генерирует сигнал → `assess()` читает файл → все проверки пройдены → override.level "FLASH" == текущий halt "FLASH" → `consume()` → файл переименован в `cb_override.consumed.<ts>.json`.
3. Бот открывает позицию. Следующий сигнал — снова упрётся в FLASH (override сгорел).

---

### Сценарий B: попытка подделки — fail-closed

**Ситуация:** Кто-то вручную создал файл `cb_override.json` с нужными полями, но без правильной подписи (или с неверным HMAC-ключом).

**Что происходит в `read_active()`:**
```
HMAC signature mismatch — possible tampering at ./state/cb_override.json
```
WARNING-лог записан. Функция вернула `None`. Бот торговать не стал — reject с кодом соответствующего halt-уровня.

---

### Сценарий C: оператор поменял настройки после выдачи override

**Ситуация:** Оператор выдал override для L3, а потом поменял `risk_cb_l3_dd` с 0.30 до 0.28.

**Что происходит:**
- `config_hash()` теперь даёт другое значение.
- `read_active()` проверяет: `override.config_hash != expected_config_hash` → `None`.
- Override недействителен. Нужно выдать заново уже с новыми настройками.

---

### Сценарий D: истёкший override

**Ситуация:** Оператор выдал `--expires-in 1h`, но смотрел рынок 2 часа и только потом запустил бот.

**Что происходит:**
- `now >= override.expires_at` → `read_active()` возвращает `None`.
- Торговли нет. Нужно выдать новый override.

## Подводные камни / что важно понимать

**1. Override — это не «выключить предохранитель».** Он позволяет совершить одну сделку. Сразу после неё предохранитель снова активен. Если нужно несколько сделок — нужно несколько override-разрешений.

**2. L1 — sticky-состояние: не снимается ни автоматически, ни через override.** Тип `OverrideLevel = Literal["L2", "L3", "FLASH"]` (src/risk/override.py:24) не включает L1 — CLI откажет с ошибкой валидации. В коде нет ни одного пути для понижения halt-уровня: обновление происходит только при строгом `>` (src/risk/manager.py:159), то есть уровень может только расти. Даже если капитал полностью восстановился и `check_drawdown()` вернёт L0 — проверка «новый L0 строго серьёзнее текущего L1?» даст «нет», ratchet не срабатывает, бот остаётся в L1. **Простой перезапуск не помогает:** `load_state()` читает сохранённое состояние из базы данных и восстанавливает L1 (src/risk/manager.py:131-133). Чтобы сбросить L1, необходимо удалить запись `risk:cb:current_level` из таблицы состояния в базе данных перед перезапуском (или полностью очистить базу состояния). Автоматического пути выхода из L1 не существует — бот останется заблокированным, пока оператор явно не очистит состояние.

**3. Уровень override должен точно совпадать с активным halt.** Если бот стоит на L3 (сильная просадка), а override выдан для L2 — он не сработает. Бот продолжит отклонять сигналы. Нужно проверить текущий уровень halt в логах или дашборде и выдать override именно для него.

**4. Смена риск-настроек аннулирует override.** Если после выдачи override оператор изменит хотя бы один из 16 параметров в allowlist (например, `risk_cb_l2_dd`) — config_hash изменится и override перестанет работать. Нужно перевыпустить.

**5. Срок действия: стандарт 1 час.** По умолчанию (`--expires-in 1h`) override действует один час. Лучше ставить минимально достаточный срок: если стратегия торгует раз в 4 часа — не нужно давать override на сутки. Чем короче окно, тем меньше риск, что пропущенный сигнал всё же активирует торговлю спустя долгое время.

**6. Путь файла не показывается в stdout.** Это намеренно (CWE-532). Путь к override-файлу настраивается через `risk_override_path` в `.env` (по умолчанию `./state/cb_override.json`). Если нужно проверить файл вручную — смотрите настройку, а не вывод команды.

**7. HMAC-ключ — минимум 32 символа.** `OverrideStore` проверяет это при инициализации (src/risk/override.py:56-57). Короткий ключ означает слабую криптографию. Используйте случайную строку, например: `openssl rand -hex 32`.

**8. Consumed-файлы остаются на диске.** Это журнал аудита — не удаляйте их без причины. По ним можно проверить историю override-разрешений. Накопление большого количества файлов (`cb_override.consumed.*.json`) — нормально, но периодически можно архивировать.
