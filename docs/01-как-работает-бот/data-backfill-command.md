# Загрузка истории котировок: команда backfill

**TL;DR:** Команда `backfill` скачивает исторические свечи (цены за прошлые периоды) с биржи Bybit и сохраняет их в компактный файл на диске. Эти данные потом используют [[what-is-backtest-overview|бэктест]] и [[wfa-validation-command|WFA]] — «испытания» стратегий на истории.

## Простыми словами

Представьте, что вы хотите проверить, работала ли ваша торговая идея в прошлом. Для этого нужна история цен: как менялась стоимость биткоина каждый час за последние три года? Биржа хранит эти данные, но отдаёт их порциями — не всё сразу.

**Backfill** (дозагрузка истории) — это именно такая операция: бот идёт на биржу, запрашивает цены за указанный период, собирает их воедино и кладёт в файл. После этого все остальные инструменты (бэктест, WFA) читают данные уже с диска, а не бегают на биржу каждый раз заново.

Аналогия из жизни: вы заходите в архив библиотеки, копируете нужные газеты за прошлые годы к себе на стол — и дальше работаете с локальной копией, не бегая в архив каждые пять минут.

**Что такое «свеча» (котировка)?** [[bar-model|Свеча]] — это запись о том, как изменялась цена за один период времени: с какой цены начали (`open`), до какой поднялись (`high`), до какой упали (`low`), на какой закрылись (`close`) и сколько было сделок за этот период (`volume`). Вместе эти пять чисел называются **OHLCV** (Open, High, Low, Close, Volume). Одна строчка в таблице = одна свеча.

**Что такое интервал свечи (таймфрейм)?** Интервал — это длительность одного периода. Например, при интервале `60` (= 1 час) каждая свеча описывает один час торгов. При интервале `D` — один торговый день.

**Что такое [[parquet-storage|Parquet]]?** Это формат хранения таблиц на диске, придуманный для данных вроде котировок. В отличие от обычного CSV (текстовый файл с запятыми), Parquet хранит данные в колоночном сжатом виде: файл занимает в разы меньше места, а читается быстрее. Дополнительно бот использует сжатие **snappy** — это алгоритм, который ещё сильнее уменьшает размер файла без потери данных.

## Как это работает у нас

Вся логика команды разбита на три уровня: разбор аргументов командной строки → главная функция `_cmd_backfill` → вспомогательная `_backfill_one_symbol`.

### Шаг 1. Разбор аргументов — что скачать?

Команда запускается так:

```bash
python -m src backfill --symbol BTCUSDT --from 2024-01-01 --to 2025-01-01
# или несколько символов сразу:
python -m src backfill --symbols BTCUSDT,ETHUSDT,SOLUSDT --from 2024-01-01 --to 2025-01-01
```

Аргументы, которые принимает команда (`src/__main__.py:829–851`):

| Аргумент | По умолчанию | Значение |
|---|---|---|
| `--symbol` | `BTCUSDT` | Один торговый инструмент |
| `--symbols` | не задан | Несколько инструментов через запятую (переопределяет `--symbol`) |
| `--interval` | `60` | Интервал свечи (см. таблицу ниже) |
| `--from` | обязателен | Дата начала в формате `YYYY-MM-DD` |
| `--to` | обязателен | Дата конца в формате `YYYY-MM-DD` |
| `--output` | `data/<symbol>_<интервал>.parquet` | Путь к выходному файлу (игнорируется при `--symbols`) |

**Поддерживаемые интервалы свечей** (`src/__main__.py:362–371`):

| Код (`--interval`) | Человеческое название | Продолжительность одной свечи |
|---|---|---|
| `5` | 5m | 5 минут |
| `15` | 15m | 15 минут |
| `30` | 30m | 30 минут |
| `60` | 1h | 1 час (по умолчанию) |
| `120` | 2h | 2 часа |
| `240` | 4h | 4 часа |
| `D` | 1d | 1 день |

### Шаг 2. Разрешение списка символов — `_resolve_symbols`

(`src/__main__.py:281–289`)

Функция `_resolve_symbols` определяет, для каких инструментов качать данные. Правило простое: если передан `--symbols` — он приоритетен; если только `--symbol` — берётся он; если не передано ничего — умолчание `BTCUSDT`.

```python
if getattr(args, "symbols", None):
    return [s.strip().upper() for s in args.symbols.split(",") if s.strip()]
sym = getattr(args, "symbol", None) or "BTCUSDT"
return [sym]
```

Все символы автоматически приводятся к верхнему регистру (`upper()`), поэтому `btcusdt` и `BTCUSDT` — одно и то же.

### Шаг 3. Перевод дат в миллисекунды — почему так?

(`src/__main__.py:349–352`)

Биржа Bybit понимает время в формате **timestamp в миллисекундах** (количество миллисекунд, прошедших с 1 января 1970 года). Поэтому дата `2024-01-01` превращается в число:

```python
start_dt = datetime.fromisoformat(args.from_date).replace(tzinfo=UTC)
end_dt   = datetime.fromisoformat(args.to_date).replace(tzinfo=UTC)
start_ms = int(start_dt.timestamp() * 1000)
end_ms   = int(end_dt.timestamp() * 1000)
```

Дата `2024-01-01 00:00:00 UTC` → примерно `1704067200000` (миллисекунды). Это просто «язык», на котором говорит Bybit API — человеку читать необязательно, бот делает это сам.

### Шаг 4. Загрузка свечей пачками — `_backfill_one_symbol` + `get_klines`

(`src/__main__.py:292–330`)

Для каждого символа вызывается `_backfill_one_symbol`. Она обращается к методу `rest.get_klines(symbol, interval, start_ms, end_ms, limit_per_call=1000)`.

**Почему пачками?** Биржа отдаёт не более 1000 свечей за один запрос. Если вам нужна история за год при интервале 1 час — это 8 760 свечей, то есть минимум 9 запросов. [[bybit-rest-source|`get_klines`]] умеет делать такую пагинацию автоматически (`src/marketdata/bybit/rest.py:165–299`).

**Как устроена пагинация?** Bybit V5 API — «конец-ориентированный»: возвращает `limit` последних свечей перед указанным `end`. Поэтому `get_klines` идёт назад во времени:

1. Первый запрос: свечи от `end_ms` назад (до 1000 штук).
2. Второй запрос: `cur_end` переставляется на время открытия самой старой полученной свечи.
3. И так далее, пока не покроет `start_ms`.
4. Все пачки собираются в хронологическом порядке (старые — первые).

Защитный предел итераций: `_KLINES_MAX_ITERS = 100_000` (`src/marketdata/bybit/rest.py:28`) — страховка от бесконечного цикла при аномальных ответах биржи.

После получения всех свечей каждая превращается в строку словаря (`src/__main__.py:312–322`):

```python
rows = [
    {
        "time":   b.close_time.isoformat(),  # время закрытия свечи в ISO 8601
        "open":   float(b.open),
        "high":   float(b.high),
        "low":    float(b.low),
        "close":  float(b.close),
        "volume": float(b.volume),
    }
    for b in bars
]
df = pd.DataFrame(rows)
```

Столбец `time` содержит время **закрытия** свечи (не открытия). Это важно: если свеча длится с 14:00 до 15:00, в `time` будет `15:00`.

### Шаг 5. Безопасное сохранение файла — атомарное переименование

(`src/__main__.py:324–328`)

Бот не пишет сразу в конечный файл. Сначала создаётся временный файл с суффиксом `.tmp`, затем он атомарно переименовывается:

```python
tmp_path = output_path.with_suffix(output_path.suffix + ".tmp")
df.to_parquet(tmp_path, index=False, compression="snappy", engine="pyarrow")
tmp_path.rename(output_path)
```

**Зачем так?** Если во время записи произойдёт сбой (выключили ноутбук, нет места на диске), конечный файл останется нетронутым. Без этого приёма можно получить «полузаписанный» Parquet, который бэктест не сможет прочитать и упадёт с непонятной ошибкой. Переименование файла — атомарная операция на уровне операционной системы (либо сделалось целиком, либо не сделалось вовсе). Это стандарт надёжной записи файлов, упомянутый в ADR 0003.

Директория создаётся при необходимости автоматически (`output_path.parent.mkdir(parents=True, exist_ok=True)`).

### Шаг 6. Имена выходных файлов

(`src/__main__.py:374–379`)

Если задан только один символ и указан `--output` — файл сохраняется по этому пути. В остальных случаях (несколько символов или `--output` не указан) имя формируется автоматически:

```
data/<SYMBOL>_<interval_label>.parquet
```

Примеры:
- `BTCUSDT`, интервал `60` → `data/BTCUSDT_1h.parquet`
- `ETHUSDT`, интервал `D` → `data/ETHUSDT_1d.parquet`
- `SOLUSDT`, интервал `15` → `data/SOLUSDT_15m.parquet`

При мультисимвольном режиме (`--symbols`) аргумент `--output` молча игнорируется — у каждого символа свой файл.

### Шаг 7. Коды возврата

(`src/__main__.py:338–342, 389–391`)

| Код | Значение |
|---|---|
| `0` | Все символы скачаны успешно (каждый вернул хотя бы одну свечу) |
| `1` | Хотя бы один символ вернул пустой ответ от биржи |

Если один из трёх символов вернул пустоту, `overall_rc` становится `1`, но остальные символы всё равно обрабатываются до конца. Частичный успех логируется предупреждением в консоль.

## Связь с BarSource (живой режим)

Файл `src/runtime/bar_source.py` ([[bar-source-live|источник свечей в live-режиме]]) — это отдельный компонент, который работает совсем иначе: он получает свежие свечи в реальном времени (каждый час/день) для работающего бота, а не скачивает историю оптом.

`BarSource.poll()` запрашивает только последние 2 свечи (`start_ms = end_ms - step_ms * 2`, `src/runtime/bar_source.py:107`) и возвращает самую свежую закрытую. Это противоположность backfill: не «дай мне всё за три года», а «дай мне последнюю закрытую свечу прямо сейчас».

Кроме того, `BarSource` защищает от look-ahead (ошибки «заглядывания в будущее»): свеча, чьё время закрытия ещё не наступило, отфильтровывается (`src/runtime/bar_source.py:84`). Backfill такой проблемы не имеет — он всегда запрашивает прошлое.

## Примеры / сценарии

### Сценарий 1: скачать год истории BTCUSDT по часовым свечам

```bash
python -m src backfill \
  --symbol BTCUSDT \
  --interval 60 \
  --from 2024-01-01 \
  --to 2025-01-01
```

Что произойдёт:
1. Бот переводит `2024-01-01` → `1704067200000` мс, `2025-01-01` → `1735689600000` мс.
2. Вызывается `get_klines` для BTCUSDT с интервалом `60`.
3. Биржа отдаёт по 1000 свечей за запрос. Год = ~8760 свечей = ~9 запросов.
4. Все свечи объединяются в таблицу pandas DataFrame.
5. Таблица записывается в `data/BTCUSDT_1h.parquet.tmp`, затем файл переименовывается в `data/BTCUSDT_1h.parquet`.
6. В консоль: `backfill: wrote 8760 bars to data/BTCUSDT_1h.parquet`
7. Программа завершается с кодом `0`.

### Сценарий 2: скачать три символа сразу

```bash
python -m src backfill \
  --symbols BTCUSDT,ETHUSDT,SOLUSDT \
  --interval 240 \
  --from 2023-01-01 \
  --to 2025-01-01
```

Что произойдёт:
1. `_resolve_symbols` получает `["BTCUSDT", "ETHUSDT", "SOLUSDT"]`.
2. Для каждого символа по очереди вызывается `_backfill_one_symbol`.
3. Файлы: `data/BTCUSDT_4h.parquet`, `data/ETHUSDT_4h.parquet`, `data/SOLUSDT_4h.parquet`.
4. Если SOLUSDT вернул пустой ответ — код возврата `1`, но BTCUSDT и ETHUSDT уже сохранены.

### Сценарий 3: пустой ответ биржи

Если биржа возвращает пустой список свечей (символ не торговался в этот период, неправильные даты и т.п.):

```
backfill: WARNING — empty kline response for SOLUSDT 2023-01-01 → 2025-01-01
```

Файл для этого символа не создаётся. Программа возвращает код `1`.

## Подводные камни / что важно понимать

**1. Даты интерпретируются как UTC, без учёта часового пояса.**
`2024-01-01` означает `2024-01-01 00:00:00 UTC`. Если вы ожидаете московское время — прибавьте 3 часа к дате начала вручную, иначе первые несколько часов истории будут «не те».

**2. Аргумент `--output` игнорируется при нескольких символах.**
При `--symbols BTCUSDT,ETHUSDT` опция `--output my_file.parquet` молча не работает — каждый символ получает свой автоматический путь. Это задокументировано в help (`src/__main__.py:849`).

**3. Команда работает через тот же REST-клиент, что и живая торговля.**
Это значит, что при `testnet=True` в [[configuration-and-settings|настройках]] данные придут с тестового окружения Bybit, а не с реальной биржи (подробнее про контуры testnet/live — [[run-modes-testnet-live-reconcile|режимы запуска]]). Проверьте файл `.env` перед запуском, если нужны реальные исторические данные.

**4. Существующий файл перезаписывается без предупреждения.**
Если `data/BTCUSDT_1h.parquet` уже есть — он будет заменён. Сохраните копию, если хотите сравнить два разных диапазона.

**5. Файл `.parquet.tmp` при сбое.**
Если процесс прервать в момент записи, в директории `data/` останется файл с суффиксом `.tmp`. Это безопасно — следующий запуск перезапишет его. Не стоит открывать `.tmp`-файл как рабочий Parquet.

**6. `BarSource` в живом режиме устроен иначе — не путайте.**
`BarSource` (файл `bar_source.py`) — компонент для живого бота: опрашивает биржу каждый период за последние 2 свечи. К команде `backfill` он отношения не имеет, они лишь разделяют один и тот же метод `get_klines` под капотом.

**7. Большие диапазоны — много запросов к бирже.**
Год часовых свечей = ~9 запросов REST. Пять лет = ~45 запросов. Bybit накладывает лимиты на количество запросов в минуту; при очень длинных диапазонах или многих символах подряд возможна временная задержка (встроенный механизм повтора [[bybit-rest-client-and-backoff|`_retry_with_backoff`]] в `rest.py` обрабатывает это автоматически).
