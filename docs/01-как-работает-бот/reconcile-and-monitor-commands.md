# Сверка с биржей и наблюдение: команды reconcile-only и monitor

**TL;DR:** `reconcile-only` — короткая проверка: бот подключается к бирже, сверяет свой внутренний учёт с реальностью и сразу выходит без торговли. `monitor` — «читай только»: показывает текущее состояние бота и последние 10 сделок, открывая базу данных в режиме, при котором случайная запись технически невозможна. **Важно:** поле `recent_halts` в выводе монитора всегда пустое из-за известного бага в SQL-запросе (см. «Подводные камни», п. 4).

## Простыми словами

Представьте, что бот — это бухгалтер, который ведёт свою тетрадь учёта. В этой тетради записано: «У меня есть 0,001 BTC открытой позиции». Но что если между прошлым запуском бота и текущим биржа что-то исполнила, или сеть прервалась, или вы перезапустили сервер? Тогда тетрадь бухгалтера может «соврать» — в ней одно, а на бирже другое.

**Команда `reconcile-only`** — это «пересчёт кассы» перед рабочим днём: бот идёт на биржу, запрашивает реальный баланс и открытые ордера, сравнивает с тем, что записано в базе данных, и говорит либо «всё сходится» (AGREE), либо «есть расхождение» (DIVERGENCE) — и завершает работу. Торговать не начинает ни при каком ответе. В основе лежит принцип [[reconcile-as-truth|«биржа всегда права»]].

Это полезно в двух случаях:
1. Вы хотите проверить состояние после перезапуска сервера — не запуская весь торговый цикл.
2. Вы настраиваете или тестируете подключение к Bybit и хотите убедиться, что API-ключи работают и данные приходят корректно.

**Команда `monitor`** — это стеклянная стена: вы смотрите внутрь работающего (или остановленного) бота и видите его снимок состояния, но ничего не трогаете. Команда открывает [[storage-and-database|базу данных SQLite]] в режиме «только чтение» (`mode=ro`) — на уровне самого SQLite запись туда физически невозможна. Это важно: если бот работает в другом процессе и активно пишет в базу, команда `monitor` не создаёт конфликтов.

Аналогия: `monitor` — как приборная панель в машине. Вы видите скорость, обороты и лампочки, но рулём управляете отдельно.

## Как это работает у нас

### Команда reconcile-only

Функция `_cmd_reconcile_only` находится в `src/__main__.py:394–456`. Она строит **минимальный** набор компонентов — только то, что нужно для сверки, без торговой стратегии, риск-менеджера и источника баров.

Шаги по коду:

**1. Загрузка настроек и параметров** (`src/__main__.py:404–408`)

```python
settings = Settings()
symbol: str = args.symbol
base_coin = symbol[:-4] if symbol.endswith(("USDT", "USDC")) else symbol
```

Берётся символ из аргумента `--symbol` (по умолчанию `BTCUSDT`). Из него автоматически выводится `base_coin` (например, из `BTCUSDT` → `BTC`), потому что именно `base_coin` используется для запроса баланса кошелька на Bybit.

**2. Инициализация базы данных** (`src/__main__.py:410–413`)

```python
mig_dir = Path(__file__).resolve().parent.parent / "migrations"
init_db(settings.db_path, mig_dir)
conn: Connection = connect(settings.db_path)
```

База данных инициализируется и мигрируется (если нужно). Та же самая база, в которую пишет живой бот. Открывается в обычном режиме — не только для чтения, потому что Reconciler может записать метку времени последней сверки.

**3. Подключение к бирже** (`src/__main__.py:415–430`)

```python
rest = BybitRESTClient(
    api_key=settings.bybit_api_key,
    api_secret=settings.bybit_api_secret,
    testnet=settings.testnet,
    demo=settings.demo,
)
filters = BybitFilters(symbol=symbol, ...)
adapter = BybitMarketAdapter(rest=rest, filters=filters)
```

Создаётся [[bybit-rest-client-and-backoff|REST-клиент к Bybit]] (`filters` — это [[bybit-filters|фильтры биржи]]: минимальные размеры и округление ордеров). Параметры `testnet` и `demo` берутся из настроек — это важно: адрес сверки всегда совпадает со средой, в которой торгует бот (нельзя случайно сверить testnet-бот с mainnet-биржей).

**4. Вычисление heal_max_age** (`src/__main__.py:434`)

```python
heal_age = _derive_heal_max_age_seconds(settings, "60")
```

`heal_max_age_seconds` — это максимальный возраст «зависшего» ордера, который Reconciler готов «вылечить» самостоятельно (автоматически пометить как исполненный). Для команды `reconcile-only` жёстко зафиксирован интервал `"60"` (1-часовая свеча), потому что полная торговая конфигурация здесь не запускается. Формула: `heal_max_age_seconds = heal_max_bars × interval_seconds` (см. `src/__main__.py:262–278`).

**5. Сборка Reconciler и Coordinator** (`src/__main__.py:436–448`)

```python
repo = ExecutionStateRepo(conn)
reconciler = Reconciler(query=adapter, base_coin=base_coin, symbol=symbol, heal_max_age_seconds=heal_age)
coordinator = Coordinator(adapter=adapter, repo=repo, reconciler=reconciler, symbol=symbol, base_coin=base_coin)
```

Создаётся только «скелет» — Coordinator и Reconciler. Никакой стратегии, никакого риск-менеджера, никакого WebSocket-потока.

**6. Запуск bootstrap и выход** (`src/__main__.py:450–456`)

```python
try:
    coordinator.bootstrap()
    print(f"reconcile-only: bootstrap complete для {symbol}")
    return 0
except Exception as e:
    print(f"ERROR: reconcile-only bootstrap failed: {e}", file=sys.stderr)
    return 1
```

Вызывается `coordinator.bootstrap()` — одна сверка — и бот завершается. Код возврата `0` = всё хорошо, `1` = ошибка.

#### Что делает bootstrap внутри

`Coordinator.bootstrap()` ([[coordinator-orchestration|Coordinator]], src/execution/coordinator.py:257–298) работает по трём сценариям:

- **Холодный старт (нет записи в БД):** запись о символе в базе отсутствует. Это первый запуск — сверять нечего, просто помечаем `_bootstrap_done = True` и выходим.

- **Тёплый старт (есть запись):** запись есть. Бот восстанавливает состояние после перезапуска. Вызывается `on_ws_reconnect()`, который запускает полноценную сверку с биржей (получает баланс кошелька и список открытых ордеров через REST), сравнивает с локальным состоянием и возвращает вердикт.

- **Расхождение (DIVERGENCE):** если реальность не совпадает с тетрадью, бот записывает в базу состояние `HALTED` с причиной `HALT_RECONCILE_DIVERGENCE` или `HALT_BOOTSTRAP_AMBIGUOUS`. Для оператора это сигнал: нужно разобраться вручную.

Сама логика сверки — в `Reconciler.reconcile()` (src/execution/reconciler.py:299–335). Она сначала делает REST-запросы к бирже (получает баланс и открытые ордера) **без удержания блокировки**, а потом без I/O и без записи применяет классификатор. Это сделано намеренно: блокирующий REST-запрос может длиться до ~15.5 секунд при rate-limit, и держать блокировку всё это время означало бы «заморозить» входящие WebSocket-сообщения.

Возможные вердикты сверки (src/execution/reconciler.py:13):

| Вердикт | Что означает |
|---|---|
| `AGREE` | Наш учёт совпадает с биржей — всё в порядке |
| `DIVERGENCE` | Расхождение — бот переходит в HALTED |
| `HEAL_ENTRY_FILLED` | Входной ордер исполнился пока бот был выключен — сверка «вылечивает» состояние |
| `EXITED` | Позиция была закрыта пока бот был выключен — состояние обновляется до FLAT |

#### Bootstrap при обычном запуске

Та же самая сверка (`coordinator.bootstrap()`) запускается **первым шагом** и при полноценном режиме `run` (см. [[startup-and-wiring]] — как собираются все компоненты). В `RuntimeManager.run()` это строка 120–121 (`src/runtime/manager.py`):

```python
self._coordinator.bootstrap()
# Sequencing invariant: bootstrap FIRST, then WS, then loop
self._ws_consumer.start()
```

То есть `reconcile-only` — это буквально «запустить только первый шаг из `run`, остановиться»: [[main-loop-tick|тиковый рабочий цикл]] при этом не запускается вовсе.

### Команда monitor

Функция `_cmd_monitor` находится в `src/__main__.py:751–816`. Это инструмент только для чтения — он не влияет на работу бота, даже если тот запущен в другом процессе в этот момент.

**Зачем нужен `monitor`, если можно просто смотреть в базу?** Монитор структурирует вывод (JSON) и выбирает только нужные поля. Обратите внимание: поле `recent_halts` в выводе сейчас всегда пустое из-за бага в коде (подробности — в разделе «Подводные камни», п. 4).

Шаги по коду:

**1. Открытие базы в режиме только для чтения** (`src/__main__.py:765–766`)

```python
db_uri = f"file:{settings.db_path}?mode=ro"
conn = sqlite3.connect(db_uri, uri=True)
```

`mode=ro` — это параметр SQLite URI. На уровне движка базы данных любая попытка записи немедленно вернёт ошибку `SQLITE_READONLY`. Это **не** программная блокировка в коде Python — это встроенная защита SQLite. Даже если в коде была бы случайная запись, она не прошла бы.

Комментарий в коде (`src/__main__.py:755`): «STRICTLY read-only (no SQL writes — SQLite WAL contention с live bot)». WAL (Write-Ahead Log) — режим SQLite для параллельной записи; `mode=ro` гарантирует, что monitor не вступает в конфликт записи с живым ботом.

**2. Чтение текущего состояния FSM** (`src/__main__.py:773–776`)

```python
state_row = conn.execute(
    "SELECT symbol, state, halt_reason, last_reconcile_at, updated_at "
    "FROM execution_state WHERE symbol = ?",
    (symbol,),
).fetchone()
```

Поля которые читаются:
- `state` — текущее состояние конечного автомата (FSM, см. ниже)
- `halt_reason` — причина аварийной остановки (если бот остановлен)
- `last_reconcile_at` — когда последний раз проводилась сверка с биржей
- `updated_at` — когда последний раз менялась запись

Если запись для символа не найдена, вывод будет `"MISSING"` — это значит, бот ещё ни разу не запускался с этим символом (нет холодного старта).

**3. Чтение последних 10 сделок** (`src/__main__.py:779–783`)

```python
trade_rows = conn.execute(
    "SELECT trade_id, exit_ts, pnl_pct, reason_code "
    "FROM trade_history WHERE symbol = ? ORDER BY exit_ts DESC LIMIT 10",
    (symbol,),
).fetchall()
```

Таблица `trade_history` — это хранилище закрытых сделок (подробнее — [[trade-fill-history]]). Поля:
- `trade_id` — номер сделки (автоинкремент)
- `exit_ts` — время закрытия сделки (ISO-8601, UTC)
- `pnl_pct` — доходность сделки в долях (например, `0.012` = +1.2%; `-0.005` = −0.5%)
- `reason_code` — код причины выхода (например, `EXIT_SL_HIT` — сработал стоп-лосс); полный каталог кодов — в [[reason-codes-assessment-output]]

**4. Чтение последних 5 аварийных остановок** (`src/__main__.py:785–792`)

```python
halt_rows: list[tuple[_Any, ...]] = []
with contextlib.suppress(sqlite3.OperationalError):
    halt_rows = conn.execute(
        "SELECT halt_ts, halt_reason, context FROM halt_log ORDER BY halt_ts DESC LIMIT 5"
    ).fetchall()
```

> **Известный баг:** этот SQL-запрос читает несуществующие колонки. Реальная схема таблицы `halt_log` (миграция `migrations/0005_halt_persistence.sql:11–16`, запись в `src/execution/state_repo.py:155` — см. [[execution-state-persistence-and-halt-audit]]) называет колонки `ts`, `reason`, `context_json`. Запрос же запрашивает `halt_ts`, `halt_reason`, `context` — SQLite отвечает «нет такой колонки: halt_ts» (`OperationalError`), но `contextlib.suppress` молча поглощает эту ошибку. В результате **`recent_halts` всегда возвращается пустым массивом `[]` на любой базе данных** — вне зависимости от того, были ли реальные аварийные остановки. Правильный запрос должен быть: `SELECT ts AS halt_ts, reason AS halt_reason, context_json AS context FROM halt_log ORDER BY ts DESC LIMIT 5`. До исправления этого бага в коде не полагайтесь на `recent_halts` для диагностики — историю остановок читайте напрямую из `halt_reason` поля текущего состояния (строка `state.halt_reason` в выводе).

**5. Формирование и вывод JSON** (`src/__main__.py:796–813`)

```python
snapshot = {
    "symbol": symbol,
    "state": {
        "current_state": state_row[1] if state_row else "MISSING",
        "halt_reason": state_row[2] if state_row else None,
        "last_reconcile_at": state_row[3] if state_row else None,
        "updated_at": state_row[4] if state_row else None,
    },
    "recent_trades": [...],
    "recent_halts": [...],
}
print(json.dumps(snapshot, default=str, indent=2))
```

Вывод всегда структурированный JSON, что удобно для скриптов и логов.

## Понятие «конечный автомат» (FSM) и его состояния

**Конечный автомат** (FSM, finite state machine — см. [[execution-state-machine]]) — это способ описать, в каком «режиме» находится бот. Как у светофора есть три состояния (красный / жёлтый / зелёный), у бота есть набор состояний. Из каждого состояния можно перейти только в разрешённые следующие.

Все состояния определены в `src/execution/state_machine.py:12–28`:

| Состояние | Простыми словами |
|---|---|
| `FLAT` | Нет открытой позиции — бот ждёт сигнала |
| `ENTRY_PENDING` | Ордер на вход отправлен на биржу, ждём исполнения |
| `LONG_OPEN` | Покупка исполнена, позиция держится, защитные ордера ещё не выставлены |
| `OCO_ARMING` | Выставляется стоп-лосс и тейк-профит (промежуточный шаг) |
| `OCO_ARMED` | Позиция защищена: оба ордера (тейк-профит + стоп-лосс) выставлены на бирже |
| `EXIT_PENDING` | Ордер на выход отправлен, ждём исполнения |
| `EXIT_SIBLING_CANCELLING` | Один из защитных ордеров сработал, отменяем второй (нормальный путь) |
| `EXIT_SIBLING_CANCEL_FAILED` | Не удалось отменить второй ордер — нужно вмешательство |
| `EXIT_SL_RESIDUAL` | Частичное исполнение — продаём остаток по рынку |
| `RECONCILING` | Восстановление после разрыва соединения: идёт сверка с биржей |
| `HALTED` | Аварийная остановка — бот не торгует. Причина записана в `halt_reason` |
| `COOLDOWN` | Период остывания после отмены HALTED |
| `ERROR` | Критическая ошибка — требуется ручной сброс через `MANUAL_RESET` |
| `KILLED` | Аппаратный рубильник сработал — бот полностью выключен |
| `PARTIAL_FILL` | Устаревшее состояние (Sprint 5, не достижимо в v2) — хранится для совместимости |
| `INIT` | Начальное состояние до первой загрузки из базы данных |

Когда `monitor` выводит `"current_state": "HALTED"`, значит бот остановился по одной из причин. Причину можно прочитать в поле `halt_reason`.

## Как читать вывод команды monitor

### Пример вывода

```json
{
  "symbol": "BTCUSDT",
  "state": {
    "current_state": "FLAT",
    "halt_reason": null,
    "last_reconcile_at": "2026-06-25T14:32:11+00:00",
    "updated_at": "2026-06-25T14:33:05+00:00"
  },
  "recent_trades": [
    {
      "trade_id": 42,
      "exit_ts": "2026-06-25T10:15:00+00:00",
      "pnl_pct": "0.0123",
      "reason_code": "EXIT_TP_HIT"
    },
    {
      "trade_id": 41,
      "exit_ts": "2026-06-24T18:42:00+00:00",
      "pnl_pct": "-0.0047",
      "reason_code": "EXIT_SL_HIT"
    }
  ],
  "recent_halts": []
}
```

**Как читать:**

- `current_state: "FLAT"` — бот работает и ждёт сигнала. Всё нормально.
- `halt_reason: null` — нет причины остановки. Бот не остановлен.
- `last_reconcile_at` — последняя сверка с биржей. Если это время давно и бот работает — возможно, что-то не так.
- `pnl_pct: "0.0123"` — сделка 42 принесла +1.23%. Формат: дробное число, положительное = прибыль, отрицательное = убыток. Значение `0.0123` означает 1.23% от вложенного капитала (`src/risk/trade_history.py:31`: `pnl_pct: Decimal  # signed (e.g. 0.012 = +1.2%)`).
- `reason_code: "EXIT_TP_HIT"` — сделка 42 закрылась, потому что сработал тейк-профит (цена достигла цели).
- `reason_code: "EXIT_SL_HIT"` — сделка 41 закрылась, потому что сработал стоп-лосс (цена пошла не туда).

### Расшифровка основных `reason_code` при выходе

| Код | Что произошло |
|---|---|
| `EXIT_TP_HIT` | Цена достигла цели — тейк-профит исполнен |
| `EXIT_SL_HIT` | Цена пошла вниз до стоп-лосса — убыток зафиксирован |
| `EXIT_SIGNAL_FLIP` | Стратегия дала обратный сигнал — позиция закрыта по логике алгоритма |
| `EXIT_FLAT_MEANREV_REVERT` | Стратегия Mean Reversion: RSI вернулся в норму, позиция закрыта |
| `EXIT_FLAT_SUPERTREND_FLIP` | Стратегия Supertrend: тренд развернулся, позиция закрыта |

### Расшифровка основных `halt_reason`

Полная таблица всех причин остановки и как из них выйти — в [[safety-stops-and-halts]]. Просадочные пороги (`HALT_S36_DD_*`, `HALT_S36_CONSECUTIVE_LOSSES`) задаёт [[circuit-breakers-drawdown-flash|автоматический предохранитель]], а `KILL_SWITCH_REQUESTED` — [[kill-switch-emergency-stop|аварийный рубильник]].

| Код | Что произошло |
|---|---|
| `HALT_RECONCILE_DIVERGENCE` | Сверка показала расхождение — наш учёт не совпадает с биржей |
| `HALT_BOOTSTRAP_AMBIGUOUS` | Невозможно однозначно восстановить состояние после перезапуска |
| `HALT_S36_DD_INTRADAY` | Внутридневная просадка превысила порог |
| `HALT_S36_DD_MULTIDAY` | Многодневная просадка превысила порог |
| `HALT_S36_CONSECUTIVE_LOSSES` | Слишком много убыточных сделок подряд |
| `HALT_S36_NO_TRADE_TIMEOUT` | Долго нет сделок — стратегия, возможно, перестала работать |
| `HALT_RUNTIME_CRASH` | Неожиданная ошибка в работе бота |
| `HALT_BAR_POLL_STALL` | Биржа не отдаёт данные о свечах N раз подряд |
| `HALT_DATA_QUALITY` | Цена свечи выглядит аномальной (flash-crash детектор) |
| `KILL_SWITCH_REQUESTED` | Оператор нажал «аварийный рубильник» командой `kill` |

## Примеры / сценарии

### Сценарий 1: Проверка после перезапуска сервера

Сервер перезапустился ночью. Вы хотите убедиться, что бот видит правильное состояние, прежде чем снова запускать торговлю.

```bash
python -m src reconcile-only --symbol BTCUSDT
```

**Возможные исходы:**

1. `reconcile-only: bootstrap complete для BTCUSDT` (код 0) — всё сошлось, можно запускать `run`.
2. `ERROR: reconcile-only bootstrap failed: ...` (код 1) — есть проблема: биржа недоступна, API-ключ неверный, или реальное состояние не совпадает с базой. Не запускайте `run` до разбора.

### Сценарий 2: Разовая проверка состояния без остановки бота

Бот уже запущен в фоне. Вы хотите посмотреть, что происходит.

```bash
python -m src monitor --symbol BTCUSDT
```

Бот в другом процессе продолжает работать — команда `monitor` открывает базу данных только для чтения и не мешает боту записывать данные.

### Сценарий 3: Чтение причины остановки

Бот остановился ночью. Утром вы запускаете:

```bash
python -m src monitor --symbol BTCUSDT
```

Получаете:

```json
{
  "state": {
    "current_state": "HALTED",
    "halt_reason": "HALT_S36_CONSECUTIVE_LOSSES",
    "last_reconcile_at": "2026-06-25T03:17:39+00:00",
    "updated_at": "2026-06-25T03:17:42+00:00"
  },
  "recent_trades": [...],
  "recent_halts": []
}
```

**Важно:** `recent_halts` здесь пустой — это не значит, что остановок не было. Это известный баг в коде (`src/__main__.py:791` — SQL-запрос читает несуществующие колонки `halt_ts/halt_reason/context`, хотя реальная схема использует `ts/reason/context_json`; ошибка молча проглатывается). Фактическую причину остановки нужно смотреть в поле `state.halt_reason`: `"HALT_S36_CONSECUTIVE_LOSSES"` означает, что было слишком много убыточных сделок подряд — штатная защита риск-менеджера. Бот сам себя остановил, чтобы не терять больше.

## Подводные камни / что важно понимать

**1. `reconcile-only` не торгует — но может изменить состояние в базе**

Если bootstrap обнаружил расхождение (DIVERGENCE), он запишет в базу `state = "HALTED"` с причиной. Это штатное поведение, но важно понимать: команда «без торговли» может изменить базу данных.

**2. `reconcile-only` всегда измеряет устарелость в 1-часовых единицах**

`heal_max_age_seconds` — это максимальный возраст «зависшего» ордера, после которого Reconciler готов автоматически пометить его как исполненный. Для команды `reconcile-only` жёстко зафиксирован интервал `"60"` (1 час) независимо от того, на каком интервале торгует живой бот (`src/__main__.py:434`). Формула: `heal_max_age_seconds = heal_max_bars × 3600` (при дефолтном `heal_max_bars = 1` → 3600 секунд = 1 час), см. `src/__main__.py:262–278`.

Если живой бот торгует на 15-минутных свечах, то один его «бар» длится 900 секунд. `reconcile-only` при этом всё равно использует порог 3600 секунд (1 час) — то есть де-факто смотрит на 4 бара назад, а не на 1. Это значит: `reconcile-only` может быть чуть терпимее к «зависшим» ордерам, чем живой бот с коротким интервалом.

**Исключение:** если `heal_max_bars` не задан в настройках (`None`), то используется поле `settings.heal_max_age_seconds` напрямую без умножения — это устаревший режим обратной совместимости (`src/__main__.py:262–263`).

**3. `monitor` покажет `MISSING`, если бот ни разу не запускался**

Если символ не встречался в базе (не было ни одного холодного старта `run`), поле `current_state` будет `"MISSING"`. Это не ошибка команды `monitor` — просто данных ещё нет.

**4. `recent_halts` всегда пустой — известный баг, не признак отсутствия остановок**

SQL-запрос мониторинга (`src/__main__.py:791`) обращается к несуществующим колонкам таблицы `halt_log`: он запрашивает `halt_ts`, `halt_reason`, `context`, тогда как реальная схема (миграция `migrations/0005_halt_persistence.sql:13–16`, запись через `src/execution/state_repo.py:155`) использует колонки `ts`, `reason`, `context_json`. SQLite отвечает `OperationalError: no such column: halt_ts`, которая тут же поглощается `contextlib.suppress` (`src/__main__.py:789`), и `recent_halts` возвращается как `[]`.

**Следствие для оператора:** если бот остановился, но `recent_halts` пуст — это не значит, что остановок не было. Причину остановки всегда смотрите в поле `state.halt_reason`. Записи в таблице `halt_log` существуют (если была реальная остановка), но прочитать их через команду `monitor` невозможно до исправления SQL-запроса в коде.

**5. `monitor` не показывает открытые ордера в реальном времени**

Команда читает только базу данных SQLite — то, что бот **записал** туда. Актуальное состояние ордеров на бирже можно увидеть только через Bybit API. Если бот упал в середине операции, `monitor` покажет последнее записанное состояние (например, `OCO_ARMING`), а на бирже может быть другая картина.

**6. `PARTIAL_FILL` в выводе monitor — историческое состояние**

Если вы видите `current_state: "PARTIAL_FILL"`, это наследие Sprint 5. В v2 это состояние недостижимо: событие `PARTIAL_FILL` теперь маршрутизируется в `EXIT_SL_RESIDUAL`. Состояние в базе данных могло быть записано старой версией бота — это не ошибка, а реликт для обратной совместимости (`src/execution/state_machine.py:19`).
