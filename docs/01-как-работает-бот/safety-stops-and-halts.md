# Тормоза и предохранители бота: стоп-файл, halt-пороги, аварийный выход

**TL;DR:** У бота есть несколько уровней защиты, которые останавливают торговлю при опасных условиях. Самый простой — ручной «рубильник» оператора (один файл-сигнал). Автоматические предохранители срабатывают при слишком большом убытке, серии проигрышей или долгом отсутствии сделок. В любой сомнительной ситуации бот предпочитает остановиться, а не рисковать деньгами — это называется принцип «fail-closed» (безопасный отказ).

---

## Простыми словами

Представьте, что бот — это водитель, который едет по трассе на автомобиле с несколькими системами безопасности:

1. **Ручной рубильник** — вы в любой момент можете нажать «стоп», написав одну команду в терминале. Бот увидит сигнал и аккуратно остановится на следующей «остановке» ([[main-loop-tick|тике]]). Подробно про красную кнопку — в [[kill-switch-emergency-stop|аварийном стопе оператора]].
2. **Автоматические предохранители** — если бот за день потерял слишком много денег, если проиграл несколько сделок подряд или если рынок «умер» и сделок нет месяцами, система сама говорит «стоп» и ждёт оператора. Это [[halt-gate-precommitted-criteria|HaltGate]] — заранее оговорённые «красные линии» демо-режима.
3. **Белый список символов** *(только в демо-режиме)* — бот торгует только теми монетами, которые вы ему явно разрешили (по умолчанию только BTCUSDT). Попытка торговать чем-то другим — мгновенная остановка.
4. **Страховка от вмешательства** — время первого запуска защищено криптографической подписью (HMAC). Если кто-то подменит эту запись, бот остановится, а не будет работать с фальсифицированными данными.
5. **Защита от сбоя программы** — если в коде произошла необработанная ошибка, бот не «зависает» и не оставляет незакрытые ордера. Он фиксирует аварию и корректно завершается.

**Принцип «fail-closed»** (безопасный отказ): в ситуации неопределённости бот всегда выбирает остановку, а не продолжение торговли. Лучше пропустить прибыльную сделку, чем получить неконтролируемый убыток.

## Как это работает у нас

### Структура защиты: порядок проверок на каждом тике

Каждые 5 секунд (по умолчанию) бот выполняет один [[main-loop-tick|«тик»]] — проверку рыночных данных и возможность открытия сделки. Прежде чем дойти до стратегии, тик проходит через цепочку защитных проверок в строгом порядке:

```
_tick():
  1. _maybe_kill_switch()       ← ручной рубильник
  2. _check_alive_inline()      ← жив ли WebSocket
  3. _check_halt_gate()         ← автоматические предохранители (только в demo-режиме)
  4. _poll_bar_and_strategy()   ← торговая логика (стратегия, риск, ордера)
```

Если любая из первых трёх проверок возвращает «стоп» — четвёртая (торговля) не выполняется вообще. (`src/runtime/manager.py:162–178`)

### 1. Ручной рубильник (kill switch)

**Что это:** физический файл-сигнал на диске (полное описание — в [[kill-switch-emergency-stop|аварийном стопе]]). Когда оператор хочет остановить бота, он запускает команду:

```bash
python -m src kill
```

Эта команда создаёт файл `.kill_switch` (путь настраивается через `runtime_kill_switch_path`, по умолчанию `.kill_switch`). (`src/platform/config.py:222–225`)

**Почему файл, а не команда напрямую?** Файл работает даже если бот запущен в другом терминале, на другом процессе или через менеджер процессов. Это самый надёжный способ передать сигнал остановки.

**Атомарная запись** — файл создаётся через временный промежуточный файл `.kill_switch.tmp`, после чего мгновенно переименовывается в целевой файл. Это исключает ситуацию, когда бот прочитает полупустой файл при сбое записи.

```python
# src/__main__.py:472-481
tmp = sentinel.with_suffix(sentinel.suffix + ".tmp")
flags = os.O_WRONLY | os.O_CREAT | os.O_TRUNC
fd = os.open(tmp, flags, 0o600)
with os.fdopen(fd, "wb") as f:
    f.write(b"")
os.replace(tmp, sentinel)  # атомарная замена
```

**Как бот видит файл:** на каждом тике метод `_maybe_kill_switch()` проверяет наличие этого файла. Если файл есть — бот устанавливает флаг `KILL_SWITCH_REQUESTED`, останавливает цикл и корректно завершается. (`src/runtime/manager.py:286–296`)

**Очистка при старте:** при запуске бот сам удаляет стоп-файл от предыдущей сессии, чтобы не остановиться мгновенно из-за «забытого» файла.

```python
# src/runtime/manager.py:117-118
if self._kill_switch_path.exists():
    self._kill_switch_path.unlink()
```

### 2. Автоматические предохранители (HaltGate)

**Что это:** четыре независимых условия, при срабатывании любого из которых бот останавливается. Работают только когда включён [[run-modes-testnet-live-reconcile|демо-режим]] (`s35_demo_active = True`). В продакшне порог «производственного» уровня проверяется отдельными механизмами [[risk-overview-decision-pipeline|риск-менеджера]] и [[circuit-breakers-drawdown-flash|автоматическими предохранителями по просадке и обвалу]].

**[[halt-gate-precommitted-criteria|HaltGate]]** — это специальный класс-оценщик (`src/risk/halt_gate.py`), которому на вход подаются четыре числа, и он проверяет их против заранее зафиксированных порогов.

#### Четыре условия остановки (в порядке приоритета):

| Приоритет | Условие | Порог по умолчанию | Код остановки |
|-----------|---------|-------------------|---------------|
| 1 (высший) | Внутридневная просадка | ≥ 20% | `HALT_S36_DD_INTRADAY` |
| 2 | Многодневная просадка | ≥ 15% | `HALT_S36_DD_MULTIDAY` |
| 3 | Серия убыточных сделок подряд | ≥ 5 | `HALT_S36_CONSECUTIVE_LOSSES` |
| 4 | Слишком долго нет сделок | ≥ 6 месяцев | `HALT_S36_NO_TRADE_TIMEOUT` |

Приоритет важен: если одновременно превышены, например, и внутридневная просадка, и серия убытков — срабатывает только первое условие (наиболее срочное). Это предотвращает «каскадные» записи в лог. (`src/risk/halt_gate.py:64–73`)

#### Откуда берутся пороги

Пороги читаются из настроек (переменных окружения / файла `.env`):

```python
# src/platform/config.py:132-155
s35_halt_dd_intraday: Decimal = Field(default=Decimal("0.20"), ...)   # 20%
s35_halt_dd_multiday: Decimal = Field(default=Decimal("0.15"), ...)   # 15%
s35_halt_consecutive_losses: int = Field(default=5, ...)
s35_halt_no_trade_months: int = Field(default=6, ...)
```

Оператор может их изменить через `.env`. Допустимые диапазоны: просадка от 0 до 50%, потери от 1 до 20 подряд, «голодание» от 1 до 24 месяцев.

#### Как рассчитываются входные данные для HaltGate

Каждый тик менеджер вычисляет четыре числа и передаёт их в `HaltGate.evaluate()`:

**Внутридневная просадка** — берётся из `equity_tracker.intraday_dd_pct()` (см. [[equity-tracking|учёт капитала и просадки]]). Это просадка от максимального значения капитала за последние 24 часа (скользящее окно, не сбрасывается в полночь). (`src/risk/equity_tracker.py:70–90`: `cutoff = now - timedelta(hours=24)`)

**Многодневная просадка** — вычисляется от максимума (HWM — high-water mark) начиная с момента первого запуска бота:

```python
# src/runtime/manager.py:240-245
hwm = self._equity_tracker.hwm_since(since_ts=activation_ts)
current = self._equity_tracker.current_total() or Decimal("0")
if hwm is not None and hwm > Decimal("0") and current < hwm:
    multiday_dd = (hwm - current) / hwm
```

Простыми словами: если максимум был 10 000 USDT, а сейчас 8 500 USDT — многодневная просадка составляет 15%.

**Серия убытков** — `trade_repo.consecutive_losses(symbol=symbol)` — количество убыточных сделок подряд, начиная с последней (сами сделки хранятся в [[trade-fill-history|истории сделок и исполнений]]).

**«Голодание» по сделкам** — вычисляется в месяцах (приближённо: `days // 30`) с момента последней закрытой сделки. Если сделок ещё не было — считается от момента первого запуска:

```python
# src/runtime/manager.py:248-254
last_ts = self._trade_repo.last_trade_ts(symbol=symbol)
if last_ts is not None:
    months_since = (self._clock() - last_ts).days // 30
else:
    months_since = (self._clock() - activation_ts).days // 30
```

Обратите внимание: `days // 30` — это целочисленное деление, то есть округление вниз. 5 месяцев и 29 дней = 5, а не 6. Порог 6 месяцев сработает только на 180-й день и позже.

### 3. Белый список разрешённых символов (fail-closed) — только в демо-режиме

> **Важно:** эта проверка выполняется только когда включён демо-режим (`s35_demo_active = True`). Весь блок `_check_halt_gate()` пропускается при `s35_demo_active = False` — никакой проверки символов не происходит вообще. (`src/runtime/manager.py:175, 193–194`)

Перед тем как запустить расчёт предохранителей, бот проверяет: является ли торгуемый символ (например, BTCUSDT) разрешённым?

```python
# src/runtime/manager.py:199-208
symbol = getattr(self._coordinator, "symbol", None)
if symbol is None or symbol not in self._settings.s35_demo_approved_symbols:
    self._coordinator.request_halt(ReasonCode.HALT_UNKNOWN_SYMBOL)
    self._stopping = True
    return True
```

По умолчанию разрешён только `BTCUSDT`. (`src/platform/config.py:156–165`)

**Почему проверка происходит первой?** Это классический «fail-closed» — лучше остановиться раньше, чем вычислять метрики для символа, которым бот не должен торговать. Это также предотвращает «побочный эффект» записи метки времени активации для неверного символа. Код остановки `HALT_UNKNOWN_SYMBOL` — один из записей [[reason-codes-assessment-output|словаря причин]]; сама остановка передаётся через `coordinator.request_halt()` (см. [[coordinator-orchestration|координатор исполнения]]).

**Нормализация регистра:** символы в белом списке автоматически приводятся к верхнему регистру при старте, чтобы опечатка в `.env` (`btcusdt` вместо `BTCUSDT`) не привела к бесконечному циклу остановки. (`src/platform/config.py:294–306`)

### 4. Защита метки времени активации (HMAC)

**Зачем это нужно:** бот запоминает время своего первого запуска (`activation_ts`, фиксируется при [[startup-and-wiring|сборке и запуске бота]]) — эта метка нужна для расчёта многодневной просадки. Если кто-то вручную изменит эту запись в базе данных (например, чтобы «сбросить» окно просадки), бот это обнаружит и остановится.

**Как работает защита:** запись `activation_ts` хранится в [[storage-and-database|базе данных]] вместе с HMAC-SHA256 подписью — цифровым отпечатком, вычисленным с помощью секретного ключа (`risk_override_hmac_key` — тот же ключ, которым оператор подписывает [[manual-override-resume|ручное снятие предохранителя]]). При чтении подпись проверяется. Если не совпадает — выброс ошибки, и бот останавливается:

```python
# src/runtime/manager.py:213-226
try:
    activation_record = self._state_repo.get_signed(
        "runtime:halt_gate:activation_ts",
        hmac_key=self._settings.risk_override_hmac_key,
    )
except ValueError as exc:
    # подпись не совпала → остановка fail-closed
    self._coordinator.request_halt(ReasonCode.HALT_UNKNOWN_SYMBOL)
    self._stopping = True
    return True
```

**HMAC** (Hash-based Message Authentication Code) — это алгоритм, который вычисляет «отпечаток пальца» данных с использованием секретного ключа. Без знания ключа подделать подпись невозможно. (`src/risk/state_repo.py:90–95`)

После первого вычисления метка времени активации кэшируется в памяти (`self._activation_ts`), чтобы не обращаться к базе данных на каждом тике. (`src/runtime/manager.py:97–99, 212`)

### 5. Верхнеуровневый предохранитель от сбоя программы

Метод `run()` оборачивает весь основной цикл в блок обработки исключений:

```python
# src/runtime/manager.py:136-149
try:
    self._main_loop()
except KeyboardInterrupt:
    self._shutdown(reason="KEYBOARD_INTERRUPT")
except Exception as e:
    self._coordinator.request_halt(ReasonCode.HALT_RUNTIME_CRASH)
    self._shutdown(reason="HALT_RUNTIME_CRASH")
    raise  # ошибка пробрасывается наверх для диагностики
else:
    self._shutdown(reason="NORMAL_EXIT")
```

Если в коде произошло что-то непредвиденное (баг, неожиданный формат данных, сетевая ошибка), бот:
1. Фиксирует событие `HALT_RUNTIME_CRASH` в базе данных.
2. Выполняет корректное завершение (`_shutdown`).
3. Пробрасывает исходную ошибку — чтобы она попала в логи и к оператору.

Это гарантирует, что даже при программном сбое бот не оставит открытые ордера без наблюдения.

### 6. Корректное завершение (_shutdown)

Когда бот останавливается по любой причине, метод `_shutdown()` выполняет несколько действий:

1. **Идемпотентность** — если `_shutdown()` вызвали дважды (например, из обработчика ошибки и потом из Ctrl+C), второй вызов ничего не делает. (`src/runtime/manager.py:417–419`)
2. **Остановка WebSocket** — прекращается получение данных о заполнении ордеров (см. [[bybit-ws-consumer|WebSocket-потребитель]]).
3. **Снимок незакрытых ордеров** — бот проверяет, есть ли ордера в состоянии ожидания (ENTRY_PENDING, EXIT_PENDING, OCO_ARMING — состояния [[execution-state-machine|конечного автомата исполнения]]) и записывает их количество в лог для операторного аудита.
4. **Структурированная запись в лог** — событие `runtime.shutdown` с указанием причины остановки и количества незакрытых ордеров.

```python
# src/runtime/manager.py:410-441 (упрощённо)
def _shutdown(self, *, reason: str) -> None:
    if getattr(self, "_shutdown_done", False):
        return  # идемпотентность
    self._shutdown_done = True
    self._stopping = True
    self._ws_consumer.stop()   # best-effort — ошибки логируются, не пробрасываются
    # ... снимок ордеров ...
    logger.info("runtime.shutdown", reason=reason, in_flight_orders=in_flight)
```

### 7. Дополнительные причины остановки

Помимо четырёх условий HaltGate и рубильника, бот может остановиться по другим причинам:

| Причина | Условие | Код |
|---------|---------|-----|
| Нет данных о ценах | N подряд неудачных запросов к биржевому API (по умолчанию 24 × 5 с = 120 с) | `HALT_BAR_POLL_STALL` |
| Плохое качество данных | Цена закрытия свечи отличается от предыдущей более чем на 0.5% | `HALT_DATA_QUALITY` |
| WebSocket молчит | Нет сообщений более 30 секунд | проверка `check_alive` |

Порог качества данных: `runtime_quality_threshold_pct = 0.005` (0.5%) — этим порогом управляет [[data-quality-detector|детектор качества данных]]. (`src/platform/config.py:234–241`)
Порог молчания WebSocket: `runtime_ws_check_alive_max_silence = 30.0` секунд — молчание отслеживается по [[bybit-ws-consumer|WebSocket-потребителю]]. (`src/platform/config.py:226–229`)
Порог стала данных: `runtime_bar_poll_stall_threshold = 24` неудачных запросов — счётчик ведёт [[bar-source-live|источник свечей в live-режиме]]. (`src/platform/config.py:214–221`)

Все эти пороги задаются в [[configuration-and-settings|настройках бота]] (`.env`). Отдельно бот следит за рассинхронизацией часов с биржей — см. [[clock-drift-monitor|монитор дрейфа часов]].

## Формулы и расчёты

### Многодневная просадка

```text
multiday_dd = (HWM - current_equity) / HWM
```

Где:
- **HWM** (High-Water Mark, «высокая отметка») — максимальный капитал с момента первого запуска бота.
- **current_equity** — текущий капитал.
- **multiday_dd** — доля потерянного от максимума (например, 0.15 = 15%).

Срабатывает при `multiday_dd >= s35_halt_dd_multiday` (по умолчанию 0.15).

(`src/runtime/manager.py:241–245`, `src/risk/halt_gate.py:66–68`)

### Приближение «месяц = 30 дней»

```text
months_since = (now - last_trade_ts).days // 30
```

`// 30` — целочисленное деление с округлением вниз. Эта формула является приближением: настоящие календарные месяцы имеют 28–31 день, но для задачи «прошло ли 6 месяцев без сделок» это достаточно точно. (`src/runtime/manager.py:250`)

## Примеры / сценарии

### Сценарий A: оператор нажимает «стоп»

1. Оператор видит, что рынок ведёт себя необычно, и решает остановить бота.
2. Вводит в терминале: `python -m src kill`
3. Создаётся файл `.kill_switch`.
4. На следующем тике (в течение 5 секунд) бот вызывает `_maybe_kill_switch()`, видит файл.
5. Фиксирует `KILL_SWITCH_REQUESTED` в базе данных (через `coordinator.request_halt()`).
6. Устанавливает `_stopping = True` → основной цикл (`_main_loop`) завершается штатно, без исключения → `run()` вызывает `_shutdown(reason="NORMAL_EXIT")` → останавливает WebSocket → записывает лог `runtime.shutdown reason=NORMAL_EXIT`. (`src/runtime/manager.py:150–151, 286–295`)
7. Бот завершён. Незакрытые позиции (если есть) отражены в логе как `in_flight_orders`.

   > **Для оператора:** ищите в логах событие `runtime.kill_switch_detected` (сигнал обнаружен) и `runtime.shutdown reason=NORMAL_EXIT` (завершение). Строки `reason=KILL_SWITCH_REQUESTED` в `runtime.shutdown` **не будет** — это намеренно: kill-switch приводит к штатному выходу из цикла, а не к аварийной остановке.

### Сценарий B: слишком большой убыток за день

1. Бот торгует и за день его капитал падает с 10 000 USDT до 7 900 USDT.
2. На очередном тике `_check_halt_gate()` вычисляет: `intraday_dd = (10000 - 7900) / 10000 = 0.21` (21%).
3. Порог 20% (`s35_halt_dd_intraday = 0.20`) превышен.
4. `HaltGate.evaluate()` возвращает `HaltTrigger.DD_INTRADAY`.
5. Менеджер логирует событие `runtime.halt_gate_fired` с деталями (символ, значения просадки).
6. Вызывается `coordinator.request_halt(HALT_S36_DD_INTRADAY)`.
7. Флаг `self._stopping = True` → основной цикл завершается.
8. `_shutdown()` записывает финальное событие в лог.

### Сценарий C: неизвестный символ при запуске

1. Оператор ошибочно настроил бота торговать `ETHUSDT`.
2. Бот запускается, `_check_halt_gate()` читает `symbol = "ETHUSDT"`.
3. Проверяет белый список: `["BTCUSDT"]` — `ETHUSDT` там нет.
4. Немедленно фиксирует `HALT_UNKNOWN_SYMBOL`, останавливается **до** любых расчётов и **до** записи метки времени активации.
5. Лог содержит: `symbol=ETHUSDT, whitelist=["BTCUSDT"]`.

### Сценарий D: подмена метки времени в базе данных

1. Кто-то напрямую изменил запись `runtime:halt_gate:activation_ts` в SQLite, чтобы «сбросить» счётчик просадки.
2. Бот читает запись, пересчитывает HMAC — подпись не совпадает.
3. `get_signed()` выбрасывает `ValueError: signature mismatch`.
4. `_check_halt_gate()` перехватывает это исключение и останавливается: `HALT_UNKNOWN_SYMBOL`.
5. Бот **не продолжает работу** с фальсифицированными данными.

### Сценарий E: программный сбой в стратегии

1. В коде стратегии возникло непредвиденное исключение (например, `ZeroDivisionError`).
2. Исключение всплывает через `_poll_bar_and_strategy()` → `_main_loop()` → попадает в `run()`.
3. `run()` перехватывает его, вызывает `request_halt(HALT_RUNTIME_CRASH)`.
4. `_shutdown(reason="HALT_RUNTIME_CRASH")` завершает WebSocket, пишет лог.
5. Исключение пробрасывается наверх — попадёт в системные логи или к оператору.

## Подводные камни / что важно понимать

**Предохранители работают только в демо-режиме — включая проверку белого списка.** Условие `if self._settings.s35_demo_active` в `_tick()` означает, что при `s35_demo_active=False` метод `_check_halt_gate()` не вызывается вообще: ни пороги просадки, ни серия убытков, **ни белый список символов** не проверяются. Это сделано намеренно: система находится в стадии тестирования. (`src/runtime/manager.py:175, 193`)

**Нельзя включить демо-режим на реальном аккаунте.** Настройки проверяются при старте (см. [[configuration-and-settings|встроенные защиты настроек]]): комбинация `s35_demo_active=True` и `live_trading=True` (или `testnet=False`) немедленно выбросит ошибку — бот не запустится вообще. Это жёсткая защита от случайного запуска тестового режима с реальными деньгами (подробнее о контурах биржи — в [[run-modes-testnet-live-reconcile|режимах запуска]]). (`src/platform/config.py:260–291`)

**«6 месяцев без сделок» — это не 180 ровных дней.** Формула `days // 30` округляет вниз. На 179-й день без сделок `months_since = 5`, а срабатывает порог при `months_since >= 6` — то есть на 180-й день. Задержка на 0–1 день приемлема для этого критерия.

**Многодневная просадка считается от запуска, не от начала дня.** Это отличается от внутридневной просадки. Даже если сегодня всё в порядке, но с момента первого запуска бот потерял 15% от своего исторического максимума — сработает `DD_MULTIDAY`.

**Ручной рубильник — не мгновенный.** Файл `.kill_switch` проверяется только на каждом тике (каждые 5 секунд). Если бот в момент создания файла уже начал обрабатывать бар (открывает ордер) — он завершит этот шаг и только потом остановится.

**При перезапуске стоп-файл удаляется автоматически.** Если бот был остановлен рубильником, а потом перезапущен — файл `.kill_switch` будет удалён в начале метода `run()`. Это намеренное поведение: предполагается, что оператор, запуская бота снова, тем самым даёт разрешение на работу.

**Незакрытые ордера при аварийной остановке.** `_shutdown()` только считает и логирует ордера в состоянии ожидания (ENTRY_PENDING, EXIT_PENDING, OCO_ARMING), но не закрывает их автоматически. Оператор должен вручную проверить позиции на бирже.
