# Как всё работает вместе: путь от свечи до сделки

**TL;DR:** Каждые несколько секунд бот смотрит на рыночную цену, решает — покупать сейчас или нет, проверяет риски, размещает ордер на бирже и записывает итог сделки в базу данных. Одновременно второй канал (WebSocket) слушает биржу «в прямом эфире» и сообщает боту, когда ордера реально исполнились.

---

## Простыми словами

Представьте автоматического кассира на рынке, который:

1. Каждые несколько секунд смотрит на табло с ценами — это **тик** (tick) торгового цикла.
2. Передаёт увиденное аналитику, который решает: «сейчас хорошие условия для покупки или нет?» — это **стратегия**.
3. Прежде чем купить, кассир идёт к риск-менеджеру: «Сколько денег можно потратить? Где ставим страховку?» — это **проверка рисков**.
4. Если всё добро — кассир отправляет заявку на биржу и сразу же договаривается о двух страховках: при какой цене фиксируем прибыль (тейк-профит) и при какой останавливаем убыток (стоп-лосс). Такой пакет из трёх связанных заявок называется **бракет-ордером** (bracket order) — подробнее см. [[oco-bracket-emulation|эмуляцию OCO]].
5. Параллельно работает «телефон»: биржа по прямому соединению (WebSocket) сообщает, когда заявка реально исполнилась — то есть когда покупка произошла.
6. Итог каждой сделки сохраняется в журнал — для статистики, аудита и обучения.

Бот сейчас торгует **только в сторону LONG** — то есть только покупает и потом продаёт. Играть на понижение (short) в версии v0.1 не предусмотрено.

## Как это работает у нас

### Шаг 0. Запуск — сборка всех компонентов

Когда оператор запускает `python -m src run`, выполняется функция `_cmd_run` (`src/__main__.py:70–226`). Она по очереди создаёт все нужные компоненты и «склеивает» их в единую систему (детальный разбор сборки — в [[startup-and-wiring|Как бот собирается и запускается]]):

| Компонент | Роль |
|---|---|
| **BarSource** | Добытчик свечей — опрашивает биржу через REST API и возвращает последнюю закрытую свечу |
| **MeanReversionRsiBBStrategy** | Генератор сигнала — анализирует свечу и решает: LONG (купить) или FLAT (выйти из позиции) |
| **RiskManager** | Контролёр — одобряет или блокирует сделку, рассчитывает объём покупки, стоп-лосс и тейк-профит |
| **Coordinator** | Исполнитель — ставит ордера на биржу, ведёт FSM (машину состояний позиции) |
| **Reconciler** | Сверщик — после каждого переподключения сравнивает наш учёт с тем, что есть у биржи |
| **BybitPrivateWSConsumer** | Слушатель — получает «факты исполнения» (fills) от биржи по WebSocket в реальном времени |
| **RuntimeManager** | Дирижёр — запускает все компоненты и управляет главным циклом |

После сборки вызывается `rm.run()` (`src/__main__.py:219`), которая передаёт управление `RuntimeManager`.

---

### Шаг 1. Запуск RuntimeManager: bootstrap → WebSocket → главный цикл

`RuntimeManager.run()` (`src/runtime/manager.py:106–151`) выполняет строго по порядку:

1. **Удаляет старый файл-«рубильник»** — если с прошлого запуска остался файл `.kill_switch`, он стирается, чтобы бот не застрял сразу после старта (`manager.py:117–118`).
2. **Bootstrap**: `coordinator.bootstrap()` — сверяет наш локальный учёт с биржей и восстанавливает состояние после перезапуска по принципу [[reconcile-as-truth|«биржа всегда права»]] (`manager.py:121`).
3. **Запускает WebSocket**: `ws_consumer.start()` открывает постоянное соединение с Bybit для получения событий исполнения в реальном времени (`manager.py:135`).
4. **Входит в главный цикл** `_main_loop()` — крутится бесконечно до команды остановки.

---

### Шаг 2. Главный цикл — тик каждые N секунд

`_main_loop()` (`manager.py:153–160`) в цикле вызывает `_tick()`, затем засыпает на `runtime_bar_poll_cadence_seconds` секунд (по умолчанию **5.0 секунды**, `src/platform/config.py:210–212`). Пошаговый разбор одного тика — в [[main-loop-tick|Главный цикл: что бот делает каждые несколько секунд]].

Один тик (`_tick()`, `manager.py:162–178`) проходит по следующим проверкам:

```text
_tick():
  1. Проверить файл-рубильник → если есть, остановиться
  2. Проверить живость WebSocket-соединения → если мёртв, пропустить тик и инициировать переподключение
  3. Если включён демо-режим → проверить HaltGate (критерии аварийной остановки)
  4. Проверить TTL у «полувооружённых» OCO-ордеров (защита от зависших заявок)
  5. → _poll_bar_and_strategy()
```

---

### Шаг 3. Получение свечи — BarSource.poll()

[[bar-source-live|BarSource]] `.poll()` (`src/runtime/bar_source.py:60–92`) — это «оконный датчик», который смотрит на последние 2 свечи и возвращает только одну — последнюю **закрытую** (завершившуюся). Данные он берёт через REST-опрос биржи (см. [[bybit-rest-source|получение данных по REST]]).

**Свеча** ([[bar-model|Bar, OHLCV]]) — это сводная информация о торгах за период: открытие (open), максимум (high), минимум (low), закрытие (close), объём (volume). Например, для часового интервала — данные за последний завершившийся час. Модель свечи: `src/marketdata/models.py:17–43`.

Важный момент: Bybit в ответе на запрос цен возвращает и текущую, ещё не закрытую свечу. `BarSource` специально её отфильтровывает — бот не должен принимать решения по неполным данным (`bar_source.py:79–86`). Это защита от «смотрения в будущее» (look-ahead).

Если REST API несколько раз подряд не отвечает — накапливается счётчик `consecutive_failures`. Когда он достигает порога (по умолчанию 24, что соответствует ~120 секундам молчания), бот останавливается с кодом `HALT_BAR_POLL_STALL` — один из [[safety-stops-and-halts|аварийных стопов]] (`manager.py:327–335`).

---

### Шаг 4. Стратегия — strategy.on_bar(bar) → Signal | None

Когда свеча получена, она передаётся в стратегию: `signal = self._strategy.on_bar(bar)` (`manager.py:346`).

**Сигнал** ([[signal-architecture|Signal]]) — это структура данных, которую стратегия возвращает, если считает, что сейчас хорошие условия. В сигнале есть:
- **side**: LONG (купить) или FLAT (выйти из позиции)
- **reason**: код-причина (например, почему решили войти)
- Снимок показателей индикаторов на момент сигнала

Если стратегия говорит «пока ничего интересного» — возвращает `None`, и тик заканчивается без сделки.

Текущая стратегия бота — [[02-стратегии/mean-reversion-strategy|MeanReversionRsiBBStrategy]]: она генерирует LONG, когда [[ema-rsi-indicators|RSI]] (индикатор перепроданности) ниже порога **и** цена пробила нижнюю [[bollinger-bands-indicator|полосу Боллинджера]] (индикатор отклонения от среднего). Оба условия должны выполняться одновременно — это «AND-шлюз» (`src/signalgen/mean_reversion_strategy.py:3–6`).

---

### Шаг 5. FLAT-сигнал → закрытие позиции

Если пришёл сигнал `FLAT` (выход) — логика особая (`manager.py:363–371`). Бот проверяет, есть ли сейчас открытая позиция (состояния LONG_OPEN, OCO_ARMING, OCO_ARMED). Если есть — вызывает `coordinator.flatten()`, который отменяет действующие защитные ордера и продаёт остаток через рыночный ордер.

Если позиции нет — FLAT-сигнал молча игнорируется, тик заканчивается.

---

### Шаг 6. LONG-сигнал — проверка состояния позиции

Для LONG-сигнала бот сначала читает текущее состояние своей **позиции** (position) — через `coordinator.current_state(symbol)` (`manager.py:359`). Позиция — это то, что у бота есть сейчас на бирже: купленная монета в ожидании продажи.

**Если позиции нет** (состояние FLAT) — переходим к риску. **Если позиция уже есть** (любое другое состояние) — сигнал пропускается (`manager.py:373–379`). Это «инвариант одного открытого ордера»: бот никогда не входит повторно, пока предыдущая сделка не закрыта.

---

### Шаг 7. Риск — RiskManager.assess(signal, mark_price)

`assessment = self._risk_manager.assess(signal, mark_price=bar.close)` (`manager.py:380`).

Риск-менеджер — это «контролёр перед кассой». Весь его конвейер проверок разобран в [[risk-overview-decision-pipeline|Как бот решает: пускать сделку или нет]]. Он проверяет (`src/risk/manager.py:202–312`):

1. **Не активирован ли стоп-режим** ([[circuit-breakers-drawdown-flash|circuit breaker / halt]]) — если да, сделка запрещается.
2. **Нет ли флэш-краша** — если цена резко провалилась с прошлой свечи, сделка запрещается.
3. **Рассчитывает объём покупки (qty)** — по [[position-sizing-kelly|формуле Келли]] с учётом фазы (сколько сделок уже было) и текущего капитала на счёте.
4. **Рассчитывает уровни стоп-лосса (sl) и тейк-профита (tp)** — через [[atr-indicator|ATR]] (средний диапазон свечей, мера волатильности): `sl = цена - k_sl × ATR` и `tp = цена + k_tp × ATR` (`risk/manager.py:288–289`).

Итог: структура `RiskAssessment` с полем `approved: True/False`. Если отказ — сигнал отклоняется с [[reason-codes-assessment-output|кодом причины]], и тик заканчивается (`manager.py:381–387`).

---

### Шаг 8. Исполнение — Coordinator.start_bracket(...)

Если риск-менеджер одобрил, вызывается (`manager.py:403–408`):

```python
self._coordinator.start_bracket(
    entry_qty=assessment.qty,
    entry_side="Buy",
    tp_price=assessment.tp_price,
    sl_trigger_price=assessment.sl_price,
)
```

`start_bracket` дирижируется [[coordinator-orchestration|Координатором]] (`src/execution/coordinator.py:336–382`) и делает следующее:

1. Генерирует уникальный `bracket_id` — идентификатор этой «группы» ордеров.
2. Отправляет **рыночный ордер на покупку** (Market Buy) на биржу.
3. Переводит внутреннее [[execution-state-machine|состояние позиции]] FLAT → ENTRY_PENDING («ожидаем исполнения входа»).
4. Сохраняет состояние в базу данных.

TP (тейк-профит) и SL (стоп-лосс) ордера **не размещаются сразу** — они ставятся после того, как придёт подтверждение исполнения входного ордера через WebSocket.

**Ордер** (order) — это заявка на биржу «купить/продать такой-то объём по такой-то цене». **Исполнение** (fill) — это когда биржа реально исполнила заявку.

### Шаг 9. Параллельный поток — WebSocket и факты исполнения

Пока тик-цикл крутится, [[bybit-private-websocket|BybitPrivateWSConsumer]] слушает биржу по постоянному каналу WebSocket (`src/execution/bybit/ws_private.py:45–60`). Он подписан на три темы: `order` (статусы ордеров), `wallet` (баланс), `execution` (детали каждого исполнения).

Когда биржа сообщает, что вход исполнен — `Coordinator` получает событие и:
1. Размещает TP и SL ордера (вооружает OCO — «одного отменяет другого»).
2. Переводит состояние в LONG_OPEN → OCO_ARMED.

Когда биржа сообщает, что TP или SL сработал — `Coordinator` фиксирует сделку закрытой.

Когда биржа сообщает о факте исполнения, `FillRecorderAdapter` получает это событие через `on_fill_event()` и **немедленно пишет запись в лог** ([[logging-and-observability|structlog-аудит]], всегда) — это «слой 1», который никогда не пропускается (`src/risk/fill_recorder_adapter.py:83`).

Параллельно адаптер пытается записать детали исполнения в базу данных (таблица `trade_fills`, `migrations/0006_trade_fills.sql:7`) — это «слой 2», лучшеусилийный. Однако в версии v0.1 эта запись **фактически не происходит**: схема базы данных пока не содержит поля `entry_signal_id` в таблице состояния, из-за чего цепочка поиска «ордер → сделка» обрывается, и адаптер логирует предупреждение и пропускает вставку (`fill_recorder_adapter.py:119–126`). Полноценная запись в БД запланирована на S13+.

Отдельная таблица `trade_history` (куда пишет `RiskManager.record_closed_trade`) в живом runtime бота в v0.1 не вызывается — соответствующий путь исполнения не подключён (`src/risk/manager.py:318–319`, 0 вызовов в live-коде). Подробнее о том, где хранятся сделки и исполнения — в [[trade-fill-history|История сделок и исполнений]]. Таким образом, единственный гарантированный след каждого исполнения в v0.1 — это запись в structlog-аудит.

### Шаг 10. Остановка и аварийные ситуации

RuntimeManager знает три способа остановиться (`manager.py:136–151`):

| Причина | Код | Что происходит |
|---|---|---|
| Оператор нажал Ctrl+C | `KEYBOARD_INTERRUPT` | Чистый выход, WebSocket закрывается |
| Аварийный сбой в коде | `HALT_RUNTIME_CRASH` | Запрашивается halt у Coordinator, WebSocket закрывается, ошибка пробрасывается |
| Нормальный выход | `NORMAL_EXIT` | WebSocket закрывается штатно |

Дополнительно, в каждом тике проверяется файл-«рубильник» `.kill_switch` (`manager.py:171`). Если оператор создал этот файл командой `python -m src kill` — бот останавливается после текущего тика. Подробнее — в [[kill-switch-emergency-stop|Аварийный стоп (kill-switch)]].

## Формулы и расчёты

### Стоп-лосс и тейк-профит через ATR

**ATR** (Average True Range) — средний диапазон свечи за последние N периодов. Простыми словами: насколько «прыгает» цена в обычный день. Чем выше ATR — тем шире ставится защита. Каноническая формула Wilder ATR и расчёт стоп-уровней разобраны в [[wilder-atr-and-stops|Wilder ATR и стоп-уровни]].

```text
стоп-лосс  = текущая_цена − k_sl × ATR(14)
тейк-профит = текущая_цена + k_tp × ATR(14)
```

- `k_sl` и `k_tp` — множители, заданные в настройках (`risk_sl_atr_multiplier` и `risk_tp_atr_multiplier`).
- `ATR(14)` — среднее за 14 свечей.

Реализация: `src/risk/manager.py:288–289`.

**Пример:** Цена BTC = 60 000 USDT, ATR = 800 USDT, k_sl = 1.5, k_tp = 2.0:
- Стоп-лосс = 60 000 − 1.5 × 800 = **58 800 USDT** (если цена упадёт сюда — фиксируем убыток и выходим)
- Тейк-профит = 60 000 + 2.0 × 800 = **61 600 USDT** (если цена вырастет сюда — фиксируем прибыль)

## Примеры / сценарии

### Сценарий A: Нормальный вход в сделку

**Момент времени 14:00.** Закрылась очередная часовая свеча BTC/USDT.

1. `BarSource.poll()` запрашивает биржу через REST API. Bybit возвращает свечу 13:00–14:00 (закрыта) и начавшуюся свечу 14:00–15:00 (незакрыта). BarSource отбрасывает незакрытую и возвращает свечу 13:00–14:00 (`bar_source.py:79–91`).

2. Стратегия видит: RSI = 32 (ниже порога 35) и цена закрытия ниже нижней полосы Боллинджера. Оба условия → сигнал `LONG`.

3. Проверяется состояние позиции: FLAT (ничего не куплено). Хорошо.

4. `RiskManager.assess()` проверяет: halt не активирован, флэш-краша нет. Рассчитывает: qty = 0.001 BTC, sl = 58 800, tp = 61 600. Одобряет.

5. `Coordinator.start_bracket()` отправляет рыночный ордер «купить 0.001 BTC». Состояние → ENTRY_PENDING.

6. Через секунду: биржа присылает по WebSocket подтверждение — «ордер исполнен по 60 050». Coordinator ставит TP-ордер на 61 600 и SL-ордер на 58 800. Состояние → OCO_ARMED.

7. `FillRecorderAdapter` фиксирует событие исполнения в structlog-аудит (гарантировано). Попытка записи в `trade_fills` в v0.1 пропускается — цепочка поиска обрывается из-за отсутствия `entry_signal_id` в схеме (`fill_recorder_adapter.py:119–126`).

### Сценарий B: Сигнал пропущен — уже есть позиция

В 15:00 стратегия снова генерирует LONG. Но состояние — OCO_ARMED (позиция открыта). Бот логирует `runtime.signal_skipped_non_flat_state` и тик заканчивается без нового ордера (`manager.py:373–378`).

### Сценарий C: Остановка по рубильнику

Оператор запускает `python -m src kill`. Это создаёт файл `.kill_switch` в корне проекта (`__main__.py:459–483`). В следующем тике `_maybe_kill_switch()` обнаруживает файл, запрашивает `request_halt(KILL_SWITCH_REQUESTED)` и устанавливает `self._stopping = True`. Цикл заканчивается, WebSocket закрывается.

## Подводные камни / что важно понимать

**1. Тик — это не свеча.** Тик происходит каждые 5 секунд (по умолчанию). Новая свеча появляется только раз в час (при интервале `60`). Большинство тиков заканчиваются ничем — `BarSource.poll()` возвращает `None`, потому что свеча не изменилась (`bar_source.py:89–91`).

**2. WebSocket и тик-цикл работают в разных потоках.** Тик-цикл — в основном потоке программы. WebSocket — в отдельном потоке (управляемом библиотекой pybit). Они общаются через Coordinator, который защищён блокировкой (RLock) — это предотвращает гонку при одновременном чтении/записи состояния позиции (`coordinator.py:1–10`).

**3. Бот только LONG.** Версия v0.1 работает на Bybit Spot (обычный рынок, не фьючерсы) — о контурах биржи и флагах см. [[run-modes-testnet-live-reconcile|Режимы запуска]]. Короткая продажа (short) не предусмотрена. FLAT-сигнал — это не «продать в шорт», а просто «закрыть имеющуюся позицию» (`manager.py:363–371`; `risk/manager.py:212–218`).

**4. TP и SL ставятся не сразу.** В момент вызова `start_bracket()` на биржу уходит только один ордер — рыночная покупка. Защитные ордера (TP/SL) ставятся лишь после того, как биржа подтвердила исполнение входа через WebSocket. Это «трёхшаговая эмуляция OCO»: у Bybit Spot нет нативного OCO-ордера.

**5. Потеря данных ≠ катастрофа.** Если REST API не отвечает несколько раз подряд — бот просто пропускает тики и накапливает счётчик. Аварийная остановка происходит только при 24 подряд неудачах (~120 секунд), а не при первой же проблеме (`config.py:214–220`).

**6. LOCKED-параметры стратегии.** Если в [[configuration-and-settings|настройках]] включён флаг `s35_demo_active`, бот принудительно использует зафиксированные параметры стратегии (RSI=14, oversold=35, BB=1.5σ), проверенные в ходе [[walk-forward-analysis|Walk-Forward Analysis]]. Эти параметры нельзя изменить через конфиг — они защищены от случайного изменения (`__main__.py:147–163`).
