# Где бот хранит данные: база, миграции и журнал сделок

**TL;DR:** Бот ведёт один файл-базу данных SQLite — в нём хранятся все закрытые сделки, текущее состояние позиции, журнал аварийных остановок и снимки капитала. Структура базы строится постепенно через «миграции» — пронумерованные SQL-сценарии, каждый из которых применяется ровно один раз и атомарно (либо полностью, либо никак).

---

## Простыми словами

Представьте, что бот — это бухгалтер, который ведёт бухгалтерскую книгу. Эта книга хранится в одном физическом файле на диске (база данных **SQLite**). Внутри файла — несколько таблиц-регистров, каждый отвечает за свой вид записей:

- **Журнал сделок** — каждая закрытая позиция со всеми цифрами: когда вошли, когда вышли, сколько заработали или потеряли, какие комиссии заплатили.
- **Текущее состояние** — что происходит прямо сейчас: открыта ли позиция, какие ордера висят на бирже (это снимок [[execution-state-machine|конечного автомата исполнения]]).
- **Журнал аварийных остановок** — хронология всех случаев, когда бот принял решение [[safety-stops-and-halts|остановиться из-за убытков]] или нештатной ситуации.
- **Снимки капитала** — периодические записи о размере счёта (как фотографии баланса в разные моменты).

SQLite — это не отдельный сервер баз данных, который нужно запускать и настраивать. Это просто один файл на диске, с которым работает бот напрямую. Никаких дополнительных программ устанавливать не нужно.

**Зачем нужны «миграции»?** Представьте, что вы ведёте бухгалтерскую книгу в тетради, и сначала завели три столбца, а потом решили добавить четвёртый. Вы не начинаете тетрадь с нуля — вы просто дорисовываете нужную колонку. Именно так работают **миграции схемы**: каждая — это маленький сценарий на языке SQL, который добавляет новую таблицу или колонку. Бот помнит, какие сценарии уже применены (в служебной таблице `schema_migrations`), и при следующем запуске пропускает уже выполненные.

## Как это работает у нас

### 1. Открытие соединения с базой: функция `connect`

Когда боту нужно работать с базой, вызывается `connect(db_path)` — функция из `src/platform/db.py:32-38`.

```python
def connect(db_path: Path) -> sqlite3.Connection:
    conn = sqlite3.connect(str(db_path))
    conn.execute("PRAGMA journal_mode=WAL")
    conn.execute("PRAGMA synchronous=NORMAL")
    conn.execute("PRAGMA foreign_keys=ON")
    return conn
```

Три строчки после открытия файла включают важные режимы:

- **`PRAGMA journal_mode=WAL`** — режим «журнала упреждающей записи» (WAL, Write-Ahead Log). Это как черновик: сначала изменение записывается в черновик, потом переносится в основной файл. Благодаря этому бот может одновременно читать старые данные и записывать новые, не блокируя себя. Без WAL каждая запись блокировала бы всю базу на время операции.
- **`PRAGMA synchronous=NORMAL`** — компромисс между скоростью и надёжностью: база фиксирует данные на диск в важных точках, но не после каждой строки. Для наших объёмов (несколько сделок в день) это оптимально.
- **`PRAGMA foreign_keys=ON`** — включает проверку «внешних ключей» (foreign keys): связи между таблицами контролируются автоматически. Например, запись в таблице детальных исполнений (fills) не может ссылаться на несуществующую сделку в `trade_history`.

Путь к файлу базы берётся из [[configuration-and-settings|настроек]]: `settings.db_path` (объявлен в `src/platform/config.py:104`).

### 2. Инициализация и накатка миграций: функция `init_db`

`init_db(db_path, migrations_dir)` вызывается при каждом [[startup-and-wiring|запуске бота]] — как в режиме реального торгового цикла (`src/__main__.py:101`), так и в режиме [[reconcile-and-monitor-commands|сверки с биржей]] (`src/__main__.py:412`). Логика функции (`src/platform/db.py:41-98`):

1. Создать папку под базу, если она ещё не существует.
2. Открыть соединение.
3. Создать служебную таблицу `schema_migrations` (если её ещё нет). Она хранит имя каждого уже применённого файла и дату применения.
4. Прочитать список всех `.sql`-файлов из папки `migrations/`, отсортировать их по **числовому** префиксу.
5. Пропустить файлы, имена которых уже есть в `schema_migrations`.
6. Для каждого нового файла — применить атомарно (подробнее ниже).

### 3. Почему порядок — числовой, а не строковый: функция `_migration_sort_key`

Казалось бы, можно просто отсортировать файлы по алфавиту. Но в нашем проекте нумерация непоследовательна: одни файлы называются `001_initial.sql`, `002_risk.sql`, а другие — `0003_execution_state.sql`, `0006_trade_fills.sql`. При алфавитной сортировке строка `"0006..."` окажется **раньше** `"001..."` (потому что символ `0` идёт перед `1`), и миграция, добавляющая внешний ключ к таблице, попытается создать его до того, как сама таблица появится — это сломает базу.

Функция `_migration_sort_key` (`src/platform/db.py:16-29`) извлекает из имени файла число (`int`) и сортирует по нему:

```python
def _migration_sort_key(filename: str) -> tuple[int, str]:
    match = _MIGRATION_VERSION_RE.match(filename)
    version = int(match.group(1)) if match else 2**63
    return (version, filename)
```

Фактический порядок применения девяти наших миграций:

| Числовой ключ | Файл | Что добавляет |
|---|---|---|
| 1 | `001_initial.sql` | Базовые таблицы: orders, fills, positions, events, runs, state |
| 2 | `002_risk.sql` | Журнал сделок `trade_history`, снимки капитала `equity_snapshots` |
| 3 | `0003_execution_state.sql` | Текущее состояние FSM по символу |
| 3 | `003_trade_history_unique.sql` | UNIQUE-индекс на `entry_signal_id` |
| 4 | `0004_execution_state_v2.sql` | Колонки OCO-ордеров (TP/SL) |
| 4 | `004_money_columns_text.sql` | Перевод денежных колонок REAL → TEXT |
| 5 | `0005_halt_persistence.sql` | Поля аварийной остановки + таблица `halt_log` |
| 6 | `0006_trade_fills.sql` | Детализированные исполнения `trade_fills` |
| 7 | `0007_bracket_exit_prices.sql` | Плановые цены TP/SL в строке состояния |

При версии-ключе 3 два файла имеют одинаковый числовой префикс — в качестве тай-брейка используется алфавитный порядок имён файлов (это второй элемент кортежа).

После сортировки функция дополнительно проверяет, что порядок не нарушен (assertion в `src/platform/db.py:70-73`), — защита от случайного регресса к лексикографической сортировке (DI-03).

### 4. Атомарная транзакция для каждой миграции

Каждая миграция применяется как единая транзакция: или всё проходит успешно, или ничего не меняется (`src/platform/db.py:87-96`).

Код строит специальный скрипт, обёрнутый в `BEGIN/COMMIT`:

```sql
BEGIN;
<содержимое sql-файла>
INSERT INTO schema_migrations (filename, applied_at) VALUES ('0006_trade_fills.sql', datetime('now'));
COMMIT;
```

Запись в `schema_migrations` включена **внутрь той же транзакции**, что и сам SQL-файл. Это значит: если при создании таблицы что-то пошло не так — откат произойдёт целиком, и следующий запуск попробует снова. Никаких «наполовину применённых» миграций быть не может.

Аналогия: это как подписывать квитанцию об оплате в тот момент, когда деньги физически переходят из рук в руки. Нельзя получить квитанцию без денег и нельзя отдать деньги без квитанции.

### 5. Защита от инъекций через имя файла

Внутри транзакционного скрипта имя файла вставляется через Python f-string (не через SQL-параметры, потому что `executescript()` их не поддерживает). Чтобы злоумышленник не мог подложить файл с именем, содержащим SQL-код, функция проверяет имя по строгому списку разрешённых символов: только буквы латиницы, цифры, точка, подчёркивание, дефис (`src/platform/db.py:7-10, 83-86`):

```python
_MIGRATION_FILENAME_RE = re.compile(r"[A-Za-z0-9._-]+")
...
if not _MIGRATION_FILENAME_RE.fullmatch(sql_file.name):
    raise ValueError(...)
```

## Главные таблицы и их роль

### `trade_history` — журнал закрытых сделок

Создаётся миграцией `002_risk.sql`. Это главная таблица учёта: каждая закрытая позиция записывается здесь одной строкой.

Ключевые колонки:

| Колонка | Тип | Смысл |
|---|---|---|
| `symbol` | TEXT | Торговая пара, например `BTCUSDT` |
| `entry_signal_id` | TEXT (UUID) | Уникальный идентификатор сигнала входа — ключ идемпотентности |
| `entry_ts` / `exit_ts` | TEXT (ISO-8601) | Время входа и выхода |
| `qty` | TEXT (Decimal) | Объём в базовой монете |
| `entry_price` / `exit_price` | TEXT (Decimal) | Цены входа и выхода |
| `pnl_quote` | TEXT (Decimal) | Прибыль/убыток в котируемой валюте (знаковое число) |
| `pnl_pct` | TEXT (Decimal) | Прибыль/убыток в долях: `0.012` = +1.2% (src/risk/trade_history.py:31) |
| `fees_paid` | TEXT (Decimal) | Суммарная комиссия по сделке (≥ 0) |
| `reason_code` | TEXT | Причина закрытия: стоп-лосс, тейк-профит и т.д. (см. [[reason-codes-assessment-output|словарь кодов причин]]) |
| `kelly_phase` | INTEGER | Фаза [[position-sizing-kelly|Kelly-сайзинга]] (1–4) на момент сделки |

Запись в таблицу происходит через `TradeHistoryRepository.insert_closed_trade()` (`src/risk/trade_history.py:44`). Используется оператор `INSERT OR IGNORE` — это значит, что повторная попытка вставить уже существующую сделку будет молча проигнорирована, а не создаст дубликат. Именно эти закрытые сделки — исходные данные для [[trade-fill-history|обучения бота]] и для статистической проверки: путь бэктеста собирает из аналогичных строк [[trade-extractor-and-records|список TradeRecord для DSR]].

### `trade_fills` — детализированные исполнения внутри сделки

Создаётся миграцией `0006_trade_fills.sql`. Одна сделка в `trade_history` может состоять из нескольких физических исполнений на бирже (например, частичное исполнение). Каждое такое исполнение — отдельная строка в `trade_fills`.

Ключевые поля: `parent_trade_id` (ссылка на `trade_history`), `exec_id` (идентификатор от Bybit, уникальный), `fill_qty`, `fill_price`, `fill_fee`.

Запись — через `FillHistoryRepository.insert_fill()` (`src/risk/fill_history.py:42`), тоже с `INSERT OR IGNORE`. Событие исполнения прилетает по [[bybit-private-websocket|приватному WebSocket]] от биржи. Биржа может прислать одно и то же событие несколько раз (гарантия «хотя бы один раз»), уникальный индекс по `exec_id` (`uq_trade_fills_exec_id`) гарантирует, что дубликат не попадёт в базу.

### `execution_state` — текущее состояние по символу

Создаётся миграцией `0003_execution_state.sql`, расширяется в `0004`, `0005`, `0007`. Это единственная строка на символ, хранящая «где сейчас находится» [[execution-state-machine|автомат исполнения ордеров (FSM)]] — благодаря ей бот переживает перезапуск и может свериться с биржей ([[reconcile-as-truth|reconcile]]).

Полный состав колонок на конец S55 (`src/execution/state_repo.py:39-45`):

| Группа | Колонки |
|---|---|
| Идентификация | `symbol`, `state`, `updated_at` |
| Позиция | `position_qty`, `entry_price` |
| OCO-ордера | `bracket_id`, `oco_tp_order_id`, `oco_sl_order_id`, `oco_main_order_id` (legacy) |
| Исполнение | `expected_oco_qty`, `arming_started_at`, `last_attempt_num` |
| Плановые цены | `bracket_tp_price`, `bracket_sl_trigger_price` (добавлены в S55) |
| Аварийные метки | `halt_reason`, `last_exit_reason`, `last_reconcile_at`, `bootstrap_at` |

Запись через `ExecutionStateRepo.upsert()` (`src/execution/state_repo.py:52`): если строки по символу ещё нет — вставляет, если есть — обновляет (INSERT ... ON CONFLICT DO UPDATE). Обновляет эту строку [[coordinator-orchestration|Coordinator — дирижёр исполнения]] на каждом шаге сделки.

**Зачем хранить `bracket_tp_price` и `bracket_sl_trigger_price`?** (добавлены миграцией `0007_bracket_exit_prices.sql`, S55 BLOCKER TL-01): когда бот открывает позицию, он знает, по какой цене хочет зафиксировать прибыль (TP) и по какой — остановить убытки (SL). Эти цены передаются при открытии [[oco-bracket-emulation|«брекета» (bracket из TP + SL)]], но до исправления они нигде не сохранялись. После исполнения входного ордера бот хотел выставить защитные ордера — но уже не помнил цены. Теперь они сохраняются в строке состояния при открытии позиции и читаются обратно при получении подтверждения исполнения.

### `equity_snapshots` — снимки капитала

Создаётся в `002_risk.sql`. Периодически записывает размер счёта в три цифры: реализованный капитал, нереализованный PnL, итого. Источник записи (`source`): `BAR_CLOSE`, `POSITION_CLOSE` или `MANUAL`.

Используется для расчёта [[equity-tracking|просадки]] — насколько капитал упал от пика за последние 24 часа (`src/risk/equity_tracker.py`). Именно эта величина запускает [[circuit-breakers-drawdown-flash|автоматические предохранители по просадке]].

### `halt_log` — журнал аварийных остановок

Создаётся в `0005_halt_persistence.sql`. Это append-only журнал: строки только добавляются, никогда не удаляются. Каждая запись — одно событие остановки с временной меткой, символом, причиной и JSON-контекстом (подробнее про протокол записи — [[execution-state-persistence-and-halt-audit|хранение состояния исполнения и журнал аварийных остановок]]).

Запись через `ExecutionStateRepo._set_halt()` (`src/execution/state_repo.py:130-163`) выполняется в строгом порядке:

1. Сначала вставляется строка в `halt_log` (аудит-запись).
2. Затем, если поле `halt_reason` в `execution_state` ещё пустое, — записывается причина (первая причина побеждает, последующие игнорируются).
3. Обе операции — в одной транзакции.

Такой порядок называется **write-ahead** (запись-вперёд): аудит-запись всегда совершается до обновления основной строки. Это значит: если в будущем транзакция вдруг разбивается на части, аудит никогда не потеряется.

### Таблицы низкоуровневого учёта ордеров

Миграция `001_initial.sql` создаёт таблицы `orders`, `fills`, `positions`, `events`, `runs`, `config`, `state`, `audit_index`. Это исходный скелет системы учёта ордеров. Денежные поля в них изначально были типа `REAL` (число с плавающей запятой) — миграция `004_money_columns_text.sql` перестроила эти таблицы и перевела денежные колонки в `TEXT`. На момент перестройки в этих таблицах не было живых данных: активный путь сохранения использует `trade_history`, а не `orders`/`fills`/`positions`.

## Формулы и расчёты

### Decimal-as-TEXT: почему деньги хранятся как текст, а не как число

В большинстве баз данных денежные суммы хранят как числа с плавающей запятой (тип `REAL`, он же `FLOAT` или `DOUBLE`). Это удобно, но опасно для денег.

**Проблема плавающей запятой:** компьютер хранит числа в двоичной системе, и многие десятичные дроби невозможно представить точно. Например:

```text
0.1 + 0.2 в Python float = 0.30000000000000004  (не 0.3!)
```

Для торговли это критично: ошибка в шестом знаке после запятой может накопиться за сотни сделок и привести к расхождению между расчётным PnL и реальным балансом.

**Наше решение:** все денежные значения хранятся как строки, представляющие `Decimal` — тип с произвольной точностью. При записи в базу Python-объект `Decimal("0.1")` превращается в строку `"0.1"`, при чтении — обратно в `Decimal`. Округление не происходит никогда.

Это правило применяется во всех новых таблицах: `trade_history`, `trade_fills`, `execution_state`, `equity_snapshots`. Колонки типа `TEXT` хранят строки вида `"29815.34000000"`. Старые таблицы (`orders`, `fills`, `positions`) переведены с `REAL` на `TEXT` миграцией `004_money_columns_text.sql`.

## Примеры / сценарии

### Сценарий 1: первый запуск бота

1. Бот стартует, вызывается `init_db(settings.db_path, migrations_dir)`.
2. Файл базы не существует — создаётся в указанной папке.
3. Таблица `schema_migrations` создаётся (она ещё пуста).
4. Все девять `.sql`-файлов применяются по порядку (числовые ключи 1, 2, 3, 3, 4, 4, 5, 6, 7).
5. После каждого файла в `schema_migrations` появляется запись вроде:

   ```
   filename: "001_initial.sql"
   applied_at: "2026-06-26 12:00:00"
   ```

6. База готова, бот начинает торговать.

### Сценарий 2: бот перезапускается (база уже есть)

1. `init_db` снова вызывается при старте.
2. `schema_migrations` уже содержит все девять имён.
3. Все миграции пропускаются (`if sql_file.name in applied: continue`).
4. База открывается «как есть», бот продолжает работу.

### Сценарий 3: закрытие сделки — что сохраняется в базе

Бот купил 0.001 BTC по 30 000 USDT и продал по 30 300 USDT. Комиссия — 0.0603 USDT за обе ноги.

В `trade_history` появляется строка:

```
symbol:       "BTCUSDT"
entry_price:  "30000.00"       <- TEXT, точный Decimal
exit_price:   "30300.00"       <- TEXT
qty:          "0.001"
pnl_quote:    "0.2397"         <- 0.3 - 0.0603 = +0.2397 USDT
pnl_pct:      "0.007990"       <- ≈ +0.8% от стоимости входа (0.3/30 = 0.01; с учётом комиссий)
fees_paid:    "0.0603"
reason_code:  "EXIT_TP_HIT"
kelly_phase:  1
```

Одновременно биржа присылает WS-событие об исполнении. В `trade_fills` добавляется строка с `exec_id` от Bybit. Если Bybit пришлёт то же событие дважды — второй `INSERT OR IGNORE` ничего не создаст (защита по `uq_trade_fills_exec_id`).

### Сценарий 4: аварийная остановка бота

Бот фиксирует, что потери за день превысили допустимый порог. Вызывается `_set_halt()`:

1. В `halt_log` вставляется: `symbol="BTCUSDT"`, `reason="HALT_DRAWDOWN_L1"`, `context_json={"drawdown": "-0.21", ...}`.
2. В `execution_state` поле `halt_reason` обновляется на `"HALT_DRAWDOWN_L1"` (только если оно ещё `NULL`).
3. Обе записи — в одной транзакции.

Если через час происходит ещё одна остановка — в `halt_log` добавится ещё одна строка (хронология), а `halt_reason` в `execution_state` останется первоначальным значением (первопричина победила).

## Подводные камни / что важно понимать

### Порядок миграций — не алфавитный

Если кто-то добавит файл миграции и назовёт его `0099_new_feature.sql`, он будет применён корректно. Но если назвать его `ABC_new.sql` (без числового префикса) — он попадёт в конец (версия `2^63`). Если же случайно нарушить порядок зависимостей (например, FK до таблицы), функция поймает это через assertion (`src/platform/db.py:70-73`) при следующем запуске.

### Миграции применяются один раз навсегда

Если в уже примененном `.sql`-файле исправить опечатку — изменение не попадёт в базу на уже существующих установках. Правильный путь: создать новую миграцию, которая вносит нужное изменение.

### Денежные колонки — это строки, не числа

При работе с базой напрямую (например, в SQLite-браузере или через SQL-запрос) числа выглядят как `"29815.34000000"`. Это нормально: в Python они читаются обратно через `Decimal(row[n])` и сохраняют полную точность. Если попытаться сложить их как строки или отсортировать как текст — получится неверный результат. В приложении это делается правильно (`src/risk/trade_history.py:163-180`).

### Идемпотентность не заменяет проверку дубликатов вручную

`INSERT OR IGNORE` защищает только от точного совпадения по уникальному индексу. Если одна и та же сделка была записана с разными `entry_signal_id` — дублирование всё равно произойдёт. Именно поэтому `entry_signal_id` — это UUID, который генерируется однажды при появлении сигнала и сопровождает всю цепочку до записи в базу.

### WAL-файлы рядом с базой

SQLite в режиме WAL создаёт рядом с файлом базы два служебных файла: `<имя>.db-wal` и `<имя>.db-shm`. Это нормально — они нужны для работы журнала. Их нельзя удалять, пока база открыта. При правильном закрытии соединения WAL-журнал автоматически «встраивается» в основной файл.
