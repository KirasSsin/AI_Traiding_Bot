# Главный цикл: что бот делает каждые несколько секунд

**TL;DR:** Каждые 5 секунд бот просыпается, проверяет, всё ли в порядке (связь, безопасность, данные), запрашивает у биржи последнюю закрытую свечу и — если стратегия говорит «войти» — открывает сделку. Если что-то пошло не так, бот останавливается сам, не торгует вслепую.

---

## Простыми словами

Представьте охранника на посту с чек-листом. Каждые 5 секунд он делает обход:

1. Проверяет, не пришёл ли приказ немедленно остановиться.
2. Смотрит, работает ли сигнализация (связь с биржей).
3. Проверяет защитные пороги (не слишком ли много потеряли денег сегодня).
4. Убеждается, что ни один незавершённый приказ не завис намертво.
5. Запрашивает последние данные о цене и решает, нужно ли что-то делать.

Если на любом шаге что-то не в порядке — охранник поднимает тревогу и завершает смену. Он **не пытается работать в темноте**.

**Тик** — это один такой обход. Всё, что бот делает за одно пробуждение, называется одним тиком.

---

## Как это работает у нас

### Главный цикл: `_main_loop`

Бот входит в бесконечный цикл сразу после запуска. На каждой итерации:
1. Выполняет один тик (`_tick`).
2. Засыпает на `runtime_bar_poll_cadence_seconds` секунд (по умолчанию **5.0 секунд**).
3. Повторяет, пока флаг `_stopping` не выставлен.

```python
# src/runtime/manager.py:153-160
def _main_loop(self) -> None:
    while not self._stopping:
        self._tick()
        time.sleep(self._settings.runtime_bar_poll_cadence_seconds)
```

Значение 5 секунд задаётся в настройках:

```python
# src/platform/config.py:210-213
runtime_bar_poll_cadence_seconds: float = Field(
    default=5.0,
    description="REST kline poll cadence (main loop tick). ADR 0022 sub-decision 2.",
)
```

Почему именно 5 секунд? Стратегия работает на часовых **свечах** (kline с биржи), которые закрываются раз в час. Опрашивать биржу каждую секунду было бы расточительством; 5 секунд — достаточно часто, чтобы не пропустить закрытие свечи, и достаточно редко, чтобы не нагружать API Bybit.

---

### Один тик: `_tick`

Это сердце бота. Каждые 5 секунд вызывается `_tick`, и он выполняет проверки строго в следующем порядке:

```python
# src/runtime/manager.py:162-178
def _tick(self) -> None:
    if self._maybe_kill_switch():      # 1. стоп-файл
        return
    if not self._check_alive_inline(): # 2. WebSocket жив?
        return
    if self._settings.s35_demo_active and self._check_halt_gate():  # 3. защитные пороги
        return
    self._coordinator.reconcile_arming_ttl(                         # 4. зависшие OCO
        ttl_seconds=self._settings.oco_arming_ttl_seconds
    )
    self._poll_bar_and_strategy()                                    # 5. свеча + стратегия
```

Порядок не случайный — каждая проверка стоит перед следующей именно потому, что её нарушение делает дальнейшую работу опасной или бессмысленной. Рассмотрим каждый шаг.

---

#### Шаг 1. Стоп-файл (`_maybe_kill_switch`)

**Что делает:** проверяет, существует ли файл `.kill_switch` в рабочей директории.

**Зачем:** это экстренная кнопка «стоп». Оператор (или скрипт мониторинга) создаёт файл с таким именем — и бот на следующем тике замечает его, записывает в локальную базу данных причину остановки ([[reason-codes-assessment-output|`KILL_SWITCH_REQUESTED`]]), переводит внутреннюю машину состояний в режим **HALTED** (остановлен) и прекращает главный цикл. Подробнее про эту «красную кнопку» — [[kill-switch-emergency-stop|аварийный стоп]].

> **Важно:** бот при этом **не отправляет на биржу никакой команды** и **не отменяет открытые ордера**. Все ордера — тейк-профит, стоп-лосс — остаются активными на бирже и продолжат выполняться по своим ценам. Бот просто перестаёт принимать новые решения. Если нужно закрыть позиции — сделайте это вручную на бирже.

```python
# src/runtime/manager.py:286-296
def _maybe_kill_switch(self) -> bool:
    if self._kill_switch_path.exists():
        self._coordinator.request_halt(ReasonCode.KILL_SWITCH_REQUESTED)
        self._stopping = True
        return True
    return False
```

Путь к файлу-сентинелю по умолчанию — `.kill_switch` (настройка `runtime_kill_switch_path`, `src/platform/config.py:222-225`). При старте бот **удаляет** старый стоп-файл, если он остался с прошлого сеанса (`src/runtime/manager.py:117-118`) — чтобы не застрять немедленно.

---

#### Шаг 2. Проверка WebSocket (`_check_alive_inline`)

**Что делает:** проверяет, когда в последний раз биржа Bybit прислала что-нибудь по каналу реального времени ([[bybit-ws-consumer|WebSocket]] — это постоянное соединение, по которому биржа присылает обновления об ордерах и балансе через [[bybit-private-websocket|приватный поток]]).

**Зачем:** если соединение «умерло» тихо (без явной ошибки), бот может пропустить подтверждения об исполнении ордеров. Лучше остановиться и переподключиться, чем торговать без обратной связи.

```python
# src/runtime/manager.py:298-302
def _check_alive_inline(self) -> bool:
    return self._ws_consumer.check_alive(
        max_silence_seconds=self._settings.runtime_ws_check_alive_max_silence
    )
```

Если биржа молчит дольше **30 секунд** (настройка `runtime_ws_check_alive_max_silence`, `src/platform/config.py:226-229`) — `check_alive` вызывает `on_disconnect`, который запускает попытку переподключения. Тик прерывается, бот не опрашивает стратегию в этом цикле.

---

#### Шаг 3. Защитные пороги — [[halt-gate-precommitted-criteria|`HaltGate`]] (только в демо-режиме)

**Что делает:** вычисляет, не нарушены ли защитные критерии торговли, и если нарушены — останавливает бот.

**Зачем:** это автоматические предохранители, аналог «страховки от себя». Они срабатывают, если:

| Критерий | Порог по умолчанию | Настройка |
|---|---|---|
| Просадка за день (intraday DD) | −20% от стартового баланса дня | `s35_halt_dd_intraday` = 0.20 |
| Просадка от пика за всё время (multiday DD) | −15% от исторического максимума | `s35_halt_dd_multiday` = 0.15 |
| Подряд убыточных сделок | 5 сделок подряд | `s35_halt_consecutive_losses` = 5 |
| Нет сделок слишком долго | 6 месяцев без закрытых сделок | `s35_halt_no_trade_months` = 6 |

Значения подтверждены: `src/platform/config.py:132-155`.

Эта проверка работает **только когда `s35_demo_active = True`** (демо-режим на тестовой бирже). Системный валидатор (`src/platform/config.py:260-291`) блокирует только одну запрещённую комбинацию: `s35_demo_active = True` **одновременно** с `live_trading = True` (реальная биржа). На production-конфигурации флаг `s35_demo_active` должен быть `False` — в этом случае проверка HaltGate просто пропускается в `_tick`, а валидатор не предъявляет никаких требований.

Бот также проверяет, что торгуемый символ входит в разрешённый список. По умолчанию разрешён только BTCUSDT. Если символ не в списке — немедленный **HALT_UNKNOWN_SYMBOL** (`src/runtime/manager.py:199-208`).

---

#### Шаг 4. Досмотр зависших OCO (`reconcile_arming_ttl`)

**OCO** (One-Cancels-the-Other — «один отменяет другой») — пара ордеров: тейк-профит и стоп-лосс. Когда один срабатывает, второй должен быть отменён. На Bybit Spot такой механизм [[oco-bracket-emulation|эмулируется вручную]] тремя отдельными ордерами.

**Зависший OCO** — это ситуация, когда ордер-пара начала «вооружаться» (бот выставил тейк-профит, но стоп-лосс ещё не выставлен), и это состояние длится слишком долго. Проверку выполняет [[coordinator-orchestration|координатор исполнения]].

Каждый тик бот проверяет: не завис ли OCO дольше **60 секунд** (`oco_arming_ttl_seconds = 60`, `src/platform/config.py:177`). Если завис — это сигнал о серьёзной проблеме, и бот останавливается (ADR 0020 sub-decision 11).

```python
# src/runtime/manager.py:177
self._coordinator.reconcile_arming_ttl(ttl_seconds=self._settings.oco_arming_ttl_seconds)
```

**TTL** (Time To Live — «время жизни») — это максимально допустимый срок для промежуточного состояния. Как срок годности: если превышен, считается испорченным.

#### Шаг 5. Опрос свечи и работа стратегии (`_poll_bar_and_strategy`)

Это основная работа тика. Разберём по шагам.

---

### Получение свечи: [[bar-source-live|`BarSource.poll`]]

**Kline (свеча)** — это запись о движении цены за определённый период. Для нашего бота — за 1 час. [[bar-model|Свеча]] содержит: цену открытия, максимум, минимум, цену закрытия и объём торгов за этот час. Называется «свечой», потому что на графике выглядит как японская свеча.

```python
# src/runtime/bar_source.py:60-92
def poll(self) -> Bar | None:
    ...
```

Метод `poll` делает следующее:

**Шаг A. Запрашивает данные у биржи** (`_fetch`). Bybit отдаёт последние 2 свечи за период в 2 часа назад от текущего момента (`src/runtime/bar_source.py:105-113`). Почему 2? Чтобы всегда захватить хотя бы одну полностью закрытую свечу, даже если текущий час ещё не завершён.

**Шаг B. Фильтрует формирующиеся свечи (look-ahead guard).** Bybit присылает в том числе текущую, ещё не закрытую свечу — «живую». Её данные изменятся к концу часа. Торговать по ней нельзя: это всё равно что принять решение, посмотрев только на половину шахматной партии.

```python
# src/runtime/bar_source.py:76-87
now_ms = self._now_ms()
latest = None
for bar in bars:
    if int(bar.close_time.timestamp() * 1000) <= now_ms:
        latest = bar  # берём только если свеча уже закрылась
```

Свеча считается **закрытой** (settled), когда её время закрытия (`close_time`) уже наступило — то есть сейчас ≥ `close_time`. Только такая свеча участвует в торговле.

**Шаг C. Дедупликация по времени закрытия.** Бот запоминает время закрытия последней обработанной свечи (`_last_close_ts`). Если новая свеча имеет то же самое или более раннее время закрытия — она уже была обработана, её игнорируют.

```python
# src/runtime/bar_source.py:88-92
close_ms = int(latest.close_time.timestamp() * 1000)
if self._last_close_ts is not None and close_ms <= self._last_close_ts:
    return None
self._last_close_ts = close_ms
return latest
```

Без этой дедупликации бот мог бы обработать одну и ту же свечу несколько раз (тик каждые 5 секунд, а свеча — раз в час), что привело бы к повторным ложным сигналам.

### Счётчик сбоев и аварийная остановка (`should_halt`)

Счётчик `consecutive_failures` растёт **только при исключении** внутри `_fetch()` — то есть когда биржа вернула ошибку или соединение прервалось. Если запрос прошёл успешно, но новой закрытой свечи ещё нет (а это происходит 719 из 720 тиков за час), счётчик сбрасывается в ноль (`src/runtime/bar_source.py:62-73`). Это важно: бот не считает «нет новой свечи» за сбой — это штатный ход работы.

После каждого вызова `poll` менеджер проверяет:

```python
# src/runtime/manager.py:327-335
if self._bar_source.should_halt(threshold=self._settings.runtime_bar_poll_stall_threshold):
    self._coordinator.request_halt(ReasonCode.HALT_BAR_POLL_STALL)
    self._stopping = True
    return
```

Код `HALT_BAR_POLL_STALL` — один из [[reason-codes-assessment-output|канонических кодов причин]], которыми бот помечает каждую остановку в журнале аудита.

По умолчанию порог — **24 подряд идущих сбоя** (`runtime_bar_poll_stall_threshold = 24`, `src/platform/config.py:214-220`). При тике раз в 5 секунд это означает: если биржа не отвечает **2 минуты подряд** (24 × 5 сек = 120 сек), бот останавливается. Валидатор настроек не позволит установить этот порог ниже 6 (30 секунд) или выше 720 (60 минут) — диапазон 6–720 гарантирует баланс между ложными тревогами и реальными проблемами.

---

### Проверка качества данных ([[data-quality-detector|`BarPriceQualityDetector`]])

Даже если свеча получена — бот проверяет, не выглядит ли цена закрытия аномально. Речь идёт о «прыжке» цены между двумя последовательными свечами.

```python
# src/runtime/manager.py:341-344
if self._quality_detector.check(current_close=bar.close):
    self._coordinator.request_halt(reason=ReasonCode.HALT_DATA_QUALITY)
    self._stopping = True
    return
```

**Как считается отклонение:**

```
отклонение = |текущая_цена_закрытия - предыдущая_цена_закрытия| / предыдущая_цена_закрытия
```

Простыми словами: насколько процентов цена изменилась с прошлой свечи? Если изменение превышает **0.5%** (`runtime_quality_threshold_pct = 0.005`, `src/platform/config.py:234-241`), бот считает данные подозрительными и останавливается.

Порог обоснован в коде: для BTCUSDT на 1-часовых свечах при цене ~$100 000 скачок цены более чем на $500 за час является нетипичным и, скорее всего, означает проблему с фидом данных (`src/marketdata/quality.py:14-18`).

Первая свеча после запуска всегда проходит проверку — нет базы для сравнения (`src/marketdata/quality.py:58-62`).

### Цепочка принятия торгового решения

Если свеча получена и прошла проверку качества:

**1. Стратегия анализирует свечу** (`strategy.on_bar(bar)`). Стратегия смотрит на свечу и возвращает [[signal-architecture|сигнал]]: войти в сделку (`LONG`), выйти (`FLAT`) или ничего не делать (`None`). (`src/runtime/manager.py:346-348`)

**2. Если сигнал «выйти» (`FLAT`)** — бот проверяет, есть ли открытая позиция. Позиция считается открытой, если состояние [[execution-state-machine|FSM]] — `LONG_OPEN`, `OCO_ARMING` или `OCO_ARMED`. В этом случае вызывается [[coordinator-orchestration|`coordinator.flatten()`]], который отменяет живые ордера и продаёт остаток. Если позиции нет — сигнал игнорируется. (`src/runtime/manager.py:363-371`)

**3. Если сигнал «войти» (`LONG`)** — применяется правило одного ордера.

**Правило одного открытого ордера** — бот не открывает новую сделку, если уже есть открытая позиция или незавершённый ордер. Вход разрешён **только из состояния `FLAT`** (нет позиции, нет ожидающих ордеров):

```python
# src/runtime/manager.py:373-379
if state is None or state != ExecutionState.FLAT:
    logger.debug("runtime.signal_skipped_non_flat_state", ...)
    return
```

**4. [[risk-overview-decision-pipeline|Риск-менеджер]] одобряет или отклоняет** (`risk_manager.assess`). Он считает [[position-sizing-kelly|размер позиции]] (сколько купить), уровень тейк-профита и стоп-лосса. Если что-то не так (например, кошелёк слишком мал для минимального [[bybit-filters|лота]]) — возвращает `approved=False` и сигнал отклоняется. (`src/runtime/manager.py:380-387`)

**5. Если одобрено — выставляется брэкет-ордер** ([[coordinator-orchestration|`coordinator.start_bracket`]]). Это пакет из трёх ордеров: вход, тейк-профит и стоп-лосс. Полный путь ордера от сигнала до закрытия — [[order-lifecycle-overview|жизненный цикл ордера]]. (`src/runtime/manager.py:403-408`)

### Перевод кода выхода (`_exit_reason`)

Стратегия может вернуть произвольную строку в качестве причины выхода. Функция `_exit_reason` переводит эту строку в канонический [[reason-codes-assessment-output|код причины]] (`ReasonCode`). Если строка не распознана, используется безопасный запасной вариант `EXIT_SIGNAL_FLIP` — чтобы неизвестная причина не привела к сбою на критическом пути закрытия позиции.

```python
# src/runtime/manager.py:304-317
@staticmethod
def _exit_reason(signal_reason: str) -> ReasonCode:
    try:
        return ReasonCode(signal_reason)
    except ValueError:
        logger.warning("runtime.exit_reason_unmapped", reason=signal_reason)
        return _DEFAULT_EXIT_REASON  # EXIT_SIGNAL_FLIP
```

## Примеры / сценарии

### Сценарий A: нормальный тик без сделки

Время: 14:23:05. Бот просыпается.

1. Стоп-файл `.kill_switch` — нет. Продолжаем.
2. WebSocket: последнее сообщение было 8 секунд назад (< 30 сек). Продолжаем.
3. Демо-режим: `s35_demo_active = False`. Пропускаем проверку порогов.
4. OCO TTL: активных OCO нет. Продолжаем.
5. Запрашиваем биржу: возвращает 2 свечи за последние 2 часа.
   - Свеча 13:00–14:00 закрыта в 14:00 (UTC) → `close_time ≤ now`. Подходит.
   - Свеча 14:00–15:00 закрылась бы в 15:00 → ещё будущее. Отброшена (look-ahead guard).
   - Выбрана свеча 13:00–14:00. Это та же свеча, что и в прошлый тик (14:22:05) → `_last_close_ts` совпадает. Возвращаем `None`.
6. `bar is None` → тик завершён, торговых действий нет.

### Сценарий B: первая новая свеча часа, вход в сделку

Время: 15:00:05. Бот просыпается.

1–4. Все проверки пройдены.
5. Запрашиваем биржу. Свеча 14:00–15:00 только что закрылась (close_time = 15:00:00, now = 15:00:05). `close_ms > _last_close_ts` (был 14:00). Это новая свеча!
6. Проверка качества: цена закрытия = $100 200. Предыдущая была $100 050. Отклонение = 0.15% < 0.5%. Проходит.
7. Стратегия анализирует свечу: RSI пересёк порог снизу, условия входа выполнены → сигнал `LONG`.
8. Текущее состояние FSM: `FLAT` — нет открытых позиций.
9. Риск-менеджер: одобряет вход, qty = 0.002 BTC, TP = $103 000, SL = $98 500.
10. `coordinator.start_bracket(...)` — на биржу уходят ордера. Тик завершён.

### Сценарий C: аварийная остановка по стоп-файлу

Оператор создал файл `.kill_switch` в рабочей директории.

Время: 15:05:05. Бот просыпается.

1. `_maybe_kill_switch()`: файл существует. → `request_halt(KILL_SWITCH_REQUESTED)` — записывает причину остановки в БД и переводит FSM в `HALTED`. `_stopping = True`. Возвращает `True`.

## Формулы и расчёты

### Отклонение цены свечи

```
отклонение (%) = |текущее_close − прошлое_close| / прошлое_close
```

**Что считает:** насколько процентов изменилась цена закрытия по сравнению с предыдущей часовой свечой.

**Наша реализация** (`src/marketdata/quality.py:65-67`):

```python
deviation_pct = abs(current_close - prior) / prior
if deviation_pct > self._threshold_pct:  # default 0.005 (0.5%)
    ...
```

Порог по умолчанию: `0.005` = 0.5%. Задаётся через `runtime_quality_threshold_pct` (`src/platform/config.py:234-241`).

### Время до аварийной остановки по опросу

```
Время до HALT_BAR_POLL_STALL = stall_threshold × poll_cadence_seconds
```

По умолчанию: 24 × 5.0 = **120 секунд** (2 минуты без ответа биржи).

Подтверждено: `src/platform/config.py:210-220`.

## Подводные камни / что важно понимать

**1. Бот торгует только по закрытым свечам.**
Это намеренное ограничение. Незакрытая свеча содержит промежуточные данные, которые изменятся. [[replay-engine-bar-by-bar|Бэктест-система]] тоже использует только закрытые свечи — это гарантирует, что live-торговля и исторические результаты сравнимы («заглядывание в будущее» исключено).

**2. Одна и та же свеча обрабатывается ровно один раз.**
Дедупликация по `_last_close_ts` не даёт стратегии получить один и тот же бар дважды. Без этого за один часовой период (720 тиков: 3600 сек / 5 сек) стратегия могла бы выдать один и тот же сигнал 720 раз. (`src/platform/config.py:210-213`)

**3. Счётчик сбоев не сбрасывается частично.**
При любом успешном ответе биржи `consecutive_failures` сбрасывается в ноль (`src/runtime/bar_source.py:73`). Нет «накопительного» эффекта между разными сессиями связи.

**4. HaltGate активен только в демо-режиме.**
На production-бирже с реальными деньгами `s35_demo_active` должен быть `False`, и проверка порогов DD / потерь пропускается в `_tick`. Это не значит, что бот работает без защиты — другие механизмы ([[circuit-breakers-drawdown-flash|circuit breakers]], kill switch, [[position-sizing-kelly|Kelly-sizing]]) работают всегда.

**5. Базовая цена качества теряется при перезапуске.**
`BarPriceQualityDetector` хранит `_last_close` только в памяти. После перезапуска бота первая свеча всегда пройдёт без проверки (нет базы для сравнения). Это допустимо для v0.1 — риск одного пропущенного аномального бара ниже, чем ложные остановки после перезапуска.

**6. Только один открытый ордер за раз (инвариант).**
Бот никогда не откроет новую сделку, пока есть незакрытая старая. Это упрощает риск-менеджмент и исключает случайное удвоение позиции.

**7. Вход на LONG, выход на FLAT — нет коротких позиций.**
Бот торгует только «купить и держать до сигнала выхода». Короткие позиции (продажа без владения активом) не поддерживаются. Это Bybit Spot — не фьючерсный рынок.
