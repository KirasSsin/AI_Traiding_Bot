# Как бот собирается и запускается (команда run)

**TL;DR:** Одна команда `python -m src run --symbol BTCUSDT` собирает все детали бота в единый рабочий механизм — от настроек и подключения к бирже до стратегии и контроля рисков — и запускает непрерывный торговый цикл. До начала торговли бот обязательно сверяется с биржей, чтобы убедиться, что его внутренний учёт совпадает с реальным.

## Простыми словами

Представьте, что вы открываете автомастерскую каждое утро. Прежде чем принимать клиентов, нужно сделать несколько вещей по порядку: открыть кассу (загрузить настройки), подключить телефон (связь с биржей), поднять ворота (база данных), проверить, закрыты ли все вчерашние счета (сверка с биржей), посадить мастеров на рабочие места (стратегия, риск-менеджер) и запустить систему приёма входящих звонков (WebSocket — канал, по которому биржа присылает информацию о сделках).

Только после того как все детали встали на место и прошла сверка, мастерская открывается и начинает работу.

В боте так же: команда `run` — это «открыть мастерскую». Она создаёт все детали в строго определённом порядке и передаёт управление `RuntimeManager` — диспетчеру, который следит за работой день и ночь (что он делает на каждом [[main-loop-tick|тике главного цикла]] — отдельная страница).

**«Символ»** — это обозначение торговой пары на бирже, например `BTCUSDT` означает «покупаем/продаём Биткоин за USDT (Tether, стабильная монета привязанная к доллару)». Из символа автоматически вычисляется, с какой монетой мы работаем: `BTCUSDT` → базовая монета `BTC` (просто отрезаем последние 4 символа — `USDT` или `USDC`).

## Как это работает у нас

### Шаг 1. Точка входа — разбор команды

Запуск: `python -m src run --symbol BTCUSDT`.

Функция `main()` (`src/__main__.py:900-908`) читает аргументы командной строки и передаёт управление нужной подкоманде. Разбором аргументов занимается `_build_parser()` (`src/__main__.py:819-897`), которая настраивает несколько подкоманд: `run`, `backfill`, `reconcile-only`, `kill`, `wfa`, `monitor`. По умолчанию символ — `BTCUSDT`.

```bash
python -m src run --symbol BTCUSDT
```

Для подкоманды `run` вызывается функция `_cmd_run(args)` (`src/__main__.py:70-226`).

### Шаг 2. Сборка зависимостей — «конвейер из деталей»

Это самый важный шаг. Здесь происходит **сборка (Dependency Injection)** — процесс, когда каждый модуль получает именно то, что ему нужно для работы, и ничего лишнего. Подобно тому, как механик получает ключ нужного размера, а не весь ящик инструментов.

Сборка идёт строго в порядке зависимостей (`src/__main__.py:94-217`):

#### 2.1. Загрузка настроек и вычисление базовой монеты

```python
settings = Settings()                    # src/__main__.py:94
symbol = args.symbol                     # например, "BTCUSDT"
base_coin = symbol[:-4] if symbol.endswith(("USDT", "USDC")) else symbol
# BTCUSDT → BTC, BTCUSDC → BTC         # src/__main__.py:96-97
```

`Settings` — это контейнер всех [[configuration-and-settings|настроек]] (ключи API, флаги тестовой сети, пути к файлам). Читается из переменных окружения.

#### 2.2. База данных

```python
init_db(settings.db_path, mig_dir)      # src/__main__.py:101 — создаёт таблицы если их нет
conn = connect(settings.db_path)        # src/__main__.py:102 — SQLite-соединение
```

`init_db` применяет миграции и создаёт таблицы; подробнее об устройстве [[storage-and-database|хранилища бота]] (какие таблицы, почему деньги хранятся в целых числах) — отдельная страница.

#### 2.3. REST-клиент (подключение к бирже по HTTP) и фильтры инструмента

**REST-клиент** ([[bybit-rest-client-and-backoff|`BybitRESTClient`]]) — это модуль для отправки команд на биржу (выставить ордер, запросить цену) по обычному HTTP-запросу, с защитой от превышения лимитов частоты запросов. Аналогия: позвонить в банк по телефону.

**Фильтры инструмента** ([[bybit-filters|`BybitFilters`]]) — правила биржи для конкретной пары: минимальный размер ордера, шаг округления цены и объёма. Сейчас используются заглушки-плейсхолдеры; в будущем (S12+) будут загружаться с биржи автоматически (`src/__main__.py:104-121`).

Критически важный момент: REST-клиент и WebSocket-потребитель строятся из **одной и той же пары** флагов `(testnet, demo)` — это гарантирует, что ордера (через REST) и подтверждения сделок (через WS) не окажутся в разных «вселенных» биржи. Нарушение этого правила — тихая денежная ошибка BYBIT-01, закрытая в S55 (`src/__main__.py:105-113`).

#### 2.4. Адаптер биржи

```python
adapter = BybitMarketAdapter(rest=rest, filters=filters)   # src/__main__.py:122
```

**[[bybit-order-adapter|Адаптер биржи]]** — посредник, который переводит команды бота (например, «купи 0.001 BTC») в формат, понятный API биржи, и обратно. Как переводчик между двумя разными языками.

#### 2.5. Вычисление «возраста состояния» для самовосстановления

```python
bar_interval = "60"    # 1 час — интервал свечей для команды run
heal_age = _derive_heal_max_age_seconds(settings, bar_interval)   # src/__main__.py:127
```

При перезапуске после сбоя бот находит в базе данных последнее сохранённое состояние. Но если оно очень старое — например, бот не работал несколько недель — ему нельзя доверять: рынок за это время мог многое изменить. Функция `_derive_heal_max_age_seconds` (`src/__main__.py:251-278`) вычисляет, насколько «свежим» должно быть старое состояние, чтобы бот мог его восстановить, а не паниковать.

**Логика (из кода):**
- Если `settings.heal_max_bars` задан (по умолчанию `1`), то `heal_age = heal_max_bars × секунд_в_интервале`. Для интервала `"60"` (1 час) → 1 × 3600 = **3600 секунд** (`src/__main__.py:262-278`).
- Если `heal_max_bars = None` (устаревший режим), используется `settings.heal_max_age_seconds` напрямую (по умолчанию `3600`).

Смысл простыми словами: «Если состояние старше 1 бара (1 часа), не пытайся его восстановить — лучше остановись и жди оператора».

#### 2.6. Хранилище состояния, Reconciler, Coordinator

```python
repo = ExecutionStateRepo(conn)          # src/__main__.py:128 — хранилище в SQLite
reconciler = Reconciler(...)             # src/__main__.py:129-134
coordinator = Coordinator(...)           # src/__main__.py:135-141
```

- **Хранилище состояния** ([[execution-state-persistence-and-halt-audit|`ExecutionStateRepo`]]) — база данных внутри бота: помнит, в каком состоянии находится каждая сделка (открыта, закрыта, ожидает исполнения).
- **Reconciler** — модуль [[reconcile-as-truth|сверки]]: при старте сравнивает то, что записано у нас в базе, с тем, что реально есть на бирже. Если расхождение — либо восстанавливает, либо сигнализирует об ошибке (принцип «биржа всегда права»).
- **[[coordinator-orchestration|Coordinator]]** — главный диспетчер сделок: через него проходят все операции с ордерами (открыть, закрыть, выставить стоп).

#### 2.7. Выбор стратегии

Здесь происходит ключевой выбор стратегии — в зависимости от настройки `s35_demo_active` (`src/__main__.py:147-163`). По умолчанию в демо-режиме запускается [[mean-reversion-strategy|стратегия возврата к среднему]] (RSI + полосы Боллинджера):

**Если `s35_demo_active = True` (демо-режим):**
```python
strategy = MeanReversionRsiBBStrategy.from_locked_s17_params(symbol=symbol)
```
Используются **замороженные (LOCKED) параметры**, проверенные и одобренные в ходе анализа Монте-Карло (p=0.018):
- `rsi_period=14`, `rsi_oversold=35`, `rsi_overbought=65`
- `bb_period=20`, `bb_std_mult=1.5`
- `and_gate_required=True`

(`src/signalgen/mean_reversion_strategy.py:43-51`)

**Если `s35_demo_active = False` (обычный режим):**
```python
strategy = MeanReversionRsiBBStrategy(
    symbol=symbol,
    rsi_period=settings.strategy_rsi_period,
    ...
)
```
Параметры берутся из `Settings` — конфигурации оператора.

**Почему LOCKED-параметры важны:** демо-режим работает с реальными деньгами на тестовой сети. Если оператор случайно укажет неверные параметры в конфиге, бот всё равно будет использовать проверенные значения — это защита от ошибки конфигурации.

#### 2.8. Риск-менеджер

```python
risk_manager = RiskManager(conn=conn, settings=settings, symbol=symbol)
# src/__main__.py:165
```

**[[risk-overview-decision-pipeline|Риск-менеджер]]** — «контролёр», который решает, разрешить ли конкретную сделку: проверяет размер позиции, допустимые потери, корректирует объём покупки.

#### 2.9. Источник свечей и WebSocket

```python
bar_source = BarSource(adapter=rest, symbol=symbol, interval=bar_interval)
# src/__main__.py:168
```

**[[bar-source-live|Источник свечей]]** (`BarSource`) — модуль, который регулярно запрашивает у биржи последнюю закрытую свечу (OHLCV — цена открытия, максимум, минимум, закрытия, объём торгов) с защитой от look-ahead. Это «пульс» бота: каждые 5 секунд (по умолчанию) опрашивается биржа, есть ли новая закрытая свеча.

```python
ws_consumer = BybitPrivateWSConsumer(
    api_key=..., api_secret=..., endpoint=ws_endpoint,
    coordinator=coordinator, reconciler=reconciler, fill_recorder=fill_recorder,
    testnet=settings.testnet, demo=settings.demo,
)
# src/__main__.py:182-191
```

**[[bybit-private-websocket|WebSocket-потребитель]]** — постоянный приватный канал с биржей для получения мгновенных уведомлений о сделках (например, «ордер исполнен») и изменении баланса. Аналогия: если REST — это «позвонить в банк», то WebSocket — это «банк сам звонит, когда что-то произошло».

#### 2.10. Стартовый баннер в логах

Сразу после сборки бот записывает в лог строку `bybit.env_resolved` с тремя ключевыми параметрами (`src/__main__.py:195-203`). Поскольку [[logging-and-observability|логирование]] настроено через `structlog.processors.JSONRenderer()` (`src/platform/logging.py:26`), весь вывод — только JSON:

```json
{"event": "bybit.env_resolved", "testnet": true, "demo": false, "rest_host": "https://api-testnet.bybit.com", "ws_endpoint": "wss://stream-testnet.bybit.com/v5/private", "level": "info", "timestamp": "2026-06-27T10:00:00Z"}
```

Поле `rest_host` содержит полный URL с протоколом (`https://`), поскольку именно так его возвращает `pybit` (`rest.endpoint`).

Это позволяет оператору сразу увидеть в первых строках лога: **куда реально пойдут ордера**. Разные пары `(testnet, demo)` дают разные «вселенные» биржи — подробный разбор [[run-modes-testnet-live-reconcile|режимов запуска]] (TESTNET, демо-мейннет, реальная торговля) в отдельной странице:

| testnet | demo | REST-хост | WS-хост |
|---------|------|-----------|---------|
| `True` | `False` | api-testnet | stream-testnet (тестовая сеть) |
| `False` | `True` | api-demo | stream-demo (бумажная торговля на mainnet) |
| `True` | `True` | api-demo-testnet | stream-demo-testnet |
| `False` | `False` | api | stream (**MAINNET — реальные деньги!**) |

(`src/__main__.py:229-248`)

#### 2.11. RuntimeManager — диспетчер процесса

```python
rm = RuntimeManager(
    coordinator=coordinator, reconciler=reconciler, ws_consumer=ws_consumer,
    bar_source=bar_source, strategy=strategy, risk_manager=risk_manager,
    settings=settings, shared_deps=risk_manager.shared_deps,
)
# src/__main__.py:208-217
```

**RuntimeManager** — главный диспетчер, который владеет жизненным циклом процесса: запуск, главный цикл, корректное завершение.

### Шаг 3. Запуск и коды завершения

```python
try:
    rm.run()
    return 0         # всё нормально
except KeyboardInterrupt:
    return 130       # Ctrl+C в узком окне ДО главного цикла
except Exception as e:
    print(f"ERROR: runtime crash: {e}", ...)
    return 1         # аварийный сбой
# src/__main__.py:219-226
```

Процесс завершается с **кодом выхода** (числом, которое операционная система читает после завершения программы):
- `0` — чистое завершение (в том числе после Ctrl+C в главном цикле — см. ниже)
- `130` — Ctrl+C во время **начального запуска** (bootstrap или открытие WebSocket), до того как главный цикл начал работу; стандарт POSIX для SIGINT
- `1` — необработанная ошибка / авария

**Почему Ctrl+C в главном цикле даёт код 0, а не 130:**
`RuntimeManager.run()` перехватывает `KeyboardInterrupt` изнутри (`src/runtime/manager.py:138-140`) — вызывает `_shutdown("KEYBOARD_INTERRUPT")` и завершается нормально. Внешний `except KeyboardInterrupt: return 130` в `_cmd_run` (`src/__main__.py:222-223`) не срабатывает. Поэтому `rm.run()` возвращает `None`, следующая строка `return 0` выполняется, и процесс завершается чисто. Код `130` реален только если Ctrl+C прилетает в узкое окно ещё до входа в `_main_loop` (например, во время `bootstrap()` или `ws_consumer.start()`).

### Шаг 4. Жизненный цикл RuntimeManager.run()

Внутри `rm.run()` (`src/runtime/manager.py:106-152`) происходит следующее:

#### 4.1. Удаление старого стоп-файла

```python
if self._kill_switch_path.exists():
    self._kill_switch_path.unlink()
# src/runtime/manager.py:117-118
```

**Стоп-файл** (`.kill_switch`) — файл-сигнал [[kill-switch-emergency-stop|аварийного стопа]], который оператор может создать чтобы мгновенно остановить бота. Если такой файл остался с прошлого сеанса, бот удаляет его при старте — иначе он сразу же снова остановится.

#### 4.2. Bootstrap (сверка с биржей) — СТРОГО ПЕРВЫМ

```python
self._coordinator.bootstrap()
# src/runtime/manager.py:121
```

**Bootstrap (первоначальная [[reconcile-as-truth|сверка]])** — проверка соответствия внутреннего учёта бота и реального состояния на бирже. Идёт СТРОГО до открытия WebSocket и до торгового цикла. Если bootstrap провалился (не удалось сверить данные) — вся последовательность прерывается, WebSocket не запускается, торговля не начинается.

Зачем это нужно: представьте, что бот упал посреди открытой позиции. При перезапуске он должен выяснить — позиция ещё открыта? Ордер уже исполнился? Только после честного ответа на эти вопросы можно продолжать. Иначе бот может выставить двойной ордер или не заметить уже случившуюся сделку.

#### 4.3. Стартовый баннер демо-режима (если активен)

Если `s35_demo_active = True`, в лог записывается баннер с параметрами защиты: одобренные символы, пороги остановки по просадке, лимиты убытков (`src/runtime/manager.py:122-134`).

#### 4.4. Запуск WebSocket

```python
self._ws_consumer.start()
# src/runtime/manager.py:135
```

Только после успешного bootstrap открывается постоянный канал с биржей для получения уведомлений о сделках.

#### 4.5. Главный цикл (_main_loop)

```python
while not self._stopping:
    self._tick()
    time.sleep(self._settings.runtime_bar_poll_cadence_seconds)
# src/runtime/manager.py:158-160
```

Цикл работает непрерывно с паузой между итерациями (`runtime_bar_poll_cadence_seconds`, по умолчанию **5.0 секунды**, `src/platform/config.py:210-212`).

Каждый [[main-loop-tick|«тик»]] (`_tick`, `src/runtime/manager.py:162-178`) выполняет по порядку:
1. **Проверка стоп-файла** — если `.kill_switch` появился, остановка.
2. **Проверка WebSocket** — если канал молчит дольше `runtime_ws_check_alive_max_silence` (по умолчанию **30.0 секунды**), считается отключённым.
3. **[[halt-gate-precommitted-criteria|HaltGate]]** (только в демо-режиме) — проверка заранее оговорённых ограничителей риска по просадке, убыткам, времени без сделок.
4. **OCO-таймер** — проверяет, не завис ли брекет-ордер в состоянии «вооружается» дольше `oco_arming_ttl_seconds` (по умолчанию **60 секунд**).
5. **Опрос свечи и стратегии** — запрос новой свечи, обработка стратегией, оценка риска, выставление ордера.

#### 4.6. Корректное завершение (_shutdown)

При остановке (через Ctrl+C, стоп-файл или ошибку) вызывается `_shutdown()` (`src/runtime/manager.py:410-445`):
- Идемпотентна (можно вызвать несколько раз — сработает только один раз)
- Останавливает WebSocket (best-effort: ошибка при остановке WS логируется, но не перебрасывается)
- Записывает в лог событие `runtime.shutdown` с причиной и количеством незавершённых ордеров

## Примеры / сценарии

### Сценарий A: Обычный запуск

```text
Оператор: python -m src run --symbol BTCUSDT

1. _cmd_run читает настройки из .env
2. Создаёт подключение к SQLite: trading.db
3. Строит REST-клиент → https://api-testnet.bybit.com
4. Лог: {"event": "bybit.env_resolved", "testnet": true, "demo": false, "rest_host": "https://api-testnet.bybit.com", "ws_endpoint": "wss://stream-testnet.bybit.com/v5/private", ...}
5. Выбирает стратегию: s35_demo_active=True → LOCKED параметры (rsi_oversold=35, bb_std_mult=1.5)
6. RuntimeManager.run():
   - Удаляет .kill_switch (если был)
   - coordinator.bootstrap() → сверка с биржей: нет открытых позиций → OK
   - ws_consumer.start() → подключился к stream-testnet.bybit.com
   - Лог демо-баннера: approved_symbols=[BTCUSDT], dd_intraday=0.20, ...
   - Входит в главный цикл: каждые 5 секунд — тик
7. На 3-м тике: новая свеча → стратегия выдаёт сигнал LONG → риск-менеджер одобряет → coordinator.start_bracket()
8. Оператор нажимает Ctrl+C в главном цикле → RuntimeManager.run() перехватывает KeyboardInterrupt (manager.py:138-140) → _shutdown("KEYBOARD_INTERRUPT") → run() возвращает None → _cmd_run выполняет return 0 → код выхода 0
```

### Сценарий B: Перезапуск после сбоя с незакрытой позицией

```text
1. Бот упал час назад — в базе осталась запись: "LONG_OPEN, ордер #123"
2. Запуск: python -m src run --symbol BTCUSDT
3. coordinator.bootstrap(): состояние в базе свежее (< 1 бара = 3600 секунд)
4. Reconciler запрашивает биржу: ордер #123 — исполнен час назад
5. Bootstrap обновляет состояние в базе до реального → OK
6. Продолжает работу уже со знанием, что позиция закрыта
```

### Сценарий C: Остановка через стоп-файл

```text
Другой терминал: python -m src kill
→ Создаёт файл .kill_switch (атомарно, права 0o600)

На следующем тике RuntimeManager:
→ _maybe_kill_switch(): файл существует → request_halt(KILL_SWITCH_REQUESTED) → _stopping=True → возвращает True (manager.py:286-295)
→ цикл while завершается (self._stopping=True) → run() уходит в ветку else → _shutdown("NORMAL_EXIT") → WS закрыт → код выхода 0

Важный нюанс: `request_halt` вызывается с кодом `KILL_SWITCH_REQUESTED` (именно с этим кодом фиксируется причина остановки в базе данных), но `_shutdown()` получает `"NORMAL_EXIT"` — потому что цикл завершился штатно, без исключения.
```

## Подводные камни / что важно понимать

**1. Bootstrap — не просто формальность, а защита от двойных ордеров.**
Без bootstrap после перезапуска бот не знает: может, он уже купил BTC? И выставит ещё один ордер. Поэтому bootstrap идёт строго первым и при неудаче полностью блокирует запуск. (`src/runtime/manager.py:120-121`)

**2. REST и WebSocket должны быть в одной «вселенной» биржи.**
Если REST-клиент настроен на тестовую сеть, а WebSocket — на mainnet (или наоборот), бот будет выставлять ордера в одном месте, а подтверждения получать из другого. Это тихая ошибка: видимых сбоев нет, но сделки не работают. Защита реализована в S55 (BYBIT-01): оба клиента строятся из одной пары `(testnet, demo)`. (`src/__main__.py:105-113`, `src/__main__.py:177-191`)

**3. LOCKED параметры нельзя изменить через конфиг в демо-режиме.**
Когда `s35_demo_active=True`, параметры стратегии берутся из `MEAN_REVERSION_S17_RELAXED_PARAMS` — иммутабельного словаря (`MappingProxyType`). Это сделано намеренно: демо-режим торгует реальными деньгами на тестовой сети, и случайное изменение конфига не должно сломать проверенную логику. (`src/signalgen/mean_reversion_strategy.py:40-52`)

**4. Фильтры инструмента сейчас — заглушки.**
`BybitFilters` в `_cmd_run` создаётся с хардкодными значениями (шаг цены 0.01, минимальный объём 0.00001 BTC). Это временно до S12+, когда они будут загружаться с биржи автоматически. Для реальной торговли нужно убедиться, что эти значения соответствуют актуальным правилам биржи для выбранного символа. (`src/__main__.py:114-121`)

**5. Главный цикл — однопоточный; WebSocket — в отдельном потоке.**
Свечи и стратегия обрабатываются в главном потоке последовательно. Уведомления с биржи (исполнение ордеров) приходят через WebSocket в параллельном потоке. Координация между ними защищена блокировками внутри `Coordinator`. Это значит: пока бот обрабатывает свечу, уведомление об исполнении не потеряется — оно подождёт и будет обработано сразу после.

**6. Порог «молчания» WebSocket — 30 секунд по умолчанию.**
Если биржа ничего не присылает по WebSocket дольше 30 секунд, бот считает соединение разорванным. Не путайте с REST-опросом свечей (каждые 5 секунд) — это разные каналы. (`src/platform/config.py:226-229`)

**7. Метод `days // 30` для вычисления «месяцев без сделок» — приближение.**
HaltGate при расчёте числа месяцев без сделок использует целочисленное деление `days // 30`. Февраль считается как 28-29 дней, что может дать небольшую погрешность в пограничных случаях. Это намеренное упрощение, задокументированное в коде. (`src/runtime/manager.py:250-254`)
