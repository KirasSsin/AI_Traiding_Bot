# История запусков — как читать и сравнивать прошлые бэктесты

**TL;DR:** вкладка HISTORY показывает все ранее запущенные бэктесты в одной таблице. Кликните по строке — раскроется подробная карточка с балансом, win rate и объяснением вердикта человеческими словами. Это одна из вкладок [[dashboard-overview|дашборда]].

## Простыми словами

Представьте себе журнал экспериментов в лаборатории. Каждый раз, когда учёный проводит опыт, он записывает результат в журнал с датой, условиями и выводом. Потом можно открыть журнал, сравнить эксперименты за разные периоды и понять, что сработало, а что нет.

Вкладка HISTORY — это именно такой журнал для наших бэктестов. Каждый раз, когда вы запускаете бэктест (проверку стратегии на исторических данных — см. [[run-backtest-form]]), результат автоматически сохраняется на диск. Потом на вкладке HISTORY вы видите весь список: какую стратегию тестировали, на каком инструменте, с каким результатом и что вынес «суд» — зелёный PASS или красный FAIL.

Одним кликом по строке таблицы раскрывается карточка с подробностями: начальный и итоговый баланс, процент выигрышных сделок, общий результат в долларах, и главное — объяснение вердикта по-русски, без терминов.

Никакого ручного сохранения не требуется — бот кеширует (запоминает и хранит) результаты сам.

## Как это работает у нас

### Откуда берётся список запусков

При открытии вкладки браузер обращается к серверу: `GET /api/runs`. Сервер вызывает функцию `list_runs()`, которая сканирует папку `data/runs/` в корне проекта и читает все файлы `*.json`. Файлы отсортированы по времени изменения — самый свежий запуск идёт первым. (src/dashboard/backtest_runner.py:1469–1489)

Из каждого JSON-файла извлекаются поля для таблицы: `run_id`, `request` (стратегия/символ/интервал/даты), `verdict`, `metrics`, `warnings_count`. Полная структура ответа остаётся на диске и загружается только при клике по строке.

### Как формируется идентификатор run_id

Каждый запуск получает уникальный идентификатор — **run_id**. Это первые 16 символов SHA-256-хеша строки вида `strategy_id|symbol|interval|start|end`. (src/dashboard/backtest_runner.py:857–859)

```python
def run_id(self) -> str:
    s = f"{self.strategy_id}|{self.symbol}|{self.interval}|{self.start}|{self.end}"
    return hashlib.sha256(s.encode()).hexdigest()[:16]
```

Простыми словами: если вы запускаете одну и ту же стратегию на одних и тех же данных дважды — run_id будет одинаковый, и бот вернёт результат из кеша (диска), не пересчитывая заново. Это экономит время. Если хотя бы один параметр изменился (другой диапазон дат, другой интервал) — получится другой run_id и будет запущен новый расчёт.

Результат сохраняется в файл `data/runs/<run_id>.json`. (src/dashboard/backtest_runner.py:316–918)

### Таблица: что означают колонки

Таблица имеет 10 колонок (9 информационных + 1 кнопка раскрытия). Реальные заголовки из кода (src/dashboard_react/src/components/tabs/HistoryTab.tsx:248–257):

| Колонка в UI | Что показывает |
|---|---|
| STRATEGY | Название стратегии (например, «ATR Breakout») |
| SYMBOL | Торговая пара (например, BTCUSDT) |
| TF | Таймфрейм — интервал свечей (1h, 4h и т. д.) |
| RANGE | Диапазон дат теста (начало…конец) |
| VERDICT | Итоговый вердикт, выделен цветом |
| SHARPE / T1 | Sharpe-коэффициент: RAW-запуск — общий Sharpe; WFA-запуск — OOS Sharpe (T1) |
| N TRADES / T5 | Количество сделок: RAW — всего; WFA — T5 (OOS-trades floor) |
| PnL % / DSR | RAW — итоговый PnL в процентах; WFA — DSR (Deflated Sharpe Ratio) |
| MC P | p-значение Monte Carlo (только для WFA; для RAW всегда «—») |
| ▸ / ▾ | Кнопка раскрытия карточки деталей |

#### Почему одна колонка показывает разные вещи для RAW и WFA

Бот поддерживает два режима тестирования: **исследовательский** (RAW) и **дисциплинированный** (WFA). Подробнее о разнице — в [[wfa-methodology]] и [[verdict-and-warnings]].

Для исследовательских запусков (вердикт `RAW` или `RAW_PRETRAIN_LEAKAGE_SUSPECTED`) в таблице отображаются простые сводные метрики: общий Sharpe, суммарное количество сделок и процент доходности. Для WFA-запусков — строгие критерии: T1 (OOS Sharpe по фолдам), T5 (количество OOS-сделок) и DSR. Полная расшифровка критериев T1–T6 и разницы между блокирующими и информационными метриками — в [[metrics-table-tiers]]. (src/dashboard_react/src/components/tabs/HistoryTab.tsx:264–283)

Логика в коде:
```typescript
const isRaw = isResearchVerdict(run.verdict)
const sharpeCell = isRaw ? fmt(m.sharpe ?? run.sharpe, 2) : fmt(m.t1_sharpe_oos, 2)
const nTradesVal = isRaw ? (m.n_trades ?? run.n_trades) : m.t5_n_trades
const pnlCell   = isRaw
  ? `${fmt(m.total_pnl_pct ?? run.total_pnl_pct, 1)}%`
  : fmt(run.dsr, 3)
const mcCell = isRaw ? '—' : fmt(run.mc_p_value, 3)
```

### Цвета вердиктов: что каждый означает

Вердикт в таблице окрашен в один из четырёх цветов — функция `verdictCellClass()` (src/dashboard_react/src/components/tabs/HistoryTab.tsx:22–38):

| Цвет | Вердикт(ы) | Смысл |
|---|---|---|
| Зелёный | `WFA_PASS`, `PASS` | Стратегия прошла все обязательные проверки |
| Оранжевый | `RAW`, `RAW_PRETRAIN_LEAKAGE_SUSPECTED` | Исследовательский запуск, не дисциплинированный WFA |
| Жёлтый | `WFA_FAIL_DATA` | Провал из-за нехватки данных (мало сделок или фолдов) |
| Красный | `WFA_FAIL`, `FAIL` | Провал по содержательным критериям |

Важный нюанс: `RAW` — **не красный**. Это намеренное решение (комментарий в коде: «S55 DASH-04: research verdicts use raw (non-red-fail) styling»). Исследовательский запуск — это не «провал», а просто другой режим без WFA-дисциплины.

Рядом с текстом вердикта отображается бейдж `WfaFailBadge` — небольшая таблетка-метка. Она появляется только для `WFA_FAIL` (красная, подпись «WFA FAIL») и `WFA_FAIL_DATA` (жёлтая, подпись «WFA FAIL · DATA»). Для PASS и RAW бейдж не отображается. (src/dashboard_react/src/components/shared/WfaFailBadge.tsx:12–35)

### Раскрытие карточки деталей (accordion)

**Accordion** — это элемент интерфейса, который при клике «раскрывается», как папка в проводнике. Здесь — при клике по строке таблицы.

Работает так (src/dashboard_react/src/components/tabs/HistoryTab.tsx:190–207):

1. Пользователь кликает строку — вызывается `handleRowClick(runId)`.
2. Если строка уже раскрыта — она закрывается. Если закрыта — открывается.
3. Если подробные данные для этого run_id ещё не загружены, браузер делает запрос `GET /api/runs/{run_id}`. Данные кешируются в памяти на время сессии (`expandedDetails`), так что второй клик по той же строке не делает повторный запрос.
4. В любой момент открыта максимум одна строка («single-open», требование архитектора C4).
5. Нажатие клавиши **ESC** закрывает открытую карточку.

Карточка состоит из кнопки «✕ закрыть» вверху, потом шести числовых показателей в сетке и текстового резюме внизу.

### RunDetailsPanel: что показывает карточка

Функция `RunDetailsPanel` (src/dashboard_react/src/components/tabs/HistoryTab.tsx:107–156) показывает шесть показателей:

| Показатель | Откуда берётся |
|---|---|
| Начальный баланс | `trade_stats.initial_balance_quote`, по умолчанию $10 000 |
| Итоговый баланс | `trade_stats.final_balance_quote`, если есть; иначе `initial × (1 + pnl_pct/100)` |
| Win rate | Доля выигрышных сделок в процентах |
| Lose rate | 100% − win rate |
| Total PnL | Абсолютная сумма прибыли/убытка в долларах и процентах |
| Profit Factor | Сумма прибылей / сумма убытков (отображается только если поле не пустое) |

**Profit Factor** (коэффициент прибыльности) — соотношение общей суммы прибылей к общей сумме убытков. Если он равен 1.5 — это значит, что на каждый потерянный доллар стратегия заработала 1 доллар 50 центов. Больше 1 — стратегия в плюсе. Те же показатели (win rate, PnL, profit factor) подробно разбираются на странице [[trade-statistics]].

Под числами — блок `summary` с человекочитаемым объяснением вердикта.

### Текстовое объяснение вердикта: функция renderSummary

Функция `renderSummary()` (src/dashboard_react/src/components/tabs/HistoryTab.tsx:61–105) формирует абзац по-русски в зависимости от вердикта:

- **PASS / WFA_PASS:** «Стратегия "{название}" сработала: пройдены все обязательные acceptance gates. Win rate X%, total PnL Y%. Strategy показала статистически значимый edge.»
- **FAIL / WFA_FAIL:** «Стратегия "{название}" не прошла WFA discipline. Provoking criterion: {первый провальный критерий}. Total PnL X%, win rate Y%. Использовать в live НЕ рекомендуется — см. Glossary вкладку для деталей.»
- **WFA_FAIL_DATA:** «Стратегия "{название}" не прошла из-за недостатка данных (n_trades < 50 OR fold count < 5). Не статистически значимый результат. Требуется больше OOS sample data.»
- **RAW:** «Стратегия "{название}" — full-period backtest без WFA discipline. ... Подвержен look-ahead bias. Не basis для live decisions.»
- **RAW_PRETRAIN_LEAKAGE_SUSPECTED:** «Стратегия "{название}" — exploratory Kronos ML результат, НЕ failed WFA gate. ... Подозревается pretrain data leakage. Не basis для live decisions — research-only, требует honest OOS валидации.»

Название стратегии берётся из `details.request.strategy_label ?? details.request.strategy_id`. Первый провальный критерий — первый элемент массива `failed_criteria`, например `"dsr_threshold"` или `"mc_gate"`. Полный перечень этих критериев и их пороги описаны в [[acceptance-gates-t1-t6]].

### Защита от взлома: валидация run_id

Когда пользователь кликает по строке и браузер запрашивает `GET /api/runs/{run_id}`, сервер должен открыть файл `data/runs/{run_id}.json`. Теоретически злоумышленник мог бы попробовать передать в качестве run_id что-то вроде `../../../etc/passwd` — и прочитать произвольный файл на сервере. Это называется **path traversal** (обход пути) — атака, при которой злоумышленник выходит за пределы разрешённой директории.

Защита реализована так: перед любым обращением к файловой системе run_id проверяется регулярным выражением `\A[a-f0-9]{16}\Z` (src/dashboard/backtest_runner.py:322–327). Это означает: ровно 16 символов, только строчные шестнадцатеричные цифры (0-9 и a-f). Если хотя бы один символ не подходит — функция `get_run()` сразу возвращает `None`, сервер отвечает 404, никакой файл не открывается. (src/dashboard/backtest_runner.py:1492–1499)

## Примеры / сценарии

### Сценарий 1: первый бэктест, пустая история

Вы только что установили дашборд. Переходите на вкладку HISTORY — видите сообщение «NO RUNS · execute first backtest above». Это значит, что в папке `data/runs/` нет ни одного JSON-файла.

### Сценарий 2: три запуска, сравниваем результаты

Вы запустили три бэктеста:
- ATR Breakout на BTCUSDT 1h за 2024 год → `WFA_PASS`, зелёный
- Volume Breakout на ETHUSDT 4h за 2024 год → `RAW`, оранжевый (это исследовательская стратегия)
- ATR Breakout на SOLUSDT 1h за 2024 год → `WFA_FAIL`, красный (провал по DSR)

Таблица показывает все три строки, свежий запуск — первым. Кликаете по провальной строке SOLUSDT — раскрывается карточка. В поле «Total PnL» — минус 8% красным цветом. В текстовом блоке написано: «Стратегия "ATR Breakout" не прошла WFA discipline. Provoking criterion: dsr_threshold. ...».

### Сценарий 3: повторный запуск тех же параметров

Вы снова нажимаете «Запустить» для ATR Breakout на BTCUSDT 1h 2024 — те же параметры. run_id будет тем же самым (хеш от одних и тех же входных данных одинаков). Сервер найдёт файл в кеше и вернёт его мгновенно, не запуская расчёт заново. В карточке появится признак `cached: true` в API-ответе (в самом UI этот флаг не отображается явно, но время ответа будет почти мгновенным).

### Сценарий 4: ESC закрывает карточку

Вы открыли карточку для одного запуска, читаете. Хотите быстро закрыть — нажимаете ESC. Карточка закрывается. Нажимаете на другую строку — открывается карточка для неё (предыдущая автоматически закрыта, так как одновременно может быть открыта только одна).

## Подводные камни / что важно понимать

**RAW — это не провал.** Оранжевый цвет не означает «плохо». `RAW` просто значит, что запуск был исследовательским, без строгой WFA-дисциплины. Такие результаты могут выглядеть привлекательно (высокий PnL), но они подвержены look-ahead bias (смотри [[verdict-and-warnings]]). Использовать их как основание для торговли нельзя.

**WFA_FAIL_DATA — стратегия не виновата.** Жёлтый вердикт означает техническую проблему с данными: слишком мало сделок (n_trades < 50) или слишком мало фолдов (< 5 окон WFA). Попробуйте расширить диапазон дат или выбрать более короткий таймфрейм — это даст больше баров и сделок.

**Кеш не имеет срока жизни.** В браузере данные о раскрытых карточках хранятся только на время текущей сессии (закрыли вкладку — данные пропали, и при следующем клике снова пойдёт запрос к серверу). Файлы на диске (`data/runs/*.json`) хранятся бессрочно — их можно удалить вручную, если нужно освободить место или принудительно пересчитать.

**Одновременно открыта только одна карточка.** Это архитектурное требование (single-open accordion). Нельзя сравнить две раскрытые карточки бок о бок в таблице — для сравнения двух запусков используйте другие вкладки дашборда или смотрите данные последовательно.

**Profit Factor отсутствует, если нет убытков.** Если в тесте все сделки прибыльные, `profit_factor` будет бесконечным — поле в карточке просто не отображается (блок рендерится только при `profitFactor !== null && profitFactor !== undefined`). (src/dashboard_react/src/components/tabs/HistoryTab.tsx:145)

**Последний запуск — первым.** Список отсортирован по времени изменения файла на диске (mtime), от нового к старому. Это значит, что если вы загрузили кешированный результат (без пересчёта), его mtime не обновляется — он останется на том же месте в списке.

**`RAW_PRETRAIN_LEAKAGE_SUSPECTED`** — особый вердикт для Kronos ML-стратегии (см. [[kronos-ml-strategy]]). Он означает не провал, а честное предупреждение: модель могла обучиться на данных, которые частично пересекаются с тестовым периодом (предобучение ML-модели могло включать «будущие» для теста данные). Такой результат непригоден как основание для принятия торговых решений.
