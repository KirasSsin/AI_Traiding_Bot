# Кеширование результатов и безопасность запросов

**TL;DR:** Дашборд сохраняет результаты бэктестов в файлы на диске — если вы нажали «Запустить» с теми же параметрами, результат возвращается мгновенно из сохранённого файла. Перед любым запросом система проверяет входные данные по строгим правилам, чтобы никто не мог обмануть бота и заставить его читать посторонние файлы.

## Простыми словами

Представьте, что вы звоните в справочную службу с вопросом «Какой курс доллара?». Оператор находит ответ, записывает его в блокнот рядом с вашим вопросом. Когда вы звоните снова с тем же вопросом через час — оператор просто смотрит в блокнот: незачем тратить время на поиск заново.

Именно так работает **кеш** в нашем дашборде. Слово «кеш» (cache) переводится как «заначка» или «хранилище» — место, где хранятся готовые ответы. [[what-is-backtest-overview|Бэктест]] (проверка стратегии на исторических данных) занимает несколько секунд или минут. Если вы запустили расчёт для одной и той же стратегии с теми же датами — незачем считать заново: ответ уже лежит на диске.

**Зачем нужна безопасность?** Дашборд — это веб-сервис: он слушает запросы из браузера по адресу `http://127.0.0.1:8000`. Любой запрос содержит параметры, которые пользователь вводит вручную — например, название актива (BTCUSDT). Если вовремя не проверить этот параметр, злоумышленник теоретически мог бы подсунуть специальную строку вроде `../../etc/passwd`, которая при наивной обработке приведёт к чтению посторонних файлов на диске. Это называется **атака обходом пути** (path traversal). Наш код ставит несколько заслонов прямо на входе, ещё до того, как параметр попадает в файловую систему.

## Как это работает у нас

### Шаг 1. Валидация входных данных на входе

Когда браузер отправляет запрос «Запустить бэктест», он передаёт несколько полей: стратегию, символ (например BTCUSDT), таймфрейм, даты начала и конца. Все они попадают в класс `BacktestPayload` и проходят три проверки до того, как хоть что-то произойдёт.

**Проверка 1 — символ (тикер актива).**

```python
_SYMBOL_RE = re.compile(r"\A[A-Z0-9]{1,20}\Z")  # app.py:62
```

Регулярное выражение — это шаблон для проверки текста. Здесь шаблон говорит: «строка должна состоять только из заглавных латинских букв A-Z и цифр 0-9, длиной от 1 до 20 символов, и больше ничего». Ключевое слово `\A...\Z` означает «строго от начала до конца» — никаких скрытых символов перевода строки или слэшей посередине. Проверка выполняется методом `fullmatch` (полное совпадение), что исключает любые попытки «спрятать» нежелательный суффикс. Если символ не проходит — запрос отклоняется с ошибкой 422 ещё до любых вычислений. `(src/dashboard/app.py:62, 105)`.

**Проверка 2 — даты.**

```python
@field_validator("start", "end")
def _validate_iso_date(cls, v: str) -> str:
    date.fromisoformat(v)  # app.py:89
```

Даты проверяются стандартной функцией Python — она принимает только строки вида `YYYY-MM-DD` (год-месяц-день) и отбрасывает всё остальное. Раньше некорректная дата вызывала внутреннюю ошибку 500; теперь она немедленно возвращает ошибку 422 с понятным сообщением. `(src/dashboard/app.py:80-92)`.

**Проверка 3 — стратегия и её зафиксированные параметры.**

Некоторые стратегии (например, `volume_breakout_iter10`, см. [[breakout-strategies|пробойные стратегии]]) имеют **зафиксированные** (LOCKED) символ и таймфрейм — их нельзя подменить через запрос. Это правило «анти-подсматривания» (anti-snooping, ADR 0059): если результаты оптимизации привязаны к конкретной паре `(BTCUSDT, 240)`, нельзя запустить ту же стратегию с другим таймфреймом и сделать вид, что параметры всё ещё релевантны. То же требование стоит за [[deflated-sharpe-ratio|DSR]] и честной проверкой через [[walk-forward-analysis|walk-forward]] — параметры регистрируются заранее. `(src/dashboard/app.py:220-254)`.

### Шаг 2. Вычисление run_id — уникального идентификатора расчёта

Каждому набору параметров соответствует единственный идентификатор — `run_id`. Он вычисляется из строки вида `strategy_id|symbol|interval|start|end` с помощью алгоритма **SHA-256**.

```python
def run_id(self) -> str:
    s = f"{self.strategy_id}|{self.symbol}|{self.interval}|{self.start}|{self.end}"
    return hashlib.sha256(s.encode()).hexdigest()[:16]  # backtest_runner.py:858-859
```

**SHA-256** — это математическая функция («хеш»), которая принимает любую строку и возвращает фиксированный «отпечаток» из 64 шестнадцатеричных символов. Если изменить хоть один символ во входной строке — отпечаток изменится полностью. Берём только первые 16 символов (`[:16]`) — этого достаточно для практической уникальности в нашем масштабе. Тот же алгоритм SHA-256 бот применяет и в другом месте — для [[kronos-security-weights-hash|проверки подлинности весов нейросети]], только там хешируется содержимое файла модели, а не строка параметров.

Важно: `initial_balance` (начальный баланс) и `variant` (вариант модели [[kronos-ml-strategy|Kronos]]) в хеш **не входят**. Это намеренное решение: кеш хранит структуру результата, а начальный баланс лишь масштабирует итоговую сумму при отображении. Подробнее — в разделе «Подводные камни». `(src/dashboard/backtest_runner.py:848-859)`.

### Шаг 3. Проверка кеша — есть ли уже готовый результат?

```python
cache_path = _RUNS_DIR / f"{run_id}.json"  # backtest_runner.py:918
if not force and cache_path.exists():
    result = json.loads(cache_path.read_text())
    result["cached"] = True
    return result
```

Если файл `data/runs/<run_id>.json` уже существует и параметр `force` не установлен — возвращаем готовый результат мгновенно. Поле `"cached": True` сигнализирует фронтенду, что данные взяты из кеша. `(src/dashboard/backtest_runner.py:916-922)`.

### Шаг 4. Одновременный запуск только одного бэктеста (threading.Lock)

Бэктест — тяжёлая операция: он загружает данные, запускает десятки итераций [[wfa-methodology|WFA]]. Если два пользователя (или два открытых окна браузера) нажмут «Запустить» одновременно, в памяти начнутся конфликты. Чтобы этого не было, используется **блокировка** (threading.Lock):

```python
_lock = threading.Lock()  # backtest_runner.py:315
with _lock:
    return _run_backtest_locked(...)  # backtest_runner.py:931-934
```

Блокировка работает как табличка «Занято» на двери туалета: пока первый запрос выполняется внутри `with _lock`, второй запрос будет терпеливо ждать снаружи. После завершения первого — второй войдёт. Дашборд позиционируется как инструмент для одного оператора (single-user dev tool), поэтому такой подход достаточен. `(src/dashboard/backtest_runner.py:315, 927-934)`.

### Шаг 5. Атомарная запись результата в файл

После окончания расчёта результат записывается в JSON-файл. Простая запись `file.write(text)` опасна: если процесс прервётся на полуслове (например, кончится место на диске), файл останется «разорванным» (torn) — невалидный JSON, который нельзя прочитать.

Поэтому мы используем атомарную запись через временный файл:

```python
def atomic_write_text(path: Path, text: str) -> None:
    tmp_path = path.with_suffix(path.suffix + ".tmp")  # _cache_io.py:26
    try:
        tmp_path.write_text(text)      # записать во временный файл
        os.replace(tmp_path, path)     # атомарно переименовать
    finally:
        if tmp_path.exists():
            tmp_path.unlink(missing_ok=True)  # убрать мусор при ошибке
```

Функция `os.replace` на POSIX-системах (Linux, macOS) — атомарная операция: читатель всегда видит либо старый файл целиком, либо новый целиком, никогда «полуготовый». `(src/dashboard/_cache_io.py:17-33)`.

### Шаг 6. Валидация run_id при чтении кеша

Когда пользователь запрашивает сохранённый результат через `GET /api/runs/{run_id}`, переданный `run_id` снова проверяется перед тем, как формируется путь к файлу:

```python
_RUN_ID_RE = re.compile(r"\A[a-f0-9]{16}\Z")  # backtest_runner.py:322

def get_run(run_id: str) -> dict | None:
    if not _is_valid_run_id(run_id):
        return None  # backtest_runner.py:1498-1499
    p = _RUNS_DIR / f"{run_id}.json"
```

Допустимый `run_id` — ровно 16 символов из набора `a-f0-9` (шестнадцатеричные). Строки вроде `../../../etc/passwd` или `abc123` длиной не 16 символов немедленно отклоняются — путь к файлу даже не формируется. `(src/dashboard/backtest_runner.py:322-327, 1492-1500)`.

### Шаг 7. HTTP-заголовки кеша для статических файлов браузера

Помимо дискового кеша результатов, дашборд управляет HTTP-кешированием ресурсов самого браузера (JS, CSS) через middleware:

```python
class _CacheControlMiddleware(BaseHTTPMiddleware):  # app.py:318
    async def dispatch(self, request: Request, call_next) -> Response:
        response = await call_next(request)
        if request.url.path.startswith("/assets/"):
            response.headers["Cache-Control"] = "public, immutable, max-age=31536000"
        else:
            response.headers["Cache-Control"] = "no-cache, no-store, must-revalidate"
```

Файлы в `/assets/` — это JS/CSS с уникальными именами (Vite добавляет хеш к имени файла при сборке). Такие файлы никогда не меняются — браузер может хранить их целый год (`max-age=31536000` секунд). Все остальные пути (API, главная страница) получают `no-cache`: браузер обязан спрашивать сервер при каждом обращении. `(src/dashboard/app.py:318-330)`.

## Формулы и расчёты

### Формула run_id

```text
run_id = SHA-256("strategy_id|symbol|interval|start|end")[:16]
```

**Что считает:** берём пять параметров запроса, склеиваем через символ `|`, вычисляем SHA-256, берём первые 16 символов результата (всегда строчные шестнадцатеричные буквы и цифры).

**Зачем именно так:** SHA-256 гарантирует, что любые два разных набора параметров дадут разный `run_id` (с вероятностью коллизии ~10⁻³⁸ — пренебрежимо мало). Это детерминировано: одни и те же параметры всегда дают один и тот же `run_id`, что позволяет находить кеш-хит без базы данных.

**Что не входит в ключ:** `initial_balance` и `variant` (Kronos mini/base). `(src/dashboard/backtest_runner.py:857-859, src/dashboard/_cache_io.py)`.

## Примеры / сценарии

### Сценарий 1. Кеш-хит — мгновенный ответ

1. Оператор выбирает стратегию `ema_crossover_s13` (см. [[ema-crossover-strategy]]), символ `BTCUSDT`, интервал `60`, даты `2023-01-01` — `2024-01-01`.
2. Браузер отправляет POST `/api/backtest`.
3. `BacktestPayload` проверяет символ (соответствует `[A-Z0-9]{1,20}`) и даты (валидный ISO).
4. `BacktestRequest.run_id()` вычисляет SHA-256 от строки `"ema_crossover_s13|BTCUSDT|60|2023-01-01|2024-01-01"` → берёт первые 16 hex-символов, допустим `"a3f7c8d92e1b0045"`.
5. Бот проверяет: существует ли файл `data/runs/a3f7c8d92e1b0045.json`? Да — возвращает его содержимое с `"cached": true`. Время ответа: доли секунды.

### Сценарий 2. Первый расчёт — запись в кеш

1. Те же параметры, но файл ещё не существует (первый запуск).
2. Бот захватывает `_lock` (никто другой не считает параллельно).
3. Запускает полный WFA — несколько секунд.
4. Результат записывается атомарно: сначала в `a3f7c8d92e1b0045.json.tmp`, затем `os.replace` переименовывает в `a3f7c8d92e1b0045.json`.
5. Следующий запрос с теми же параметрами — уже кеш-хит.

### Сценарий 3. Принудительный пересчёт (force=true)

Оператор устанавливает флажок «Пересчитать принудительно» в форме. Параметр `force=True` пропускает проверку кеша — бот считает заново и перезаписывает файл новым результатом. Используется, например, если обновились исторические данные в parquet-файле.

### Сценарий 4. Атака обходом пути — отклонение

Злоумышленник отправляет `symbol = "../../etc/passwd"`. Валидатор `_SYMBOL_RE.fullmatch("../../etc/passwd")` немедленно возвращает `None` — регулярное выражение не совпадает. Запрос отклоняется с ошибкой 422. Файловая система не затронута.

### Сценарий 5. Попытка прочитать чужой файл через run_id

Злоумышленник отправляет `GET /api/runs/../../../../etc/passwd`. `_is_valid_run_id` проверяет: длина строки не 16 символов, не только hex-цифры. Возвращает `None` → ответ 404. Путь к диску не формируется.

## Подводные камни / что важно понимать

**1. Начальный баланс не входит в ключ кеша.**

`run_id` вычисляется из пяти параметров: стратегия, символ, интервал, дата начала, дата конца. `initial_balance` в ключ не входит. Это значит: если вы запустили бэктест с балансом $10 000, получили результат, затем изменили баланс на $50 000 и нажали «Запустить» — дашборд вернёт кешированный результат с $10 000 и выставит `"cached": true`. Чтобы пересчитать с новым балансом — используйте флаг `force=true`. `(src/dashboard/backtest_runner.py:857-859)`. Подробнее: [[run-backtest-form]].

**2. Кеш хранится на диске между сессиями.**

Файлы в `data/runs/` сохраняются между перезапусками сервера. Если вы обновили исторические данные (скачали свежий [[parquet-storage|parquet]] через [[data-backfill-command|backfill]]), старые кешированные результаты не устаревают автоматически — их нужно пересчитать принудительно через `force=true`.

**3. Только один бэктест одновременно.**

`threading.Lock` гарантирует единственный параллельный расчёт. Если один расчёт уже идёт, второй запрос будет ждать. Это правильный выбор для инструмента одного оператора — но если открыть несколько вкладок браузера и нажать «Запустить» в каждой, лишние запросы встанут в очередь. `(src/dashboard/backtest_runner.py:315, 931)`.

**4. Атомарная запись защищает от «разорванного» файла, но не от сбоя диска.**

Если диск заполнен в момент записи временного файла, `write_text` выбросит исключение до `os.replace` — старый кешированный файл останется нетронутым. Это хорошее поведение: нет полуготового файла, нет потери предыдущего результата. `(src/dashboard/_cache_io.py:26-33)`.

**5. Дашборд доступен только с `127.0.0.1` — это не публичный сервис.**

Заголовок `app.py` явно фиксирует: `Localhost-only (127.0.0.1:8000). NO auth, NO CORS (single-user dev tool)`. Эта архитектурная позиция «инструмент одного оператора» описана в [[dashboard-overview|общем обзоре дашборда]]. Меры безопасности (валидация символа, run_id) — защита от случайных или автоматических некорректных запросов, не от целенаправленных атак. Если дашборд открыт в интернет — это ошибка конфигурации. `(src/dashboard/app.py:3-4)`.

**6. HTTP-кеш браузера и дисковый кеш результатов — разные вещи.**

`_CacheControlMiddleware` управляет тем, как долго браузер хранит JS/CSS (год для `/assets/*`, запрет кеша для API). Это не связано с кешем JSON-результатов в `data/runs/`. Путаница между ними — частая ошибка при отладке. `(src/dashboard/app.py:318-330)`.
