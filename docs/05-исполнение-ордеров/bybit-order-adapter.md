# Адаптер Bybit: как бот отправляет ордера на биржу

**TL;DR:** Адаптер — единственное место, где команда «купи 0.01 BTC» превращается в реальный HTTP-запрос на биржу Bybit. Он проверяет ордер по правилам биржи ещё до отправки, переводит ошибки биржи на понятный боту язык и защищает от нескольких известных ловушек Bybit Spot V5.

---

## Простыми словами

Представьте, что бот — это директор завода, а биржа Bybit — поставщик сырья. Директор не звонит поставщику лично: для этого есть **менеджер по закупкам** (адаптер). Менеджер:

1. Принимает заявку от директора («купи 0.01 BTC по рынку»).
2. Проверяет, что заявка не нарушает условия договора с поставщиком (минимальный объём, допустимые шаги цены).
3. Оформляет заявку в нужном формате (JSON для Bybit API).
4. Отправляет заявку и получает подтверждение (номер ордера).
5. Если поставщик ответил ошибкой — переводит её на язык, понятный директору (например: «недостаточно средств», «лимит запросов превышен»).

Без адаптера каждый модуль бота должен был бы знать все нюансы Bybit API — форматы полей, запрещённые комбинации, коды ошибок. Адаптер инкапсулирует (прячет внутрь) всю эту сложность. Наружу торчит простой интерфейс: «отправь рыночный ордер», «отмени ордер», «покажи баланс».

**pybit** — это готовая Python-библиотека, которая умеет «разговаривать» с Bybit API. Адаптер использует pybit как транспорт (способ доставки сообщений), добавляя поверх него свои проверки и перевод ошибок.

## Как это работает у нас

### Класс `BybitMarketAdapter` — фасад спотовых ордеров

`BybitMarketAdapter` — главный класс адаптера (src/execution/bybit/adapter.py:149). Он работает только со спотовыми ордерами (v0.1 scope, ADR 0020). Принимает два объекта при создании: `rest` — обёртка над pybit (см. [[bybit-rest-client-and-backoff]]), и `filters` — [[bybit-filters|правила биржи]] для конкретного инструмента.

Публичные свойства:
- `step_size` — минимальный шаг количества (сколько монет), отдаётся наружу вместо прямого доступа к внутреннему `_filters` (src/execution/bybit/adapter.py:157–165, ARCH-03).
- `min_order_qty` — минимальное количество для ордера, используется [[coordinator-orchestration|координатором]] для классификации пыли (src/execution/bybit/adapter.py:168–176, BYBIT-05).

---

### `place_order()` — рыночный ордер (Market Buy/Sell)

Рыночный ордер — это приказ купить или продать «прямо сейчас по лучшей доступной цене». Бот использует его при входе в позицию.

**Шаг 1: проверка запрещённых полей**

Bybit Spot V5 отклоняет с ошибкой 170130 ряд полей, которые работают на фьючерсах, но не в споте. Вместо того чтобы ждать ошибки от биржи, адаптер проверяет ещё до отправки:

```python
_BANNED_SPOT_FIELDS = (
    "tpslMode", "takeProfit", "stopLoss",
    "tpOrderType", "slOrderType", "triggerDirection",
)
```

(src/execution/bybit/adapter.py:14–21)

Если кто-то передаст хоть одно из этих полей в `extra_payload` — адаптер немедленно поднимает `ValueError`, не тратя запрос на биржу (src/execution/bybit/adapter.py:199–204).

**Шаг 2: запрет `marketUnit=quoteCoin`**

В Bybit есть два режима указания количества для рыночных ордеров:
- `baseCoin` — «купи X монет» (например, 0.001 BTC)
- `quoteCoin` — «купи на Y долларов» (например, на 60 USDT)

Мы **всегда** используем `baseCoin`. Режим `quoteCoin` вызывал накопление ошибок в 16-м знаке после запятой (дрейф точности), что было обнаружено при зондировании (probe S2 v2, ADR 0020 sub-decision 3). Если кто-то передаст `marketUnit=quoteCoin` — адаптер выбросит `ValueError` (src/execution/bybit/adapter.py:207–212).

**Шаг 3: проверка фильтров биржи**

Перед отправкой вызывается `self._filters.validate_order(qty=qty)` (src/execution/bybit/adapter.py:215). Если количество вне допустимых пределов — будет `FilterViolation` ещё до запроса. **Важно:** для рыночных ордеров проверка минимального нотионала (qty × цена) пропускается, потому что у рыночного ордера нет фиксированной цены в момент сборки — она определится биржей.

**Шаг 4: сборка payload и отправка**

Адаптер собирает словарь с обязательными полями и отправляет через `_call_rest()`:

```python
payload = {
    "category": "spot",
    "symbol": symbol,
    "side": side,           # "Buy" или "Sell"
    "orderType": "Market",
    "qty": str(qty),        # количество в виде строки
    "marketUnit": "baseCoin",
}
```

(src/execution/bybit/adapter.py:217–224)

**Шаг 5: разбор ответа**

Если биржа вернула `retCode != 0` — ошибка переводится в `ReasonCode` через `map_error()` и поднимается как `BybitAPIError`. Если успех — возвращается `OrderAck` с `order_id` (идентификатором ордера от биржи) (src/execution/bybit/adapter.py:230–237).

---

### `place_limit_order()` — лимитный ордер (тейк-профит)

**Лимитный ордер** (Limit) — приказ продать по конкретной цене или лучше. Используется как нога тейк-профита в [[oco-bracket-emulation|OCO-скобке]] (ADR 0020 sub-decision 2). Тип `GTC` (Good Till Cancelled) — «стоит, пока не отменят вручную».

Отличие от рыночного: здесь передаётся цена, поэтому проверка нотионала (qty × price) выполняется полностью (src/execution/bybit/adapter.py:285, filters.py:67–69). Payload добавляет поля `orderType=Limit`, `timeInForce=GTC`, `price` (src/execution/bybit/adapter.py:284–303).

---

### `place_stop_market_order()` — стоп-рыночный ордер (стоп-лосс)

**Стоп-лосс** (Stop Market) — ордер, который «спит» до тех пор, пока цена не упадёт до заданного уровня, а потом срабатывает как рыночный. Это защита от больших потерь: «если цена упала до X — продавай немедленно по рынку».

Ключевые особенности нашего стоп-ордера:
- `orderFilter=StopOrder` — помечает ордер как стоп (src/execution/bybit/adapter.py:259).
- `triggerPrice` — цена срабатывания (src/execution/bybit/adapter.py:261).
- `triggerBy=LastPrice` — сравниваем с последней рыночной ценой (src/execution/bybit/adapter.py:262).
- **Нет поля `timeInForce`** — намеренно: Bybit Spot тихо переписывает `GTC` → `IOC` для стоп-ордеров (обнаружено в probe v3-D). `IOC` (Immediate Or Cancel) означает: «исполни сейчас или отмени». Частичное исполнение IOC обрабатывается системой через `EXIT_SL_RESIDUAL` (см. [[emergency-flatten-and-residual]], src/execution/bybit/adapter.py:250–252).

---

### `cancel_order()` — отмена ордера

Отменяет конкретный ордер по его биржевому ID. Важный нюанс: если ордер уже исполнился к моменту отмены (гонка), Bybit возвращает код 110001. Это **не фатально** — адаптер обрабатывает это как «ордер уже в терминальном состоянии» и возвращает `CancelResult(cancelled=False, reason_code=REJECT_ORDER_ALREADY_TERMINAL)` вместо исключения (src/execution/bybit/adapter.py:306–317, ADR 0020 sub-decision 6).

Защита сделана двойной: проверяется И `retCode == 110001`, И `reason is REJECT_ORDER_ALREADY_TERMINAL` — чтобы будущие изменения маппинга не могли случайно проглотить другую ошибку (src/execution/bybit/adapter.py:315).

`cancel_all_orders()` — массовая отмена всех открытых ордеров по символу, используется при экстренном выравнивании ([[emergency-flatten-and-residual|flatten]]) и [[kill-switch-emergency-stop|аварийном останове]] (src/execution/bybit/adapter.py:319–326).

---

### Чтение состояния биржи

**`get_order()`** — получить снимок конкретного ордера. Возвращает `OrderSnapshot` с полями: статус, исполненное количество, комиссия, средняя цена. Используется обработчиком отмены сиблинга и [[reconcile-as-truth|рекончилером]] (src/execution/bybit/adapter.py:328–351).

**`get_open_orders()`** — список активных ордеров (статусы: Untriggered/New/PartiallyFilled). Используется для обнаружения предыдущих попыток при перезапуске (ADR 0020 sub-decision 9, src/execution/bybit/adapter.py:353–361).

**`get_order_history()`** — последние завершённые ордера (Filled/Cancelled/Rejected) за ~7 дней. Тоже для обнаружения прошлых попыток (src/execution/bybit/adapter.py:363–373).

**`get_wallet_balance()`** — единственная достоверная информация о том, сколько монеты есть на счёте (тот же путь питает [[account-balance|баланс в дашборде]]). На споте Bybit нет `get_position` как на фьючерсах — баланс кошелька и есть позиция (ADR 0020 sub-decision 4). Возвращает `WalletSnapshot` с полями: всего, доступно, заблокировано. Важная деталь: пустая строка в `availableToWithdraw` означает «все средства заблокированы» — адаптер преобразует её в ноль (src/execution/bybit/adapter.py:375–400).

---

### `_call_rest()` — обёртка над повторными попытками

Все REST-вызовы идут через `_call_rest()` (src/execution/bybit/adapter.py:125–146). Внутри он вызывает `_retry_with_backoff` из уровня marketdata, который делает автоматические повторные попытки при временных ошибках (превышение лимита запросов 170005/170222).

Если повторные попытки исчерпаны, `_retry_with_backoff` поднимает `rest.BybitAPIError` — базовый класс без поля `.reason`. Проблема: координатор ловит `adapter.BybitAPIError` и смотрит на `.reason` для коротких замыканий (например, код 110072 означает «дубликат, всё хорошо»). Если бы ошибка дошла в виде базового класса без `.reason` — координатор не смог бы её правильно обработать и мог бы сделать лишнюю продажу (BYBIT-02).

Решение (S55 BYBIT-03): `_call_rest()` перехватывает `rest.BybitAPIError` и перепаковывает в `adapter.BybitAPIError` с заполненным `.reason`. `adapter.BybitAPIError` наследуется от `rest.BybitAPIError`, поэтому один `except` покрывает оба варианта.

---

### Защитная распаковка ответа: `_safe_extract_list` и `_safe_extract_list_or_empty`

Bybit V5 API возвращает данные в формате `response["result"]["list"]`. Прямое обращение через `resp["result"]["list"]` падает с невразумительным `KeyError` если биржа изменила схему ответа — без указания, какой именно запрос упал.

Два вспомогательных метода решают это (S47 T10, bybit-api-reviewer S38 M2):

- `_safe_extract_list()` — для запросов, где `result.list` обязан присутствовать (get_order, get_wallet_balance). Если ключа нет — поднимает `BybitAdapterError` с понятным сообщением (src/execution/bybit/adapter.py:24–45).
- `_safe_extract_list_or_empty()` — для листинговых запросов (get_open_orders, get_order_history), где отсутствие ключа `list` нормально означает «нет ордеров». Возвращает пустой список. Поднимает ошибку только если `result` не словарь (src/execution/bybit/adapter.py:48–68).

### Маппинг ошибок: `errors.py`

Bybit возвращает числовые коды ошибок (`retCode`). Функция `map_error()` переводит их в осмысленные `ReasonCode` (src/execution/bybit/errors.py:54–56):

| retCode | ReasonCode | Смысл |
|---------|-----------|-------|
| 10001 | `INVALID_PARAM` | Неверный параметр запроса |
| 10002 | `CLOCK_DRIFT` | Время на сервере и бирже разошлись |
| 10003 | `WRONG_API_KEY` | Неверный API-ключ |
| 10006 | `RATE_LIMIT_HIT` | Превышен лимит запросов |
| 10016 | `EXCHANGE_MAINTENANCE` | Биржа на техобслуживании |
| 110001 | `REJECT_ORDER_ALREADY_TERMINAL` | Ордер уже исполнен/отменён |
| 110007 | `INSUFFICIENT_BALANCE` | Недостаточно средств |
| 110017 | `FILTER_VIOLATION` | Нарушение фильтра биржи |
| 110072 | `REJECT_DUPLICATE_ORDER` | Дублирующийся ID ордера |
| 170005 | `RATE_LIMIT_HIT` | Лимит частоты ордеров |
| 170131 | `FILTER_VIOLATION` | Нарушение фильтра (альт. код) |
| 170140 | `FILTER_VIOLATION` | Нарушение фильтра (альт. код) |
| 170213 | `FILTER_VIOLATION` | Нарушение фильтра (альт. код) |
| 170222 | `RATE_LIMIT_HIT` | Лимит числа активных ордеров |
| любой другой | `UNKNOWN_ERROR` | Неизвестная ошибка |

(src/execution/bybit/errors.py:26–51)

**Важно:** это биржевой `ReasonCode` только для уровня адаптера. Он **отдельный** от канонического `ReasonCode` в `src/risk/reason_codes.py` — и не должен с ним смешиваться (src/execution/bybit/errors.py:19–22).

Код `REJECT_DUPLICATE_ORDER` (110072) — особый случай: если бот при перезапуске пытается отправить ордер с тем же ID, что уже прошёл, биржа отвечает 110072. Это значит «предыдущая отправка уже сработала» — и координатор трактует это как успех, а не ошибку (S51 D1).

### `BybitFilters` — правила биржи для инструмента

`BybitFilters` (src/marketdata/filters.py:13) — неизменяемая модель (frozen=True) с параметрами конкретного торгового инструмента от Bybit:

| Поле | Откуда | Смысл |
|------|--------|-------|
| `step_size` | `basePrecision` | Минимальный шаг количества (шаг лота). Например, 0.000001 BTC |
| `tick_size` | `tickSize` | Минимальный шаг цены. Например, 0.01 USDT |
| `min_order_qty` | `minOrderQty` | Минимально допустимое количество монет в ордере |
| `max_order_qty` | `maxOrderQty` | Максимально допустимое количество |
| `min_order_amt` | `minOrderAmt` | Минимальный нотионал (qty × цена) в квотируемой валюте |

(src/marketdata/filters.py:19–23, 41–45)

**Округление вниз** (`ROUND_DOWN`): и `round_qty()`, и `round_price()` всегда округляют вниз, никогда вверх. Это принцип «не превышай задуманное количество» — если пользователь хочет купить на 100 USDT, бот никогда не купит на 100.01 (src/marketdata/filters.py:48–54).

**`validate_order()`** — проверяет три условия перед отправкой на биржу (src/marketdata/filters.py:56–69):
1. `qty >= min_order_qty` — количество не меньше минимума.
2. `qty <= max_order_qty` — количество не больше максимума.
3. `qty * price >= min_order_amt` — нотионал (стоимость ордера в долларах) не меньше минимума. Этот пункт **пропускается**, если цена не передана — так происходит для рыночных ордеров (нет фиксированной цены в момент сборки).

## Формулы и расчёты

### Округление количества (round_qty)

```text
округлённое_qty = floor(qty / step_size) × step_size
```

**Расшифровка:** делим желаемое количество на минимальный шаг лота, берём целую часть (floor = «отбросить остаток»), умножаем обратно. Результат гарантированно кратен шагу лота и не превышает желаемое.

Пример: step_size = 0.000001 BTC, хотим купить 0.0012345 BTC.
- 0.0012345 / 0.000001 = 1234.5
- floor(1234.5) = 1234
- 1234 × 0.000001 = 0.001234 BTC

(src/marketdata/filters.py:48–50)

### Округление цены (round_price)

```text
округлённая_цена = floor(цена / tick_size) × tick_size
```

Та же логика, но для цены. tick_size = 0.01 USDT, цена = 65432.567 USDT.
- 65432.567 / 0.01 = 6543256.7
- floor(6543256.7) = 6543256
- 6543256 × 0.01 = 65432.56 USDT

(src/marketdata/filters.py:52–54)

### Проверка нотионала

```text
нотионал = qty × price
если нотионал < min_order_amt → FilterViolation
```

**Нотионал** — стоимость ордера в котируемой валюте (обычно USDT). Биржа требует минимальный нотионал, чтобы не засорять книгу ордеров микросделками. Если бот хочет купить очень маленькое количество монеты по очень низкой цене — стоимость сделки может оказаться ниже минимума, и биржа отклонит ордер. Мы проверяем это сами заранее.

(src/marketdata/filters.py:67–69)

## Примеры / сценарии

### Сценарий 1: обычная покупка BTC

Бот решил купить 0.001 BTC (BTCUSDT). Координатор вызывает:

```python
adapter.place_order(symbol="BTCUSDT", side="Buy", qty=Decimal("0.001"), order_link_id="CID-001")
```

1. Проверка запрещённых полей — все чисты.
2. `marketUnit` не передан → по умолчанию `baseCoin`.
3. `validate_order(qty=0.001)`: 0.001 > 0.000048 (min) — ОК; нотионал не проверяется (рыночный ордер).
4. Payload отправляется на биржу через pybit.
5. Биржа отвечает `{retCode: 0, result: {orderId: "EX-12345", orderLinkId: "CID-001"}}`.
6. Возвращается `OrderAck(order_id="EX-12345", order_link_id="CID-001")`.

### Сценарий 2: слишком маленькое количество

Бот пытается продать 0.00001 BTC (меньше min_order_qty = 0.000048):

```python
adapter.place_order(symbol="BTCUSDT", side="Sell", qty=Decimal("0.00001"))
```

На шаге 3 `validate_order` поднимает `FilterViolation: qty 0.00001 < min_order_qty 0.000048`. Запрос на биржу **не отправляется** — адаптер экономит квоту API.

### Сценарий 3: попытка отменить уже исполненный ордер

OCO-скобка: TP сработал, бот пытается отменить SL:

```python
result = adapter.cancel_order(symbol="BTCUSDT", order_id="EX-SL-99")
```

Биржа отвечает `{retCode: 110001, retMsg: "order already finished"}`. Адаптер видит 110001 + REJECT_ORDER_ALREADY_TERMINAL и возвращает `CancelResult(cancelled=False, reason_code=REJECT_ORDER_ALREADY_TERMINAL)` — не исключение. Координатор знает: «SL уже не активен, всё нормально».

### Сценарий 4: дублирующийся ID ордера при перезапуске (110072)

Бот упал и перезапустился. При восстановлении пытается разместить SL с тем же `order_link_id`, что и раньше. Биржа отвечает `retCode=110072`. Адаптер транслирует это в `REJECT_DUPLICATE_ORDER`. Координатор видит 110072 + REJECT_DUPLICATE_ORDER → трактует как «предыдущий ордер дошёл, считай успехом» (S51 D1).

### Сценарий 5: исчерпание повторных попыток (rate limit)

Биржа временно ограничила запросы (170222). `_retry_with_backoff` делает несколько попыток и сдаётся. Поднимает `rest.BybitAPIError`. `_call_rest()` ловит его и перепаковывает в `adapter.BybitAPIError(reason=RATE_LIMIT_HIT)`. Координатор получает ошибку с `.reason=RATE_LIMIT_HIT` и может правильно обработать ситуацию — не путая с нехваткой баланса или другой ошибкой.

## Подводные камни / что важно понимать

**1. Два разных `ReasonCode` в одном проекте**

В проекте существует два одноимённых enum `ReasonCode`:
- `src/execution/bybit/errors.py` — биржевой, только для адаптера, 10 кодов.
- `src/risk/reason_codes.py` — канонический, для всей системы риска, 67+ кодов (см. [[reason-codes-assessment-output]]).

Они не взаимозаменяемы. Биржевой `ReasonCode` — это «сырой» перевод числовых кодов Bybit. Канонический — полный язык событий всего бота. Путать их нельзя.

**2. Рыночный ордер не знает свою цену**

Когда бот отправляет рыночный ордер — он не знает, по какой цене сделка фактически исполнится. Это известно только после исполнения. Поэтому проверка минимального нотионала при рыночных ордерах намеренно пропускается — нет числа, которое подставить.

**3. `timeInForce` намеренно отсутствует у стоп-ордеров**

На спотовом рынке Bybit тихо меняет `GTC` на `IOC` для стоп-ордеров без предупреждения. Если бы мы передавали `timeInForce=GTC` — биржа всё равно исполняла бы ордер как `IOC`. Мы просто не передаём это поле, и биржа работает с `IOC`-семантикой — систе обрабатывает частичные исполнения через `EXIT_SL_RESIDUAL`.

**4. Округление только вниз, никогда вверх**

`round_qty` и `round_price` всегда округляют вниз (`ROUND_DOWN`). Это не ошибка — это осознанный выбор. Округление вверх могло бы нарушить желаемый размер позиции или создать ордер дороже задуманного.

**5. Ошибка схемы ответа vs. пустой список**

`_safe_extract_list` и `_safe_extract_list_or_empty` — разные функции для разных ситуаций. Если `result.list` отсутствует у `get_wallet_balance` — это настоящая ошибка схемы. Если `result.list` отсутствует у `get_open_orders` — это просто «нет активных ордеров». Смешивать их нельзя.

**6. Состояние кошелька — единственная истина о позиции**

На споте нет `get_position` как на фьючерсах. `get_wallet_balance` — это и есть позиция. Пустая строка в `availableToWithdraw` — не null и не ошибка, это Bybit-сигнал «все деньги заблокированы». Адаптер заменяет пустую строку нулём.

## Связанные документы

- [[oco-bracket-emulation]] — как три отдельных ордера (Market + Limit TP + Stop SL) собираются в связку. Адаптер поставляет примитивы для каждой ноги.
- [[coordinator-orchestration]] — Coordinator вызывает методы адаптера в правильном порядке; адаптер — его единственный путь к бирже.
- [[emergency-flatten-and-residual]] — `cancel_all_orders()` и рыночный sell используются при аварийном выравнивании; именно здесь важен `REJECT_DUPLICATE_ORDER` (110072) и `EXIT_SL_RESIDUAL`.
- [[bybit-rest-client-and-backoff]] — `_retry_with_backoff` и `rest.BybitAPIError`, которые адаптер использует как транспорт и перепаковывает.
- [[order-lifecycle-overview]] — полный жизненный цикл ордера от сигнала до закрытия: адаптер — один из узлов в этой цепочке.
- [[reconcile-as-truth]] — Reconciler использует `get_order()` и `get_order_history()` адаптера для восстановления достоверного состояния.
- [[bybit-filters]] — модель `BybitFilters` и `validate_order()`, на которую адаптер опирается перед отправкой; общий файл `filters.py` (округление, минимальный нотионал).
- [[execution-state-machine]] — FSM ордера меняет состояния по ответам адаптера (`OrderAck`, `OrderSnapshot`) — адаптер поставляет ей факты от биржи.
- [[bybit-private-websocket]] — второй, push-канал того же ордера: адаптер отправляет команды (REST), приватный WS сообщает об их исполнении в реальном времени.
- [[execution-state-persistence-and-halt-audit]] — `get_open_orders()` / `get_order_history()` адаптера используются при перезапуске для обнаружения прошлых попыток (ADR 0020 sub-decision 9).
- [[reason-codes-assessment-output]] — канонический `ReasonCode` системы риска (67+ кодов), от которого биржевой `ReasonCode` адаптера намеренно ОТДЕЛЁН (контраст, не путать).
- [[kill-switch-emergency-stop]] — аварийный стоп дёргает `cancel_all_orders()` адаптера, чтобы мгновенно снять все открытые ордера.
- [[account-balance]] — дашборд показывает баланс, получаемый тем же путём `get_wallet_balance()`, что использует адаптер.
- [[reconcile-and-monitor-commands]] — команда `reconcile-only` строит достоверную картину через `get_*`-методы адаптера без торговли.
- [[run-modes-testnet-live-reconcile]] — режим запуска (TESTNET / демо-мейннет / live) определяет, по какому контуру Bybit реально бьют вызовы адаптера.
- [[bybit-rest-source]] — соседний REST-слой Bybit, но для рыночных данных (свечи/история), а не для ордеров — общий транспорт pybit, разные задачи.
- [[clock-drift-monitor]] — код `CLOCK_DRIFT` (10002) в маппинге ошибок адаптера — та же проблема рассинхрона локальных часов и времени биржи.

За техническими деталями: `llm-wiki/wiki/project/components/execution-adapter.md` (если создан) и ADR 0020.
