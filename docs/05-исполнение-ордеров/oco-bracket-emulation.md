# Эмуляция OCO: брекет из 3 ордеров (вход + тейк-профит + стоп-лосс)

**TL;DR:** Биржа Bybit не умеет «один сработал — другой отменяется» на Спот-рынке, поэтому бот сам собирает эту логику из трёх ордеров: рыночный вход + лимит-тейк-профит + стоп-стоп-лосс. Отменить «лишний» ордер после срабатывания первого бот тоже делает сам — программно.

## Простыми словами

Представьте, что вы купили квартиру и хотите её продать при одном из двух условий: либо цена вырастет до вашей мечты (и вы фиксируете прибыль), либо цена упадёт до вашего порога боли (и вы выходите с минимальным убытком). В классическом брокерском мире такой двойной приказ называется **OCO — One-Cancels-the-Other** (один отменяет другой): срабатывает один — второй автоматически снимается.

На профессиональных биржах (фьючерсы, акции) OCO — стандартная функция. Но **Bybit Spot V5** (рынок реальных монет, не деривативов) эту функцию не поддерживает. Попытка отправить единый ордер с одновременными тейк-профитом и стоп-лоссом возвращает ошибку `ErrCode 170130` — биржа просто не знает таких полей на Спот-рынке (ADR 0020, подтверждено probe-скриптом v1).

Поэтому наш бот делает OCO сам — через три отдельных ордера. Мы называем такую связку **брекет** (от английского bracket — «скобки», которые «зажимают» сделку с двух сторон):

1. **Вход** — рыночная покупка (исполняется мгновенно по текущей цене).
2. **Тейк-профит** — лимитный ордер на продажу по желаемой высокой цене (ждёт на бирже).
3. **Стоп-лосс** — стоп-рыночный ордер на продажу при падении цены до защитного уровня (тоже ждёт на бирже).

После того как один из двух ордеров (ТП или СЛ) срабатывает, бот отменяет второй. Это и есть «один отменяет другой» — только руками бота, а не биржи.

**Аналогия:** вы ставите будильник на 7:00, чтобы встать на работу. Рядом — другой будильник на 8:30, «запасной». Как только сработает первый и вы встанете — вы отключаете второй, потому что он уже не нужен. Вот так же работает брекет.

## Как это работает у нас

### Шаг 0. Чистые структуры данных, никакого I/O

Прежде всего — разделение ответственности. Файл `src/execution/bracket.py` — это **чистые функции и структуры данных**. Они описывают, что именно нужно сделать, но ничего не отправляют на биржу самостоятельно. Никаких HTTP-запросов, никакого обращения к базе данных — только вычисления и описания.

Три структуры (dataclass):

```python
@dataclass(frozen=True, slots=True)
class BracketLeg:      # одна «нога» брекета
    role: Role         # "entry", "tp" или "sl"
    side: Literal["Buy", "Sell"]
    qty: Decimal       # количество монеты
    price: Decimal | None         # цена для лимитного ордера (None у рыночного)
    trigger_price: Decimal | None # триггер-цена для стоп-ордера (None у остальных)
    order_link_id: str            # наш уникальный ID ордера

@dataclass(frozen=True, slots=True)
class BracketLegs:     # все три ноги вместе
    entry: BracketLeg
    tp: BracketLeg
    sl: BracketLeg

@dataclass(frozen=True, slots=True)
class BracketParams:   # входные параметры для сборки брекета
    symbol: str
    entry_qty: Decimal
    entry_side: Literal["Buy", "Sell"]
    tp_price: Decimal
    sl_trigger_price: Decimal
    bracket_id: str    # уникальный ID брекета (8 символов из UUID)
    attempt: int       # номер попытки (для повторных ордеров)
```

(src/execution/bracket.py:24-49)

### Шаг 1. build_bracket() — сборка трёх ног

Функция `build_bracket()` принимает параметры и возвращает готовое описание трёх ордеров. Ключевые моменты:

**Сторона выхода — всегда противоположна входу.** Если вход — Buy (покупка), то и тейк-профит, и стоп-лосс — Sell (продажа). Бот не торгует в шорт на Спот, поэтому эта логика однозначная:

```python
def build_bracket(p: BracketParams) -> BracketLegs:
    exit_side: Literal["Buy", "Sell"] = "Sell" if p.entry_side == "Buy" else "Buy"
```

(src/execution/bracket.py:80-81)

Три ноги отличаются только типом: у входа нет ни цены, ни триггера (рыночный ордер исполняется «как есть»); у ТП — цена, нет триггера; у СЛ — триггер-цена, нет цены исполнения (рынок исполняется по лучшей доступной цене после срабатывания триггера):

```python
entry=BracketLeg(role="entry", side=p.entry_side, qty=p.entry_qty,
                 price=None, trigger_price=None, ...),
tp=BracketLeg(   role="tp",    side=exit_side,    qty=p.entry_qty,
                 price=p.tp_price, trigger_price=None, ...),
sl=BracketLeg(   role="sl",    side=exit_side,    qty=p.entry_qty,
                 price=None, trigger_price=p.sl_trigger_price, ...),
```

(src/execution/bracket.py:82-113)

### Шаг 2. make_order_link_id() — предсказуемый ID ордера

Каждый ордер на бирже получает наш **клиентский идентификатор** (orderLinkId — это как наш собственный номер на посылке, который биржа принимает наряду со своим). Формат:

```
oco-{bracket_id}-{role}-{attempt}
```

Пример для брекета с ID `7abe87bf`, первая попытка:
- вход: `oco-7abe87bf-entry-1`
- тейк-профит: `oco-7abe87bf-tp-1`
- стоп-лосс: `oco-7abe87bf-sl-1`

(src/execution/bracket.py:52-57, подтверждено tests/unit/test_bracket_builder.py:25-27)

**Зачем предсказуемый ID?** Это называется **идемпотентность** — если отправить один и тот же запрос дважды (например, из-за сбоя сети), биржа увидит одинаковый `orderLinkId` и вернёт ответ «ордер уже существует», а не создаст второй ордер. Без предсказуемого ID возможна двойная продажа монеты.

Bybit ограничивает длину `orderLinkId` **36 символами**. `bracket_id` — это первые 8 символов UUID (короткое, предсказуемое), поэтому самый длинный ID `oco-{8}-entry-{N}` занимает не более 20 символов — запас большой (src/execution/bracket.py:55-56).

### Шаг 3. compute_oco_qty() — количество с учётом комиссии

Здесь самый тонкий момент всей системы. Купили 0.001 BTC — но реально на балансе чуть меньше. Почему?

**На Bybit Spot комиссия за покупку (BUY) списывается из купленной монеты (BTC), а не из USDT.** Купили 0.001 BTC, комиссия тейкера 0.1% = 0.000001 BTC → на счёт поступает 0.000999 BTC, а не 0.001. Если попытаться продать 0.001 BTC — биржа вернёт ошибку `170131 "Insufficient balance"`, потому что такого количества на балансе нет.

То, что остаётся (0.000001 BTC в этом примере), называется **пыль** (dust) — слишком маленький остаток, чтобы его продать или отменить. Брекет «застревает» с этой пылью навсегда, если не учесть комиссию заранее.

Функция `compute_oco_qty()` решает эту проблему:

```python
def compute_oco_qty(
    *,
    cum_exec_qty: Decimal,   # сколько BTC фактически куплено
    cum_exec_fee: Decimal,   # комиссия в валюте fee_currency
    fee_currency: str,       # в какой валюте взяли комиссию
    base_coin: str,          # базовая монета (BTC в паре BTCUSDT)
    qty_step: Decimal,       # минимальный шаг лота (напр. 0.000001 BTC)
) -> Decimal:
    net = cum_exec_qty - cum_exec_fee if fee_currency == base_coin else cum_exec_qty
    if net <= 0:
        return Decimal("0")
    return (net / qty_step).quantize(Decimal("1"), rounding=ROUND_DOWN) * qty_step
```

(src/execution/bracket.py:116-133)

Логика в словах:
- Если комиссия взята в BTC (базовой монете) — вычитаем её из полученного количества.
- Если комиссия взята в USDT (при продаже) — BTC количество не меняется.
- Результат **всегда округляем вниз** (ROUND_DOWN) до [[bybit-filters|шага лота]] (минимальной единицы количества, которую принимает биржа). Почему именно вниз — потому что продать больше, чем есть на балансе, нельзя физически. Округление вверх означало бы попытку продать несуществующее.

### Шаг 4. Размещение ног через адаптер

После того как `build_bracket()` описал три ордера, [[coordinator-orchestration|координатор]] (`src/execution/coordinator.py`) отправляет их на биржу через три разных метода [[bybit-order-adapter|адаптера]] (`src/execution/bybit/adapter.py`):

**Нога 1 — рыночный вход** (`place_order`):

```python
self._adapter.place_order(
    symbol=self._symbol,
    side=legs.entry.side,    # "Buy"
    qty=legs.entry.qty,
    order_link_id=legs.entry.order_link_id,
)
```

(src/execution/coordinator.py:362-367)

Адаптер обязательно передаёт `marketUnit=baseCoin` (src/execution/bybit/adapter.py:223) — это «купить в BTC», а не «потратить USDT». Вариант `quoteCoin` (потратить USDT) запрещён: эмпирически он возвращает количество с 16 знаками после запятой, которое нельзя корректно округлить до шага лота.

**Нога 2 — тейк-профит** (`place_limit_order`):

Лимитный ордер — это «продать по конкретной цене». Параметры по коду:

```python
payload = {
    "orderType": "Limit",
    "timeInForce": "GTC",   # Good Till Cancelled — стоит, пока не отменят
    "qty": str(qty),
    "price": str(price),
    "marketUnit": "baseCoin",
    "orderLinkId": order_link_id,
}
```

(src/execution/bybit/adapter.py:286-296)

**GTC (Good Till Cancelled)** — время жизни ордера: «стой, пока не сработаешь или не отменят». Тейк-профит может ждать часами или днями — это нормально.

**Нога 3 — стоп-лосс** (`place_stop_market_order`):

Стоп-рыночный ордер — это «при падении цены до триггера автоматически продать по рынку». Параметры:

```python
payload = {
    "orderType": "Market",
    "orderFilter": "StopOrder",   # Bybit-специфичный маркер стоп-ордера
    "qty": str(qty),
    "triggerPrice": str(trigger_price),   # цена срабатывания
    "triggerBy": "LastPrice",             # триггер по последней цене сделок
    "marketUnit": "baseCoin",
    # timeInForce — намеренно ОТСУТСТВУЕТ (см. «Подводные камни»)
}
```

(src/execution/bybit/adapter.py:254-265)

### Шаг 5. Отмена «лишнего» ордера после срабатывания

Как только бот получает уведомление по [[bybit-private-websocket|WebSocket]] (поток событий от биржи в реальном времени), что один из ордеров исполнился — немедленно отменяется второй:

- Сработал стоп-лосс (`orderStatus=Triggered` для SL) → отменить тейк-профит.
- Сработал тейк-профит (`orderStatus=Filled` для TP) → отменить стоп-лосс.

(src/execution/coordinator.py:443-448)

Отмена ордера, который уже успел исполниться до того, как пришла команда отмены, возвращает ошибку биржи `110001` («ордер не существует или завершён»). Это **нормальная ситуация**, не ошибка — код классифицирует её как [[reason-codes-assessment-output|`REJECT_ORDER_ALREADY_TERMINAL`]] и игнорирует (src/execution/bybit/adapter.py:315-316).

## Формулы и расчёты

### Формула fee-aware количества

**Задача:** определить, сколько BTC можно продать в ТП/СЛ, после того как биржа сообщила о заполнении ордера на покупку.

**Формула** (src/execution/bracket.py:130-133):

```
oco_qty = FLOOR_TO_STEP( cumExecQty − cumExecFee )   если fee в базовой монете
oco_qty = FLOOR_TO_STEP( cumExecQty )                  если fee в котируемой монете (USDT)
```

Где `FLOOR_TO_STEP(x)` — округление вниз до ближайшего кратного шагу лота:

```
FLOOR_TO_STEP(x, step) = floor(x / step) × step
```

**Расшифровка простыми словами:**
- `cumExecQty` — сколько BTC реально куплено (биржа сообщает в событии `Filled`).
- `cumExecFee` — комиссия. Если её взяли в BTC, нужно вычесть из количества.
- `FLOOR_TO_STEP` — обрезаем «хвост» дробной части, который не кратен минимальному лоту. Именно обрезаем (вниз), а не округляем (которое могло бы дать число чуть больше баланса).

**Реализация в Python:**
```python
net = cum_exec_qty - cum_exec_fee if fee_currency == base_coin else cum_exec_qty
return (net / qty_step).quantize(Decimal("1"), rounding=ROUND_DOWN) * qty_step
```

(src/execution/bracket.py:130-133)

Для точных денежных расчётов используется тип `Decimal` (не `float`) — чтобы избежать ошибок округления с плавающей точкой.

## Примеры / сценарии

### Сценарий A: нормальный ход (ТП срабатывает)

Условия: покупаем 0.001 BTC по цене 65 000 USDT. ТП — 70 000, СЛ — 60 000.

1. **Бот генерирует bracket_id** = `"7abe87bf"` (8 символов UUID).

2. **Вход** — Market BUY 0.001 BTC:
   - Биржа исполняет, возвращает `cumExecQty=0.001`, `cumExecFee=0.000001`, `feeCurrency="BTC"`.

3. **Вычисляем oco_qty** (src/execution/bracket.py:130-133):
   ```
   net = 0.001 - 0.000001 = 0.000999 BTC
   qty_step = 0.000001
   oco_qty = floor(0.000999 / 0.000001) × 0.000001 = 999 × 0.000001 = 0.000999 BTC
   ```

4. **Тейк-профит** — Limit Sell 0.000999 BTC @ 70 000 USDT (GTC):
   - `orderLinkId = "oco-7abe87bf-tp-2"` (attempt=2, т.к. entry был attempt=1).

5. **Стоп-лосс** — Stop Market Sell 0.000999 BTC, trigger @ 60 000 USDT:
   - `orderLinkId = "oco-7abe87bf-sl-2"`.

6. Цена растёт до 70 000 → срабатывает ТП → бот получает событие `Filled` для ТП → отправляет `cancel_order` для СЛ → СЛ отменён → позиция закрыта с прибылью.

### Сценарий B: стоп-лосс срабатывает

Всё то же самое, только цена падает до 60 000 → биржа триггерит СЛ (переходит в статус `Triggered`) → бот немедленно отменяет ТП → СЛ исполняется по рынку → позиция закрыта с ограниченным убытком.

### Сценарий C: тонкий рынок, частичное исполнение СЛ

В редкой ситуации резкого обвала (flash crash) стаканная глубина на уровне СЛ может оказаться недостаточной. Тогда стоп-рыночный ордер исполнится лишь частично (статус `PartiallyFilled`). В этом случае:

- Бот переходит в состояние `EXIT_SL_RESIDUAL` (см. [[emergency-flatten-and-residual|аварийное закрытие и остаток]]).
- Отменяет ТП (чтобы не было «сиротского» ордера на продажу монеты, которой уже нет).
- Немедленно отправляет дополнительный Market Sell на остаток.

(src/execution/coordinator.py:520-610, ADR 0020 sub-decision 4)

### Сценарий D: почему 0.000643, а не 0.000644 (реальные данные из probe v3-B)

Из реального тестирования на Demo-аккаунте Bybit:
- Заказано: 0.000644 BTC.
- `cumExecQty` = 0.000644, `cumExecFee` = 0.000000644 BTC.
- Без нашей формулы → попытка продать 0.000644 → ошибка 170131 (подтверждено эмпирически).
- С нашей формулой → `net = 0.000643356` → FLOOR до шага 0.000001 → продаём **0.000643** → ошибки нет (ADR 0020 sub-decision 6).

## Подводные камни / что важно понимать

**1. Bybit Spot молча переписывает GTC→IOC для стоп-ордеров.**

Если отправить стоп-ордер с `timeInForce=GTC` (стоять, пока не отменят), биржа втихую переписывает его на `IOC` (немедленно исполнить или отменить). Это означает, что при срабатывании стоп-лосс превращается в «мгновенный» ордер — и если в стакане недостаточно покупателей, часть позиции не продастся (сценарий C выше).

Именно поэтому в коде поле `timeInForce` **намеренно отсутствует** в payload стоп-ордера (подтверждено тестом: `assert "timeInForce" not in p`, tests/unit/test_bybit_adapter_stop.py:24). Отправлять поле, которое биржа всё равно проигнорирует, нет смысла.

**2. Гонка при отмене (cancel race) — это нормально.**

Когда СЛ срабатывает, между событием `Triggered` и фактическим `Filled` проходят миллисекунды. За это время бот пытается отменить ТП. Но ТП может успеть сам исполниться до того, как отмена дойдёт до биржи. В этом случае биржа вернёт `110001` («ордер уже завершён»). Это не ошибка — бот её классифицирует как `REJECT_ORDER_ALREADY_TERMINAL` и продолжает работу (src/execution/bybit/adapter.py:314-316).

**3. ROUND_DOWN — строго вниз.**

Округление количества всегда вниз, никогда вверх. Если вычисленное net-количество 0.000999356 BTC при шаге 0.000001, то продаём 0.000999 — не 0.001 (которое превышает баланс). Остаток 0.000000356 BTC — это «допустимая пыль» ниже минимального лота, её нельзя продать, она остаётся на балансе.

**4. TTL периода арминга — 60 секунд.**

Пока бот размещает ТП и СЛ после исполнения входного ордера, он находится в промежуточном состоянии `OCO_ARMING`. Если что-то пошло не так и бот завис в этом состоянии дольше **60 секунд**, он переходит в [[safety-stops-and-halts|`HALTED`]] с кодом `HALT_OCO_ARM_TIMEOUT`. Это защита от ситуации, когда открытая позиция осталась без защиты на длительное время (src/execution/coordinator.py:877-895).

**5. Запрещённые поля — не отправляются вообще.**

Поля `tpslMode`, `takeProfit`, `stopLoss`, `tpOrderType`, `slOrderType`, `triggerDirection` запрещены на Spot V5. Если код случайно попытается их передать, адаптер выбросит исключение ещё до отправки на биржу (src/execution/bybit/adapter.py:14-21, 199-204). Это «барьер» против случайных регрессий.

**6. Формат ID в flatten-ордерах отличается.**

При экстренной отмене позиции (flatten) бот использует другой префикс: `flat-{bracket_id}-{kind}-{attempt}`. Например: `flat-7abe87bf-emg-1` (аварийная отмена) или `flat-7abe87bf-res-1` (остаток после частичного СЛ). Это позволяет отличить в журнале «плановый выход» от «аварийного» (src/execution/bracket.py:60-77).
