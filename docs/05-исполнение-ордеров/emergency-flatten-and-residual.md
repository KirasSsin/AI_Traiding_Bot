# Аварийное закрытие позиции и остаток после стопа (защита от двойной продажи)

**TL;DR:** Когда боту нужно срочно выйти из позиции — он делает это по строгому каскаду: отменяет все ордера, проверяет кошелёк и продаёт. Если при продаже что-то пошло не так по сети (запрос ушёл, но ответ не вернулся), бот не пытается продать снова — он останавливается и ждёт оператора, потому что вторая попытка может означать продажу того, чего уже нет («двойная продажа»).

## Простыми словами

Представьте, что вы продаёте квартиру и уже подписали договор, но курьер потерял вашу копию. Вы не знаете — договор зарегистрирован или нет. Если вы немедленно попытаетесь подписать второй договор с другим покупателем — вы продадите квартиру дважды, а это катастрофа.

Именно такая ситуация возникает с биржей: бот отправил ордер на продажу, но интернет-соединение прервалось до того, как биржа вернула подтверждение. Ордер **мог** исполниться. Попытка продать снова (с другим id) — это «двойная продажа»: вы пытаетесь продать монеты, которых у вас уже нет. На Spot-рынке это означает **фантомный шорт** — отрицательный баланс монет, которого не должно быть.

Бот решает эту проблему с помощью трёх концепций:

1. **Трёхрезультатный исход** — вместо простого «получилось / не получилось» у каждой попытки продажи есть три состояния: «продано», «точно не ушло», «неизвестно». Только при «точно не ушло» можно пробовать снова.

2. **Идемпотентный ключ ордера** — каждая *логически одна и та же* попытка продажи получает один и тот же уникальный ID. Если биржа получила запрос дважды с одним ID, она сама откажет второму с кодом «дубликат» — и это считается успехом, а не ошибкой.

3. **Классификация пыли** — если после стопа остаётся кусочек монеты меньше минимального размера ордера, биржа всё равно его не примет. Бот не пытается продать заведомо отклонимое количество — просто считает позицию закрытой.

Аналогия: **стоп-лосс** — это как договорённость с брокером «продай, если цена упадёт до X». Но иногда ваш брокер успевает продать только часть акций (потому что покупателей на все сразу не хватило) — тогда нужно продать остаток отдельно. Это и есть сценарий с «остатком» (residual). Как именно устроены стоп-лосс и тейк-профит вокруг позиции — см. [[oco-bracket-emulation|эмуляцию OCO-брекета]].

## Как это работает у нас

### Функция `flatten()` — аварийный каскад

Это главная функция принудительного выхода из позиции. Вызывается когда бот решает, что позицию нужно немедленно закрыть — по любой причине (расхождение данных при [[reconcile-as-truth|сверке с биржей]], внешний сигнал оператора и т.д.). Оркестрацией этого вызова управляет [[coordinator-orchestration|координатор исполнения]].

`src/execution/coordinator.py:687–739`

**Шаг 1 — Отменить все ордера.**
Прежде чем продавать, бот отменяет все живые ордера на бирже (`cancel_all_orders`). Иначе может получиться ситуация, когда и рыночная продажа пройдёт, и TP-ордер самоисполнится — итого продадим в два раза больше, чем есть.

**Шаг 2 — Узнать сколько монет есть.**
Бот читает кошелёк через API (`get_wallet_balance`) и вычисляет `free_qty = wallet_balance - locked` — то есть «свободные монеты» (не заблокированные под другими ордерами). Поле `wallet_balance` содержит всё, `locked` — что занято биржей.

**Шаг 3 — Округлить вниз до шага лота.**
Биржа принимает только кратные значения. Например, если шаг `0.001`, а свободных `0.0057`, то продать можно только `0.005`. Округление всегда вниз (`_step_floor`), чтобы не попытаться продать больше, чем есть на бирже. `src/execution/coordinator.py:871–875` Откуда берутся шаг лота и минимальный размер ордера — см. [[bybit-filters|фильтры биржи]].

**Шаг 4 — Попытка первая (попытка-1).**
Бот отправляет рыночный ордер на продажу (Market Sell) через [[bybit-order-adapter|адаптер Bybit]] с deterministic ID вида `flat-{bracket_id}-emg-1`. Результат — одно из трёх состояний `_SendOutcome`:

| Результат | Что произошло | Следующий шаг |
|-----------|--------------|---------------|
| `SENT_OK` | Продано (или биржа говорит «дубликат — уже было») | Стоп, позиция закрыта |
| `NOT_SENT` | Биржа синхронно отказала до исполнения | Можно попробовать попытку-2 |
| `UNKNOWN` | Сетевой сбой после отправки | **HALT** — оператор разбирается |

**Шаг 5 — При `NOT_SENT` — попытка-2 с уменьшенным объёмом.**
Иногда биржа отказывает из-за фильтров (например, из-за копеечной разницы в округлении). Тогда бот вычитает один шаг лота из объёма (`qty - qty_step`) и пробует снова с ID `flat-{bracket_id}-emg-2`. Если и это не сработало (`NOT_SENT`) — HALT.

**Шаг 6 — Если обе попытки провалились или хотя бы одна вернула `UNKNOWN` — HALT (`FLATTEN_FAILED` → `HALTED`).**

```python
# src/execution/coordinator.py:717-739
outcome = self._try_place_market_sell(qty, link_id=self._emg_link_id(flatten_key, 1))
if outcome is _SendOutcome.SENT_OK:
    return
if outcome is _SendOutcome.UNKNOWN:
    self._halt_flatten(trigger_reason, cause="attempt1_unknown_outcome")
    return
retry_qty = self._step_floor(qty - qty_step, qty_step)
if retry_qty > Decimal("0"):
    outcome = self._try_place_market_sell(retry_qty, link_id=self._emg_link_id(flatten_key, 2))
    if outcome is _SendOutcome.SENT_OK:
        return
    if outcome is _SendOutcome.UNKNOWN:
        self._halt_flatten(trigger_reason, cause="attempt2_unknown_outcome")
        return
self._halt_flatten(trigger_reason, cause="both_attempts_not_sent")
```

### Класс `_SendOutcome` — трёхрезультатный исход

`src/execution/coordinator.py:46–87`

Это перечисление с тремя значениями — ключевое архитектурное решение (ADR 0020, исправление S55 BYBIT-02):

- **`SENT_OK`** — ордер принят биржей. Включает случай, когда биржа вернула код `110072` (дубликат) — это значит, что наш более ранний ордер с таким же ID уже прошёл. Считается успехом.
- **`NOT_SENT`** — синхронный отказ. Биржа ответила кодом ошибки ещё до того, как что-то попало в «книгу ордеров» (matching engine). Вторая попытка безопасна.
- **`UNKNOWN`** — сетевой сбой. Соединение прервалось уже после того, как запрос был отправлен. Ордер мог дойти до биржи. Вторая попытка с другим ID — риск двойной продажи.

### Функция `_try_place_market_sell()` — как классифицируются ошибки

`src/execution/coordinator.py:789–857`

Функция ловит три класса ошибок и превращает их в `_SendOutcome`:

1. **`BybitAPIError`** — биржа вернула структурированный ответ с ненулевым кодом ошибки. Это синхронный отказ. Исключение: если retCode == `110072` (OrderLinkedID duplicate) — возвращаем `SENT_OK`.

2. **`_NETWORK_UNKNOWN_EXC`** — сетевые исключения: `OSError`, `socket.timeout`, `requests.exceptions.RequestException`, `pybit.exceptions.FailedRequestError`. Это значит соединение упало на транспортном уровне (обёртку повторов и обработку лимитов частоты запросов см. в [[bybit-rest-client-and-backoff|REST-клиенте Bybit]]). Возвращаем `UNKNOWN`. `src/execution/coordinator.py:70–87`

3. **Любое другое исключение** — трактуется как `NOT_SENT` (консервативно). Примечание в коде: если ошибка возникла уже после успешной отправки (например, при разборе ответа биржи), то эта классификация технически неверна — но правильная реализация сложнее и отмечена как задача.

### Идемпотентность через `make_flatten_link_id()`

`src/execution/bracket.py:60–77`

Каждый Market Sell при flatten получает deterministic ID по шаблону:

```
flat-{bracket_id}-{kind}-{attempt}
```

где `kind` = `"emg"` (аварийный flatten) или `"res"` (остаток после IOC-стопа), `attempt` — номер попытки (1 или 2).

Важно: попытка-1 и попытка-2 несут **разные** ID (`-emg-1` vs `-emg-2`). Поэтому идемпотентность Bybit работает только внутри одной логической попытки (защищает от повторной отправки того же запроса из-за rate-limit retry). Между двумя попытками дедупликации нет — именно поэтому UNKNOWN-исход требует HALT, а не авто-переход к попытке-2.

Для ID соблюдается ограничение Bybit: не длиннее 36 символов. Если длина превышена — функция выбрасывает `ValueError`. `src/execution/bracket.py:75–76`

### Обработка retCode 110072 как успеха

`src/execution/coordinator.py:806–820, 586–594`

Bybit возвращает `110072 OrderLinkedID is duplicate` когда мы отправляем ордер с тем же `orderLinkId`, который уже прошёл. Это значит: предыдущая попытка с таким ID успешно исполнилась, а мы просто получаем подтверждение задним числом.

Бот проверяет оба условия одновременно: `exc.ret_code == 110072` **и** `exc.reason is AdapterReasonCode.REJECT_DUPLICATE_ORDER`. Такая двойная проверка нужна, чтобы не «проглотить» другую ошибку, если маппинг в `_MAP` когда-то изменится.

### Функция `_handle_sl_partial()` — дослать остаток

`src/execution/coordinator.py:520–610`

Стоп-ордер на Bybit Spot может выполниться частично (IOC — Immediate-Or-Cancel). Это значит: биржа продала часть монет, а оставшуюся часть (`leavesQty`) вернула. О частичном исполнении бот узнаёт из события `PartiallyFilled`, приходящего по [[bybit-private-websocket|приватному WebSocket]]. Бот должен дослать остаток отдельным рыночным ордером.

**Почему сначала отменяют TP, а потом продают остаток:**
Если оставить TP (Take Profit) висеть на бирже и продать остаток — позиция становится нулевой. Но TP всё ещё живёт. Если цена вдруг вырастет до TP — ордер самоисполнится, и бот **продаст монеты, которых нет** (фантомный шорт). Поэтому алгоритм:

1. Перевести состояние в `EXIT_SL_RESIDUAL` (`PARTIAL_FILL` → `EXIT_SL_RESIDUAL`).
2. Отменить TP-ордер (best-effort, не блокирует основной путь).
3. Если `leavesQty == 0` — стоп фактически закрыл всё. Переход в `FLAT`.
4. Если `leavesQty > 0` — продать остаток рыночным ордером с ID `flat-{bracket_id}-res-{attempt}`.

```python
# src/execution/coordinator.py:534-541
self._transition(ExecutionEvent.PARTIAL_FILL)  # OCO_ARMED → EXIT_SL_RESIDUAL
row = self._repo.get(self._symbol)
if row is not None and row.oco_tp_order_id is not None:
    self._best_effort_cancel(row.oco_tp_order_id)
raw_leaves_qty = Decimal(evt.get("leavesQty", "0"))
if raw_leaves_qty <= 0:
    self._transition(ExecutionEvent.RESIDUAL_FLATTENED)
    return
```

### Классификация неустранимой пыли (BYBIT-05)

`src/execution/coordinator.py:548–558`

После округления `leavesQty` вниз до шага лота может оказаться, что результат меньше минимального размера ордера (`min_order_qty`). Такой ордер биржа гарантированно отклонит — это «пыль», которую никак не продать.

Бот не пытается отправить заведомо отклонимый ордер. Вместо этого он:
1. Логирует ситуацию.
2. Переходит в `RESIDUAL_FLATTENED` (считает позицию закрытой).

Монеты-пыль остаются на кошельке — это нормально. Потеря минимальна (меньше одного шага лота) и несопоставима с риском ложного HALT.

```python
# src/execution/coordinator.py:548-558
qty_step = self._qty_step()
leaves_qty = self._step_floor(raw_leaves_qty, qty_step)
if leaves_qty <= Decimal("0") or leaves_qty < self._min_order_qty():
    _log.info("flatten.ioc_residual_dust ...")
    self._transition(ExecutionEvent.RESIDUAL_FLATTENED)
    return
```

### Вспомогательные функции

**`_step_floor(value, step)`** — округление вниз до шага. `src/execution/coordinator.py:871–875`
Формула: `floor(value / step) * step`. Если `step <= 0` или `value <= 0` — возвращает `0`.

**`_qty_step()`** — шаг лота монеты. `src/execution/coordinator.py:859–863`
Читает `self._adapter.step_size` — публичный аксессор, скрывающий внутреннюю структуру фильтров биржи (ARCH-03). Поле `_filters` снаружи не видно.

**`_min_order_qty()`** — минимальный размер ордера. `src/execution/coordinator.py:865–869`
Читает `self._adapter.min_order_qty`. Аналогичный публичный аксессор (BYBIT-05).

### Связь с FSM (автоматом состояний)

Весь этот денежный путь порождает события, которые меняют состояние бота (полный список состояний и разрешённых переходов — в [[execution-state-machine|конечном автомате исполнения]]):

| Событие FSM | Откуда | Куда |
|-------------|--------|------|
| `PARTIAL_FILL` | `_handle_sl_partial`: IOC стоп закрыл частично | `OCO_ARMED` → `EXIT_SL_RESIDUAL` |
| `RESIDUAL_FLATTENED` | Остаток продан (или это пыль) | `EXIT_SL_RESIDUAL` → `FLAT` |
| `FLATTEN_FAILED` | Аварийное закрытие провалилось | `EXIT_SL_RESIDUAL` → `HALTED` |
| `FLATTEN_FAILED` | То же при аварийном flatten | `OCO_ARMED` / `LONG_OPEN` / ... → `HALTED` |

`src/execution/state_machine.py:129–137`

## Формулы и расчёты

### Округление вниз до шага лота

```
qty = floor(free_qty / qty_step) * qty_step
```

**Простыми словами:** делим количество монет на шаг лота, отбрасываем дробную часть (всегда вниз), умножаем обратно. Получаем наибольшее количество, которое точно кратно шагу.

**Пример:** свободно `0.0057 BTC`, шаг `0.001 BTC`. Считаем: `0.0057 / 0.001 = 5.7` → `floor(5.7) = 5` → `5 * 0.001 = 0.005 BTC`. Продаём `0.005`, остаток `0.0007` — пыль.

**Реализация:** `src/execution/coordinator.py:871–875`, функция `_step_floor`.

### Объём остатка после IOC-стопа

Из WS-события приходит поле `leavesQty` — количество, которое стоп не успел продать. После округления вниз:

```
leaves_qty = _step_floor(raw_leaves_qty, qty_step)
if leaves_qty < min_order_qty: → пыль, RESIDUAL_FLATTENED
else: → Market Sell на leaves_qty
```

## Примеры / сценарии

### Сценарий 1 — Успешный аварийный flatten

Допустим, на кошельке `0.5 ETH`, шаг `0.001`:

1. Бот вызывает `flatten(reason=HALT_RECONCILE_DIVERGENCE)`.
2. Отменяются все ордера.
3. Кошелёк: `wallet_balance=0.5`, `locked=0.0` → `free_qty=0.5`.
4. Округляем: `_step_floor(0.5, 0.001) = 0.5` (уже кратно).
5. ID попытки-1: `flat-a1b2c3d4-emg-1`.
6. Market Sell `0.5 ETH` — биржа отвечает OK.
7. `_try_place_market_sell` возвращает `SENT_OK`. Каскад завершён.

### Сценарий 2 — Сетевой сбой на попытке-1 (UNKNOWN)

1. Попытка-1: запрос ушёл, соединение оборвалось — поймали `OSError`.
2. `_try_place_market_sell` возвращает `UNKNOWN`.
3. Бот немедленно вызывает `_halt_flatten(cause="attempt1_unknown_outcome")`.
4. FSM: `→ HALTED`, записывается `HALT_FLATTEN_FAILED`.
5. Попытка-2 **не делается**. Оператор проверяет биржу вручную.

### Сценарий 3 — IOC-стоп с остатком

Купили `1.0 BTC` по стопу, биржа продала только `0.6 BTC`, вернула `leavesQty=0.4`:

1. Приходит WS-событие `PartiallyFilled` для SL-ордера.
2. `_handle_sl_partial` переводит в `EXIT_SL_RESIDUAL`.
3. Отменяется TP-ордер (чтобы не стал «сиротой»).
4. `raw_leaves_qty = 0.4`.
5. Округляем: `_step_floor(0.4, 0.001) = 0.4` (уже кратно).
6. `0.4 >= min_order_qty` → продолжаем.
7. ID: `flat-{bracket_id}-res-1`.
8. Market Sell `0.4 BTC` — OK.
9. FSM: `RESIDUAL_FLATTENED` → `FLAT`.

### Сценарий 4 — Пыль: остаток слишком мал

После IOC-стопа `leavesQty=0.00005 BTC`, `min_order_qty=0.001 BTC`:

1. Округляем: `_step_floor(0.00005, 0.001) = 0.0` (меньше шага).
2. `leaves_qty <= 0` → классифицируем как пыль.
3. Логируем, переходим в `RESIDUAL_FLATTENED` → `FLAT`.
4. `0.00005 BTC` остаётся на кошельке — ничтожная сумма, HALT не поднимаем.

### Сценарий 5 — Дубликат как подтверждение успеха

1. Попытка-1 ушла на биржу, ответ не получен — поймали `socket.timeout` → `UNKNOWN`.
   (Только что объяснили: это HALT. Но предположим — тот же ID через `_retry_with_backoff` внутри адаптера успел повторить до `_NETWORK_UNKNOWN_EXC` и получил 110072.)
2. Bybit возвращает `retCode=110072`, `reason=REJECT_DUPLICATE_ORDER`.
3. `_try_place_market_sell` проверяет оба поля: `exc.ret_code == 110072` и `exc.reason is AdapterReasonCode.REJECT_DUPLICATE_ORDER`.
4. Оба условия выполнены → возвращается `SENT_OK`.
5. Каскад останавливается — наша предыдущая попытка с тем же ID была принята биржей.

## Подводные камни / что важно понимать

**Две попытки — это не «повтор одного ордера».** Попытки-1 и -2 несут разные ID (`-emg-1` vs `-emg-2`). Для Bybit это два разных ордера. Поэтому переход к попытке-2 безопасен только когда точно известно, что попытка-1 не была исполнена (`NOT_SENT`). `UNKNOWN` — это запрет на попытку-2.

**HALT при UNKNOWN — это не поломка, это правильно.** Когда бот остановился по `UNKNOWN`, это означает «мы не знаем, продали или нет». Оператор должен зайти в биржу, проверить статус ордера с ID `flat-{bracket_id}-emg-1` и либо вручную подтвердить продажу, либо дать боту команду возобновить работу.

**TP нужно отменять ДО продажи остатка, а не после.** Порядок важен: если сначала продать остаток, а потом не успеть отменить TP — TP может самоисполниться на пустой позиции, создав фантомный шорт. `src/execution/coordinator.py:536–537`

**«Дедупликация» защищает только одну логическую попытку.** Один ID `flat-X-emg-1` защищает от случайного двойного исполнения именно попытки-1 (например, из-за retry в rate-limit ситуации). Но не защищает попытку-2 от попытки-1 — для этого и нужен `UNKNOWN` → `HALT`.

**Код 110072 обрабатывается особым образом.** Почти все коды ошибок биржи — это `NOT_SENT`. Но 110072 — исключение: он означает, что ордер уже прошёл. Перепутать значит либо поднять ложный HALT (если считать ошибкой), либо зациклиться (если считать неизвестной ошибкой).

**Как сохраняется причина HALT (γ-паттерн).** В строке состояния `ExecutionStateRow` есть поле `halt_reason: str | None` (`src/execution/state_repo.py:29`). Как это состояние и неизменяемый журнал `halt_log` хранятся в базе — см. [[execution-state-persistence-and-halt-audit|хранение состояния исполнения и журнал аварийных остановок]]. Метод `_set_halt()` записывает его по правилу «первое значение остаётся навсегда»: если поле уже заполнено — следующие вызовы его не меняют (`src/execution/state_repo.py:158–163`). Поэтому при провале flatten в поле `halt_reason` всегда окажется `HALT_FLATTEN_FAILED` — именно этот код пишет `_halt_flatten()` через `_set_halt()` (`src/execution/coordinator.py:747–755`). Аргумент `reason=`, с которым вызвали `flatten()` (например, `HALT_RECONCILE_DIVERGENCE`), называется «причина-инициатор» (`trigger_reason`) и сохраняется в таблице `halt_log` в поле `context_json` — он не попадает в `halt_reason` строки, а дополняет картину в аудит-журнале (`src/execution/state_repo.py:154–157`). Итог для оператора: смотрите `halt_reason` в таблице `execution_state` (там будет `HALT_FLATTEN_FAILED`), а за полным контекстом — в `halt_log.context_json` (там будет `trigger_reason`, `cause` и снимок состояния на момент HALT; ADR 0021, γ-pattern).
