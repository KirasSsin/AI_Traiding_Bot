# Хранение состояния исполнения и журнал аварийных остановок

**TL;DR:** Бот записывает текущее состояние позиции (в какой фазе находится, сколько монет куплено, какие ордера активны) в базу данных после каждого шага — чтобы при перезапуске точно знать, что происходило. Каждая аварийная остановка фиксируется в отдельном неизменяемом журнале аудита.

---

## Простыми словами

Представьте, что вы управляете магазином и ведёте кассовую книгу. Каждый раз, когда покупатель платит или вы выдаёте товар, вы записываете в книгу актуальный баланс. Если свет неожиданно выключится — вы откроете книгу и сразу увидите, в каком состоянии была касса перед отключением. Бот делает то же самое: после каждого важного шага (выставил ордер, ордер исполнился, выставил стоп-лосс) он обновляет запись в базе данных.

**Зачем это нужно?** Программы иногда падают или перезапускаются. Если бот упадёт в момент, когда позиция открыта (монеты куплены, ордера выставлены), а при перезапуске не будет знать об этом — он может купить снова, или, наоборот, проигнорировать уже открытую сделку. [[01-как-работает-бот/storage-and-database|База данных]] — это «память» бота, которая переживает любой сбой.

Кроме текущего состояния бот ведёт второй, отдельный **журнал аварийных остановок** (halt_log). Это как чёрный ящик самолёта: каждый раз, когда бот принудительно [[01-как-работает-бот/safety-stops-and-halts|останавливается]] по какой-либо причине, в журнал добавляется новая запись с точным описанием того, что случилось и в каком состоянии был бот в этот момент. Удалить или изменить старые записи нельзя — журнал только пополняется (append-only).

## Как это работает у нас

### Таблица execution_state: одна строка на монету

Вся информация о текущем состоянии хранится в таблице `execution_state`. На каждую торговую пару (например, BTCUSDT) — ровно одна строка. Это как карточка клиента в картотеке: одна карточка, которую обновляют при каждом изменении.

Таблица была создана миграцией `0003_execution_state.sql` и расширялась в трёх последующих миграциях. Финальный набор полей (колонок) описан в классе `ExecutionStateRow` (`src/execution/state_repo.py:16–37`):

| Поле | Тип | Что хранит |
|---|---|---|
| `symbol` | текст | торговая пара (BTCUSDT) — первичный ключ |
| `state` | текст | текущая фаза [[05-исполнение-ордеров/execution-state-machine\|FSM]] (FLAT, ENTRY_PENDING, LONG_OPEN, OCO_ARMING, OCO_ARMED, RECONCILING, HALTED, COOLDOWN...) |
| `position_qty` | текст (Decimal) | количество монет в позиции |
| `entry_price` | текст (Decimal) | цена входа |
| `oco_main_order_id` | текст | устаревшее название (S5); перепрофилировано в S21: хранит ID входного ордера (entry_ack.order_id), который reconciler читает при восстановлении после сбоя |
| `bracket_id` | текст | идентификатор текущего брокетного ордера |
| `oco_tp_order_id` | текст | ID ордера Take Profit (взять прибыль) |
| `oco_sl_order_id` | текст | ID ордера Stop Loss (стоп-потеря) |
| `expected_oco_qty` | текст (Decimal) | ожидаемый объём выхода |
| `arming_started_at` | текст | ISO-метка, когда началось выставление TP+SL |
| `last_attempt_num` | целое | счётчик попыток выставления TP+SL (уникальность ID) |
| `updated_at` | текст | ISO-метка последнего обновления |
| `halt_reason` | текст | причина первой аварийной остановки (primary-wins) |
| `last_exit_reason` | текст | причина последнего выхода из позиции |
| `last_reconcile_at` | текст | ISO-метка последней сверки с биржей |
| `bootstrap_at` | текст | ISO-метка запуска процесса (записывается один раз) |
| `bracket_tp_price` | текст (Decimal) | запланированная цена TP (добавлена в S55 TL-01) |
| `bracket_sl_trigger_price` | текст (Decimal) | запланированная цена срабатывания SL (добавлена в S55 TL-01) |

**Почему денежные поля хранятся как текст, а не как число?** Это принципиальное решение. Компьютерные числа с плавающей точкой (тип float/REAL) не могут точно хранить суммы вроде «0.1 BTC»: внутри это превращается в бесконечную дробь, и при каждой операции возникает крошечная погрешность. Для денег это недопустимо — ошибка в десятом знаке после запятой в расчётах объёма накапливается и может привести к неверному количеству ордера. Поэтому бот хранит денежные значения как строку текста («0.00312500»), а перед расчётами превращает их в тип `Decimal`, который гарантирует точность до произвольного числа знаков. Миграция `004_money_columns_text.sql` исправила оставшиеся таблицы (orders, fills, positions), где ещё были REAL-колонки.

(src/execution/state_repo.py:16–37; migrations/0003_execution_state.sql; migrations/0004_execution_state_v2.sql:6–11; migrations/0007_bracket_exit_prices.sql:10–11)

### Класс ExecutionStateRow: строгий объект данных

Чтение из базы данных и запись в неё происходит через класс `ExecutionStateRow` — замороженный (неизменяемый после создания) объект данных. «Замороженный» означает, что случайно изменить значение поля нельзя: нужно создать новый объект с изменёнными полями. Это защита от незаметных ошибок.

Функция `_row_to_dataclass()` (`src/execution/state_repo.py:166–186`) преобразует сырую строку из SQLite обратно в объект Python: каждое денежное поле через `Decimal(r[N])`, каждое опциональное поле — с проверкой на `None`.

---

### upsert(): вставить или обновить за одну операцию

Метод `upsert()` (`src/execution/state_repo.py:52–101`) — ключевая операция записи. Его название расшифровывается как «insert or update» (вставить или обновить).

Логика: если записи для данного символа ещё нет — создать новую строку. Если уже есть — обновить все поля. Это делается одной атомарной SQL-командой:

```sql
INSERT INTO execution_state (symbol, state, ...)
VALUES (...)
ON CONFLICT(symbol) DO UPDATE SET state=excluded.state, ...
```

«Атомарная» означает, что операция либо выполнится целиком, либо не выполнится вовсе — промежуточного состояния не бывает. Если бот упадёт в середине записи, база данных не окажется в испорченном состоянии.

(src/execution/state_repo.py:52–101)

### get() и find_by_order_id(): чтение состояния

Метод `get(symbol)` (`src/execution/state_repo.py:103–111`) читает текущую строку для указанной торговой пары. Возвращает `None`, если запись ещё не создана (например, при первом запуске).

Метод `find_by_order_id(order_id)` (`src/execution/state_repo.py:113–128`) решает специфическую задачу: когда биржа присылает уведомление об исполнении ордера (по [[05-исполнение-ордеров/bybit-private-websocket|WebSocket]] — постоянному каналу связи), она передаёт свой внутренний ID ордера. Бот должен понять, какому именно [[05-исполнение-ордеров/oco-bracket-emulation|брокетному ордеру]] (TP или SL) этот ID соответствует. Метод ищет строку, в которой любое из полей `oco_main_order_id`, `oco_tp_order_id` или `oco_sl_order_id` совпадает с переданным ID. Это механизм, благодаря которому FillRecorderAdapter (записывает факт исполнения) узнаёт `bracket_id` по любому из ID входящих в него ордеров.

(src/execution/state_repo.py:103–128; комментарий «S12 Q5 — used by FillRecorderAdapter for WS orderId → bracket_id resolution»)

### Журнал аварийных остановок: таблица halt_log

Таблица `halt_log` создана миграцией `0005_halt_persistence.sql:11–19`. В отличие от `execution_state`, из неё ничего не удаляется и не изменяется — только добавляются новые строки:

```sql
CREATE TABLE halt_log (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol       TEXT    NOT NULL,
    ts           TEXT    NOT NULL,
    reason       TEXT    NOT NULL,
    context_json TEXT    NOT NULL
);
CREATE INDEX halt_log_symbol_ts ON halt_log(symbol, ts);
```

Поле `context_json` — это JSON-объект с полным описанием ситуации на момент остановки (подробнее — ниже). Индекс по `(symbol, ts)` позволяет быстро найти все остановки по конкретной паре и упорядочить их по времени.

(migrations/0005_halt_persistence.sql:11–19)

### _set_halt(): атомарная запись аварийной остановки

Метод `_set_halt()` в `ExecutionStateRepo` (`src/execution/state_repo.py:130–163`) — единственная точка записи информации об остановке. Он следует правилу «сначала аудит»:

1. Записать строку в `halt_log` (аудит всегда, безусловно).
2. Только потом — попытаться обновить поле `halt_reason` в `execution_state`.

Оба шага выполняются в одной транзакции. Порядок важен: если в будущем транзакция будет разделена, аудитная запись сохранится в любом случае.

**Правило идемпотентности «первая причина побеждает» (primary-wins):** поле `halt_reason` в `execution_state` записывается только один раз — для первой остановки. Если бот остановился по одной причине, а потом ещё раз была вызвана остановка по другой — вторая причина в колонке `halt_reason` не перезаписывает первую. Логика в коде:

```python
# Обновить halt_reason только если он ещё NULL (т.е. первая остановка)
self._conn.execute(
    "UPDATE execution_state SET halt_reason = ?, updated_at = ? "
    "WHERE symbol = ? AND halt_reason IS NULL",
    (reason, ts, symbol),
)
```

Но в `halt_log` — запись добавляется при каждой остановке, первой, второй, и далее. Оператор всегда видит полную хронологию.

Метод безопасен для случая, когда строки в `execution_state` ещё нет (bootstrap — первый запуск): тогда только аудитная запись добавляется, обновление `halt_reason` пропускается.

(src/execution/state_repo.py:130–163)

### Coordinator._set_halt(): что сохраняется в context_json

`ExecutionStateRepo._set_halt()` принимает готовый словарь контекста. Этот словарь формирует вышестоящий `Coordinator._set_halt()` (`src/execution/coordinator.py:970–999`). [[05-исполнение-ордеров/coordinator-orchestration|Координатор]] собирает текущее состояние бота перед записью:

```python
ctx = {
    "state_at_halt": row.state.name,        # в какой фазе был бот
    "position_qty": str(row.position_qty),   # сколько монет держали
    "oco_tp_id": row.oco_tp_order_id,        # ID ордера Take Profit
    "oco_sl_id": row.oco_sl_order_id,        # ID ордера Stop Loss
    "expected_qty": str(row.expected_oco_qty), # ожидаемый объём выхода
    "last_event": last_event.name,           # какое событие спровоцировало остановку
    "last_attempt_num": row.last_attempt_num, # номер попытки выставления TP+SL
    "arming_started_at": row.arming_started_at, # когда началось выставление
}
```

Этот набор даёт оператору полную картину: в какой фазе упал бот, что было открыто, какое событие стало последним.

(src/execution/coordinator.py:970–999)

### Эволюция схемы через прямые миграции

База данных расширялась поэтапно через «прямые» миграции (forward-only): каждая добавляет колонки или создаёт таблицы, никогда не удаляет существующее. SQLite ограничивает изменение типа существующей колонки, поэтому всё расширение идёт через `ALTER TABLE ... ADD COLUMN`.

| Миграция | Что добавила |
|---|---|
| `0003_execution_state.sql` | Базовая таблица: symbol, state, position_qty, entry_price, oco_main_order_id, updated_at |
| `0004_execution_state_v2.sql` | bracket_id, oco_tp_order_id, oco_sl_order_id, expected_oco_qty, arming_started_at, last_attempt_num — OCO-эмуляция тремя ордерами |
| `0005_halt_persistence.sql` | halt_reason, last_exit_reason, last_reconcile_at, bootstrap_at + таблица halt_log с индексом |
| `0007_bracket_exit_prices.sql` | bracket_tp_price, bracket_sl_trigger_price — S55 BLOCKER TL-01 |

Поле `oco_main_order_id` — пример перепрофилирования поля: оно появилось в первой реализации OCO через один «главный» ордер (S5). Когда пришли к эмуляции тремя отдельными ордерами (0004), старое поле не удалили, а дали ему новую роль (S21, ADR 0021 SD-3): теперь в нём хранится ID входного (покупного) ордера. [[05-исполнение-ордеров/reconcile-as-truth|Reconciler]] читает это значение при восстановлении после сбоя — по нему он запрашивает у биржи статус входного ордера и определяет, был ли он исполнен (`coordinator.py:379–384`).

Миграция `0007_bracket_exit_prices.sql` исправила критическую ошибку S55 TL-01: до неё цены TP и SL, переданные в `start_bracket()`, нигде не сохранялись. Когда входной ордер исполнялся (fill) и нужно было выставить TP+SL, бот не знал, по каким ценам это делать, и никогда не выставлял защитные ордера.

## Примеры / сценарии

### Сценарий 1: обычная сделка

1. Бот в состоянии `FLAT`, в строке `execution_state`: `state="FLAT"`, `position_qty="0"`.
2. Стратегия подаёт сигнал на покупку → бот выставляет рыночный ордер → `upsert` обновляет строку: `state="ENTRY_PENDING"`.
3. Биржа подтверждает исполнение → `upsert`: `state="LONG_OPEN"`, `position_qty="0.00312"`, `entry_price="67543.21"`.
4. Бот выставляет TP и SL → `upsert`: `state="OCO_ARMING"`, `arming_started_at="2026-06-26T12:01:00Z"`, `oco_tp_order_id="tp-abc"`, `oco_sl_order_id="sl-xyz"`.
5. Оба ордера подтверждены → `upsert`: `state="OCO_ARMED"`.
6. Срабатывает TP → `state="EXIT_PENDING"` → `state="FLAT"`, `position_qty="0"`, `last_exit_reason="EXIT_TP_HIT"`.

На каждом шаге — один вызов `upsert()`. Если бот упадёт на шаге 4, при перезапуске он увидит `state="OCO_ARMING"` и `arming_started_at` — и продолжит процесс выставления ордеров.

### Сценарий 2: аварийная остановка

1. Бот в `state="OCO_ARMING"`, выставление TP+SL не завершается дольше 60 секунд (TTL из [[01-как-работает-бот/configuration-and-settings|`oco_arming_ttl_seconds = 60`]], `src/platform/config.py:177`).
2. Координатор вызывает `_set_halt(reason=HALT_OCO_ARM_TIMEOUT, ...)`.
3. В базе за одну транзакцию:
   - В `halt_log` добавляется строка: `reason="HALT_OCO_ARM_TIMEOUT"`, `ts="2026-06-26T12:02:01Z"`, `context_json={"state_at_halt":"OCO_ARMING", "position_qty":"0.00312", ...}`.
   - В `execution_state` поле `halt_reason` меняется с `NULL` на `"HALT_OCO_ARM_TIMEOUT"`.
4. FSM переходит в `HALTED`.
5. Если через секунду пришёл ещё один триггер остановки (например, ошибка сети) — в `halt_log` добавляется вторая строка, но `halt_reason` в `execution_state` остаётся `"HALT_OCO_ARM_TIMEOUT"` (primary-wins).

Оператор открывает базу и читает хронологию по `halt_log`: кто первый, кто второй, с каким контекстом.

### Сценарий 3: поиск ID ордера по WebSocket

1. Биржа присылает через WebSocket: «ордер `ord-tp-abc` исполнен».
2. FillRecorder вызывает `find_by_order_id("ord-tp-abc")`.
3. База ищет строку, где `oco_tp_order_id = "ord-tp-abc"` — находит, возвращает строку с `bracket_id`.
4. FillRecorder записывает факт исполнения с правильным `bracket_id`.

## Подводные камни / что важно понимать

**1. Таблица execution_state — одна строка навсегда.** Бот работает с одной торговой парой (v0.1 одна пара), но строка никуда не исчезает между сделками — только обновляется. При первом запуске строка создаётся `upsert()` в момент первой записи состояния.

**2. halt_reason — только первая причина.** Если бот остановился по одной причине, а потом произошло что-то ещё — второе событие видно только в `halt_log`, но не в `halt_reason`. Это намеренно: первопричина важнее последствий. Оператор должен читать оба источника.

**3. Нет записи halt_log без строки в execution_state — неправда.** `_set_halt()` явно поддерживает «bootstrap path»: если строки в `execution_state` ещё нет (бот упал до первого `upsert`), аудитная запись всё равно добавляется в `halt_log`.

**4. bracket_tp_price / bracket_sl_trigger_price — критические поля.** До S55 TL-01 они не существовали. Если бот перезапустится с базой, созданной до миграции `0007`, эти поля будут `NULL` — и при попытке выставить TP+SL после входного fill координатор вызовет `HALT_OCO_ARM_TIMEOUT`, а не выставит ордера. Это поведение fail-closed (безопасное закрытие вместо «голой» позиции без защиты).

**5. float для денег — запрещён.** Пример: `0.1 + 0.2` в Python-float = `0.30000000000000004`. Для количества монет и цен это недопустимо — разница в последних знаках ведёт к неверному объёму ордера, который биржа может отклонить. Все денежные значения хранятся как строки Decimal.

**6. Поле arming_started_at — только в состоянии OCO_ARMING.** В других состояниях оно может содержать метку предыдущей попытки — проверять его имеет смысл только когда `state == "OCO_ARMING"`. Смотри комментарий: `arming_started_at: str | None  # ISO-8601 UTC; only set in OCO_ARMING` (`src/execution/state_repo.py:26`).

**7. Поле oco_main_order_id — живое, не пустое.** В текущей версии бот записывает в это поле ID входного (покупного) ордера сразу после выставления (`coordinator.py:384`: `oco_main_order_id=entry_ack.order_id`). Если открываете базу вручную и видите там реальный ID ордера — это норма. Поле называется «oco_main» по историческим причинам (S5), но его роль изменена в S21: reconciler читает его как `LocalState.entry_order_id` при восстановлении после сбоя (`coordinator.py:238`).

|---|---|
| `HALT_OCO_ARM_TIMEOUT` | Попытка выставить TP+SL длилась дольше 60 секунд (TTL). Позиция открыта, но без защитных ордеров — бот останавливается, чтобы не оставлять «голую» позицию. |
| `HALT_FLATTEN_FAILED` | Не удалось продать позицию [[05-исполнение-ордеров/emergency-flatten-and-residual\|аварийным образом]]. Бот останавливается в трёх случаях: (1) первая попытка вернула неопределённый исход (сетевая ошибка после отправки — ордер возможно уже исполнился); (2) вторая попытка тоже вернула неопределённый исход; (3) обе попытки не были отправлены вообще. Важно: при сценарии (1) бот останавливается сразу — без второй попытки — чтобы не продать дважды. Оператор должен вручную сверить позицию на бирже и закрыть её при необходимости. (`coordinator.py:724–739`) |
| `HALT_PHANTOM_SL` | Зарезервированный код, описывающий угрозу «призрачного» SL: TP-ордер мог исполниться, пока мы пытались его отменить — тогда возникла бы «фантомная» короткая позиция на спотовом рынке (невозможная в норме). На практике бот реагирует иначе: отменяет TP-ордер по принципу «лучшее усилие без гарантии» (fire-and-forget, `coordinator.py:537`) и продолжает аварийный выход из позиции. Код `HALT_PHANTOM_SL` в текущей реализации нигде не испускается через `_set_halt()` — он зарезервирован как описание угрозы, которую предотвращает немедленная отмена TP. |
| `HALT_RECONCILE_DIVERGENCE` | [[05-исполнение-ордеров/reconcile-as-truth\|Сверка с биржей]] выявила несоответствие: бот думал, что позиции нет, а биржа говорит, что есть (или наоборот). |
| `HALT_EXIT_RECONCILE_DIVERGENCE` | То же самое, но при сверке в момент выхода из позиции. |
| `HALT_BOOTSTRAP_AMBIGUOUS` | При запуске (bootstrap) сверка с биржей дала неоднозначный результат — бот не может определить, есть ли открытая позиция. |
| `HALT_RUNTIME_CRASH` | В [[01-как-работает-бот/main-loop-tick\|основном цикле бота]] возникло необработанное исключение (ошибка программы). |
| `HALT_BAR_POLL_STALL` | Бот не смог получить свежие данные о ценах N раз подряд (по умолчанию N=24, то есть 24×5с = 120 секунд). Смотри `runtime_bar_poll_stall_threshold = 24` (`src/platform/config.py:214–221`). |
| `HALT_DATA_QUALITY` | [[07-данные/data-quality-detector\|Данные о цене выглядят аномально]] (отклонение от предыдущего бара превышает порог 0.5%, `src/platform/config.py:234–241`). |

(src/risk/reason_codes.py:78–119)
