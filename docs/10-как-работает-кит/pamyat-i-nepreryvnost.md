# Память кита: как ИИ помнит между сессиями

**TL;DR:** Каждый разговор с ИИ начинается с чистого листа — без памяти прошлого. Чтобы работа не терялась, проект использует четыре слоя памяти: живой файл-состояние, семантический поиск по прошлым сессиям, институциональная память каждого агента и структурированная база знаний. Все вместе они позволяют «киту» точно продолжить с того места, где он остановился.

## Простыми словами

Представьте, что вы наняли специалиста-консультанта. Каждый раз, когда он приходит к вам на встречу, он забывает всё, что вы обсуждали раньше — как будто это первая встреча. Приходится тратить время, объясняя заново: «Вот проект, мы на такой-то стадии, вот что решили неделю назад…»

Именно такая проблема с языковыми моделями: **контекстное окно** — то есть «рабочая память» ИИ во время сессии — обнуляется, когда разговор заканчивается. Следующий разговор начинается абсолютно чистым.

В нашем проекте эту проблему решают четыре инструмента:

1. **Файл-состояние SPRINT_STATE.md** — это «записная книжка консультанта», которую он обязательно читает в самом начале каждой встречи. В ней написано: над каким спринтом работаем, на какой фазе остановились, какая задача сейчас в работе.

2. **Семантический поиск claude-mem** — архив всех прошлых сессий. Можно спросить: «Мы решали эту проблему раньше?» — и поиск за секунды найдёт ответ из прошлых разговоров.

3. **Память агентов** (`.claude/agent-memory/`) — каждый специалист-агент (ревьюер кода, трейдинг-эксперт и т.д.) ведёт собственный «журнал уроков» с ловушками и паттернами, которые он уже видел в этом проекте.

4. **База знаний llm-wiki** — структурированная кураторская библиотека: архитектура, решения, компоненты. Её читают первой, прежде чем лезть в «сырой» код.

## Как это работает у нас

### Слой 1 — SPRINT_STATE.md: рабочая память между сессиями

Файл `llm-wiki/wiki/project/SPRINT_STATE.md` — самый важный документ в системе. Именно его кит обязан читать первым делом при каждом запуске, до любого кода и любых вопросов (CLAUDE.md, «Первое действие каждой сессии»).

Что в нём хранится:

- Номер текущего спринта и его фаза (например, `sprint: 56`, `phase: 4-execution`)
- Ветка git и последний тег (`branch: feature/sprint-56-project-docs`)
- Краткое описание текущего блока работы
- Поле «Следующее действие» — буквально с чего начать

Пример реального содержимого (SPRINT_STATE.md, строки 1–15):

```text
sprint: 56
phase: 4-execution
branch: feature/sprint-56-project-docs
tag: v0.1.0-alpha.55
---
Следующее действие: WF-1 (scan/inventory всего src/ + кита) → финализировать список страниц docs/
```

Благодаря этому файлу кит не тратит время на перечитывание многостраничных планов — он просто берёт «Следующее действие» и продолжает.

**Жёсткое ограничение размера:** файл должен оставаться меньше 6 КБ. Это не дань аккуратности, а техническое правило — Read-инструмент имеет ограничение в ~25 000 токенов (~90 КБ), и раздутый SPRINT_STATE.md буквально заблокировал бы старт сессии. История прошлых спринтов хранится отдельно (см. ниже).

(CLAUDE.md, «Правила файла»: «BUDGET ≤ 6 KB BINDING»)

### Слой 2 — claude-mem: семантический поиск по прошлым сессиям

**Семантический поиск** — это не простой поиск по ключевым словам (как Ctrl+F), а поиск по смыслу. Достаточно написать «как мы решали проблему с аннуализацией Шарпа» — и система найдёт прошлые сессии, где это обсуждалось, даже если там использовались другие слова.

Используется через MCP-сервер (MCP — это «сервер инструментов», внешняя программа, которую кит может вызывать как инструмент). Вызов выглядит так:

```text
mcp__plugin_claude-mem_mcp-search__smart_search "<вопрос>"
```

В нашем каскаде поиска claude-mem занимает второй шаг — его проверяют, только если в базе знаний llm-wiki ответа не нашлось.

При старте сессии MCP автоматически загружает до 50 наблюдений из прошлых разговоров (development-workflow.md, «ФАЗА 0b — Старт сессии (АВТОМАТИЧЕСКИ, хуки)»).

**Уборка памяти:** когда наблюдений накопится много (каждые 5 спринтов или больше 30 наблюдений), запускают `anthropic-skills:consolidate-memory` — это склеивает похожие записи и убирает шум, чтобы поиск оставался точным (kit-overview-ru.md, строка 58).

### Слой 3 — Память агентов: институциональное знание

Каждый специализированный агент (см. [[agenty-revyuery]]) ведёт собственную «записную книжку» в директории `.claude/agent-memory/<имя-агента>/`. Там хранятся уроки, которые агент извлёк из работы именно с нашим проектом.

Структура у каждого агента одинакова:
- `MEMORY.md` — тонкий индекс: одна строка на урок со ссылкой
- Отдельные `.md`-файлы под каждый урок или паттерн

Например, агент `doc-writer` накопил более 130 файлов уроков: `lesson_dsr_kurtosis_pearson_trap.md`, `lesson_fsm_pattern.md`, `lesson_halt_ratchet_atomic_flush.md` и т.д. — каждый описывает нюанс именно нашего кода, который нельзя узнать из учебника.

Всего в проекте 14 агентов со своей памятью (`.claude/agent-memory/`):

| Агент | Специализация |
|-------|--------------|
| `architecture-reviewer` | Архитектура, паттерны DI, конкурентность |
| `bybit-api-reviewer` | Протокол Bybit V5, REST/WebSocket |
| `dashboard-reviewer` | Дашборд FastAPI + React |
| `data-integrity-reviewer` | SQLite, Parquet, целостность данных |
| `doc-reviewer` | Согласованность документации |
| `doc-reviewer-depth` | Глубокое ревью документов |
| `doc-writer` | Написание docs/ из кода |
| `frontend-developer` | React-компоненты |
| `python-reviewer` | Стиль Python, type hints |
| `quant-stats-reviewer` | Математика: DSR, Kelly, MC |
| `security-auditor` | Безопасность, API-ключи, HMAC |
| `test-engineer` | Тесты, покрытие, property-тесты |
| `trader-expert` | Торговые решения, стратегии |
| `trading-logic-reviewer` | Логика стратегий, FSM, исполнение |

Важно: `.claude/agent-memory/` это **проектная** директория внутри репозитория, не глобальная. Файл MEMORY.md создаётся агентом автоматически при первой записи — если его ещё нет, это нормально.

(tooling-inventory-ru.md, раздел 1: «Все имеют `memory: project` (institutional knowledge в `.claude/agent-memory/<agent>/MEMORY.md`)»)

### Слой 4 — llm-wiki: кураторская база знаний

`llm-wiki/wiki/` — это структурированная база знаний о проекте: архитектурные решения (ADR), описания компонентов, история спринтов, паттерны. Её принципиальное отличие от «сырого» кода — она скомпилирована и сжата: прочитать компонент из wiki в 4–7 раз дешевле по токенам, чем читать сырой ADR.

Структура (llm-wiki/CLAUDE.md):

```
wiki/
├── index.md                    # каталог всех страниц
├── log.md                      # хронологический журнал событий
├── trading/                    # стратегии, индикаторы, концепции
└── project/
    ├── architecture/           # SOP, tooling, kit-overview
    ├── components/             # компоненты (FSM, риск, бэктест...)
    ├── sprints/                # canonical sprint-NN.md страницы
    └── decisions/              # ADR 0001-0071+
```

### Каскад поиска — в каком порядке кит ищет информацию

Это ключевое правило работы, зафиксированное в ADR 0043. Порядок жёсткий и обязательный:

```
Вопрос → проверяй по порядку:

  ШАГ 1: wiki/<страница>.md
           (кураторская база, структурирована, самая дешёвая)
      ↓ не нашёл / недостаточно
  ШАГ 2: claude-mem smart_search "<вопрос>"
           (семантический поиск по прошлым сессиям)
      ↓ не нашёл
  ШАГ 2.5: claude-mem:smart-explore
           (структурный поиск по корпусу)
      ↓ нужно текущее состояние кода
  ШАГ 3: Grep (поиск по тексту в src/)
      ↓ нужен полный контент
  ШАГ 4: Read файл с offset+limit
           (самый дорогой — используем последним)
```

**Почему именно такой порядок?** Токены — это стоимость работы ИИ. Прочитать wiki-страницу стоит в 4–7 раз дешевле, чем читать сырой файл. Найти ответ через семантический поиск занимает секунды против минут ручного чтения. Правило «wiki → mem → grep → read» — это не педантизм, а экономия ресурсов (tooling-inventory-ru.md, раздел 13).

(kit-overview-ru.md, «Cascade rule (BINDING per ADR 0043)»)

### Где хранится история спринтов

SPRINT_STATE.md не хранит историю — только текущее состояние. История живёт в трёх местах (SPRINT_STATE.md, «История спринтов (где искать)»):

| Хранилище | Что там |
|-----------|---------|
| `llm-wiki/wiki/project/sprints/sprint-NN-<slug>.md` | Canonical-страница каждого спринта: что сделано, что исправлено, метрики |
| `llm-wiki/wiki/log.md` | Хронологический журнал (append-only): корабельный бортжурнал проекта |
| `llm-wiki/wiki/project/architecture/current-state.md` | Канонические счётчики + карта спринтов |

### Когда что создаётся

| Событие | Что появляется |
|---------|---------------|
| Начало нового спринта — фаза 2 | Предварительный бэклог (pre-s{N}-backlog.md) |
| Фаза 2/8 при архитектурном решении | ADR в `wiki/project/decisions/` |
| Фаза 3 (планирование) | Plan-файл в `wiki/project/plans/<дата>-sprint-N-<slug>.md` |
| Фаза 8 (корабль) | Страница спринта `sprints/sprint-NN-<slug>.md` |
| Фазы 6/9 (ревью / закрытие) | Запись в `wiki/log.md` |

### mark_chapter и spawn_task: навигация в длинных сессиях

Во время работы кит периодически ставит «главы» (mark_chapter) — это разделители в транскрипте сессии, по которым потом можно быстро найти нужный момент. Примерно как закладки в книге. Вызывается через MCP `ccd_session`:

```text
mcp__ccd_session__mark_chapter "Sprint 56 — ориентирование"
```

Если во время работы над задачей возникает побочная проблема (например, найден баг не в scope текущего спринта), используется `spawn_task` — это создаёт отдельную мини-сессию-«чип» для этой задачи, не засоряя основной контекст.

(tooling-inventory-ru.md, раздел 7.2)

## Примеры / сценарии

### Сценарий: начало новой сессии после недельного перерыва

1. Кит читает `SPRINT_STATE.md` → видит: `sprint: 56`, `phase: 4-execution`, «Следующее действие: WF-1 (scan/inventory всего src/ + кита) → финализировать список страниц docs/».
2. Проверяет git: `git branch --show-current && git log --oneline -3` — убеждается, что находится на правильной ветке.
3. Вызывает `mark_chapter "Sprint 56 — session resume"`.
4. Начинает работу с «Следующего действия» — без вопросов «где мы?», без перечитывания планов.

Весь старт занимает ~2 минуты вместо 15–20 при пересказе всего контекста заново.

### Сценарий: ревьюер обнаруживает нестандартный паттерн в коде

Агент `quant-stats-reviewer` в процессе работы понимает, что аннуализация коэффициента Шарпа в нашем проекте сделана нестандартно (умножают на √8760 вместо √252). Это специфика нашего кода.

Он записывает это в `.claude/agent-memory/quant-stats-reviewer/` как урок. В следующем спринте, когда тот же агент встретит тот же код, он не будет заново «открывать» эту нестандартность — урок уже есть в памяти.

### Сценарий: вопрос «мы это уже решали?»

Кит работает над новым модулем и хочет знать: «Как мы решили проблему OCO-эмуляции?». Вместо того чтобы перечитывать десятки файлов:

1. **ШАГ 1:** ищет в wiki — находит `llm-wiki/wiki/project/components/execution.md` → есть описание OCO через три ордера. Готово.
2. Если бы не нашёл — **ШАГ 2:** `mem-search "OCO emulation"` → нашлись бы записи из спринта S6.

## Подводные камни / что важно понимать

**SPRINT_STATE.md растёт — и это опасно.** История — злейший враг лимита 6 КБ. В спринте S46 файл раздулся до 86 КБ (1239 строк) из-за накопленных исторических секций, что заблокировало старт сессии. Теперь правило жёсткое: история уходит в `log.md` и `sprint-NN.md`, в SPRINT_STATE.md — только текущее состояние.

**MEMORY.md агента может не существовать.** Это нормально — файл создаётся при первой записи. Не надо паниковать, видя «файл не найден», при первом запуске нового агента.

**Семантический поиск — не замена коду.** claude-mem ищет по прошлым сессиям, а не по текущему состоянию кода. Если функция переименована с момента прошлого разговора — поиск вернёт устаревший ответ. Для текущего состояния кода — Grep.

**Ответ из памяти ≠ актуальный ответ.** Перед тем как рекомендовать функцию или путь, найденные в памяти агента, нужно проверить, существует ли они сейчас: `ls <путь>` или `grep <функция> src/`. Паттерн зафиксирован в MEMORY.md: «Верифицировать перед рекомендацией».

**consolidate-memory нужен регулярно.** После ~30 наблюдений семантический поиск начинает давать шум. `anthropic-skills:consolidate-memory` (каждые 5 спринтов) — это техническое обслуживание памяти, не опциональное дополнение.
