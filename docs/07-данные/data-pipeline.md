# Конвейер данных: seed → stream → persist

**TL;DR:** Перед тем как бот начнёт торговать, он сначала проверяет архив свечей и латает любые дыры через REST-запросы, а затем подключается к WebSocket и получает новые свечи в режиме реального времени — каждую сохраняет на диск в формате Parquet.

## Простыми словами

Представьте, что бот — это аналитик, которому нужна полная история цен за последние недели или месяцы, прежде чем он начнёт принимать решения. Если в этой истории есть пробелы (например, биржа была недоступна несколько часов), аналитик сначала звонит на биржу и запрашивает пропущенные данные, а потом садится перед монитором и смотрит на новые цены в прямом эфире.

Именно это и делает **конвейер данных** (data pipeline — «сборочная линия» для рыночных данных):

1. **Проверяет архив** — есть ли пробелы в сохранённых свечах?
2. **Заполняет пробелы** — запрашивает пропущенные свечи через [[bybit-rest-source|REST-запрос]] (обычный интернет-запрос «дай мне данные за такой-то период»).
3. **Подключается к потоку** — переключается на [[bybit-ws-consumer|WebSocket]] (постоянное соединение с биржей, по которому данные поступают автоматически в реальном времени).
4. **Сохраняет каждую свечу** — пишет на диск в формате [[parquet-storage|Parquet]] (компактный столбцовый формат для аналитических данных).

Если во время работы WebSocket-соединение «пропустило» несколько минут или часов — конвейер немедленно вставляет в архив специальную **GAP-метку** (пометку «здесь была дыра»), чтобы downstream-индикаторы ([[ema-rsi-indicators|RSI]], [[atr-indicator|ATR]] и т.п.) не получили искажённые окна расчёта.

## Как это работает у нас

### Главная функция: `MarketDataPipeline.run()`

Точка входа — асинхронный метод `run()` класса `MarketDataPipeline` (src/marketdata/pipeline.py:44–64). Он последовательно запускает три фазы.

```python
async def run(self, max_bars: int | None = None) -> None:
    await self._seed_gaps()        # Фаза 1: залатать пробелы через REST
    if max_bars == 0:
        return                     # seed-only режим (для тестов)
    self._ws.start()               # Фаза 2: открыть WebSocket
    count = 0
    async for msg in self._ws.stream():   # Фаза 3: читать поток
        gap_bars, bar = self._builder.process_with_gap_fill(msg)
        if gap_bars:
            self._writer.append(gap_bars)  # сначала GAP-метки
        if bar is not None:
            self._writer.append([bar])     # потом реальная свеча
            count += 1
            if max_bars is not None and count >= max_bars:
                return
```

Параметр `max_bars`:
- `None` — работать бесконечно (боевой режим).
- `N > 0` — остановиться после N подтверждённых свечей (удобно для тестов).
- `0` — режим **seed-only**: только залатать пробелы, к WebSocket не подключаться. Используется в тестах и при инициализации архива (src/marketdata/pipeline.py:49–50).

---

### Фаза 1: `_seed_gaps()` — заполнение пробелов

(src/marketdata/pipeline.py:66–78)

Метод вызывает `find_gaps()`, получает список пробелов, и для каждого делает REST-запрос к бирже:

```python
async def _seed_gaps(self) -> None:
    gaps = find_gaps(self._parquet_dir, interval_ms=self._interval_ms)
    for gap_start, gap_end in gaps:
        start_ms = int(gap_start.timestamp() * 1000)
        end_ms   = int(gap_end.timestamp() * 1000)
        bars = self._rest.get_klines(
            symbol=self._symbol,
            interval=self._ws_interval,
            start_ms=start_ms,
            end_ms=end_ms,
        )
        if bars:
            self._writer.append(bars)
```

Если REST-запрос вернул пустой список (например, биржа не имеет данных за этот период), ничего не записывается — пробел остаётся пробелом.

---

### Нахождение пробелов: `find_gaps()`

(src/marketdata/gaps.py:9–35)

**Простыми словами:** функция читает все `.parquet`-файлы из папки архива, выписывает для каждой свечи `open_time` (когда свеча открылась) и `close_time` (когда закрылась), сортирует их и ищет места, где соседние свечи «не стыкуются».

**Алгоритм шаг за шагом:**

1. Найти все файлы `*.parquet` в директории, отсортировать их по имени (src/marketdata/gaps.py:14).
2. Прочитать из каждого файла только два столбца: `open_time` и `close_time` (src/marketdata/gaps.py:21–25). Это быстро — Parquet поддерживает выборку столбцов без чтения всего файла.
3. Создать отсортированный список пар `(open_time, close_time)` — каждая пара описывает одну свечу (src/marketdata/gaps.py:27).
4. Пройти по парам и сравнить соседей (src/marketdata/gaps.py:30–34):

```python
step = timedelta(milliseconds=interval_ms)
for i in range(len(paired) - 1):
    _, prev_close = paired[i]
    next_open, _ = paired[i + 1]
    if next_open > prev_close and next_open - prev_close >= step:
        gaps.append((prev_close, next_open))
```

**Что означает условие:** если `open_time` следующей свечи строго позже `close_time` предыдущей **И** разрыв не меньше одного интервала (`step`) — это пробел. Функция возвращает пару `(prev_close, next_open)` — то есть `gap_start` = момент, когда закончилась последняя известная свеча, `gap_end` = момент, когда началась первая свеча после дыры.

**Пример:** если интервал 1 час и в архиве есть свечи за 00:00–01:00, 01:00–02:00, а затем 05:00–06:00 — функция вернёт пробел `(02:00, 05:00)`, т.е. три пропущенных часа.

Пустая директория → немедленно возвращает `[]` (src/marketdata/gaps.py:15–16), пробелов нет.

---

### Фаза 2: WebSocket-поток и GAP-маркеры

После заполнения пробелов конвейер запускает WebSocket-соединение с биржей (`self._ws.start()`) и входит в бесконечный цикл чтения сообщений (src/marketdata/pipeline.py:51–53).

Каждое сообщение обрабатывается через [[bar-builder-ws|`BarBuilder.process_with_gap_fill()`]] (src/marketdata/bar_builder.py:47–68). Этот метод:

1. Проверяет, не «прыгнул» ли WebSocket через один или несколько интервалов.
2. Если прыжок есть — генерирует **одну синтетическую GAP-свечу на каждый пропущенный интервал** (не одну на весь пробел, а именно по одной на каждый «слот»).
3. Возвращает список GAP-свечей и реальную закрытую свечу.

**Почему по одной на каждый слот?** Если бот пропустил 3 часа, то downstream-индикаторы (например, скользящая средняя за 10 часов) будут «видеть» дыру в ровно 3 бара, а не одну «заглушку». Это предотвращает корруппцию окон расчёта (помечено в коде как DI-01, src/marketdata/bar_builder.py:55).

**Структура GAP-свечи** (src/marketdata/bar_builder.py:99–117):

| Поле | Значение |
|------|----------|
| `open`, `high`, `low`, `close` | `0` — нули, не форвард-фил! |
| `volume` | `0` |
| `data_quality` | `DataQuality.GAP` |
| `open_time` / `close_time` | реальное время пропущенного слота |

Нули вместо «последней известной цены» — намеренное решение (edge-cases.md #1): форвардное заполнение ценой замаскировало бы пробел и создало ложные сигналы индикаторов.

Порядок записи на диск важен: сначала `gap_bars` (GAP-метки), потом реальная свеча — это гарантирует хронологическую последовательность (src/marketdata/pipeline.py:55–61).

### Фаза 3: сохранение в Parquet

Каждый вызов `self._writer.append(bars)` создаёт **новый файл** `.parquet` в директории архива (src/marketdata/storage.py:41–84). Имя файла содержит временной диапазон:

```text
btcusdt_60_20260420120000-20260420130000.parquet
```

Формат: `{symbol}_{interval}_{close_first}-{close_last}.parquet`.

Записи ведутся **атомарно**: сначала данные пишутся во временный файл `.tmp`, затем через `os.replace()` (атомарная операция на POSIX-системах) переименовываются в финальное имя. Параллельно записывается файл-контрольная сумма `.sha256`. Если процесс упадёт в середине записи — в архиве не останется битого файла (src/marketdata/storage.py:68–83).

---

### Protocol-интерфейсы: независимость от конкретных классов

Класс `MarketDataPipeline` принимает объекты через два интерфейса-протокола (src/marketdata/pipeline.py:12–18):

```python
class _RESTClient(Protocol):
    def get_klines(self, symbol: str, interval: str, start_ms: int, end_ms: int) -> list[Bar]: ...

class _WSConsumer(Protocol):
    def start(self) -> None: ...
    def stream(self) -> Any: ...  # AsyncIterator[dict[str, Any]]
```

**Protocol** (протокол) — это контракт «что умеет делать объект», без привязки к конкретному классу. Это позволяет в тестах передать mock-объект (макет-заглушку), а в боевом режиме — настоящий Bybit-клиент. Pipeline не знает и не должен знать, откуда берутся данные — он работает с любым объектом, у которого есть нужные методы.

## Примеры / сценарии

### Сценарий A: первый запуск бота, архив пуст

1. `run()` вызывает `_seed_gaps()`.
2. `find_gaps()` находит пустую директорию → возвращает `[]`.
3. Пробелов нет, REST-запросов нет.
4. Конвейер сразу переходит к WebSocket.
5. Каждая закрытая свеча записывается в новый `.parquet`-файл.

### Сценарий B: архив есть, но пропущены 3 часа

Архив содержит свечи до 02:00, потом — начиная с 05:00. Интервал 1 час.

1. `find_gaps()` читает все `.parquet`-файлы, видит: `close_time` бара в 02:00 → `open_time` следующего в 05:00.
2. Разрыв = 3 часа ≥ 1 час (один `step`) → пробел `(02:00, 05:00)`.
3. `_seed_gaps()` запрашивает REST: `get_klines(start_ms=02:00, end_ms=05:00)` → получает 3 свечи (02:00, 03:00, 04:00).
4. Эти три свечи записываются в архив.
5. Конвейер переходит к WebSocket.

### Сценарий C: WebSocket «провалился» на 2 интервала

В ходе работы WebSocket прислал свечу 10:00–11:00 (open_time=10:00), потом связь прервалась, и следующее подтверждённое сообщение пришло для свечи с open_time=12:00 (свеча 12:00–13:00).

1. `process_with_gap_fill()` видит: последняя подтверждённая имела open_ms=10:00, новая open_ms=12:00.
2. Разрыв = 2 интервала (12:00 - 10:00 = 2ч), значит один слот пропущен: 11:00–12:00.
3. Генерируется одна GAP-свеча для слота 11:00–12:00 (нули по OHLCV, `data_quality=GAP`).
4. `pipeline.run()` сначала записывает GAP-свечу, затем реальную свечу 12:00–13:00.

### Сценарий D: режим seed-only (`max_bars=0`)

```python
await pipeline.run(max_bars=0)
```

Полезен в тестах: бот заполняет пробелы через REST и выходит, не открывая WebSocket-соединение. Тест может затем проверить, что правильные свечи были записаны (src/marketdata/pipeline.py:49–50, тест `test_pipeline_seeds_gap_via_rest` в tests/unit/test_pipeline.py:189–221).

## Подводные камни / что важно понимать

**Один `.parquet`-файл на каждый `append()`**. Это означает, что после нескольких часов работы в директории накапливается много небольших файлов. Консолидация (слияние мелких файлов) явно помечена как «out of scope v0.1» (src/marketdata/storage.py:30–31). При большом объёме данных это может замедлить `find_gaps()`, которая читает все файлы при каждом запуске.

**GAP-свечи — нули, не «последняя цена»**. Если индикатор или стратегия не фильтрует `data_quality == GAP`, она получит ряд нулей вместо реальных цен. Стратегии должны проверять поле [[data-quality-detector|`data_quality`]] перед расчётом.

**Условие пробела — двойное** (src/marketdata/gaps.py:33): `next_open > prev_close` AND `next_open - prev_close >= step`. Первое условие означает «есть разрыв во времени», второе — «разрыв не меньше одного интервала». Это защищает от ложных срабатываний при микро-погрешностях timestamp (когда `next_open` опережает `prev_close` на миллисекунды, а не на целый интервал).

**WebSocket-сообщения с `confirm=false` игнорируются**. Биржа присылает промежуточные обновления внутри живой свечи — конвейер их пропускает и записывает только закрытую («подтверждённую») свечу (src/marketdata/bar_builder.py:40–45). Тот же принцип «только закрытая свеча» защищает от [[bar-source-live|look-ahead]] и в live-режиме торговли. Счётчик `count` в `run()` растёт только при `bar is not None` (src/marketdata/pipeline.py:60–63).

**Protocol-интерфейсы не проверяются в runtime**. Python-протоколы — статическая типизация. Если передать объект с неверной сигнатурой метода, ошибка проявится только при вызове, не при создании `MarketDataPipeline`.

**REST-запросы — синхронные внутри async-функции**. `_seed_gaps()` помечен как `async`, но сам REST-вызов (`self._rest.get_klines(...)`) выполняется синхронно (src/marketdata/pipeline.py:71–78). Если биржа отвечает медленно, это заблокирует event loop на время ожидания.
