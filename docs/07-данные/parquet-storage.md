# Хранение свечей: формат Parquet и целостность файлов

**TL;DR:** Бот сохраняет каждую порцию свечей в отдельный файл формата Parquet на диске. Рядом автоматически создаётся «контрольная сумма» (SHA-256), чтобы при следующем запуске можно было убедиться, что файл не испорчен. Запись спроектирована так, что сбой питания или ошибка в середине записи не оставят повреждённого файла.

---

## Простыми словами

Представьте, что бот — это исследователь, который каждый день ведёт журнал цен. Вместо обычной тетради он пишет в специально сложенную папку-архив. Вот ключевые свойства этой «папки»:

**Что такое Parquet?**

Parquet — это формат хранения данных, придуманный специально для аналитики. В отличие от обычного текстового файла (CSV), Parquet хранит данные по столбцам, а не по строкам, и автоматически их сжимает. Это означает: занимает меньше места на диске и читается значительно быстрее, когда нам нужно, например, взять только цены закрытия за месяц.

**Что такое сжатие Snappy?**

Snappy — это алгоритм сжатия: он «уплотняет» данные перед записью, чтобы они занимали меньше места. Главное его качество — он работает очень быстро, почти не замедляя запись и чтение. Это компромисс: не самое сильное сжатие из возможных, зато практически без потерь времени. Для финансовых данных, где нам часто нужно читать файлы обратно, это правильный выбор.

**Что такое атомарная запись?**

Представьте, что вы переписываете важный документ: начали стирать старое, не дописали новое — и вдруг погас свет. В итоге документ испорчен: ни старого, ни нового. Атомарная запись решает эту проблему: мы сначала пишем в черновик (временный файл), и только когда черновик полностью готов — мгновенно заменяем им оригинал. Операция замены либо случается целиком, либо не случается вообще. Промежуточного испорченного состояния не бывает.

**Что такое SHA-256 и зачем он нужен?**

SHA-256 — это математическая функция, которая превращает любой файл в уникальный «отпечаток пальца» длиной 64 символа. Если в файле изменился хотя бы один байт — отпечаток полностью меняется. Бот сохраняет этот отпечаток рядом с каждым Parquet-файлом (в так называемом sidecar-файле). При следующей проверке бот снова считает отпечаток и сравнивает: совпал — файл цел, не совпал — файл повреждён.

**Что такое sidecar-файл?**

Sidecar (буквально «коляска у мотоцикла») — это файл-компаньон, который всегда идёт рядом с основным. У каждого `.parquet` файла есть своя коляска `.sha256`, в которой хранится его контрольная сумма. Они всегда ходят парой.

## Как это работает у нас

### Класс `ParquetBarWriter` — кто управляет записью

`ParquetBarWriter` (src/marketdata/storage.py:28–84) — это объект, который знает, куда и как писать файлы. При создании ему указывают три вещи:
- **`directory`** — папка на диске, куда складывать файлы (создаётся автоматически, если её нет);
- **`symbol`** — торговая пара, например `BTCUSDT`;
- **`interval`** — временной интервал свечи, например `1h`.

```python
writer = ParquetBarWriter(
    directory=Path("/data/bars"),
    symbol="BTCUSDT",
    interval="1h"
)
```

(src/marketdata/storage.py:35–39)

---

### Шаг 1 — Метод `append()`: принимаем список свечей

Метод `append()` (src/marketdata/storage.py:41–84) принимает список объектов [[bar-model|`Bar`]] и сохраняет их в один новый файл. Если список пуст — выбрасывается ошибка `ValueError("cannot append empty bar list")` (src/marketdata/storage.py:44).

Первым делом список свечей превращается в таблицу формата Apache Arrow — это промежуточное представление данных в памяти, оптимизированное для колоночного хранения. Каждая свеча раскладывается по столбцам (src/marketdata/storage.py:46–59).

---

### Шаг 2 — Формирование имени файла

Имя файла строится автоматически по шаблону:

```text
{symbol}_{interval}_{first_close_time}-{last_close_time}.parquet
```

Например, для пакета часовых свечей BTCUSDT с 20 апреля 2026 года 01:00 по 03:00 UTC:

```text
btcusdt_1h_20260420010000-20260420030000.parquet
```

Имя строится из поля `close_time` первой и последней свечи пакета (src/marketdata/storage.py:61–65). Символ приводится к нижнему регистру.

---

### Шаг 3 — Схема столбцов Parquet

Каждый файл содержит строго фиксированный набор столбцов (src/marketdata/storage.py:13–25):

| Столбец | Тип | Что хранит |
|---|---|---|
| `open_time` | timestamp(ns, UTC) | Время открытия свечи (с точностью до наносекунды, в UTC) |
| `close_time` | timestamp(ns, UTC) | Время закрытия свечи |
| `open` | float64 | Цена открытия |
| `high` | float64 | Максимальная цена за период |
| `low` | float64 | Минимальная цена за период |
| `close` | float64 | Цена закрытия |
| `volume` | float64 | Объём торгов |
| `trade_count` | int64 | Количество сделок |
| `data_quality` | string | Пометка [[data-quality-detector\|качества]]: OK / GAP / STALE / SUSPECT |

Времена хранятся в UTC с точностью до наносекунды (`pa.timestamp("ns", tz="UTC")`) — это максимальная точность, которая предотвращает любые проблемы с часовыми поясами при последующем анализе.

---

### Шаг 4 — Атомарная запись: черновик → оригинал

Это главный защитный механизм. Вместо того чтобы писать сразу в финальный файл, система работает в три этапа (src/marketdata/storage.py:70–83):

**Этап A — Запись во временный файл:**

```python
tmp_path = path.with_suffix(path.suffix + ".tmp")
tmp_sidecar = sidecar.with_suffix(".sha256.tmp")
pq.write_table(table, tmp_path, compression="snappy")
```

Parquet-таблица записывается в файл `...parquet.tmp`. Если в этот момент что-то пойдёт не так — финальный файл не тронут.

**Этап B — Вычисление SHA-256 и запись sidecar во временный файл:**

```python
digest = _sha256(tmp_path)
tmp_sidecar.write_text(digest)
```

Контрольная сумма считается прямо с временного файла и записывается в `...sha256.tmp`.

**Этап C — Атомарное переименование обоих файлов:**

```python
os.replace(tmp_path, path)
os.replace(tmp_sidecar, sidecar)
```

`os.replace()` — это POSIX-операция (POSIX — стандарт, которому следуют Linux и macOS). Она гарантирует, что переименование происходит мгновенно и неделимо: любой процесс, читающий папку в этот момент, увидит либо старый файл, либо уже новый — никогда «полузаписанный».

**`finally`-блок — уборка при ошибке:**

```python
finally:
    if tmp_path.exists():
        tmp_path.unlink(missing_ok=True)
    if tmp_sidecar.exists():
        tmp_sidecar.unlink(missing_ok=True)
```

Если на любом из этапов A–C возникнет ошибка (например, кончилось место на диске) — блок `finally` удалит временные файлы. В результате в папке не останется ни финального файла (он не был переименован), ни мусорных `.tmp` (они удалены). Директория остаётся чистой.

---

### Функция `_sha256()` — вычисление контрольной суммы

```python
def _sha256(path: Path) -> str:
    h = hashlib.sha256()
    with path.open("rb") as fh:
        for chunk in iter(lambda: fh.read(65536), b""):
            h.update(chunk)
    return h.hexdigest()
```

(src/marketdata/storage.py:87–93)

Файл читается блоками по **64 KB** (65536 байт). Это важно: большой файл нельзя загрузить целиком в память без риска её исчерпать, поэтому хеш накапливается постепенно, блок за блоком. Результат — строка из 64 шестнадцатеричных символов (например, `a3f1c2d4...`).

---

### Функция `verify_parquet()` — проверка целостности

```python
def verify_parquet(path: Path) -> bool:
    sidecar = path.with_suffix(".sha256")
    if not sidecar.exists():
        return False
    expected = sidecar.read_text().strip()
    return _sha256(path) == expected
```

(src/marketdata/storage.py:96–106)

Функция возвращает `True` если файл цел, `False` — в любом другом случае:
- sidecar-файл не найден → `False` (src/marketdata/storage.py:103–104);
- хеш не совпал → `False` (src/marketdata/storage.py:106);
- всё в порядке → `True`.

Важно: функция **не бросает исключение** — она возвращает булево значение. Вызывающий код сам решает, что делать с результатом. Это сделано намеренно, чтобы проверку целостности можно было встроить в простое условие `if verify_parquet(path):` без блоков `try/except`.

---

### Стратегия «один `append` — один файл»

Каждый вызов `append()` создаёт новый файл. Слияния нескольких мелких файлов в один (consolidation) в версии v0.1 не реализовано — это явно отмечено в docstring класса (src/marketdata/storage.py:32). Это означает, что если бот часто пишет маленькие порции данных, со временем в папке накопится много небольших файлов.

## Примеры / сценарии

### Сценарий 1: Нормальная запись трёх свечей

Допустим, бот скачал три часовые свечи BTCUSDT и хочет их сохранить. Вот что происходит по шагам:

1. Вызывается `writer.append([bar_01, bar_02, bar_03])`.
2. Формируется имя файла, например `btcusdt_1h_20260420010000-20260420030000.parquet`.
3. Данные записываются в `btcusdt_1h_...parquet.tmp` со сжатием Snappy.
4. Вычисляется SHA-256 → `a3f1c2d4...` (64 символа).
5. Хеш записывается в `btcusdt_1h_...sha256.tmp`.
6. `os.replace()` переименовывает `.parquet.tmp` → `.parquet`.
7. `os.replace()` переименовывает `.sha256.tmp` → `.sha256`.
8. В папке остаётся ровно два файла: `.parquet` и `.sha256`. Никаких `.tmp`.

(подтверждение: тест `test_writer_leaves_no_tmp_file_on_success` — tests/unit/test_parquet_storage.py:52–59)

### Сценарий 2: Сбой во время переименования

Представим, что диск переполнился прямо в момент `os.replace()`. Что произойдёт:

1. `pq.write_table()` успешно записал `.parquet.tmp`.
2. `tmp_sidecar.write_text()` успешно записал `.sha256.tmp`.
3. `os.replace(tmp_path, path)` → выбрасывает `OSError`.
4. Управление переходит в `finally`-блок.
5. `.parquet.tmp` и `.sha256.tmp` удаляются.
6. В папке — пусто. Финального файла нет, мусора нет.

(подтверждение: тест `test_writer_atomic_no_partial_final_on_failure` — tests/unit/test_parquet_storage.py:62–82)

### Сценарий 3: Обнаружение повреждённого файла

Допустим, какая-то программа случайно дописала один байт в конец готового Parquet-файла.

```python
verify_parquet(path)  # → False
```

Функция считает SHA-256 от изменённого файла, сравнивает с сохранённым в `.sha256` — они не совпадают, возвращается `False`. Данные трогать не нужно, никаких исключений — просто сигнал «этот файл под вопросом».

(подтверждение: тест `test_verify_parquet_detects_corruption` — tests/unit/test_parquet_storage.py:114–123)

### Сценарий 4: Несколько `append` — несколько файлов

Два вызова `append` создают два независимых файла, каждый со своим sidecar:

```text
btcusdt_1h_20260420010000-20260420020000.parquet
btcusdt_1h_20260420010000-20260420020000.sha256
btcusdt_1h_20260420030000-20260420050000.parquet
btcusdt_1h_20260420030000-20260420050000.sha256
```

(подтверждение: тест `test_sidecar_written_for_multiple_appends` — tests/unit/test_parquet_storage.py:145–155)

## Подводные камни / что важно понимать

**Накопление мелких файлов.** Стратегия «один append — один файл» проста и безопасна, но если бот часто сохраняет небольшие порции, папка постепенно заполнится сотнями файлов. Слияние (consolidation) не реализовано в v0.1 и явно помечено как «out of scope» (src/marketdata/storage.py:32). При большом числе файлов анализ потребует их ручного объединения.

**SHA-256 считается с временного файла, не с финального.** Это правильно: хеш вычисляется до операции `os.replace()`, т.е. от тех самых байт, которые окажутся в финальном файле. Замена не меняет содержимое, только путь. (src/marketdata/storage.py:74)

**`verify_parquet` не бросает исключение при отсутствии sidecar.** Это намеренное решение (src/marketdata/storage.py:97–99): отсутствующий sidecar — не исключительная ситуация, а один из возможных ответов («не знаю, проверь вручную»). Код, вызывающий эту функцию, должен обрабатывать `False` как сигнал тревоги.

**Пустой список — ошибка.** Вызов `append([])` немедленно вызывает `ValueError` (src/marketdata/storage.py:44). Перед передачей списка убедитесь, что в нём есть хотя бы одна свеча.

**Имя файла берётся из `close_time`, а не из `open_time`.** Это важно понимать при поиске файлов вручную: если вы ищете свечу, открывшуюся в 00:00, — в имени файла будет 01:00 (время закрытия часовой свечи). (src/marketdata/storage.py:63–64)

**Поля `Decimal` приводятся к `float64` при записи.** Модель `Bar` хранит цены как `Decimal` (для точности расчётов в Python), но в Parquet они сохраняются как `float64` (src/marketdata/storage.py:50–54). При чтении обратно это `float64`, а не `Decimal`. Для торговых расчётов, где важна точность, используйте значения из модели `Bar` напрямую, а не из Parquet.
