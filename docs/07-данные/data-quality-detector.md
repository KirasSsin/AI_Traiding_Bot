# Детектор качества данных: выявление зависшего или испорченного фида

**TL;DR:** Каждую новую свечу бот сравнивает её цену закрытия с предыдущей. Если цена скакнула более чем на 0,5% за один бар — бот считает это признаком сломанного потока данных и немедленно останавливает торговлю.

## Простыми словами

Представьте, что вы следите за ценой нефти на электронном табло. Цена меняется плавно: 70, 70.10, 70.25, 70.15 — всё в разумных пределах. Но вдруг табло показывает 90 — мгновенный скачок на 28%. Вы не побежите немедленно скупать или продавать нефть: скорее всего, табло зависло или передаёт мусорные данные.

Бот сталкивается с той же проблемой. Биржа Bybit поставляет данные о закрытых [[bar-model|свечах]] (часовых баров) через REST-запросы. Иногда этот поток данных может:
- **Зависнуть** (stale feed — бот получает одно и то же старое значение снова и снова),
- **Испортиться** (corrupted feed — данные приходят, но содержат нереалистичные значения).

В обоих случаях если бот примет испорченные данные за реальную цену, он может открыть сделку по ложному сигналу и потерять деньги.

**Детектор качества данных** — это простая защитная проверка: перед тем как стратегия получит новую свечу, система сначала задаёт вопрос: «А не слишком ли сильно изменилась цена за один бар?» Если изменение выглядит неправдоподобно большим — торговля немедленно останавливается (происходит так называемый halt — принудительная остановка бота).

Аналогия из жизни: это как счётчик на спидометре, который предупреждает, если за долю секунды машина «ускорилась» с 60 до 600 км/ч — явно что-то неправильно с прибором.

## Как это работает у нас

### Шаг 1. Создание детектора при запуске бота

Когда бот стартует, `RuntimeManager` создаёт один экземпляр `BarPriceQualityDetector` и держит его в памяти на протяжении всей работы процесса (`src/runtime/manager.py:102–104`):

```python
self._quality_detector = BarPriceQualityDetector(
    threshold_pct=settings.runtime_quality_threshold_pct
)
```

Порог берётся из [[configuration-and-settings|настроек бота]] (`src/platform/config.py:234–241`):

```python
runtime_quality_threshold_pct: Decimal = Field(
    default=Decimal("0.005"),
    description=(
        "Bar price quality threshold (relative deviation, default 0.5%). "
        "S9 Q1 — REST-vs-REST consecutive bar quality detector. "
        "Triggers HALT_DATA_QUALITY via Coordinator.request_halt."
    ),
)
```

По умолчанию порог = **0.005**, то есть **0,5% относительного отклонения**. Настройка называется `RUNTIME_QUALITY_THRESHOLD_PCT` в переменных среды и изменяема без правки кода.

### Шаг 2. Конструктор — проверка порога

При создании объекта (`src/marketdata/quality.py:43–49`) проверяется, что порог строго положителен. Нулевой или отрицательный порог не имеет смысла (остановил бы торговлю при любом изменении цены) — конструктор выбрасывает `ValueError`:

```python
def __init__(self, *, threshold_pct: Decimal) -> None:
    if threshold_pct <= 0:
        raise ValueError(...)
    self._threshold_pct = threshold_pct
    self._last_close: Decimal | None = None
```

Внутри класс хранит только одно поле — `_last_close`: цена закрытия последней виденной свечи (или `None` до первого вызова).

### Шаг 3. Проверка каждой новой свечи — метод `check()`

Каждый раз, когда [[main-loop-tick|`_tick()` главного цикла]] в RuntimeManager получает новую закрытую свечу от [[bar-source-live|источника баров]], **до** того как стратегия увидит бар, вызывается (`src/runtime/manager.py:341–344`):

```python
if self._quality_detector.check(current_close=bar.close):
    self._coordinator.request_halt(reason=ReasonCode.HALT_DATA_QUALITY)
    self._stopping = True
    return
```

Внутри `check()` происходит следующее (`src/marketdata/quality.py:51–79`):

**Шаг 3а. Сохранить предыдущую цену, обновить baseline.**

```python
prior = self._last_close
self._last_close = current_close
```

Сначала сохраняется старое значение в локальную переменную `prior`, затем `_last_close` немедленно обновляется до текущей цены. Это значит, что baseline скользящий: каждый бар становится точкой отсчёта для следующего.

**Шаг 3б. Первый вызов — нет baseline, вернуть False.**

```python
if prior is None:
    return False  # No baseline yet
```

При первом вызове `prior` равен `None` — сравнивать не с чем. Детектор просто запоминает первую цену и возвращает `False` (нет проблемы, можно торговать). Halt не вызывается.

**Шаг 3в. Защита от нулевой предыдущей цены.**

```python
if prior <= 0:
    return False  # Defensive: avoid division by zero or negative anchor
```

Если предыдущая цена по какой-то причине оказалась нулевой или отрицательной — вычислять относительное отклонение невозможно (деление на ноль). В этом случае тоже возвращается `False`: бот не паникует, а просто пропускает проверку.

**Шаг 3г. Вычисление относительного отклонения и сравнение с порогом.**

```python
deviation_pct = abs(current_close - prior) / prior
if deviation_pct > self._threshold_pct:
    ...
    return True
return False
```

Если отклонение **строго больше** порога (`>`, а не `>=`) — детектор возвращает `True`, что означает «остановись». При равенстве точно порогу — считается нормальным (`False`). Это подтверждено тестом: `100000 → 100500` при пороге 0.005 даёт `False` (`tests/unit/test_quality_detector.py:53–57`).

**Шаг 3д. Логирование предупреждения.**

Когда порог превышен, перед возвратом `True` бот записывает предупреждение в лог (`src/marketdata/quality.py:70–77`):

```python
deviation_q = deviation_pct.quantize(Decimal("0.000001"))
logger.warning(
    "data_quality.deviation_exceeds_threshold",
    prior_close=str(prior),
    current_close=str(current_close),
    deviation_pct=str(deviation_q),
    threshold_pct=str(self._threshold_pct),
)
```

Важная деталь: `deviation_pct` — это объект типа `Decimal`, и операции с `Decimal` могут давать числа с 50+ знаками после запятой (например, `0.00601000000000000...`). Чтобы лог был читаемым, значение округляется до 6 знаков (`quantize(Decimal("0.000001"))`). Само сравнение с порогом выполняется по полной точности — округление только для вывода в лог.

### Шаг 4. Остановка бота

Если `check()` вернул `True`, RuntimeManager:
1. Запрашивает halt через [[05-исполнение-ордеров/coordinator-orchestration|координатор]]: `coordinator.request_halt(reason=ReasonCode.HALT_DATA_QUALITY)` (`src/runtime/manager.py:342`)
2. Устанавливает флаг `_stopping = True` — это выходит из главного цикла опроса баров
3. Возвращает управление — стратегия текущий бар **не получает**

`HALT_DATA_QUALITY` — это специальный [[reason-codes-assessment-output|код причины остановки]], зарегистрированный в `src/risk/reason_codes.py:82`. Далее по цепочке остановки этот код переводит [[execution-state-machine|конечный автомат исполнения]] в терминальное состояние `HALTED` и записывается в [[execution-state-persistence-and-halt-audit|журнал аварийных остановок]]. Общая карта всех тормозов бота — на странице [[safety-stops-and-halts|тормоза и предохранители]].

## Формулы и расчёты

### Формула относительного отклонения

```text
deviation_pct = |current_close - prior_close| / prior_close
```

**Простыми словами:** берём разницу между новой и старой ценой, делаем её неотрицательной (модуль — не важно, упала или выросла), и делим на старую цену. Получаем долю: 0.005 = 0,5%, 0.01 = 1%.

**Наша реализация** (`src/marketdata/quality.py:65`):

```python
deviation_pct = abs(current_close - prior) / prior
```

Используется тип `Decimal` (точная десятичная арифметика) — нет погрешностей числа с плавающей запятой (float), что важно при работе с финансовыми ценами.

### Условие остановки

```text
Halt = deviation_pct > threshold_pct
```

| Значение `threshold_pct` | Что значит | Для BTC при цене $100 000 |
|---|---|---|
| 0.005 (по умолчанию) | 0,5% | скачок более $500 за один 1H бар |
| 0.010 | 1,0% | скачок более $1 000 за один 1H бар |

**Почему именно 0,5%?** Для часового бара (1H) BTC к USDT изменение более $500 в одно мгновенное значение — нетипично для нормальных рыночных условий, но хорошо отделяет реальные движения от «мусорных» данных. Это обосновано в docstring модуля (`src/marketdata/quality.py:15–18`).

## Примеры / сценарии

### Сценарий А — Нормальная работа (торговля продолжается)

Бот получает последовательность баров BTC/USDT:

| Бар | Цена закрытия | prior | deviation_pct | Результат |
|-----|---------------|-------|----------------|-----------|
| 1 | $100 000 | None | — | False (первый бар) |
| 2 | $100 200 | $100 000 | 0,20% | False (< 0,5%) |
| 3 | $100 400 | $100 200 | 0,20% | False (< 0,5%) |
| 4 | $100 500 | $100 400 | 0,10% | False (< 0,5%) |

Торговля продолжается нормально.

### Сценарий Б — Зависший фид, а потом резкий скачок

Иногда зависший фид проявляется не одним «мусорным» баром, а долгим стоянием на месте, а потом — скачком к реальной цене:

| Бар | Цена закрытия | prior | deviation_pct | Результат |
|-----|---------------|-------|----------------|-----------|
| 1 | $100 000 | None | — | False |
| 2 | $100 000 | $100 000 | 0,00% | False |
| 3 | $100 000 | $100 000 | 0,00% | False |
| 4 | $100 700 | $100 000 | **0,70%** | **True → HALT** |

На баре 4 бот останавливается: слишком большой скачок. Даже если это «реальная» цена после зависания, торговать в такой ситуации небезопасно.

### Сценарий В — Граничный случай: ровно 0,5%

Цена BTC: $100 000 → $100 500. Отклонение = 500/100 000 = 0,005 — ровно равно порогу.

Проверка: `0.005 > 0.005` → **False**. Торговля продолжается. Порог строгий: «больше», а не «больше или равно» (`src/marketdata/quality.py:66`; подтверждено тестом `tests/unit/test_quality_detector.py:53–57`).

### Сценарий Г — Падение цены (симметрично)

Падение тоже проверяется, так как используется `abs()`:

Цена: $100 000 → $99 400. Отклонение = |99 400 − 100 000| / 100 000 = 0,006 = 0,6% > 0,5% → **True → HALT**.

Подтверждено тестом `tests/unit/test_quality_detector.py:33–37`.

### Сценарий Д — Скользящий baseline

Baseline обновляется после каждого бара, даже если halt не сработал. Это значит, что детектор сравнивает каждый бар с **непосредственно предыдущим**, а не с начальной ценой:

| Бар | Цена | prior | deviation_pct |
|-----|------|-------|----------------|
| 1 | $100 000 | None | — |
| 2 | $100 200 | $100 000 | 0,20% → baseline теперь $100 200 |
| 3 | $100 800 | $100 200 | **0,60%** → HALT |

Подтверждено тестом `tests/unit/test_quality_detector.py:60–66`.

## Подводные камни / что важно понимать

### 1. Состояние хранится только в памяти — при рестарте бота baseline сбрасывается

Детектор не сохраняет `_last_close` в базу данных или файл. Если бот перезапустился — первый бар после запуска всегда пройдёт без проверки (вернёт `False`, baseline устанавливается заново). Это сознательное решение для v0.1: простота важнее полноты защиты в момент старта (`src/marketdata/quality.py:30–34`).

Практический вывод: если бот упал и перезапустился во время аномального движения рынка, он не сразу это обнаружит — первый бар «амнезирован».

### 2. Детектор работает только с REST-данными, а не с WebSocket-потоком

Существующая архитектура (Sprint 8, ADR 0022) использует [[bybit-rest-source|REST для получения закрытых баров]]. WebSocket-подписка на свечи ([[bybit-ws-consumer|WS-потребитель]] и [[bar-builder-ws|построитель свечей из WS-потока]]) не задействована в live-цикле детектора, поэтому сравниваются только REST-закрытые бары между собой (REST-vs-REST). Это объяснено в docstring модуля (`src/marketdata/quality.py:7–18`): WS-обновления частичных баров создавали бы ложные срабатывания при per-bar сравнении.

### 3. Проверка выполняется до стратегии — бот никогда не торгует на «подозрительном» баре

Последовательность в `_tick()` принципиальна (`src/runtime/manager.py:338–346`): сначала вызывается `quality_detector.check()`, и только если он вернул `False` — бар передаётся стратегии. Если halt сработал, стратегия текущий бар не видит совсем.

### 4. Точно на пороге — не halt

Если отклонение в точности равно порогу (например, ровно 0,5%), halt не срабатывает. Условие строгое: `deviation_pct > self._threshold_pct`. Это позволяет корректно обрабатывать «круглые» числа без ложных срабатываний.

### 5. Порог единый для всех символов — без индивидуальной подстройки в v0.1

Один и тот же процентный порог применяется к любому торговому инструменту. Для v0.1 с одной парой (BTC/USDT) это нормально. При расширении на другие инструменты с иной волатильностью может потребоваться per-symbol настройка — это помечено как ограничение дизайна v0.1 (`src/marketdata/quality.py:18`).

### 6. Нулевая предыдущая цена: защита, а не ошибка

Если первый бар пришёл с ценой 0 (что само по себе аномалия), а второй — с реальной ценой, детектор вернёт `False` и пропустит второй бар без проверки. Это компромисс: лучше пропустить одну проверку, чем уронить бота на делении на ноль. Тест: `tests/unit/test_quality_detector.py:40–44`.

### 7. Halt — терминальная операция для текущего процесса

После `HALT_DATA_QUALITY` флаг `_stopping = True` выставляется немедленно, и главный цикл опроса баров завершается (`src/runtime/manager.py:343`). Бот не продолжает работу и не пытается «переждать» аномалию. Для возобновления торговли требуется ручной перезапуск.
