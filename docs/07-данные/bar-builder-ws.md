# Построитель свечей: WebSocket-поток и обработка пропусков

**TL;DR:** `BarBuilder` принимает сырые сообщения биржи в реальном времени и превращает их в готовые свечи. Стратегия видит только полностью закрытые свечи — незавершённые данные отбрасываются. Если биржа пропустила одну или несколько свечей, бот заполняет дыру синтетическими «заглушками», чтобы счётчики технических индикаторов не съехали.

---

## Простыми словами

Представьте, что биржа — это репортёр, который каждую минуту (или каждый час) сообщает: «Вот итоги торгов за этот период: открытие, максимум, минимум, закрытие, объём». Такую порцию данных трейдеры называют **свечой** ([[bar-model|Bar]]) — от старинного способа рисовать графики в виде свечей.

Но репортёр не ждёт конца минуты — он шепчет промежуточные данные прямо по ходу торгов: «Пока что максимум 60100, закрытие пока 60050...». Это **частичная свеча** (partial bar) — незавершённая. Если бот будет реагировать на такие промежуточные данные, он может принять решение, основанное на неполной картине.

Поэтому у нас действует простое правило: **бот реагирует только на закрытую свечу**. Биржа сама сообщает, что свеча закончена, отправляя специальный признак `confirm=true`. Пока этот признак не пришёл — данные игнорируются.

**Что такое WebSocket (WS)?** Это технология постоянного соединения с биржей в реальном времени — как телефонная трубка, которую не кладут: биржа сама «говорит» боту о каждом изменении без того, чтобы бот каждый раз спрашивал. Приёмом этих сообщений занимается отдельный модуль — [[bybit-ws-consumer|WebSocket-потребитель]], а `BarBuilder` уже собирает из них готовые свечи.

**Что бывает, если данные пропали?** Иногда связь с биржей прерывается на несколько минут, или биржа замолкает. Когда связь восстанавливается, оказывается, что несколько свечей пропущено — в ряду данных образовалась **дыра**. [[technical-indicators|Технические индикаторы]] (например, скользящая средняя за 14 периодов) смотрят назад на фиксированное число свечей. Если в этом окне окажется дыра, индикатор получит неверные данные — как если бы вы пересчитывали среднее по тесту, в котором часть страниц вырвана.

Чтобы этого не произошло, `BarBuilder` при обнаружении пропуска автоматически создаёт **синтетические GAP-свечи** — специальные заглушки с нулевыми ценами, которые заполняют дыру. Заглушки получают метку `DataQuality.GAP`, которую стратегии **обязаны** проверять перед расчётом индикаторов — иначе нулевые OHLC попадут в буферы как реальные цены. Сами заглушки сохраняют правильный счёт: индикатор «знает», что в этом месте были отсутствующие данные, а не реальные нули.

## Как это работает у нас

### Шаг 1 — Настройка при создании

При создании `BarBuilder` принимает два обязательных параметра: торговую пару (`symbol`, например `"BTCUSDT"`) и длину одного интервала в миллисекундах (`interval_ms`). На основе `interval_ms` он сразу определяет строковое название интервала для хранения (например, `3_600_000 мс → "1h"`). Полный словарь поддерживаемых интервалов:

| `interval_ms` | Строка |
|---|---|
| 60 000 | `"1m"` |
| 300 000 | `"5m"` |
| 900 000 | `"15m"` |
| 3 600 000 | `"1h"` |
| 14 400 000 | `"4h"` |
| 86 400 000 | `"1d"` |

(src/marketdata/bar_builder.py:14–21)

Также инициализируется внутренняя переменная `_last_confirmed_open_ms = None` — она запоминает время открытия последней успешно обработанной закрытой свечи. Пока ни одной свечи не принято, переменная равна `None`. (src/marketdata/bar_builder.py:31)

---

### Шаг 2 — Основной метод: `process(msg)`

Это главный входной пункт для каждого сообщения от биржи.

```python
def process(self, msg: dict[str, object]) -> Bar | None:
    open_ms = int(msg["start"])
    confirm = bool(msg["confirm"])
    self._check_order(open_ms)
    if not confirm:
        return None
    bar = self._build_bar(msg, data_quality=DataQuality.OK)
    self._last_confirmed_open_ms = open_ms
    return bar
```
(src/marketdata/bar_builder.py:33–45)

Логика по шагам:

1. **Извлекает время открытия** из поля `"start"` сообщения (Unix-время в миллисекундах).
2. **Читает признак закрытия** из поля `"confirm"` (биржевой флаг — `true` означает «свеча закрыта»).
3. **Проверяет порядок** через `_check_order()` — защита от дублей и перепутанных сообщений (подробнее ниже).
4. **Если свеча НЕ закрыта** (`confirm = false`) — метод немедленно возвращает `None`. Частичные данные полностью игнорируются. Вышестоящий код не получает ничего.
5. **Если свеча закрыта** — строит объект `Bar` с меткой `DataQuality.OK` и запоминает время этой свечи как «последнюю подтверждённую».

Важно: `_last_confirmed_open_ms` обновляется **только** после успешно закрытой свечи. Частичные (промежуточные) обновления не сдвигают это значение.

---

### Шаг 3 — Метод с заполнением дыр: `process_with_gap_fill(msg)`

Это расширенная версия `process()`, которая дополнительно проверяет, не пропустил ли бот какие-то свечи.

```python
def process_with_gap_fill(self, msg: dict[str, object]) -> tuple[list[Bar], Bar | None]:
    open_ms = int(msg["start"])
    gap_bars: list[Bar] = []
    if (
        self._last_confirmed_open_ms is not None
        and open_ms > self._last_confirmed_open_ms + self._interval_ms
    ):
        gap_open_ms = self._last_confirmed_open_ms + self._interval_ms
        while gap_open_ms < open_ms:
            gap_bars.append(self._synth_gap_bar(gap_open_ms))
            gap_open_ms += self._interval_ms
    real_bar = self.process(msg)
    return gap_bars, real_bar
```
(src/marketdata/bar_builder.py:47–68)

Метод возвращает пару: `(список GAP-свечей, настоящая свеча)`.

**Логика определения дыры.** Если последняя подтверждённая свеча была в момент `T`, то следующая ожидаемая свеча должна быть в `T + interval_ms`. Если пришедшее сообщение имеет время открытия, которое больше, чем `T + interval_ms` — значит, как минимум одна свеча пропущена.

**Алгоритм заполнения.** Переменная `gap_open_ms` начинается с первого ожидаемого, но не пришедшего момента (`last_confirmed + interval_ms`) и шагает вперёд через каждый интервал, пока не достигнет времени реально пришедшей свечи. На каждом шаге создаётся одна синтетическая GAP-свеча. Это принципиально важно: **один маркер на каждый пропущенный слот**, а не один на всю дыру.

После генерации всех GAP-свечей вызывается обычный `process(msg)`, который обрабатывает настоящую свечу стандартным образом.

Реальное использование — в [[data-pipeline|`MarketDataPipeline`]]`.run()`, откуда готовые свечи уходят на запись в [[parquet-storage|Parquet-хранилище]]: (src/marketdata/pipeline.py:54–61)

```python
gap_bars, bar = self._builder.process_with_gap_fill(msg)
if gap_bars:
    self._writer.append(gap_bars)
if bar is not None:
    self._writer.append([bar])
```

### Шаг 4 — Защита порядка: `_check_order(open_ms)`

```python
def _check_order(self, open_ms: int) -> None:
    if self._last_confirmed_open_ms is None:
        return
    if open_ms == self._last_confirmed_open_ms:
        raise OutOfOrderError(f"duplicate open_ms={open_ms} after confirm")
    if open_ms < self._last_confirmed_open_ms:
        raise OutOfOrderError(
            f"out-of-order: {open_ms} < last confirmed {self._last_confirmed_open_ms}"
        )
```
(src/marketdata/bar_builder.py:70–78)

Метод проверяет два опасных случая:

- **Дубликат** (`open_ms == last_confirmed`): пришла свеча с тем же временем, что уже была подтверждена. Такое бывает при переподключении к WebSocket — биржа может прислать «свежую» копию уже полученного сообщения. Бросается `OutOfOrderError` с меткой `"duplicate"`.
- **Свеча из прошлого** (`open_ms < last_confirmed`): сообщение с более ранним временем пришло позже. Бросается `OutOfOrderError` с меткой `"out-of-order"`.

Важный нюанс: проверка выполняется **до** проверки флага `confirm`. Это значит, что даже частичное (незакрытое) сообщение может вызвать `OutOfOrderError`, если его время открытия совпадает с уже подтверждённой свечой. Однако на практике частичные сообщения с одинаковым `open_ms` не поднимают исключения — они блокируются только если `open_ms` равен `_last_confirmed_open_ms` (то есть уже подтверждённому). Промежуточные обновления одной и той же ещё не закрытой свечи проходят беспрепятственно (см. тест `test_duplicate_non_confirmed_is_ignored`). (src/marketdata/bar_builder.py:52–57 в тестах)

### Шаг 5 — Сборка свечи: `_build_bar(msg, data_quality)`

```python
def _build_bar(self, msg: dict[str, object], data_quality: DataQuality) -> Bar:
    open_ms = int(msg["start"])
    open_time = datetime.fromtimestamp(open_ms / 1000, tz=UTC)
    close_time = open_time + timedelta(milliseconds=self._interval_ms)
    return Bar(
        symbol=self._symbol,
        interval=self._interval_literal,
        open_time=open_time,
        close_time=close_time,
        open=Decimal(str(msg["open"])),
        ...
    )
```
(src/marketdata/bar_builder.py:80–97)

Два момента, которые отличают нашу реализацию:

- **Время всегда в UTC.** `datetime.fromtimestamp(open_ms / 1000, tz=UTC)` — явный часовой пояс UTC, не «локальный» компьютерный. Это гарантирует одинаковое поведение на любой машине. За тем, чтобы системные часы не разошлись с временем биржи, следит отдельный [[clock-drift-monitor|монитор рассинхронизации часов]].
- **Время закрытия вычисляется**, а не берётся из сообщения: `close_time = open_time + timedelta(milliseconds=self._interval_ms)`. Поле `"end"` из WS-сообщения биржи не используется — только вычисленное значение.
- **Цены через `Decimal(str(...))`** — дробные числа хранятся точно без погрешностей округления (специфика Python: `float` теряет копейки на больших ценах).
- Поле `trade_count` всегда `0` — Bybit V5 WS kline не передаёт количество сделок в payload, поэтому значение не заполняется.
- Поле `is_closed` всегда `True` — метод вызывается только для подтверждённых свечей.

### Шаг 6 — Создание синтетической GAP-свечи: `_synth_gap_bar(open_ms)`

```python
def _synth_gap_bar(self, open_ms: int) -> Bar:
    """Synthetic GAP bar — per edge-cases.md #1, NO forward-fill OHLC."""
    ...
    return Bar(
        ...
        open=Decimal("0"),
        high=Decimal("0"),
        low=Decimal("0"),
        close=Decimal("0"),
        volume=Decimal("0"),
        trade_count=0,
        is_closed=True,
        data_quality=DataQuality.GAP,
    )
```
(src/marketdata/bar_builder.py:99–117)

**Почему все цены равны нулю, а не копируют предыдущую свечу?** Это сознательное решение, зафиксированное в edge-cases.md #1: при пропуске данных нет смысла притворяться, что цена «стояла на месте» (это называется forward-fill). Ноль — честный сигнал: «здесь нет данных». Технические индикаторы, которые получат такую свечу, обязаны её пропустить — для этого стратегии **должны** проверять метку `DataQuality.GAP`. Важно: по состоянию на текущую реализацию все стратегии (`strategy.py:64`, `donchian_strategy.py:76`, `supertrend_strategy.py:136` и др.) фильтруют поступающие свечи только по `bar.is_closed` и **не читают** `data_quality`. GAP-свеча имеет `is_closed=True` (`bar_builder.py:115`) и поэтому проходит gate стратегий, а нулевые OHLC попадают в буферы индикаторов. Проверка `DataQuality.GAP` в коде стратегий — нереализованное требование. Forward-fill создал бы ложный сигнал: индикатор «думал» бы, что торги шли с неизменной ценой, хотя на самом деле данных нет.

Метка `DataQuality.GAP` — это один из четырёх возможных уровней качества данных, определённых в модели `DataQuality`: `OK`, `GAP`, `STALE`, `SUSPECT`. (src/marketdata/models.py:10–14) Уровни `STALE` и `SUSPECT` проставляет уже [[data-quality-detector|детектор качества данных]] — отдельный слой проверки фида.

## Примеры / сценарии

### Сценарий А — Нормальная работа

Бот настроен на часовые свечи (`interval_ms = 3_600_000`). Биржа присылает 3 сообщения за период 11:00–13:00:

| Время | `confirm` | Действие `process()` |
|---|---|---|
| 11:23 (partial) | `false` | Возвращает `None` — промежуточное, игнорируем |
| 11:58 (partial) | `false` | Возвращает `None` — ещё не закрыта |
| 12:00:00 (closed) | `true` | Возвращает `Bar(open_time=11:00, close_time=12:00, quality=OK)` |

На выходе одна свеча за период 11:00–12:00.

---

### Сценарий Б — Пропущено несколько свечей (DI-01)

Последняя подтверждённая свеча: `open_ms = 1000` (условно). Интервал: `interval_ms = 100`. Новое сообщение: `open_ms = 1400`.

Проверка дыры: `1400 > 1000 + 100` → дыра есть.

Алгоритм gap-fill:
```
gap_open_ms = 1000 + 100 = 1100  → создаём GAP-свечу за [1100–1200]
gap_open_ms = 1100 + 100 = 1200  → создаём GAP-свечу за [1200–1300]
gap_open_ms = 1200 + 100 = 1300  → создаём GAP-свечу за [1300–1400]
gap_open_ms = 1300 + 100 = 1400  → 1400 == 1400, цикл завершается
```

`process_with_gap_fill` возвращает `([GAP@1100, GAP@1200, GAP@1300], Bar@1400)` — три заглушки и одну настоящую свечу. Именно этот случай закреплён в регрессионном тесте `test_multi_interval_gap_emits_one_bar_per_missing_slot`. (tests/unit/test_bar_builder.py:99–116)

---

### Сценарий В — Защита от дубликата

Бот получил и подтвердил свечу с `open_ms = 1745193600000`. Затем переподключился к WebSocket и биржа прислала ту же свечу повторно. Метод `_check_order()` обнаруживает: `open_ms == _last_confirmed_open_ms` → бросает `OutOfOrderError("duplicate open_ms=...")`. Вышестоящий код должен перехватить это исключение и обработать переподключение. (tests/unit/test_bar_builder.py:59–63)

## Подводные камни / что важно понимать

**1. GAP-свечи — маркеры, а не данные.** Все цены в GAP-свече равны нулю (`Decimal("0")`). Стратегии обязаны проверять `data_quality` перед использованием свечи. Если не проверять — технический индикатор получит нули как реальные цены и выдаст бессмысленный сигнал.

**2. Один маркер на каждый пропущенный слот — критично.** До исправления DI-01 при пропуске трёх свечей создавался только один GAP-маркер. Индикаторы с окном в 14 периодов «смотрели назад» и не замечали, что в их окне скрыта дыра в два периода — расчёты съезжали без видимой ошибки. Теперь каждый пропущенный слот получает свою заглушку. (src/marketdata/bar_builder.py:47–68, комментарий «DI-01»)

**3. Состояние `_last_confirmed_open_ms` критично.** При первом запуске оно равно `None` — в этом случае защита от дублей и out-of-order не работает (нет точки сравнения). Это намеренно: первая свеча всегда принимается без проверки.

**4. `trade_count` всегда 0.** Bybit V5 kline WebSocket не передаёт количество сделок внутри периода. Если нужна эта метрика — нужно использовать REST-запрос или агрегировать из потока сделок отдельно.

**5. Только закрытые тайм-фреймы из списка.** `BarBuilder` при создании делает прямой поиск `interval_ms` в словаре `_INTERVAL_LITERAL`. Если передать нестандартное значение (например, `120_000` для двухминутных свечей) — возникнет `KeyError` при инициализации. Поддерживаются только: 1m, 5m, 15m, 1h, 4h, 1d.

**6. `OutOfOrderError` — не тихое игнорирование.** При получении дублирующегося или «из прошлого» сообщения метод бросает исключение, а не просто отбрасывает данные. Это гарантирует, что нарушение порядка не пройдёт незамеченным — вышестоящий код обязан явно обработать этот случай.
