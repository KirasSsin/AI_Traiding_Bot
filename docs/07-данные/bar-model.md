# Свеча (Bar): структура и правила валидации

**TL;DR:** Свеча — это «снимок» торговли за один временной интервал (например, за 1 час). Каждая свеча содержит ровно 12 полей, и бот **автоматически проверяет** корректность данных при её создании — некорректную свечу создать невозможно.

## Простыми словами

Представьте, что вы ведёте дневник цены на бензин. За каждый день вы записываете:
- **С какой цены начался день** (open — цена открытия)
- **Какой была максимальная цена** (high — максимум)
- **Какой была минимальная цена** (low — минимум)
- **На какой цене закончился день** (close — цена закрытия)
- **Сколько литров продали за день** (volume — объём торгов)
- **Сколько отдельных сделок состоялось** (trade_count — количество сделок)

В торговле такая запись за один период называется **свечой** (candlestick или bar). Название «свеча» появилось потому, что на графике такая запись выглядит как свеча с фитилями — верхний фитиль показывает максимум, нижний — минимум, а тело свечи — промежуток между ценой открытия и закрытия.

Термин **OHLCV** — это просто аббревиатура первых букв: Open + High + Low + Close + Volume (Открытие + Максимум + Минимум + Закрытие + Объём).

Зачем боту нужны свечи? Все [[signal-architecture|стратегии]] торгового бота принимают решения на основе исторических и текущих свечей. Без корректных данных свечей — нет сигнала, нет сделки. Поэтому свеча — это фундаментальный «кирпичик» всей системы.

## Как это работает у нас

### Класс Bar — структура свечи

Класс `Bar` описан в `src/marketdata/models.py`. Это **неизменяемый** объект с данными: после того как свеча создана, изменить её поля нельзя. Неизменяемость гарантируется настройкой `frozen=True` в конфигурации модели — попытка присвоить новое значение любому полю вызовет ошибку. (src/marketdata/models.py:20)

Каждая свеча содержит ровно 12 полей:

| Поле | Тип | Обязательное | Что означает |
|------|-----|:---:|---|
| `symbol` | строка | Да | Торговая пара, например `BTCUSDT` |
| `interval` | фиксированный список | Да | Временной интервал свечи |
| `open_time` | дата+время с UTC | Да | Момент открытия свечи |
| `close_time` | дата+время с UTC | Да | Момент закрытия свечи |
| `open` | Decimal | Да | Цена в начале периода |
| `high` | Decimal | Да | Максимальная цена за период |
| `low` | Decimal | Да | Минимальная цена за период |
| `close` | Decimal | Да | Цена в конце периода |
| `volume` | Decimal | Да | Суммарный объём торгов (≥ 0) |
| `trade_count` | целое число | Да | Число отдельных сделок (≥ 0) |
| `is_closed` | булев флаг | Да | Завершилась ли свеча |
| `data_quality` | перечисление | Нет (по умолчанию `OK`) | Статус качества данных |

(src/marketdata/models.py:17–33)

### Поле symbol: только пары с USDT

Торговая пара должна соответствовать шаблону `^[A-Z]+USDT$` — это означает: одна или несколько заглавных латинских букв, после которых идёт `USDT`. Пример корректного значения: `BTCUSDT`, `ETHUSDT`, `SOLUSDT`. Значения вида `btcusdt`, `BTC/USDT`, `BTCUSD` — будут отвергнуты автоматически. (src/marketdata/models.py:22)

Бот работает исключительно на спотовом рынке Bybit с котировочной валютой USDT, поэтому другие форматы пар не нужны.

### Поле interval: шесть допустимых значений

Временной интервал свечи — это строго одно из: `"1m"`, `"5m"`, `"15m"`, `"1h"`, `"4h"`, `"1d"`. Любое другое значение (например `"2h"` или `"30m"`) вызовет ошибку валидации. (src/marketdata/models.py:23)

Эти значения соответствуют интервалам, которые поддерживает биржа Bybit; задавать произвольные нельзя.

### Временные метки: только UTC, никакой двусмысленности

Поля `open_time` и `close_time` используют тип `AwareDatetime` из библиотеки Pydantic. Смысл слова «aware» (осведомлённый) — время **всегда содержит информацию о часовом поясе**. Бот принимает только UTC (координированное всемирное время). (src/marketdata/models.py:24–25)

Если попытаться передать обычную дату без указания часового пояса (так называемый «наивный» datetime), Pydantic немедленно отклонит такую свечу. Это защита от типичной ошибки программирования, когда время Москвы случайно смешивается с UTC и все временные окна сдвигаются.

Проверка работает: тест `test_bar_rejects_naive_open_time` в `tests/unit/test_marketdata_models.py:104–120` подтверждает, что наивный `datetime` вызывает `ValidationError`.

### Цены и объём: Decimal-арифметика

Поля `open`, `high`, `low`, `close`, `volume` используют тип `Decimal`, а не обычные числа с плавающей точкой (`float`). (src/marketdata/models.py:26–30)

Зачем? В обычной математике компьютера число 0.1 нельзя представить точно в двоичной системе — возникают незаметные ошибки округления. Для цен и объёмов даже малая ошибка может привести к тому, что [[wilder-atr-and-stops|стоп-лосс]] (заранее установленный лимит потерь) сработает не на той цене. Тип `Decimal` хранит число точно — без накопленных округлений.

При создании свечи из биржевых данных значения всегда преобразуются через `Decimal(str(...))`, а не через `Decimal(float(...))` — это принципиально важно, так как преобразование через строку сохраняет исходную точность. Это видно в коде [[bar-builder-ws|сборщика свечей]]: (src/marketdata/bar_builder.py:89–93)

### Инвариант OHLC: автоматическая проверка физической корректности

После создания всех полей свечи, но до её возврата в программу, автоматически выполняется метод `_ohlc_invariants`. Он проверяет три логических правила: (src/marketdata/models.py:35–43)

1. **`high >= max(open, close)`** — максимум не может быть ниже ни цены открытия, ни цены закрытия. Иначе данные биржи противоречат физическому смыслу.
2. **`low <= min(open, close)`** — минимум не может быть выше ни цены открытия, ни цены закрытия.
3. **`close_time > open_time`** — свеча не может закрыться раньше, чем открылась (или в тот же момент).

Нарушение любого из этих условий немедленно вызывает ошибку `ValueError`, и свеча не создаётся. Это предотвращает «тихое» проникновение некорректных данных биржи в расчёты стратегий.

Пример: если биржа передаёт `high=59900`, а `open=60000` — это физически невозможно (дневной максимум не может быть ниже цены открытия). Метод зафиксирует эту ошибку. Тест `test_bar_high_must_be_max` в `tests/unit/test_marketdata_models.py:32–47` проверяет именно этот случай.

### Перечисление DataQuality: четыре статуса качества

Каждая свеча несёт «ярлык» качества — поле `data_quality`. (src/marketdata/models.py:10–14)

| Статус | Значение | Реально используется? |
|--------|----------|----------------------|
| `OK` | Нормальная свеча | Да — значение по умолчанию для всех реальных баров |
| `GAP` | Синтетическая заглушка для пропуска | Да — выставляется сборщиком при разрыве данных |
| `STALE` | Зависший фид | Нет — зарезервировано; в коде не присваивается нигде |
| `SUSPECT` | Подозрительное отклонение | Нет — зарезервировано; в коде не присваивается нигде |

Важный момент: в реальной работе бота `data_quality` принимает ровно два значения — `OK` и `GAP`. Значения `STALE` и `SUSPECT` объявлены в перечислении как задел на будущее, но ни одна функция во всём проекте их не выставляет (проверено: `grep -rn "STALE\|SUSPECT" src/` не находит ни одного присвоения). (src/marketdata/models.py:13–14)

**GAP-свеча** — это особый случай. Когда биржевой поток данных «молчал» несколько интервалов, система не может просто пропустить недостающее время — иначе [[technical-indicators|индикаторы]], считающие историю последних N свечей, получат неверное окно. Вместо этого для каждого пропущенного интервала создаётся синтетическая свеча с нулевыми ценами и объёмом и статусом `GAP`. (src/marketdata/bar_builder.py:104–117)

**Важно понимать:** поле `data_quality` читает только один компонент — модуль хранения `storage.py`, который записывает его строковое значение в [[parquet-storage|Parquet-файл]] (src/marketdata/storage.py:56). Стратегии не проверяют это поле совсем: метод `_append_bar()` в `strategy.py` пропускает бар только если `is_closed=False`, символ не совпадает или нарушена хронология — но не по `data_quality`. (src/signalgen/strategy.py:62–74) Аналогично, [[data-quality-detector|детектор аномальных цен]] `BarPriceQualityDetector.check()` принимает только числовую цену закрытия, поле `data_quality` он не читает. (src/marketdata/quality.py:51) Это означает, что GAP-свеча с нулевыми ценами и `is_closed=True` сейчас проходит через буфер стратегии и попадает в расчёты индикаторов — это известное ограничение текущей версии.

Заметьте: нули в полях GAP-свечи (`open=0, high=0, low=0, close=0, volume=0`) нарушают инвариант OHLC (ведь `high >= max(open, close)` выполняется, когда всё равно нулю) — инвариант формально соблюдается. (src/marketdata/bar_builder.py:104–117)

## Примеры / сценарии

### Сценарий 1: корректная часовая свеча BTC

Представьте торговлю биткоином с 00:00 до 01:00 UTC 20 апреля 2026 года. За этот час:
- Торги начались по 60 000 USD
- В какой-то момент цена достигла 60 500 USD (максимум)
- В какой-то момент падала до 59 800 USD (минимум)
- Час закончился на 60 200 USD
- Торгов было на 125.5 BTC суммарно, состоялось 3421 сделка

Структура свечи (так её можно создать напрямую, например в тесте):

```python
Bar(
    symbol="BTCUSDT",
    interval="1h",
    open_time=datetime(2026, 4, 20, 0, 0, 0, tzinfo=UTC),
    close_time=datetime(2026, 4, 20, 1, 0, 0, tzinfo=UTC),
    open=Decimal("60000"),
    high=Decimal("60500"),
    low=Decimal("59800"),
    close=Decimal("60200"),
    volume=Decimal("125.5"),
    trade_count=3421,
    is_closed=True,
    data_quality=DataQuality.OK,
)
```

Замечание: поле `trade_count=3421` здесь показывает возможности модели. В реальной работе бота все источники данных (WS, REST, бэктест) жёстко передают `trade_count=0` — реальное количество сделок API Bybit не возвращает. (src/marketdata/models.py, тест в tests/unit/test_marketdata_models.py:13–30)

### Сценарий 2: GAP-свеча при пропуске данных

Допустим, биржа передаёт свечи за 00:00 и за 02:00, но свечи за 01:00 нет. Система обнаруживает разрыв: следующая ожидаемая свеча должна была быть за 01:00, но вместо неё пришла 02:00. Сборщик `BarBuilder.process_with_gap_fill()` автоматически создаёт одну GAP-свечу за 01:00 с нулевыми ценами перед реальной 02:00. (src/marketdata/bar_builder.py:47–68)

Если пропущено несколько интервалов подряд (например, три часа), создаётся по одной GAP-свече на каждый пропущенный слот в хронологическом порядке.

### Сценарий 3: попытка создать некорректную свечу

Если биржа передаёт данные, где `high=59 900`, но `open=60 000`:

```text
ValueError: high must be >= max(open, close)
```

Свеча не создаётся. Ошибка «всплывает» в вызывающий код, который должен решить, как с ней обращаться (логировать, игнорировать бар, запросить повтор).

## Подводные камни / что важно понимать

**Неизменяемость — это не ограничение, а гарантия.** Стратегии получают объект `Bar` и знают, что никакой другой код не может тихо изменить, например, `close`-цену уже после расчётов. В Python изменение замороженного поля вызывает `ValidationError`. (src/marketdata/models.py:20)

**GAP-свечи имеют нулевые цены, это нормально.** Нули в OHLC для GAP-свечи — намеренное решение («NO forward-fill OHLC» согласно комментарию кода). Форвардное заполнение (т.е. скопировать цены предыдущей свечи) создало бы иллюзию реальных данных там, где их нет. Нули явно сигнализируют: «здесь был пропуск, не используй». (src/marketdata/bar_builder.py:100)

**`trade_count` всегда равен 0 на всех путях.** Ни [[bybit-ws-consumer|WebSocket-сборщик]], ни [[bybit-rest-source|REST-клиент]], ни [[kronos-backtest-runner|Kronos-раннер]] не передают реальное количество сделок — все три пути жёстко прописывают `trade_count=0`: `BarBuilder._build_bar()` (src/marketdata/bar_builder.py:94), `_synth_gap_bar()` (src/marketdata/bar_builder.py:114), `bybit/rest.py` (src/marketdata/bybit/rest.py:268), `kronos_runner.py` (src/backtest/kronos_runner.py:138). Поле объявлено в модели и сохраняется в Parquet, но фактически является «мёртвым» — всегда нуль. Сценарий с `trade_count=3421` (ниже в разделе примеров) достижим только при прямом создании объекта `Bar` в тестах, не через реальный конвейер данных.

**`is_closed=False` означает «свеча ещё не завершилась».** Сборщик `BarBuilder.process()` возвращает `None` для незакрытых баров и создаёт `Bar` только при `confirm=True`. Незавершённую свечу система возвращает только в специальных сценариях — стратегии работают исключительно с закрытыми свечами. (src/marketdata/bar_builder.py:33–45)

**Статусы `STALE` и `SUSPECT` — зарезервированы, но не используются.** Эти два значения объявлены в перечислении `DataQuality` (src/marketdata/models.py:13–14), однако ни один путь в коде их не присваивает. Класс `BarPriceQualityDetector` (src/marketdata/quality.py:51) работает иначе: он сравнивает числовые цены закрытия последовательных свечей и при отклонении свыше 0.5% (`threshold_pct=Decimal("0.005")`) возвращает `True` — но не записывает `SUSPECT` в поле `data_quality` (свеча неизменяема). Сигнал об аномалии идёт по отдельному каналу — через `coordinator.request_halt()`. Поле `data_quality` при этом **не изменяется**. (src/marketdata/quality.py:29–79)

**Naive datetime — мгновенная ошибка.** Если где-то в коде время создаётся без явного указания UTC (например, `datetime.now()` без `tz=UTC`), попытка создать `Bar` с таким временем вызовет `ValidationError`. Это намеренная «стена» на границе системы — защита от сдвигов временных окон. Тест `tests/unit/test_marketdata_models.py:104` подтверждает это поведение.

- [[signal-architecture]] — как стратегии получают закрытые свечи через `on_bar` и превращают их в сигнал

- [[replay-engine-bar-by-bar]] — движок бэктеста проигрывает те же свечи бар за баром для симуляции сделок
- [[end-to-end-overview]] — единая карта: свеча → сигнал стратегии → проверка риска → ордер
- [[data-backfill-command]] — команда backfill: как исторические свечи скачиваются и складываются для бэктестов

**Точность и стопы (зачем Decimal):**
- [[wilder-atr-and-stops]] — расчёт стоп-уровней по цене свечи; ошибка округления цены = стоп на неверном уровне
- [[atr-indicator]] — ATR-волатильность считается из high/low/close свечей; вход в Decimal-арифметику
