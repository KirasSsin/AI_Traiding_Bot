# Монитор рассинхронизации часов: локальное время vs. время биржи

**TL;DR:** Перед началом работы бот сравнивает системные часы компьютера с официальным временем биржи Bybit. Если расхождение больше 1 секунды — бот сигнализирует об ошибке, не позволяя торговать с рассинхронизированными часами.

## Простыми словами

Представьте, что вы договорились встретиться с партнёром ровно в полдень, но ваши часы отстают на две минуты. Вы придёте вовремя по своим часам — но на самом деле опоздаете. В трейдинге та же проблема: бот постоянно работает со временем.

**Рассинхронизация часов (clock drift)** — это когда системные часы вашего компьютера (или сервера, где работает бот) показывают немного другое время, чем часы биржи. Казалось бы, пара секунд — мелочь. Но это может привести к двум серьёзным проблемам:

1. **Временные метки ордеров** — биржа Bybit проверяет, не устарел ли запрос. Если часы компьютера отстают, биржа может отклонить ордер с кодом ошибки `10002` (именно это кодирует [[reason-codes-assessment-output|ReasonCode.CLOCK_DRIFT]] в нашем маппере ошибок — `src/execution/bybit/errors.py:29`).

2. **«Будущие» свечи** — бот содержит защиту от look-ahead (чтения будущих данных): живая свеча, чей `close_time` ещё не наступил, отбрасывается как незакрытая (см. [[bar-source-live]]). Если часы компьютера убегают вперёд относительно биржи, закрытые свечи биржи могут выглядеть «из будущего» с точки зрения локального времени.

Для защиты от этих ситуаций в проекте реализован `ClockDriftMonitor` — он запрашивает официальное время у Bybit и сравнивает его с системными часами. При расхождении больше **1 секунды** бросается ошибка. Это задокументировано как edge-case #9 в каталоге крайних случаев.

**UTC** — это мировое координированное время, единый стандарт без часовых поясов. Биржа и бот общаются исключительно в UTC, чтобы не было путаницы с летним/зимним временем.

## Как это работает у нас

Весь код монитора содержится в одном файле: `src/marketdata/clock.py` (34 строки).

### Шаг 1. Интерфейс клиента биржи

```python
class _ServerTimeClient(Protocol):
    def get_server_time(self) -> datetime: ...
```

`_ServerTimeClient` — это «договор» (Protocol): любой объект, у которого есть метод `get_server_time()`, возвращающий дату-время, подходит в качестве клиента. В продакшне это `BybitRESTClient` (`src/marketdata/bybit/rest.py:148`, см. [[bybit-rest-source]]), но при тестировании можно подставить любую заглушку.

### Шаг 2. Создание монитора

```python
class ClockDriftMonitor:
    def __init__(self, rest_client: _ServerTimeClient, threshold_ms: int = 1000) -> None:
        self._client = rest_client
        self.threshold_ms = threshold_ms
```

При создании монитор получает два параметра (`src/marketdata/clock.py:23-25`):

- `rest_client` — клиент для запроса времени биржи.
- `threshold_ms` — порог дрейфа в миллисекундах. По умолчанию **1000 мс = 1 секунда**. Это подтверждено в тесте `test_default_threshold_is_1000ms` (`tests/unit/test_clock.py:37-40`).

### Шаг 3. Проверка расхождения — метод `check_drift()`

```python
def check_drift(self) -> int:
    local = datetime.now(tz=UTC)
    server = self._client.get_server_time()
    drift_ms = int((server - local).total_seconds() * 1000)
    if abs(drift_ms) > self.threshold_ms:
        raise ClockDriftError(drift_ms, self.threshold_ms)
    return drift_ms
```

По шагам (`src/marketdata/clock.py:27-33`):

1. Фиксируется **локальное время** прямо сейчас: `local = datetime.now(tz=UTC)`.
2. Запрашивается **время биржи**: `server = self._client.get_server_time()`. Реальный REST-клиент обращается к эндпоинту Bybit V5, разбирает поле `timeSecond` и возвращает `datetime` с точностью до секунды (`src/marketdata/bybit/rest.py:148-154`).
3. Вычисляется дрейф: `drift_ms = int((server - local).total_seconds() * 1000)`. Это разница «время биржи минус локальное время» в миллисекундах.
4. Если модуль дрейфа превышает порог — бросается `ClockDriftError`. Иначе возвращается числовое значение дрейфа.

### Шаг 4. Ошибка дрейфа — `ClockDriftError`

```python
class ClockDriftError(RuntimeError):
    def __init__(self, drift_ms: int, threshold_ms: int) -> None:
        super().__init__(f"Clock drift {drift_ms}ms > threshold {threshold_ms}ms")
        self.drift_ms = drift_ms
        self.threshold_ms = threshold_ms
```

`ClockDriftError` (`src/marketdata/clock.py:11-17`) — это специализированный класс ошибки. Он несёт два атрибута: фактический дрейф в мс и использованный порог. Сообщение ошибки читаемо: например, `Clock drift 2500ms > threshold 1000ms`.

### Связь с Bybit REST-клиентом

Реальный клиент для получения серверного времени — `BybitRESTClient.get_server_time()` (`src/marketdata/bybit/rest.py:148-154`). Он вызывает `_retry_with_backoff()` (тот же механизм повторов, что и в [[bybit-rest-client-and-backoff|REST-клиенте исполнения]]) для защиты от временных ошибок сети, проверяет код ответа Bybit (`retCode == 0`) и возвращает `datetime.fromtimestamp(ts_s, tz=UTC)`, где `ts_s` — поле `timeSecond` из ответа биржи. Важно: `timeSecond` содержит Unix-время с точностью **до секунды** (не до миллисекунды), поэтому результат округлён до целых секунд.

### Статус интеграции в runtime

На текущий момент `ClockDriftMonitor` не подключён к автоматическому запуску бота (`grep -r "ClockDriftMonitor" src/` показывает только определение в `clock.py`). Монитор реализован и полностью покрыт тестами, но вызов `check_drift()` при старте бота — ручная операция или будущая интеграция. В edge-case каталоге (edge-case #9) описан полный сценарий реакции: CLOCK_DRIFT → ресинхронизация → 3 неудачи → [[safety-stops-and-halts|HALT]] (после чего [[execution-state-machine|FSM]] переводит бота в состояние `HALTED`).

## Формулы и расчёты

### Формула дрейфа

```text
drift_ms = int( (server_time − local_time).total_seconds() × 1000 )
```

Расшифровка простыми словами:

- `server_time` — момент времени, который Bybit считает «сейчас» (в UTC).
- `local_time` — момент времени, который системные часы компьютера считают «сейчас» (в UTC), зафиксированный **до** запроса к бирже.
- Разность даёт объект `timedelta` (промежуток времени).
- `.total_seconds()` превращает промежуток в дробное число секунд.
- Умножение на 1000 переводит в миллисекунды.
- `int(...)` отбрасывает дробную часть — дрейф выражается целым числом миллисекунд.

**Знак** дрейфа:
- `drift_ms > 0` означает, что биржа «живёт в будущем» относительно локальных часов (локальные часы отстают).
- `drift_ms < 0` означает, что биржа «живёт в прошлом» относительно локальных часов (локальные часы убежали вперёд).

**Условие срабатывания:** `abs(drift_ms) > threshold_ms`. То есть порог применяется по модулю — важна только *величина* расхождения, а не его направление.

Реализация: `src/marketdata/clock.py:30-31`.

### Порог по умолчанию

| Параметр | Значение | Источник |
|---|---|---|
| `threshold_ms` (по умолчанию) | 1000 мс = 1 секунда | `src/marketdata/clock.py:23` |
| Условие ошибки | `abs(drift_ms) > 1000` | `src/marketdata/clock.py:31` |

## Примеры / сценарии

### Сценарий A: часы синхронизированы — всё в порядке

Локальное время: 12:00:00.000 UTC  
Серверное время Bybit: 12:00:00.200 UTC

```text
drift_ms = int((12:00:00.200 − 12:00:00.000).total_seconds() × 1000)
         = int(0.2 × 1000)
         = 200
abs(200) > 1000? → НЕТ
```

`check_drift()` возвращает `200`. Никаких ошибок — это нормальная сетевая задержка.

### Сценарий B: часы разошлись — ошибка

Например, VPS-сервер после обновления сбросил NTP-синхронизацию.  
Локальное время: 12:00:05.000 UTC  
Серверное время Bybit: 12:00:00.000 UTC (биржа «в прошлом»)

```text
drift_ms = int((12:00:00.000 − 12:00:05.000).total_seconds() × 1000)
         = int(−5.0 × 1000)
         = −5000
abs(−5000) > 1000? → ДА
```

Бросается `ClockDriftError(drift_ms=-5000, threshold_ms=1000)`. Сообщение: `Clock drift -5000ms > threshold 1000ms`. Тест, покрывающий этот случай: `test_drift_exceeds_threshold_raises` в `tests/unit/test_clock.py:27-34`.

### Сценарий C: первый вызов в тесте, небольшой искусственный дрейф

Тест `test_drift_within_threshold_returns_ms` создаёт «серверное» время = локальное + 200 мс. Монитор возвращает значение в диапазоне (−2000, 2000) мс с `abs(drift) < 1000` (`tests/unit/test_clock.py:16-23`). Широкий диапазон `(-2000, 2000)` в проверке — это запас на реальную задержку выполнения кода между строками `local = datetime.now(...)` и `check_drift()` внутри теста.

## Подводные камни / что важно понимать

**1. Измерение включает сетевую задержку.** Между строкой `local = datetime.now(tz=UTC)` и получением `server_time` проходит время HTTP-запроса к Bybit (обычно 50–300 мс). Это означает, что реальный drift_ms включает в себя половину round-trip-времени. Для порога в 1 секунду это некритично, но нужно понимать: абсолютная точность измерения ±150 мс.

**2. Точность серверного времени — до секунды.** Bybit возвращает поле `timeSecond` (целые секунды Unix), а не миллисекундное `timeNano`. Значит, дрейф до 500 мс в пользу либо локальных, либо серверных часов может быть артефактом округления, а не реальным расхождением. Порог в 1000 мс с запасом учитывает это.

**3. Два разных CLOCK_DRIFT.** В проекте есть два места, связанных с дрейфом часов:
   - `ClockDriftError` из `src/marketdata/clock.py` — наша локальная проверка при старте.
   - Код ошибки Bybit `10002` → `ReasonCode.CLOCK_DRIFT` в `src/execution/bybit/errors.py:29` — биржа сама сообщает, что запрос устарел.
   Это разные механизмы: первый — наша превентивная проверка, второй — ответная реакция биржи на уже отправленный запрос.

**4. Монитор не подключён к автозапуску.** В текущей версии `ClockDriftMonitor` нужно создавать и вызывать вручную. Это не вызывается автоматически при старте `RuntimeManager` или других компонентов. Edge-case #9 описывает желаемое поведение (ресинхронизация → 3 ошибки → HALT), но его оркестровка не реализована в `src/` на момент документации.

**5. Dev-машина vs. облако.** На локальной машине macOS NTP обычно синхронизирует время с точностью < 100 мс. В облачных окружениях (особенно после миграции VPS или перезапуска контейнера) часы могут «улететь» на несколько секунд. Для продакшн-деплоя рекомендуется убедиться, что `chrony` или `systemd-timesyncd` работает корректно перед запуском бота.

**6. Порог можно изменить.** `threshold_ms` — параметр конструктора, не жёстко зашитая константа. Если биржа работает из-за геолокации с задержкой > 500 мс, порог можно увеличить при создании экземпляра монитора.
