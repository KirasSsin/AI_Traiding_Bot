# WebSocket-потребитель: real-time поток свечей

**TL;DR:** Бот держит постоянное соединение с биржей Bybit и получает новые данные о ценах практически мгновенно. `BybitWSConsumer` — это тонкая оболочка, которая превращает поток сырых биржевых сообщений в удобную очередь, из которой остальной код бота читает по одному сообщению за раз.

---

## Простыми словами

Представьте, что вы следите за курсом акций. Есть два способа это делать:

1. **Обычный запрос (REST)** — вы каждые несколько секунд звоните в банк и спрашиваете: «А сколько сейчас стоит?» Работает, но медленно и нагружает и вас, и банк. (Именно так устроен второй канал данных бота — [[bybit-rest-source|REST-источник]] для загрузки истории.)
2. **Живой поток (WebSocket)** — вы один раз подключаетесь к «прямой трансляции», и банк сам присылает вам обновление каждый раз, когда что-то изменилось.

**WebSocket** (веб-сокет) — это именно второй способ: постоянное двустороннее соединение через интернет, по которому данные текут непрерывно без лишних запросов.

Наш бот использует WebSocket-соединение с Bybit, чтобы получать **kline** (произносится «кей-лайн») — свечи в реальном времени. **Kline** (или **свеча**, [[bar-model|Bar]]) — это обобщённая картинка о торгах за один интервал времени: как цена открылась, каким был максимум и минимум, где закрылась, и сколько было сделок.

**Но есть одна техническая сложность** — «проблема двух потоков», о которой речь пойдёт ниже. Её решение — главная задача класса `BybitWSConsumer`.

## Как это работает у нас

### Шаг 1. Создание потребителя (`__init__`)

Класс `BybitWSConsumer` создаётся с тремя параметрами:

- `symbol` — какую торговую пару слушать (например, `"BTCUSDT"` — биткоин к доллару).
- `interval` — интервал свечи в минутах (например, `"60"` — часовые свечи).
- `testnet` — использовать тестовую биржу (`True`) или настоящую (`False`).

При создании объекта инициализируется **очередь** (`asyncio.Queue`) — пустой список, куда будут складываться поступающие сообщения:

```python
self._queue: asyncio.Queue[dict[str, Any]] = asyncio.Queue()
```

`asyncio.Queue` — это специальная очередь, безопасная для асинхронного кода (см. ниже про «два потока»). Также сохраняются заглушки `_loop = None` и `_ws = None` — они заполнятся при запуске.

(src/marketdata/bybit/ws.py:18–24)

---

### Шаг 2. Запуск соединения (`start`)

Метод `start()` должен вызываться **из асинхронного контекста** (то есть внутри уже запущенного async-цикла). Он выполняет три действия:

```python
def start(self) -> None:
    self._loop = asyncio.get_running_loop()          # (1) захватываем текущий event loop
    self._ws = WebSocket(testnet=self._testnet, channel_type="spot")  # (2) создаём WS-соединение
    self._ws.kline_stream(
        interval=self._interval,
        symbol=self._symbol,
        callback=self._on_message,                   # (3) регистрируем callback
    )
```

Разберём каждое действие:

**1. `asyncio.get_running_loop()`** — получаем ссылку на текущий **event loop** (событийный цикл). Event loop — это «диспетчер» асинхронного Python: он решает, какой кусок кода выполнять в данный момент. Ссылка нужна для того, чтобы позже безопасно передать данные из другого потока (см. Шаг 3).

**2. `WebSocket(testnet=..., channel_type="spot")`** — создаём WebSocket-соединение к бирже Bybit через библиотеку `pybit`. Параметр `channel_type="spot"` означает «спотовый рынок» — торговля реальными монетами (в отличие от фьючерсов). Бот работает именно на споте.

**3. `kline_stream(..., callback=self._on_message)`** — подписываемся на поток свечей для нашего символа и интервала. Слово `callback` (колбэк) — это функция, которую pybit будет вызывать каждый раз, когда придёт новое сообщение от биржи.

(src/marketdata/bybit/ws.py:26–34)

Проверка в тестах подтверждает точные параметры: `WebSocket` вызывается с `testnet=True, channel_type="spot"`, а `kline_stream` получает `interval` и `symbol` именно из конструктора. (tests/unit/test_bybit_ws.py:48–57)

### Шаг 3. Мост между двумя потоками (`_on_message`)

Здесь — самое важное и нетривиальное место во всём компоненте.

**Проблема.** Библиотека `pybit` запускает WebSocket в **отдельном системном потоке** (thread). Поток — это как второй «параллельный работник» внутри программы. Основной же цикл бота работает в **asyncio event loop** — специальном однопоточном асинхронном диспетчере.

Если callback из чужого потока попытается напрямую положить данные в asyncio-очередь, это может вызвать **гонку данных** (race condition) — непредсказуемый конфликт, когда два работника пытаются изменить одно и то же одновременно. Это может привести к зависанию, пропуску данных или сбою.

**Решение — `call_soon_threadsafe`:**

```python
def _on_message(self, msg: dict[str, Any]) -> None:
    data = msg.get("data") or []
    if not data:
        return
    assert self._loop is not None
    self._loop.call_soon_threadsafe(self._queue.put_nowait, data[0])
```

`call_soon_threadsafe` — это специальный метод event loop, разработанный именно для таких ситуаций: он позволяет **потоку pybit** безопасно передать работу (`self._queue.put_nowait`) **в event loop бота**. Сам event loop потом выполнит её, когда придёт его очередь.

Что именно кладётся в очередь? Из каждого WS-сообщения берётся `data[0]` — **первый элемент массива `data`**. Биржа Bybit присылает массив, потому что в теории может прислать несколько свечей разом, но на практике kline-обновление — это всегда один элемент. Берём именно нулевой (первый), игнорируя остальные.

Если `data` пустой (например, пришло служебное сообщение о подключении, а не данные) — callback просто ничего не делает и возвращается.

(src/marketdata/bybit/ws.py:36–43)

### Шаг 4. Чтение потока (`stream`)

```python
async def stream(self) -> AsyncIterator[dict[str, Any]]:
    while True:
        msg = await self._queue.get()
        yield msg
```

`stream()` — это **асинхронный генератор** (async generator). Он работает как бесконечная труба: вызывающий код пишет `async for msg in consumer.stream()`, и получает сообщения одно за другим — каждый раз, когда они появляются в очереди.

`await self._queue.get()` — это асинхронное ожидание: пока очередь пуста, event loop занимается другими делами (не зависает), а как только в очередь попадает новое сообщение — функция «просыпается» и отдаёт его наружу через `yield`.

Цикл `while True` означает, что поток никогда не останавливается сам по себе — он продолжается, пока бот работает.

(src/marketdata/bybit/ws.py:45–49)

### Полная картина: как элементы соединяются

```text
Биржа Bybit
    │  (WebSocket-соединение)
    ↓
pybit WebSocket (отдельный системный поток)
    │  callback(_on_message) при каждом сообщении
    ↓
call_soon_threadsafe → queue.put_nowait(data[0])
    │  (безопасная передача в event loop бота)
    ↓
asyncio.Queue  ←──── мост между потоками
    │  queue.get() при каждой итерации stream()
    ↓
async for msg in consumer.stream()
    │
    ↓
MarketDataPipeline (pipeline.py) → BarBuilder → сохранение в Parquet
```

`BybitWSConsumer` — это только первое звено цепочки. Он лишь принимает сырой WS-payload и кладёт его в очередь. Дальнейшую обработку (превращение в Bar-объект, обнаружение пропусков, запись на диск) выполняет [[data-pipeline|`MarketDataPipeline`]] через [[bar-builder-ws|`BarBuilder`]], а закрытые свечи сохраняются в [[parquet-storage|формат Parquet]]. (src/marketdata/pipeline.py:53–64)

## Примеры / сценарии

### Сценарий: первые два часовых сообщения от биржи

Предположим, бот подписан на `BTCUSDT` с интервалом `60` (часовые свечи).

**Шаг 1.** Биржа присылает первое сообщение (свеча ещё не закрылась, `confirm=False`):

```text
{
  "topic": "kline.60.BTCUSDT",
  "data": [
    {"start": 1719360000000, "confirm": false, "open": "60000", "high": "60100", ...}
  ]
}
```

Callback `_on_message` срабатывает. Берётся `data[0]` — словарь с полями `start`, `confirm`, `open` и т.д. Через `call_soon_threadsafe` он попадает в очередь.

**Шаг 2.** `stream()` возвращает этот словарь вызывающему коду. `BarBuilder.process()` видит `confirm=False` и возвращает `None` — свечу ещё не записывает, ждёт подтверждения.

**Шаг 3.** Биржа присылает второе сообщение (свеча закрылась, `confirm=True`):

```text
{
  "topic": "kline.60.BTCUSDT",
  "data": [
    {"start": 1719360000000, "confirm": true, "open": "60000", "high": "60200", "low": "59800", "close": "60050", "volume": "12.5"}
  ]
}
```

`BarBuilder.process()` видит `confirm=True` и создаёт законченный `Bar`-объект, который записывается в Parquet.

---

Тест `test_stream_yields_messages_from_callback` воспроизводит именно этот сценарий: два callback-вызова с разными значениями `start`, и проверяет, что `stream()` выдаёт оба сообщения в правильном порядке. (tests/unit/test_bybit_ws.py:11–44)

## Подводные камни / что важно понимать

### 1. `start()` нужно вызывать внутри async-функции

Если вызвать `start()` вне async-контекста (например, в обычной синхронной функции), `asyncio.get_running_loop()` выбросит исключение — нет запущенного event loop. Именно поэтому в `MarketDataPipeline.run()` метод `ws.start()` вызывается внутри `async def run(...)`. (src/marketdata/pipeline.py:51)

### 2. Берётся только `data[0]` — всегда первый элемент

Биржа технически может прислать несколько элементов в `data`, но для kline-стрима это не происходит. Код явно берёт только нулевой элемент (`data[0]`). Если биржа когда-нибудь изменит формат и пришлёт несколько элементов за раз — остальные будут молча проигнорированы. (src/marketdata/bybit/ws.py:43)

### 3. Пустые сообщения отбрасываются без ошибки

Pybit периодически присылает служебные пакеты (например, «соединение установлено», heartbeat-пинги). Они не имеют полезного поля `data` или `data` у них пустой. Защита `if not data: return` в `_on_message` их молча пропускает. (src/marketdata/bybit/ws.py:38–40)

### 4. `channel_type="spot"` — это константа, не параметр

Тип канала жёстко задан как `"spot"` (спотовый рынок) прямо в коде `start()`. Изменить его без правки кода нельзя. Бот не предназначен для фьючерсов или маржинальной торговли. (src/marketdata/bybit/ws.py:29) А вот параметр `testnet` определяет, к какому контуру биржи (тестовому или реальному) подключается поток — см. [[run-modes-testnet-live-reconcile|режимы запуска]].

### 5. Очередь неограничена — накопление при отставании

`asyncio.Queue()` создаётся без параметра `maxsize`, то есть она неограничена. Если по какой-то причине код бота начнёт отставать от скорости сообщений от биржи (например, стратегия тормозит), очередь будет тихо накапливаться в памяти. В нормальных условиях это не проблема, так как часовые свечи приходят раз в час.

### 6. Нет автоматического переподключения

`BybitWSConsumer` не содержит логики для обнаружения разрыва соединения и самовосстановления. Это зона ответственности более высокого уровня системы (runtime manager / health check). Если WS-соединение оборвётся — `stream()` просто застынет в ожидании новых сообщений, которые не придут. Для сравнения: [[bybit-private-websocket|приватный WebSocket]] (поток исполнений ордеров) построен на том же паттерне `pybit`, но у него уже есть сторожевой таймер `check_alive()` и логика переподключения — именно то, чего здесь нет.
