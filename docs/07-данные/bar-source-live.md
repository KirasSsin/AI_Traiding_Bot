# Источник свечей в live-режиме: polling, дедупликация, защита от look-ahead

**TL;DR:** В live-торговле бот каждые 5 секунд спрашивает биржу Bybit: «закрылась ли новая свеча?». Компонент `BarSource` забирает ответ, отбрасывает незакрытые и дублирующиеся свечи, и передаёт стратегии только один раз — именно ту свечу, которая уже «зафиксирована» историей.

## Простыми словами

Представьте, что вы следите за биржевым табло, на котором цена меняется каждую секунду. Но вас интересует не мгновенная цена, а итог каждого часа — так называемая **свеча** (или бар): цена в начале часа, максимум, минимум и цена в конце. Только когда час закончился, свеча считается «закрытой» и зафиксированной — она уже не изменится.

Стратегия бота принимает решения только по таким закрытым свечам. Но биржа Bybit всегда возвращает и текущую, ещё не закрытую свечу — она продолжает меняться прямо сейчас. Если бы бот реагировал на неё, он торговал бы по «данным из будущего»: то, что кажется сигналом сейчас, к концу часа может оказаться совсем другим. Это называется **look-ahead** (взгляд вперёд) — классическая ловушка, которая делает стратегию прибыльной только на бумаге. Ту же ловушку в бэктесте предотвращает [[replay-engine-bar-by-bar|движок проигрывания истории]], который «открывает» бары строго по одному.

`BarSource` — это «охранник на входе»: он периодически опрашивает биржу (это называется **polling**, то есть опрос по расписанию — в отличие от [[bar-builder-ws|push-модели через WebSocket]]), проверяет каждую полученную свечу и пропускает дальше только те, что действительно закрылись. Кроме того, он помнит, какую свечу передал стратегии в прошлый раз — и не отправляет её снова (**дедупликация**). Если биржа долго не отвечает, компонент считает сбои и в какой-то момент говорит RuntimeManager: «хватит, нужно остановить торговлю» (**HALT**).

## Как это работает у нас

### Шаг 0. Создание: что настраивается при запуске

```python
# src/runtime/bar_source.py:41–58
class BarSource:
    def __init__(
        self,
        *,
        adapter: Any,
        symbol: str,
        interval: str = "60",
        now_fn: Callable[[], float] | None = None,
    ) -> None:
```

При создании `BarSource` принимает четыре параметра:

- **`adapter`** — объект, который умеет обращаться к Bybit REST API за свечами. В production это `BybitRESTClient` — слой [[bybit-rest-source|получения данных по REST]] с методом `get_klines` (src/marketdata/bybit/rest.py:127). Конкретно при запуске бота создаётся так: `rest = BybitRESTClient(...)`, после чего `bar_source = BarSource(adapter=rest, ...)` — эта сборка происходит на [[startup-and-wiring|старте бота]] (src/__main__.py:108, 168).
- **`symbol`** — тикер инструмента, например `"BTCUSDT"`.
- **`interval`** — временной интервал свечи. По умолчанию `"60"` — это 60 минут (1 час). Полный список поддерживаемых интервалов — 13 значений Bybit V5 (см. ниже). Если передать неизвестный интервал, `BarSource` сразу падает с `ValueError` — ошибка обнаруживается ещё до первого опроса.
- **`now_fn`** — необязательная функция, возвращающая текущее время в секундах. Если не указана, используется стандартная `time.time`. Этот параметр нужен для тестов: в тестах можно «заморозить» время и проверять логику без реального ожидания (подробнее — в разделе [[#Injectable clock]]).

Два служебных поля инициализируются сразу:

```python
self._last_close_ts: int | None = None  # ms epoch, последняя переданная свеча
self.consecutive_failures: int = 0       # счётчик сбоев подряд
```

(src/runtime/bar_source.py:57–58)

### Шаг 1. `poll()` — один цикл опроса

Главный публичный метод — `poll()`. Он вызывается RuntimeManager на каждом [[main-loop-tick|тике главного цикла]] — каждые 5 секунд (по умолчанию, настройка `runtime_bar_poll_cadence_seconds = 5.0` в config.py:210; см. [[configuration-and-settings|настройки бота]]). Логика работает так:

```python
# src/runtime/bar_source.py:60–92
def poll(self) -> Bar | None:
```

**Результат:** либо один закрытый, новый бар типа [[bar-model|`Bar`]], либо `None` (ничего нового нет или произошла ошибка).

Внутри `poll()` происходит четыре вещи по порядку:

#### 1а. Запрос к бирже (`_fetch`)

```python
# src/runtime/bar_source.py:62–64
try:
    bars = self._fetch()
except Exception as e:  # noqa: BLE001 — caller decides halt vs continue
    self.consecutive_failures += 1
    ...
    return None
```

Метод `_fetch()` обращается к [[bybit-rest-source|адаптеру REST]] (его метод `get_klines`) и просит последние два бара:

```python
# src/runtime/bar_source.py:104–113
def _fetch(self) -> list[Bar]:
    step_ms = self._INTERVAL_MS[self._interval]
    end_ms = self._now_ms()
    start_ms = end_ms - step_ms * 2  # окно = последние 2 бара
    return self._adapter.get_klines(
        symbol=self._symbol,
        interval=self._interval,
        start_ms=start_ms,
        end_ms=end_ms,
    )
```

Почему **два** бара, а не один? Потому что Bybit V5 всегда включает текущую (ещё формирующуюся) свечу. Запрашивая два бара, мы гарантируем, что предыдущий — уже закрытый — попадёт в выборку даже если текущий формирующийся займёт «последнее место».

**Если `_fetch()` бросил исключение** (сеть упала, таймаут, ошибка API) — счётчик `consecutive_failures` увеличивается на 1, метод возвращает `None`. RuntimeManager на следующем тике проверит `should_halt()`.

При успехе — `consecutive_failures` **сбрасывается в 0**: восстановление засчитывается немедленно.

```python
# src/runtime/bar_source.py:73
self.consecutive_failures = 0
```

#### 1б. DI-02 Look-ahead guard: отбрасываем незакрытые свечи

Это самый важный шаг. Bybit REST API всегда возвращает ещё формирующуюся текущую свечу — у неё `is_closed=True` в ответе API, но на практике её `close_time` находится **в будущем**. Адаптер (`rest.py:269`) записывает `is_closed=True` для всех баров механически, не проверяя реальное время. Поэтому поле `is_closed` само по себе не служит защитой.

`BarSource` использует другой критерий: **сравнение `close_time` бара с текущим временем**.

```python
# src/runtime/bar_source.py:81–87
now_ms = self._now_ms()
latest = None
for bar in bars:
    if int(bar.close_time.timestamp() * 1000) <= now_ms:
        latest = bar  # самый свежий из уже закрытых (список oldest-first)
if latest is None:
    return None
```

Проход идёт по всем барам в окне. Бар «закрыт» для нас только если `close_time ≤ now`. Если `close_time > now` — бар ещё формируется, даже если API сказал `is_closed=True`. Такие бары молча отбрасываются. Если в окне нет ни одного закрытого бара — `poll()` возвращает `None`.

**Важная деталь:** формирующийся бар не продвигает внутренний курсор `_last_close_ts`. То есть когда тот же бар через час наконец закроется — он будет корректно обнаружен и отправлен стратегии. Тест в test_bar_poller.py:186–206 специально проверяет именно этот сценарий.

#### 1в. Дедупликация по `close_time`

После look-ahead-проверки у нас есть `latest` — самый свежий закрытый бар. Но возможно, мы уже отправили его стратегии на прошлом тике. Сравниваем:

```python
# src/runtime/bar_source.py:88–92
close_ms = int(latest.close_time.timestamp() * 1000)
if self._last_close_ts is not None and close_ms <= self._last_close_ts:
    return None  # уже обработан
self._last_close_ts = close_ms
return latest
```

Если `close_time` нового бара совпадает или меньше, чем у последнего переданного — возвращаем `None`. Иначе запоминаем новый `close_time` в `_last_close_ts` и возвращаем бар стратегии.

Таким образом, стратегия получает каждый закрытый бар **ровно один раз**, сколько бы раз Bybit ни вернул его в ответе.

### Шаг 2. `should_halt()` — сигнал к остановке при стабильных сбоях

```python
# src/runtime/bar_source.py:94–96
def should_halt(self, *, threshold: int) -> bool:
    """True if consecutive_failures hit threshold — caller emits HALT_BAR_POLL_STALL."""
    return self.consecutive_failures >= threshold
```

После каждого вызова `poll()` RuntimeManager проверяет `should_halt(threshold=N)`. Если счётчик достиг порога — RuntimeManager запрашивает у [[coordinator-orchestration|координатора]] остановку торговли с [[reason-codes-assessment-output|кодом причины]] `HALT_BAR_POLL_STALL`:

```python
# src/runtime/manager.py:326–334
bar = self._bar_source.poll()
if self._bar_source.should_halt(threshold=self._settings.runtime_bar_poll_stall_threshold):
    logger.error(
        "runtime.bar_poll_stall",
        consecutive_failures=self._bar_source.consecutive_failures,
        threshold=self._settings.runtime_bar_poll_stall_threshold,
    )
    self._coordinator.request_halt(ReasonCode.HALT_BAR_POLL_STALL)
    self._stopping = True
    return
```

Значение порога — настраиваемое, по умолчанию **24** (src/platform/config.py:214–221). Допустимый диапазон от 6 до 720 (config.py:245–249).

### Шаг 3. Injectable clock (`now_fn`) — тестируемость

```python
# src/runtime/bar_source.py:98–102
def _now_ms(self) -> int:
    now_s = self._now_fn() if self._now_fn is not None else time.time()
    return int(now_s * 1000)
```

Если в конструктор передана `now_fn`, она используется вместо реального системного времени. В тестах это позволяет «заморозить» момент времени и проверять граничные условия look-ahead guard (тест test_bar_poller.py:147–165).

Если `now_fn` не передана, используется `time.time` — модульная ссылка, что позволяет и обычному `monkeypatch.setattr("src.runtime.bar_source.time.time", ...)` работать корректно (тест test_bar_poller.py:63–87).

### Поддерживаемые интервалы

`BarSource` поддерживает ровно 13 строковых обозначений интервалов Bybit V5 (src/runtime/bar_source.py:25–39):

| Строка | Длительность | Длина интервала (мс) |
|--------|-------------|---------------------|
| `"1"` | 1 минута | 60 000 |
| `"3"` | 3 минуты | 180 000 |
| `"5"` | 5 минут | 300 000 |
| `"15"` | 15 минут | 900 000 |
| `"30"` | 30 минут | 1 800 000 |
| `"60"` | 1 час (default) | 3 600 000 |
| `"120"` | 2 часа | 7 200 000 |
| `"240"` | 4 часа | 14 400 000 |
| `"360"` | 6 часов | 21 600 000 |
| `"720"` | 12 часов | 43 200 000 |
| `"D"` | 1 день | 86 400 000 |
| `"W"` | 1 неделя | 604 800 000 |
| `"M"` | ~1 месяц (30д) | 2 592 000 000 |

В v0.1 бот использует только `"60"` (1-часовые свечи). Остальные интервалы в словаре — готовая инфраструктура на будущее.

**Важно:** `BarSource._INTERVAL_MS` и словарь `intervals` внутри метода `BybitRESTClient.get_klines` (rest.py:189–197) — **разные словари** с разными наборами поддерживаемых интервалов. `intervals` — это локальная переменная внутри метода, а не атрибут класса. В `BarSource` 13 интервалов (все Bybit V5), в `BybitRESTClient.get_klines` — 7 (только те, что нужны для торговли и дашборда). Если передать интервал, который есть в `BarSource._INTERVAL_MS`, но отсутствует в `get_klines`, ошибка возникнет уже в адаптере.

## Формулы и расчёты

### Окно запроса в `_fetch()`

```
start_ms = now_ms - 2 × interval_ms
end_ms   = now_ms
```

Простыми словами: «дай мне данные за последние два периода, считая сейчас за конец». Для 1-часовых свечей это означает запрос за последние 2 часа — достаточно, чтобы гарантированно захватить последнюю закрытую свечу.

Реализация (src/runtime/bar_source.py:105–107):

```python
step_ms = self._INTERVAL_MS[self._interval]
end_ms = self._now_ms()
start_ms = end_ms - step_ms * 2
```

### Критерий закрытости бара

```
бар закрыт ⟺ close_time_ms ≤ now_ms
```

Простыми словами: бар считается зафиксированным, если его время закрытия уже наступило или наступило ровно сейчас. Всё, что в будущем — ещё формируется (src/runtime/bar_source.py:84).

### Критерий дедупликации

```
бар новый ⟺ close_time_ms > _last_close_ts
```

Если закрытое время нового бара строго больше запомненного — это новый бар. Иначе — уже видели (src/runtime/bar_source.py:89).

### Расчёт порога сбоев в секундах

```
время_до_HALT = threshold × cadence_seconds
```

При настройках по умолчанию: `24 × 5 = 120 секунд = 2 минуты`.

Это означает: если биржа не отвечает 2 минуты подряд — бот останавливает торговлю. Эта цифра откалибрована в ADR 0022: слишком короткий порог приведёт к ложным остановкам при обычных временных сбоях Bybit; слишком длинный — к торговле вслепую.

## Примеры / сценарии

### Сценарий A: нормальная работа, новая свеча появляется каждый час

```text
Время 14:05 (UTC):
  poll() → _fetch() запрашивает [12:05..14:05]
  Bybit возвращает:
    бар [13:00–14:00] close_time=14:00 → 14:00 ≤ 14:05 ✓ закрыт
    бар [14:00–15:00] close_time=15:00 → 15:00 > 14:05 ✗ формирующийся
  look-ahead guard: formирующийся отброшен, latest = бар [13:00–14:00]
  _last_close_ts = None → новый! → _last_close_ts = 14:00_ms
  Возврат: бар [13:00–14:00] → стратегия его обрабатывает

Время 14:10 (UTC):
  poll() → Bybit снова возвращает те же два бара
  look-ahead guard: формирующийся [14:00–15:00] отброшен, latest = [13:00–14:00]
  Дедупликация: close_ms == _last_close_ts → None
  Возврат: None → стратегия ничего не делает

Время 15:05 (UTC):
  poll() → _fetch() запрашивает [13:05..15:05]
  Bybit возвращает:
    бар [14:00–15:00] close_time=15:00 → 15:00 ≤ 15:05 ✓ теперь закрыт!
    бар [15:00–16:00] close_time=16:00 → 16:00 > 15:05 ✗ формирующийся
  latest = бар [14:00–15:00]
  Дедупликация: close_ms (15:00) > _last_close_ts (14:00) → новый!
  → _last_close_ts = 15:00_ms
  Возврат: бар [14:00–15:00] → стратегия обрабатывает
```

### Сценарий B: сеть упала, потом восстановилась

```text
Тики 1–5: _fetch() бросает RuntimeError("network down")
  consecutive_failures: 1, 2, 3, 4, 5
  should_halt(threshold=24) → False (ещё терпимо)

Тики 6–23: аналогично, consecutive_failures = 23

Тик 24: снова ошибка, consecutive_failures = 24
  should_halt(threshold=24) → True
  RuntimeManager → coordinator.request_halt(HALT_BAR_POLL_STALL)
  Торговля останавливается. (src/runtime/manager.py:333)

--- если бы сеть восстановилась на тике 10:

Тик 10: _fetch() успешен
  consecutive_failures = 0  ← сброс немедленно
  should_halt(threshold=24) → False
  Торговля продолжается без прерывания.
```

### Сценарий C: бар как раз закрывается

```text
now_ms = 1_700_007_200_000 (= 14:00:00 UTC в миллисекундах)
settled = бар [13:00–14:00], close_time_ms = 1_700_007_200_000

Проверка: close_time_ms (1_700_007_200_000) ≤ now_ms (1_700_007_200_000) → True
Бар засчитан как закрытый — граничный случай «закрыт ровно сейчас» корректен.
```

Этот сценарий покрыт тестом test_bar_poller.py:152–165.

## Подводные камни / что важно понимать

### 1. `is_closed=True` от Bybit не означает «закрыт» для нашего бота

Это самое неочевидное место. Адаптер `rest.py` жёстко кодирует `is_closed=True` для всех баров, которые возвращает Bybit (rest.py:269). Причина: Bybit V5 kline API всегда включает текущую формирующуюся свечу, но отдельного флага «это незакрытая свеча» не предоставляет в REST ответе в том смысле, который нам нужен. Поэтому `BarSource` использует единственно надёжный критерий: сравнение `close_time` с реальным временем. Поле `is_closed` игнорируется при look-ahead-проверке (DI-02).

### 2. Формирующийся бар НЕ продвигает курсор дедупликации

Когда `poll()` видит только формирующийся бар и возвращает `None` — `_last_close_ts` не обновляется. Это сделано специально: когда этот же бар через час закроется, он должен корректно пройти дедупликацию и попасть к стратегии. Если бы курсор продвигался, бар «потерялся» бы навсегда (тест test_bar_poller.py:186–206).

### 3. Порог сбоев (24) нельзя делать слишком маленьким

Минимально допустимое значение по конфигу — **6** (= 30 секунд при cadence=5s). Меньше 6 — слишком высока вероятность ложной остановки при обычном кратком сбое Bybit. Максимум — **720** (= 3600 секунд = 1 час). Больше 1 часа означало бы, что бот может торговать без данных дольше, чем длится одна свеча — это недопустимо (src/platform/config.py:245–249).

### 4. Остановка при стабильных сбоях — это безопасность, а не «паника»

`HALT_BAR_POLL_STALL` относится к классу «сигнального трубопровода» (signal-pipeline halt) — одному из [[safety-stops-and-halts|тормозов бота]]: бот не видит рынок и не может принимать решения. Открытые позиции при этом **не затрагиваются**: [[oco-bracket-emulation|OCO-ордера]] (take profit и stop loss) остаются активными на бирже. Потеря данных ≠ потеря денег — но торговать вслепую тоже нельзя.

### 5. Слабое место: пропуск сигнала при долгом stall

Если бот не получал данных, например, 40 минут (до достижения порога остановки), и за это время закрылся бар с хорошим сигналом — этот сигнал будет пропущен. Когда связь восстановится (до порога), `BarSource` получит уже более новый бар. Это **slippage по сигналу**, не ошибка данных. Мониторится через лог-событие `runtime.bar_poll_stall` с полем `consecutive_failures`.

### 6. `BarSource` и `BybitRESTClient.get_klines` — разные словари интервалов

`BarSource._INTERVAL_MS` содержит все 13 интервалов Bybit V5 (для вычисления окна запроса). Метод `BybitRESTClient.get_klines` в rest.py содержит локальную переменную `intervals`, которая поддерживает только 7 интервалов (`"5"`, `"15"`, `"30"`, `"60"`, `"120"`, `"240"`, `"D"`) (rest.py:189–197). Создать `BarSource` с интервалом `"720"` технически можно — ошибка возникнет только при первом `poll()` внутри адаптера.
