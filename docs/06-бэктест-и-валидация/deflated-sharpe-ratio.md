# Deflated Sharpe Ratio (DSR): поправка на удачу и многократные попытки

**TL;DR:** Обычный коэффициент Шарпа врёт, когда стратегий тестировалось много — одна из них выглядит хорошей просто по случайности. DSR делает поправку: учитывает, сколько попыток было, насколько доходности «кривые» (несимметричные), и насколько мала выборка. Наш бот допускает стратегию в live-торговлю только если DSR ≥ 0.95 — то есть с вероятностью не менее 95% у неё есть реальное преимущество, а не просто везение.

---

## Простыми словами

Представьте, что вы выбираете врача из 100 кандидатов, бросая монетку: кто-то вылечит больного по чистой случайности. Если потом сказать «вот лучший врач — его монетка выпала орлом 12 раз подряд», это совсем не значит, что он хороший врач. Просто при большом числе кандидатов кому-то обязательно везёт.

С торговыми стратегиями ровно та же ловушка. Если протестировать 100 разных наборов параметров, один из них почти наверняка покажет высокий **[[sharpe-sortino-metrics|коэффициент Шарпа]]** — стандартную меру «доходность делённая на риск» — просто потому что нам повезло. Это называется **selection bias** (смещение отбора): мы выбираем лучший результат из многих, а потом делаем вид, что он один был.

**DSR (Deflated Sharpe Ratio, «сдутый Шарп»)** — формула, которую разработали математики Бейли и Лопес де Прадо в 2014 году, чтобы честно ответить на вопрос: «С какой вероятностью реальное преимущество стратегии положительное, даже с учётом того, что мы перебрали N вариантов?» Ответ — число от 0 до 1, интерпретируемое как вероятность.

DSR понижает («сдувает») ваш Шарп тремя способами:

1. **Штраф за множественное тестирование** — чем больше стратегий проверено, тем выше «планка» (нужен Шарп значительно лучше нуля, чтобы отличить себя от удачи).
2. **Штраф за форму распределения доходностей** — если доходности «перекошены» (много мелких прибылей, редкие огромные убытки) или имеют «тяжёлые хвосты», обычная статистика переоценивает надёжность. DSR это учитывает через **асимметрию** и **эксцесс** распределения.
3. **Штраф за малый размер выборки** — при 30 сделках неопределённость намного выше, чем при 1000. DSR корректирует на `√(n − 1)`.

В нашем боте порог: **DSR ≥ 0.95** (src/backtest/research_wfa.py:37) — стратегия должна пройти этот фильтр вместе с шестью другими критериями ([[acceptance-gates-t1-t6|T1-T6]]), прежде чем её разрешено запускать вживую.

## Как это работает у нас

Всю математику делают два файла: `src/analytics/dsr.py` (расчёт) и `src/analytics/cross_trial_log.py` (хранение истории попыток). Разберём каждую функцию.

### 1. `compute_returns` — подготовка доходностей

```python
# src/analytics/dsr.py:32–51
def compute_returns(trades: list[TradeRecord], *, use_log: bool = True) -> list[float]:
```

Принимает список закрытых сделок (каждая — объект [[trade-extractor-and-records|`TradeRecord`]] с полем `pnl_pct`). Возвращает список доходностей в нужном виде.

По умолчанию (`use_log=True`) вычисляется **логарифмическая доходность** (log-доходность): `log(1 + r)`. Это математически корректно при сложном процентном накоплении — логарифмы можно складывать, тогда как простые проценты складывать нельзя.

Особый случай: если сделка завершилась полным убытком (`pnl_pct == -1.0`, то есть потеряно 100%), логарифм уходит в минус-бесконечность. Функция явно записывает `-math.inf` в список (src/analytics/dsr.py:47). Эти значения потом фильтруются в `compute_dsr`, чтобы не испортить среднее и дисперсию.

### 2. `compute_dsr` — главная формула

```python
# src/analytics/dsr.py:54–173
def compute_dsr(
    trades, *, benchmark_sharpe=0.0, n_trials=1,
    sigma_sr=None, annualization_factor=None, use_log=True
) -> float:
```

Это ядро всей системы. Возвращает число от 0 до 1 — вероятность того, что истинный Шарп стратегии выше порогового, с учётом всех поправок.

Возвращает `NaN` в четырёх ситуациях (src/analytics/dsr.py:64–69):
- `n < 2` — нет данных или одна сделка (дисперсия не определена)
- Менее двух конечных доходностей после фильтрации `-inf`
- Все доходности одинаковые (дисперсия равна нулю)
- `denom_inner ≤ 0` — редкое математическое вырождение при экстремальных skew/kurtosis

**Шаги вычисления:**

**Шаг 1 — Считаем «сырой» Шарп по сделкам** (src/analytics/dsr.py:112–117):

```python
mean = sum(finite_returns) / len(finite_returns)
var  = sum((r - mean)**2 for r in finite_returns) / (len(finite_returns) - 1)
std  = math.sqrt(var)
sharpe = mean / std
```

Это обычный Шарп: средняя доходность делённая на стандартное отклонение. Важно: он вычисляется **по сделкам**, без нормировки на год — это «per-trade» Шарп.

**Шаг 2 — Асимметрия и эксцесс** (src/analytics/dsr.py:124–125):

```python
skew = float(stats.skew(finite_returns, bias=False))
kurt = float(stats.kurtosis(finite_returns, bias=False, fisher=False))
```

Здесь критически важный момент: `fisher=False`. Это означает **Пирсоновский эксцесс** (Pearson kurtosis, полный), а не «избыточный» (excess). Для нормального распределения Пирсоновский эксцесс = 3. Если бы мы использовали `fisher=True` (excess), для нормального распределения получился бы 0, и формула Bailey давала бы систематически неверный DSR — это был реальный баг (BLOCKER S9), который был исправлен и зафиксирован в коде с явным комментарием (src/analytics/dsr.py:119–123).

**Шаг 3 — Поправка на множественное тестирование** (src/analytics/dsr.py:130–163):

Если `n_trials > 1` (проверялось несколько стратегий), вычисляется «скорректированный эталон» — тот Шарп, который нужно превзойти с учётом удачи при N попытках. Подробнее — в разделе «Формулы».

Если `n_trials == 1` — скорректированный эталон равен просто `benchmark_sharpe` (по умолчанию 0).

**Шаг 4 — Итоговый DSR** (src/analytics/dsr.py:165–173):

Вычисляется z-статистика и пропускается через функцию нормального распределения Φ. Результат — вероятность от 0 до 1.

### 3. `compute_dsr_with_status` — с флагом надёжности

```python
# src/analytics/dsr.py:176–211
def compute_dsr_with_status(*, trades, n_trials=1, sigma_sr=None,
                             annualization_factor=None, benchmark_sharpe=0.0,
                             use_log=True) -> dict[str, Any]:
```

Обёртка над `compute_dsr`, которая добавляет флаг о том, достаточно ли данных. По ADR 0056 три уровня (src/analytics/dsr.py:193–195):

| Число сделок | DSR | Статус |
|---|---|---|
| `n < 10` | `NaN` (не вычисляется) | `INSUFFICIENT_TRADES` |
| `10 ≤ n < 30` | вычисляется | `UNDERPOWERED` |
| `n ≥ 30` | вычисляется | `GATE_ELIGIBLE` |

Статус `UNDERPOWERED` означает: DSR посчитан, но к нему нужно относиться с осторожностью — выборка мала. `GATE_ELIGIBLE` — выборка достаточная, результат считается надёжным.

### 4. `CrossTrialLog` — журнал истории попыток

```python
# src/analytics/cross_trial_log.py:97–232
class CrossTrialLog:
```

Файл `data/cross_trial_sharpes.json` — постоянная «память» бота о том, какие Шарпы показывали все предыдущие запуски WFA ([[walk-forward-analysis|walk-forward анализа]]). Это нужно, чтобы DSR знал, сколько попыток уже было и каков разброс Шарпов между ними. Отдельная страница про этот журнал: [[cross-trial-log|CrossTrialLog]].

Каждая запись — это `TrialEntry`: спринт, символ торгового инструмента, класс стратегии и OOS Шарп (src/analytics/cross_trial_log.py:73–87).

**Ключевые методы:**

- `append_trial(sprint, oos_sharpe, symbol, strategy_class)` — добавляет запись. **Идемпотентна** по паре `(sprint, symbol)`: если такая запись уже есть — обновляет её, а не дублирует (src/analytics/cross_trial_log.py:180–195). Это защищает от случаев, когда дашборд перезапускается и пытается добавить одно и то же дважды.
- `n_trials()` — общее число записей в журнале (src/analytics/cross_trial_log.py:143–148). Это глобальный счётчик всех испытаний, включая разные символы и стратегии.
- `sigma_sr(strategy_class=None)` — стандартное отклонение OOS Шарпов (src/analytics/cross_trial_log.py:197–232). Подробнее ниже.

**Атомарная запись** (src/analytics/cross_trial_log.py:193–195): сначала записывается во временный файл `.tmp`, затем переименовывается — так не бывает «наполовину записанного» файла при сбое.

### 5. `sigma_sr` — разброс Шарпов между попытками

```python
# src/analytics/cross_trial_log.py:197–232
def sigma_sr(self, strategy_class: str | None = None) -> float | None:
```

**sigma_SR** (от sigma Sharpe Ratio) — стандартное отклонение OOS Шарпов по всем прошлым попыткам. Это мера того, насколько сильно Шарп «прыгает» от прогона к прогону.

Три ситуации (src/analytics/cross_trial_log.py:225–232):
- **0 записей** → возвращает `None` (вызывающий код использует `n_trials=1`)
- **1–2 записи** → возвращает `NaN` (статистически недопустимо: степени свободы `df < 2`)
- **≥ 3 записей** → возвращает реальное стандартное отклонение

**Двухуровневое разделение (S51 D5):** аргумент `strategy_class` разграничивает два понятия:
- **sigma_SR** считается **внутри класса стратегий** (например, только «supertrend»). Это предотвращает «отравление»: если у стратегии ATR-breakout был катастрофический Шарп −89 в одном прогоне, это не должно влиять на оценку разброса для supertrend (src/analytics/cross_trial_log.py:205–210).
- **N_trials** (общее число попыток) остаётся **глобальным** — считаются все записи из всех стратегий и символов. Это методологически верно: мы действительно делали много попыток, и штраф за это справедлив.

## Формулы и расчёты

### Eq. 12: скорректированный эталонный Шарп (поправка на N попыток)

```
SR* = SR_benchmark + σ_SR × [(1 − γ) × Φ⁻¹(1 − 1/N) + γ × Φ⁻¹(1 − 1/(N × e))]
```

Где (src/analytics/dsr.py:158–161):
- `SR_benchmark` — минимальный Шарп, который мы хотим превзойти (по умолчанию 0)
- `σ_SR` — стандартное отклонение Шарпов по прошлым попыткам (берётся из `CrossTrialLog`)
- `γ = 0.5772156649` — **постоянная Эйлера-Маскерони**, математическая константа ≈ 0.577
- `N` — число протестированных стратегий
- `e` — основание натурального логарифма ≈ 2.718
- `Φ⁻¹` — обратная **функция нормального распределения** (quantile function)

**Простыми словами:** чем больше N (попыток), тем выше SR* — «планка», которую надо взять. Если N=1, SR* = SR_benchmark = 0 (никакой поправки). Если N=10, планка выше. Если N=100 — ещё выше. Это математически отражает идею «докажи, что ты лучше, чем случайный выбор из N».

### Eq. 13: итоговый DSR

```
DSR = Φ(z),   где  z = (SR − SR*) × √(n − 1) / √(1 − skew × SR + (kurtosis − 1)/4 × SR²)
```

Где (src/analytics/dsr.py:165–173):
- `SR` — «сырой» Шарп стратегии (per-trade, без годовой нормировки)
- `SR*` — скорректированный эталон из Eq. 12
- `n` — число сделок
- `skew` — **асимметрия** доходностей (skewness): насколько распределение «перекошено» в одну сторону
- `kurtosis` — **Пирсоновский эксцесс** (полный, не избыточный): насколько «тяжёлые» хвосты. Для нормального распределения = 3
- `Φ` — функция нормального распределения (CDF), переводит z в вероятность [0, 1]

**Простыми словами:** числитель `(SR − SR*)` — насколько наш Шарп лучше скорректированного минимума. Знаменатель — «поправочный коэффициент» за форму распределения. `√(n − 1)` — чем больше сделок, тем увереннее оценка. Весь дробный аргумент z затем переводится в вероятность через `Φ`.

### Поправка на единицы измерения (S55 QS-1)

Это тонкое место, которое вызвало реальный баг (HIGH QS-1, Sprint 55). В Eq. 12 все три величины — SR, SR* и σ_SR — должны быть **в одной единице измерения**:

- Внутренний Шарп (`mean / std` по сделкам) — **per-trade**, без нормировки
- σ_SR из `CrossTrialLog` — **аннуализированный** (умножен на `√(bars_per_year / mean_holding)` при записи)

Чтобы они совпали, `compute_dsr` получает параметр `annualization_factor` и **делит** σ_SR на него, возвращая к per-trade масштабу (src/analytics/dsr.py:156–157):

```python
if annualization_factor is not None and annualization_factor > 0:
    sigma_sr = sigma_sr / annualization_factor
```

Альтернатива — умножить SR вверх до годового масштаба — математически некорректна (Eq. 13 чувствительна к частоте), поэтому сделан обратный вариант.

## Примеры / сценарии

### Сценарий А: первый запуск, одна стратегия

Предположим: стратегия сделала 50 сделок, средняя log-доходность 0.002, стандартное отклонение 0.010. Это даёт per-trade Шарп ≈ 0.2. Доходности близки к нормальным (skew ≈ 0, kurtosis ≈ 3). Это первый прогон, `n_trials = 1`.

- Eq. 12 не применяется: `SR* = 0` (нет поправки)
- Знаменатель Eq. 13: `√(1 − 0 × 0.2 + (3 − 1)/4 × 0.2²) = √(1 + 0.5 × 0.04) = √1.02 ≈ 1.01`
- z = `(0.2 − 0) × √49 / 1.01 ≈ 0.2 × 7 / 1.01 ≈ 1.386`
- DSR = Φ(1.386) ≈ 0.917

Результат: DSR ≈ 0.917. Ниже порога 0.95 — стратегия не проходит. Вердикт: FAIL по критерию `dsr_threshold`.

### Сценарий Б: пятый запуск той же стратегии, N=5, σ_SR = 0.3

Теперь в журнале 5 записей, sigma_sr (within-class) = 0.3 (в годовом масштабе). Допустим, `annualization_factor = 9` (sqrt(8100) ≈ 90 — условно), тогда σ_SR de-annualized ≈ 0.3 / 9 = 0.033.

- Eq. 12: `SR* = 0 + 0.033 × [(1 − 0.577) × Φ⁻¹(1 − 1/5) + 0.577 × Φ⁻¹(1 − 1/(5 × e))]`
- `Φ⁻¹(0.8) ≈ 0.842`, `Φ⁻¹(1 − 1/13.6) ≈ Φ⁻¹(0.927) ≈ 1.45`
- `SR* ≈ 0.033 × (0.423 × 0.842 + 0.577 × 1.45) ≈ 0.033 × (0.356 + 0.837) ≈ 0.033 × 1.193 ≈ 0.039`

Скорректированная планка выросла с 0 до 0.039. Это небольшой штраф при 5 попытках — планка повышается умеренно.

### Сценарий В: слишком мало сделок

9 сделок → `compute_dsr_with_status` возвращает `{"dsr": NaN, "status": "INSUFFICIENT_TRADES", "n_trades": 9}` (src/analytics/dsr.py:200–201). DSR не считается. Вердикт: FAIL (NaN не проходит ни один числовой порог).

## Подводные камни / что важно понимать

**1. Два разных порога DSR в системе**

В `research_wfa.py` ([[research-kernel-execution-model|путь research-ядра]]) порог: `dsr_value >= 0.95` (src/backtest/research_wfa.py:37, 345). В `__main__.py` ([[wfa-validation-command|путь `_cmd_wfa`]]): `dsr_value > 0` (src/__main__.py:704). Это намеренная разница: `_cmd_wfa` — более ранняя проверка, research_wfa — строгий финальный фильтр. Не путайте их.

**2. Pearson vs excess kurtosis — исторический баг**

Использование `fisher=False` (Pearson kurtosis) — намеренное и критическое. Если бы код использовал `fisher=True` (excess, по умолчанию в scipy), для нормального распределения формула давала бы `(0 − 1)/4 = −0.25` вместо `(3 − 1)/4 = 0.5` — систематически заниженный знаменатель, завышенный DSR. Этот баг был обнаружен (S9 BLOCKER) и зафиксирован с явным комментарием (src/analytics/dsr.py:119–123).

**3. sigma_SR обязателен при n_trials > 1**

Если `n_trials > 1` и `sigma_sr` не передан — `compute_dsr` бросает `ValueError`. Если `sigma_sr=NaN` — тоже `ValueError` (src/analytics/dsr.py:131–144). Это защита от тихого «отравления»: NaN < 0 в Python возвращает False, что позволило бы NaN просочиться без ошибки.

**4. Новая стратегия временно избегает штрафа N_trials**

Если у класса стратегий в журнале меньше 3 записей, sigma_SR статистически недопустим (df < 2). В этом случае `effective_n_trials` принудительно ставится в 1 (src/backtest/research_wfa.py:307–308). Это единственный Bailey-корректный вариант: без sigma_SR применить множественный штраф математически невозможно. Но это не «бесплатный пропуск» — DSR является лишь одним из пяти ворот (L1 Sharpe, L2 [[monte-carlo-permutation|MC]], L3 n_eff, L4 T5-floor и сам DSR — src/backtest/research_wfa.py:331-348); стратегия без истории всё равно должна пройти все четыре предшествующих критерия.

**5. Идемпотентность — защита от дублей при перезапусках**

`append_trial` при дублировании по `(sprint, symbol)` обновляет запись, а не добавляет новую (src/analytics/cross_trial_log.py:179–189). Это важно: дашборд может перерисовываться много раз, и каждый раз потенциально вызывать append. Без этой защиты N_trials рос бы искусственно.

**6. Единицы измерения: annualization_factor**

Без `annualization_factor` sigma_SR и per-trade Шарп несопоставимы по масштабу — это даёт неверный SR* в Eq. 12. Фактор вычисляется как `sqrt(bars_per_year / _MEAN_HOLDING_BARS_PLACEHOLDER)` (src/backtest/research_wfa.py:321), где `_MEAN_HOLDING_BARS_PLACEHOLDER = 100.0` — это условная заглушка (реальное среднее время удержания позиции из бэктеста недоступно). Остаточная погрешность считается второстепенной по сравнению с самой поправкой (src/backtest/research_wfa.py:318–320).

**7. DSR в live-режиме — без cross-trial штрафа**

В `live_trade_reporter.py` DSR вычисляется с `n_trials=1` (src/analytics/live_trade_reporter.py:158). Это осознанное решение: live-мониторинг пересчитывает единственную гипотезу, а не перебирает новые варианты. Журнал `CrossTrialLog` для этого не используется.

**Близнец в другом разделе (та же тема, тех.глубина):**

**Предпосылки (что нужно понимать до DSR):**
- [[sharpe-sortino-metrics]] — базовый коэффициент Шарпа, который DSR и «сдувает»; DSR = Шарп с поправками на удачу, форму распределения и размер выборки
- [[cross-trial-log]] — журнал OOS-Шарпов всех прошлых прогонов; поставляет `sigma_SR` и `N_trials` — без него множественная поправка Eq. 12 невозможна
- [[trade-extractor-and-records]] — формирование `list[TradeRecord]`, который принимает `compute_dsr`; мост между прогоном и аналитикой

**Соседние ворота и WFA-конвейер:**
- [[acceptance-gates-t1-t6]] — шесть критериев T1-T6, с которыми DSR работает совместно; PASS = L1 AND L2 AND L3 AND L4 AND DSR — все пять блокирующих ворот одновременно (src/backtest/walk_forward.py:219-224, research_wfa.py:342-350)
- [[walk-forward-analysis]] — DSR применяется к агрегированным OOS сделкам всех фолдов WFA; понимание WFA необходимо для понимания «откуда берутся trades»
- [[monte-carlo-permutation]] — MC и DSR дополняют друг друга: MC проверяет «не случаен ли результат» через перестановки, DSR — через статистику множественного тестирования
- [[mc-permutation-test]] — та же тема MC в разделе «Индикаторы и расчёты» (ворота L2); эмпирический аналог статистической поправки DSR
- [[wfa-reporter-three-sharpe-series]] — три вида Шарпа в системе и как они соотносятся с per-trade Шарпом внутри DSR
- [[replay-engine-metrics]] — где считается исходный Шарп по сделкам до всякой DSR-поправки
