# Walk-forward анализ (WFA): честная проверка на невиданных данных

**TL;DR:** WFA — это способ проверить, работает ли стратегия по-настоящему, а не просто «подогнана» под прошлые данные. История делится на 5 скользящих блоков: учимся на первой части, проверяем на второй, сдвигаем окно вперёд — и так 5 раз. Только честные результаты «невиданного» теста идут в итоговую оценку.

## Простыми словами

Представьте, что вы хотите убедиться, что ваша торговая стратегия действительно работает, а не просто случайно угадала прошлые движения рынка. Обычный **[[what-is-backtest-overview|бэктест]]** (проверка «на истории») похож на то, как если бы студент зубрил ответы из решебника: на тех же задачах он сдаст экзамен на отлично, но на новых — провалится. Это называется **переобучение**, или **подгонка** (overfitting) — стратегия «запомнила» конкретную историю, а не нашла реальную закономерность.

Walk-forward анализ решает эту проблему по аналогии с честным экзаменом:

1. Берём длинную историю котировок — скажем, 4520 свечей.
2. Делим её на 5 последовательных блоков (**фолдов**). Каждый фолд состоит из двух частей:
   - **Обучающее окно (train / in-sample, IS)** — здесь стратегия «проходит тренировку»: подтверждаем, что параметры работали на этих данных.
   - **Тестовое окно (test / out-of-sample, OOS)** — это данные, которые стратегия никогда раньше «не видела». Именно здесь мы проверяем честность.
3. Между обучением и тестом — **карантин (embargo)**: 20 свечей, которые не входят ни в обучение, ни в тест. Это защита от скрытой «утечки» — индикаторы (например, скользящие средние) считаются по нескольким предыдущим барам и могут «заглянуть» в тест через самые последние обучающие бары. Карантин обрывает этот канал.
4. Проверяем результаты: если стратегия стабильно зарабатывает на невиданных данных во всех 5 фолдах — это хороший знак реальной работоспособности.

Ключевое слово: **только OOS-сделки** учитываются в итоговой оценке ([[deflated-sharpe-ratio|DSR]], [[monte-carlo-permutation|Monte-Carlo]], [[acceptance-gates-t1-t6|метрики T1–T6]]). IS-результат нужен только для сравнения: если стратегия зарабатывает на тренировке, но теряет на тесте — это красный флаг переобучения.

## Как это работает у нас

### Шаг 1. WindowSplitter — генератор окон

`WindowSplitter` — это «инструмент разметки», который говорит: «вот границы каждого из 5 фолдов». Он задаётся четырьмя параметрами-умолчаниями из ADR 0014 (src/backtest/walk_forward.py:21–27):

| Параметр | Значение (high-freq) | Что означает |
|---|---|---|
| `train_bars` | 2000 | размер обучающего окна в барах |
| `test_bars` | 500 | размер тестового окна в барах |
| `embargo_bars` | 20 | карантин между обучением и тестом |
| `k_folds` | 5 | количество фолдов (скользящих окон) |

**Минимально необходимый объём данных** считается по формуле:

```
min_required = train_bars + embargo_bars + k_folds × test_bars
```

Для high-freq (5м, 15м, 1ч): 2000 + 20 + 5 × 500 = **4520 баров**
Для low-freq (4ч, 1д): 1500 + 20 + 5 × 250 = **2770 баров**

Это вычисляется в `_min_required_bars()` (src/backtest/research_wfa.py:87–89) и в `WindowSplitter.split()` (src/backtest/walk_forward.py:48). Если данных меньше — бот возвращает `WFA_FAIL_DATA` и останавливается. Это **fail-closed** поведение: лучше честно сказать «нет данных», чем запустить неполный тест и получить мусорный результат.

### Шаг 2. Метод split() — расчёт границ фолдов

`WindowSplitter.split(total_bars=N)` (src/backtest/walk_forward.py:40–59) генерирует для каждого фолда `k` четыре индекса: `(train_start, train_end, test_start, test_end)`.

Принцип **скользящего сдвига (rolling advance)**: каждый следующий фолд сдвигается ровно на `test_bars` баров вперёд относительно предыдущего:

```
train_start = k × test_bars          (k = 0, 1, 2, 3, 4)
train_end   = train_start + train_bars
test_start  = train_end + embargo_bars
test_end    = test_start + test_bars
```

Для режима high-freq (train=2000, test=500, embargo=20, k=5) расположение фолдов выглядит так:

| Фолд | Обучение [от:до) | Карантин | Тест [от:до) |
|---|---|---|---|
| 0 | бары 0–1999 | 2000–2019 | 2020–2519 |
| 1 | бары 500–2499 | 2500–2519 | 2520–3019 |
| 2 | бары 1000–2999 | 3000–3019 | 3020–3519 |
| 3 | бары 1500–3499 | 3500–3519 | 3520–4019 |
| 4 | бары 2000–3999 | 4000–4019 | 4020–4519 |

Обратите внимание: обучающие окна **перекрываются** — фолд 0 и фолд 1 оба включают бары 500–1999. Это нормально: цель не обучение модели (параметры зафиксированы), а проверка стабильности стратегии в разные периоды. Тестовые окна при этом **не пересекаются** — каждый OOS-кусок уникален.

Границы — **полуоткрытые интервалы** `[start, end)`: бар с индексом `train_end` в обучение не входит, бар `test_end` в тест не входит (src/backtest/walk_forward.py:43–46).

### Шаг 3. Два пути исполнения WFA

В нашем проекте существует **два разных механизма** запуска WFA для разных типов стратегий:

#### Путь A — WalkForwardRunner (для стратегий с [[replay-engine-bar-by-bar|replay-движком]])

Используется для [[donchian-runner-and-reference-run|Donchian-стратегии]] и одного символа через [[single-symbol-wfa-and-data-loading|`data_loading`]]. `WalkForwardRunner.run()` (src/backtest/walk_forward.py:85–152):

1. Для каждого фолда нарезает DataFrame на `train_window` и `test_window`.
2. Вызывает `replay_fn(train_window, config)` → IS-результат.
3. Вызывает `replay_fn(test_window, config)` → OOS-результат.
4. Считает отношение OOS/IS Sharpe: `ratio = oos_sharpe / is_sharpe` (если IS-Sharpe = 0, ratio = 0).
5. Собирает все OOS-сделки из всех фолдов в единый пул для DSR и Monte-Carlo.

IS-результат нужен именно для вычисления отношения OOS/IS Sharpe — это вход в ворота L1 (см. ниже).

#### Путь B — run_research_wfa (для исследовательских стратегий с LOCKED-параметрами)

Используется для [[atr-breakout-strategy|ATR Breakout]], [[volume-breakout-strategy|Volume Breakout]], [[supertrend-strategy|Supertrend]]. Эти стратегии считают PnL через отдельную [[research-kernel-execution-model|research-модель исполнения]]. Функция `run_research_wfa()` (src/backtest/research_wfa.py:103–377):

**Ключевое отличие от пути A**: обучающий срез `(tr_start:tr_end)` намеренно **не передаётся** в `backtest_fn`. Почему? У этих стратегий параметры зафиксированы заранее (LOCKED), никакой подстройки по каждому фолду не происходит. Обучающее окно для них — только ориентир позиционирования тестового окна, не реальное IS-обучение (src/backtest/research_wfa.py:131–139, 196–197).

Это важно: `wfa_params["train_bars"]` в возвращаемом словаре отражает не «мы обучились на 2000 барах», а «тест-окна начинаются с такого-то смещения». Для будущих стратегий, которые будут подстраивать параметры per-фолд, потребуется иная обёртка.

В остальном путь B делает то же самое: нарезает тестовые слайсы, запускает `backtest_fn(test_slice, params, bars_per_year)` для каждого фолда, собирает OOS-сделки и Sharpe-коэффициенты.

### Шаг 4. Агрегация результатов

После 5 фолдов у нас есть:

- **Список Sharpe по фолдам** (`fold_sharpes`): один Sharpe на каждый фолд, вычисленный на OOS-периоде.
- **Пул всех OOS-сделок** (`all_oos_trades`): все сделки из всех тестовых окон в хронологическом порядке.

Из этого считаются **два разных агрегата Sharpe** (src/backtest/research_wfa.py:227–246):

| Метрика | Как считается | Зачем |
|---|---|---|
| `trial_mean_fold_oos_sharpe` | Среднее арифметическое Sharpe по 5 фолдам | Стабильность от фолда к фолду; идёт в [[cross-trial-log|cross-trial log]] для DSR |
| `trial_oos_sharpe` | Sharpe по всему пулу OOS-сделок как единому ряду | Суммарная доходность; информационная метрика |

Эти метрики **не взаимозаменяемы**: первая отвечает на вопрос «стабильно ли зарабатываем в каждом периоде?», вторая — «каков суммарный результат по всем периодам вместе?». Подробнее об этих числах — в [[wfa-reporter-three-sharpe-series]].

### Шаг 5. Уровни валидации (Acceptance Gate)

После WFA результаты проходят проверку в два этапа. Важно: **два пути WFA используют одни и те же уровни, но смысл порога L1 различается** — потому что Путь A вычисляет отношение OOS/IS Sharpe, а Путь B запускает только тестовые фолды и работает с сырым OOS Sharpe напрямую.

#### Ворота внутри evaluate_acceptance_gate() — L1–L4

Функция `evaluate_acceptance_gate()` содержит четыре уровня, объединённых по AND (src/backtest/walk_forward.py:155–242). Достаточно провалить один — стратегия получает `WFA_FAIL`.

| Уровень | Порог | Что проверяет |
|---|---|---|
| **L1** (ADR 0014) | значение ≥ 0.7 в **каждом** из 5 фолдов | Стабильность по фолдам (смысл — разный для путей A и B, см. ниже) |
| **L2** (ADR 0015) | MC p-value ≤ 0.05 | Прибыль не случайна ([[monte-carlo-permutation]]) |
| **L3** (ADR 0052) | n_eff ≥ 50 | Достаточно эффективных сделок |
| **L4** (ADR 0052) | n_raw ≥ 50 | Минимальное число сделок ([[acceptance-gates-t1-t6|T5-floor]]) |

**Что именно проверяет L1 в каждом пути:**

- **Путь A (WalkForwardRunner / Donchian)**: IS-прогон запускается, поэтому `fold_sharpes` содержат **отношения OOS/IS Sharpe** (вычислены в `walk_forward.py:130`: `ratio = oos_sharpe / is_sharpe`). Ворота L1 проверяют: «результат на невиданных данных не хуже 70% от результата на обучении».
- **Путь B (run_research_wfa / ATR Breakout, Volume Breakout, Supertrend)**: IS-прогон отсутствует, поэтому `fold_sharpes` содержат **сырые OOS Sharpe** каждого фолда. Они передаются в `evaluate_acceptance_gate` как `fold_oos_is_sharpe_ratios` (src/backtest/research_wfa.py:331–332). Ворота L1 проверяют: «OOS Sharpe в каждом фолде ≥ 0.7» — не отношение, а абсолютное значение. Смысл другой: «стратегия зарабатывает в каждом тестовом периоде, а не только суммарно».

#### Дополнительная проверка DSR — только Путь B

DSR **не является частью** `evaluate_acceptance_gate()` — это явно указано в комментарии кода: «DSR is computed and reported (informational) but NOT в gate decision» (src/backtest/walk_forward.py:170–171). В Пути B DSR добавляется в `failed_criteria` отдельно, уже после вызова функции ворот (src/backtest/research_wfa.py:341–348):

```python
failed_criteria: list[str] = list(gate["failed_criteria"])
dsr_pass = dsr_value >= DSR_THRESHOLD
if not dsr_pass:
    failed_criteria.append("dsr_threshold")
```

| Проверка | Порог | Где выполняется |
|---|---|---|
| **[[deflated-sharpe-ratio|DSR]]** (ADR 0056) | DSR ≥ 0.95 | Вручную после gate-функции, только в `run_research_wfa` |

Путь A (`WalkForwardRunner`) не выполняет DSR-проверку: агрегированные OOS-сделки передаются вызывающему коду для дальнейшей обработки.

Пороги зафиксированы как константы в коде (src/backtest/research_wfa.py:37–41):

```python
DSR_THRESHOLD = 0.95
SHARPE_THRESHOLD = 0.7
P_THRESHOLD = 0.05
N_EFF_THRESHOLD = 50
T5_FLOOR = 50
```

Итоговый вердикт:
- `WFA_PASS` — все уровни пройдены (L1–L4 + DSR в Пути B).
- `WFA_FAIL` — хотя бы один уровень провален. Возвращается список `failed_criteria` с именами проваленных критериев.
- `WFA_FAIL_DATA` — недостаточно данных ещё до запуска фолдов.

### Шаг 6. Тиры по частоте (get_wfa_tier_params)

Не все таймфреймы одинаковы: на 4-часовом графике в том же реальном периоде времени умещается в 4 раза меньше свечей, чем на часовом. Поэтому параметры WFA зависят от интервала (src/backtest/research_wfa.py:51–77):

| Тир | Интервалы | train_bars | test_bars | min_required |
|---|---|---|---|---|
| **High-freq** | 5м, 15м, 1ч (и все остальные) | 2000 | 500 | 4520 |
| **Low-freq** | 4ч (`240`), дневной (`D`) | 1500 | 250 | 2770 |

`k_folds=5` и `embargo_bars=20` одинаковы для обоих тиров.

Функция `get_wfa_tier_params(interval)` возвращает нужный набор параметров: если интервал в `frozenset({"240", "D"})` — low-freq, иначе — high-freq.

## Формулы и расчёты

### Минимально необходимый объём данных

```
min_required = train_bars + embargo_bars + k_folds × test_bars
```

Простыми словами: нужно вместить одно полное обучающее окно, плюс карантин, плюс K непересекающихся тестовых окон.

Для high-freq: 2000 + 20 + 5 × 500 = **4520 баров** (src/backtest/research_wfa.py:88–89)
Для low-freq: 1500 + 20 + 5 × 250 = **2770 баров**

### L1 gate — порог ≥ 0.7 (смысл разный для двух путей)

**Путь A (WalkForwardRunner):** IS-прогон запускается в каждом фолде, поэтому L1 проверяет отношение:

```
ratio = OOS_Sharpe / IS_Sharpe    (для каждого фолда отдельно)
```

Простыми словами: «во сколько раз результат на невиданных данных хуже или лучше, чем на обучении». Если OOS_Sharpe = 0.8 и IS_Sharpe = 1.0, то ratio = 0.8 — это ≥ 0.7, фолд проходит. Если IS_Sharpe = 0, ratio = 0 — фолд проваливается (src/backtest/walk_forward.py:130, 193–198).

**Путь B (run_research_wfa):** IS-прогон отсутствует — в каждом фолде запускается только тестовый срез. L1 проверяет сам OOS Sharpe:

```
fold_sharpe >= 0.7    (для каждого фолда отдельно)
```

Простыми словами: «стратегия должна зарабатывать в каждом тестовом периоде». Фолд с OOS Sharpe = 0.5 провалит L1, даже если средний по всем фолдам хороший. Порог 0.7 — тот же самый, но применяется к абсолютному значению Sharpe, а не к отношению (src/backtest/research_wfa.py:331–334).

### trial_mean_fold_oos_sharpe (среднее по фолдам)

```
trial_mean_fold_oos_sharpe = среднее(fold_sharpes)
```

Среднее арифметическое OOS-Sharpe по всем 5 фолдам. Эта метрика идёт в `CrossTrialLog` для расчёта DSR: она отражает «типичный» результат стратегии на одном периоде (src/backtest/research_wfa.py:227–229).

### trial_oos_sharpe (суммарный OOS Sharpe)

```
trial_oos_sharpe = mean(all_pnls) / std(all_pnls, ddof=1) × sqrt(bars_per_year / mean_holding)
```

Sharpe, вычисленный по всем OOS-сделкам из всех фолдов как единому ряду. Аннуализация использует номинальный плейсхолдер `mean_holding=100 баров` — реальное время удержания позиций в исследовательских ранерах не вычисляется (src/backtest/research_wfa.py:43–48, 240–244). Это **информационная** метрика, не участвующая в gates.

## Примеры / сценарии

### Сценарий А: стратегия проходит WFA (Путь B — ATR Breakout)

Допустим, ATR Breakout тестируется на BTCUSDT с 5000 баров по 1-часовому графику (high-freq tier). Это Путь B: IS-прогон не запускается, L1 проверяет сырой OOS Sharpe каждого фолда.

**Данных достаточно**: 5000 ≥ 4520 — проходим дальше.

Запускаем 5 фолдов. Каждый фолд возвращает OOS Sharpe:

| Фолд | OOS Sharpe | L1 (≥ 0.7)? |
|---|---|---|
| 0 | 1.8 | да |
| 1 | 1.5 | да |
| 2 | 1.2 | да |
| 3 | 1.4 | да |
| 4 | 1.6 | да |

**L1**: все OOS Sharpe ≥ 0.7 → пройдено.

Из 5 тестовых периодов собираем все сделки — допустим, 120 штук. Monte-Carlo говорит p=0.01 ≤ 0.05 → **L2 пройдено**. Сделок 120 ≥ 50 → **L3 и L4 пройдены**. DSR=0.97 ≥ 0.95 → **DSR пройдено** (добавляется вне evaluate_acceptance_gate — в run_research_wfa:342–348).

Итог: `WFA_PASS`.

### Сценарий Б: стратегия проваливает L1 (Путь B)

Та же ATR Breakout стратегия на другом символе. Фолд 2 дал OOS Sharpe = 0.5 < 0.7.

`failed_criteria = ["sharpe_gate"]`, вердикт `WFA_FAIL`.

Что это значит содержательно: в третьем тестовом периоде стратегия зарабатывала ниже минимально приемлемого уровня (Sharpe ниже 0.7). Один плохой период — и стратегия в целом не проходит, независимо от результатов остальных четырёх фолдов.

*Для Пути A (Donchian / WalkForwardRunner) картина другая: провальным считался бы фолд, в котором отношение OOS/IS Sharpe < 0.7 — то есть на тестовых данных стратегия показала меньше 70% от своего «учебного» результата.*

### Сценарий В: недостаточно данных

Пытаемся запустить WFA для нового токена, котируемого всего 3000 баров (1ч). Порог 4520 > 3000.

Вместо запуска WFA сразу возвращается:

```python
{"verdict": "WFA_FAIL_DATA", "failed_criteria": ["data_volume"], ...}
```

Бот не молчит и не запускает неполный тест — он явно сообщает, что данных не хватает.

## Подводные камни / что важно понимать

### 1. Перекрытие обучающих окон — это нормально

Обучающие окна в соседних фолдах частично пересекаются (фолд 0 учится на барах 0–1999, фолд 1 — на 500–2499). Это не ошибка: так устроен rolling-WFA. Перекрытие в IS-окнах не подрывает честность проверки, потому что **тестовые окна не пересекаются**.

### 2. Карантин защищает от тонкой утечки

Индикаторы вроде скользящей средней или RSI смотрят назад на N предыдущих баров. Без карантина последние бары обучения «заглядывают» в тест через вычисленные значения индикаторов. 20 баров карантина обрывают этот канал.

### 3. LOCKED-параметры: train-срез — позиционер, не учитель

Для стратегий ATR Breakout, Volume Breakout, Supertrend параметры зафиксированы до запуска WFA и не меняются от фолда к фолду. В `run_research_wfa` обучающий срез намеренно не передаётся в `backtest_fn` — реальной подстройки нет (src/backtest/research_wfa.py:131–139). Это радикально отличается от классического WFA, где IS-данные используются для подбора параметров: здесь IS-окно служит только ориентиром для смещения тестовых окон.

### 4. Два Sharpe — не взаимозаменяемы

`trial_mean_fold_oos_sharpe` — среднее по фолдам — отражает **стабильность** стратегии. `trial_oos_sharpe` — суммарный по сделкам — отражает общий уровень результата. Первый идёт в CrossTrialLog и DSR. Смешивать их нельзя.

### 5. trial_oos_sharpe — информационная, не gate-метрика

Sharpe по пулу всех OOS-сделок аннуализируется с номинальным плейсхолдером `mean_holding=100` (src/backtest/research_wfa.py:43–48). Реальное среднее время удержания позиции в исследовательских ранерах не хранится в `_TradeRecord`. Это число показывает порядок, но не участвует ни в одном из gate-критериев.

### 6. Антиснупинг: параметры WFA фиксируются ДО прогона

Параметры WindowSplitter (`train_bars`, `test_bars`, `embargo_bars`, `k_folds`) зафиксированы в коде заранее (ADR 0014 + S45 amendment) — их нельзя выбирать постфактум, глядя на результаты. Если бы мы подбирали параметры разбиения под лучший результат, это было бы скрытой формой переобучения: мы бы не нашли хорошую стратегию, а нашли хорошее разбиение под конкретную историю.

### 7. Fail-closed при нехватке данных

Если данных меньше `min_required`, бот возвращает `WFA_FAIL_DATA` и не запускает неполный WFA. Это принципиально важно: молчаливый запуск с меньшим числом фолдов или с уменьшенными окнами дал бы результат, несопоставимый с эталонными порогами, откалиброванными под полный 5-фолдовый WFA.
