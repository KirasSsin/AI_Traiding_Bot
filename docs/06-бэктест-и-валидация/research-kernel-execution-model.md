# Research-ядро исполнения (_backtest_single): отдельная модель для стратегий-пробоев

**TL;DR:** Для стратегий-пробоев ([[06-бэктест-и-валидация/atr-breakout-strategy|ATR Breakout]], [[06-бэктест-и-валидация/volume-breakout-strategy|Volume Breakout]], [[06-бэктест-и-валидация/supertrend-strategy|Supertrend]], [[kronos-exploratory-runner|Kronos]]) в боте существует отдельная машина бэктеста — «research-ядро». Она считает прибыль по-другому, чем основная система, потому что основная система технически не в состоянии точно воспроизвести оригинальный исследовательский расчёт этих стратегий.

## Простыми словами

Представьте, что в игре в шахматы у вас есть два способа сохранить партию: официальная запись партии (основная система) и ваш личный блокнот. Обе фиксируют одни и те же ходы, но по-разному.

В нашем боте тоже две системы бэктеста:

1. **Основная система** ([[06-бэктест-и-валидация/replay-engine-bar-by-bar|`replay_engine`]]) — универсальная, как официальная партийная запись. Используется для большинства стратегий (EMA-кроссовер, [[donchian-runner-and-reference-run|Donchian]]). Она работает с реальными размерами позиций, системой [[position-sizing-kelly|Kelly]] (специальная формула расчёта размера сделки) и другими правилами.

2. **Research-ядро** (`_backtest_single`) — специализированная, как личный блокнот. Используется только для стратегий-пробоев. Она считает прибыль принципиально иначе: **суммирует результаты сделок как простые доли**, без учёта реального капитала и без компаундинга.

**Почему нельзя просто использовать основную систему?** Потому что у неё три структурных несовместимости с этими стратегиями (подробнее — в следующем разделе). Если бы мы всё же прогнали эти стратегии через основную систему, цифры были бы другими, и сравнение с исследовательскими результатами стало бы некорректным. ADR 0064 закрепил решение: для стратегий-пробоев — дословный перенос исследовательской модели.

**Аналогия:** вы тестировали рецепт торта на кухонных весах (research), а потом хотите воспроизвести его промышленными весами (основная система). Но весы откалиброваны по-разному. Честнее оставить оба набора результатов, чем «пересчитывать» и получать нечто третье.

## Как это работает у нас

### Почему отдельная система — три несовместимости

Обе стратегии (ATR Breakout и Volume Breakout) намеренно обходят основной `replay_engine`. Причины прописаны прямо в docstring каждого раннера:

**Несовместимость 1: параметр стоп-лосса.**
В `replay_engine` множитель ATR-стопа (`sl_atr_mult`) берётся из глобального конфига (значение по умолчанию 1.5×). Но у каждой стратегии-пробоя свой оптимальный множитель, найденный в ходе исследования — например, у BTCUSDT 4H ATR Breakout это `atr_stop_mult = 1.5`, а у BTCUSDT 15M — `3.0`. Передать нужный параметр через sweep-параметр в основной системе нельзя.
(src/backtest/atr_breakout_runner.py:5–12)

**Несовместимость 2: режим long_only.**
`replay_engine` работает в режиме `long_only=True`, что подавляет сигналы `-1` (обратный выход из позиции). Стратегии-пробои используют именно обратный сигнал как один из двух способов выхода. Без него система не воспроизводит исследовательское поведение.
(src/backtest/volume_breakout_runner.py:8–10)

**Несовместимость 3: способ расчёта прибыли.**
`replay_engine` использует [[walk-forward-analysis|WFA]] (Walk-Forward Analysis) с сайзингом 10% капитала — то есть в каждой сделке ставится 10% от текущего депозита. В исследовании же применяется **последовательно-аддитивный PnL** (подробнее — в следующем подразделе). Это принципиально разные модели; нельзя сравнивать их результаты напрямую.
(src/backtest/atr_breakout_runner.py:9–12, src/backtest/volume_breakout_runner.py:11–13)

---

### Последовательно-аддитивный PnL: в чём разница

**Компаундинг** (метод основной системы) — каждая сделка ставит долю от текущего, уже выросшего или упавшего капитала. Если депозит вырос с 1000$ до 1200$, следующая сделка на 10% = 120$.

**Последовательно-аддитивный PnL** (метод research-ядра) — каждая сделка считается как будто вы ставите одну и ту же «единицу». Прибыль сделки — это просто процент от цены входа. Результат всего теста — **сумма процентов всех сделок**. Размер капитала не меняет ничего.

Формально: каждая сделка даёт `pnl_pct = (цена_выхода − цена_входа) / цена_входа − 2 × комиссия`. Итог всего теста = `СУММА pnl_pct × 100%`. Нет умножения на размер позиции, нет Kelly, нет компаундинга. **Нотионал (номинал позиции — подразумеваемая «единичная ставка») равен 1.**
(src/backtest/atr_breakout_runner.py:240–254, src/backtest/volume_breakout_runner.py:166–181)

### Структура _TradeRecord

Запись о каждой сделке хранит минимум:

```python
@dataclass
class _TradeRecord:
    entry_idx: int      # индекс бара входа
    exit_idx: int       # индекс бара выхода
    entry_price: float  # цена входа (с проскальзыванием)
    exit_price: float   # цена выхода (с проскальзыванием)
    pnl_pct: float      # чистый PnL = (exit-entry)/entry − 2×комиссия (дробь, не ×100)
```

Заметьте: нет суммы в долларах, нет размера позиции — только процентная доля. Все расчёты метрик строятся на массиве `pnl_pct`.
(src/backtest/atr_breakout_runner.py:135–141, src/backtest/volume_breakout_runner.py:46–52)

### _backtest_single (ATR Breakout): шаг за шагом

Функция `_backtest_single` в `atr_breakout_runner.py` — это дословный перенос алгоритма из исследовательского скрипта.

**Шаг 1. Загрузка данных и вычисление ATR.**
Из датафрейма берутся массивы `close`, `open_`, `low`. Вычисляются два ATR-массива через функцию [[wilder-atr-and-stops|`_wilder_atr`]]: один для сигнала пробоя (`atr_arr` с периодом `atr_period`), другой для стопа (`atr_stop` с периодом `atr_stop_period`). Если оба периода совпадают — один массив используется для обоих.
(src/backtest/atr_breakout_runner.py:177–178)

**Шаг 2. Прогрев (warmup).**
Первые `max(atr_period, atr_stop_period) + 3` баров пропускаются — ATR ещё не стабилен.
(src/backtest/atr_breakout_runner.py:183)

**Шаг 3. Сигнал входа (проверяется на баре i, использует данные i−1 и i−2).**
```
close[i-1] > close[i-2] + atr_breakout_mult × atr[i-2]
```
Цена закрытия вчера должна превысить позавчерашнюю цену плюс запас в несколько ATR. Индекс `i−2` — намеренно: берётся окно, которое **не включает текущий бар** и даже не включает предыдущий бар закрытия (anti-look-ahead). Исполнение сделки — по цене открытия текущего бара `open[i]` с проскальзыванием `+0.05%`.
(src/backtest/atr_breakout_runner.py:186–191, 204)

**Шаг 4. Проверка ATR стопа перед входом.**
При входе берётся `atr_stop[i-1]`. Если это значение NaN (ATR ещё не посчитан) — сделка **пропускается**, позиция не открывается. Нет валидного стопа — нет сделки.
(src/backtest/atr_breakout_runner.py:201–207)

**Шаг 5. Стоп-лосс — ПЕРВЫЙ приоритет.**
На каждом баре i, пока открыта позиция, сначала проверяется: `low[i] <= stop_price`.
`stop_price = entry_price − entry_atr × atr_stop_mult`.
Если минимум бара достиг стопа — выход по цене стопа с проскальзыванием `−0.05%`. Сделка записывается.
(src/backtest/atr_breakout_runner.py:209–215)

**Шаг 6. Обратный сигнал — ВТОРОЙ приоритет.**
Только если стоп не сработал, проверяется:
```
close[i-1] < close[i-2] − atr_breakout_mult × atr[i-2]
```
Цена вчера упала ниже позавчерашней минус ATR-запас — значит, пробой вниз. Выход по `open[i]` с проскальзыванием `−0.05%`.
(src/backtest/atr_breakout_runner.py:216–221)

**Шаг 7. Mark-to-market на последнем баре.**
Если в конце данных позиция ещё открыта — она принудительно закрывается по последней цене закрытия `close[-1]` с проскальзыванием.
(src/backtest/atr_breakout_runner.py:224–228)

### _backtest_single (Volume Breakout): отличия от ATR Breakout

Логика та же, но условие входа другое — здесь два условия должны выполняться **одновременно**:

1. **Пробой канала:** `close[i-1] > roll_high[i-2]` — закрытие вчера выше максимума [[donchian-channel-indicator|канала Донкиана]] за последние `lookback_n` баров (окно заканчивается на `i−2`).
2. **Объёмное подтверждение:** `volume[i-1] > vol_mean[i-1] × vol_mult` — объём вчера превысил скользящее среднее объёма в `vol_mult` раз. Объём берётся на `i−1` (включает вчерашний бар).

Условие выхода:
1. **ATR-стоп — ПЕРВЫЙ приоритет:** `low[i] <= stop_price` (аналогично ATR Breakout).
2. **Выход из канала — ВТОРОЙ приоритет:** `close[i-1] < roll_low[i-2]` — закрытие ниже нижней границы канала.

Комиссия и проскальзывание — идентичны ATR Breakout: 0.1% тейкер за сторону, 0.05% проскальзывание.
(src/backtest/volume_breakout_runner.py:106–146)

### Загрузка данных: _load_parquet_df

ATR Breakout хранит прямой словарь `PARQUET_BY_COMBO`: `(symbol, interval) → путь к parquet-файлу`. [[parquet-storage|Parquet]] — это формат хранения данных, компактный и быстрый для числовых таблиц (аналог Excel-таблицы, но для машин).

При загрузке файл нормализуется: колонка со временем может называться `'ts'` (формат Binance) или `'time'` (формат Bybit). Функция обнаруживает нужный вариант и унифицирует в колонку `'_ts'`. После нормализации данные фильтруются по диапазону дат.
(src/backtest/atr_breakout_runner.py:259–296)

Volume Breakout использует общую функцию `load_ohlcv` из модуля [[single-symbol-wfa-and-data-loading|`data_loading`]].

### build_research_runner_envelope: обёртка для дашборда

После того как `_backtest_single` вернул результат, функция `build_research_runner_envelope` (из `research_runner_envelope.py`) «упаковывает» его в формат, понятный дашборду.

[[dashboard-overview|Дашборд]] ожидает определённые ключи — те же, что отдаёт основная система (`replay_engine`). Но у research-ядра нет WFA, нет [[deflated-sharpe-ratio|DSR]] (Deflated Sharpe Ratio — статистически скорректированный Sharpe), нет [[monte-carlo-permutation|Monte Carlo]]. Поэтому пустые поля заполняются сигнальными `null`-значениями, а вердикт ставится `"RAW"`.

**Предупреждение `raw_full_period`:** при каждом запуске без WFA в результат вставляется предупреждение высокого уровня:
```
"Acceptance gate skipped — WFA retrofit pending S43.
 Displayed PnL is full-period training number, NOT OOS-validated."
```
Это не ошибка — это честность интерфейса. Цифры на экране — это результат на **всём** периоде данных, включая тот, на котором параметры подбирались. Это НЕ независимая проверка «на будущем».
(src/backtest/research_runner_envelope.py:75–87)

**После WFA:** если `wfa_result` передан в конверт, предупреждение `raw_full_period` автоматически убирается, а `verdict`, `dsr`, `mc_p_value` заполняются реальными значениями.
(src/backtest/research_runner_envelope.py:109–111, 129–143)

### Sub-period robustness: устойчивость по под-периодам

Дополнительная честность: кривая капитала делится на **5 равных кусков** по времени, и для каждого куска вычисляется PnL (разница капитала в конце и начале куска). Затем считается, сколько кусков из 5 были прибыльными (`N/5`).

| N прибыльных из 5 | Уровень чипа | Смысл |
|-------------------|-------------|-------|
| 5/5 | info (синий) | Стратегия стабильна во всех периодах |
| 3–4/5 (≥ 60%) | warn (жёлтый) | Большинство периодов прибыльны, есть просадки |
| < 3/5 (< 60%) | high (красный) | Прибыль сосредоточена в отдельных промежутках |

(src/backtest/research_runner_envelope.py:23–104)

## Формулы и расчёты

### PnL одной сделки

```
pnl_pct = (exit_price − entry_price) / entry_price − 2 × COMMISSION_TAKER
```

Простыми словами: **доходность** (насколько изменилась цена в процентах) минус **двойная комиссия** (0.1% за вход плюс 0.1% за выход). Проскальзывание (0.05%) уже встроено в `entry_price` и `exit_price` — они корректируются при записи.

Числа из кода:
- `_COMMISSION_TAKER = 0.001` (0.1%) — тейкер-комиссия Bybit
- `_SLIPPAGE = 0.0005` (0.05%) — проскальзывание в сторону потерь

Итого транзакционные издержки round-trip: 0.2% комиссии + 0.10% проскальзывание = **0.30% на каждую сделку**.

(src/backtest/atr_breakout_runner.py:38–39, 212–214)

### Итоговый PnL теста

```
total_pnl_pct = СУММА(pnl_pct) × 100
```

Просто сложение всех дробных результатов, переведённых в проценты. НЕ умножение, НЕ компаундинг.

### Коэффициент Шарпа research-ядра

```
Sharpe = (среднее(pnl_pct) / std(pnl_pct)) × sqrt(bars_per_year / mean_holding)
```

Расшифровка:
- `среднее(pnl_pct) / std(pnl_pct)` — «средний результат делённый на нестабильность». Это базовая форма Sharpe per-trade.
- `sqrt(bars_per_year / mean_holding)` — нормировка на «сколько раз в год мы торгуем». `mean_holding` — среднее количество баров, которое открыта позиция.

Это **не** стандартный per-bar [[replay-engine-metrics|Sharpe]] из `replay_engine`. Здесь нормировка через **среднее время удержания позиции** (mean holding), а не через количество всех баров. Поэтому числа могут быть значительно выше.

Пример расчёта: если mean_holding = 15 баров на 4H-данных, то `bars_per_year / mean_holding = 2191 / 15 ≈ 146` сделок в год. `sqrt(146) ≈ 12` — это множитель аннуализации.

(src/backtest/atr_breakout_runner.py:241–248)

Если `pnl_std == 0` (все сделки одинаковы) → Sharpe = NaN. Если `mean_holding == 0` → Sharpe = 0.

### Виль­дер ATR (Wilder ATR)

ATR (Average True Range — «средний истинный диапазон») — мера волатильности цены. Wilder-вариант (по имени его создателя) использует специальное сглаживание: первое значение — простое среднее за `period` баров, затем — рекурсия:

```
ATR[t] = (ATR[t-1] × (period−1) + TR[t]) / period
```

где `TR[t]` — истинный диапазон бара (максимум из: high−low, |high−prev_close|, |low−prev_close|).

Первые `period−1` баров — NaN (расчёт ещё не готов).

(src/backtest/indicators.py:17–51)

**Важно:** в проекте существует несколько реализаций ATR. Research-ядро использует общую функцию `_wilder_atr` из `src/backtest/indicators.py`, которая была извлечена в S55 для устранения дублирования кода (DRY — «Don't Repeat Yourself»).

## Примеры / сценарии

### Сценарий 1: Успешная сделка ATR Breakout (4H BTCUSDT)

Допустим, мы на баре `i = 100`. Параметры: `atr_breakout_mult = 2.5`, `atr_stop_mult = 1.5`, `atr_period = 9`, `atr_stop_period = 21`.

**Условия:**
- `close[99] = 68 500$`, `close[98] = 67 000$`
- `atr[98] = 400$` → порог = 67 000 + 2.5 × 400 = **68 000$**
- Условие входа: `68 500 > 68 000` — **выполнено**
- `atr_stop[99] = 350$` (21-периодный ATR) — не NaN → можно открывать
- Цена входа: `open[100] × 1.0005 = 69 000 × 1.0005 ≈ 69 035$`
- Стоп: `69 035 − 350 × 1.5 = 69 035 − 525 = 68 510$`

**Выход через 8 баров (bar 108):**
- `low[108] = 68 490$` — достигает стопа `68 510$`? Нет, 68 490 < 68 510 → **стоп срабатывает**
- Цена выхода: `68 510 × 0.9995 = 68 476$`
- `pnl_gross = (68 476 − 69 035) / 69 035 = −0.0081` (−0.81%)
- `pnl_net = −0.0081 − 0.002 = −0.0101` (−1.01%)
- `mean_holding` пополняется значением 8 баров

### Сценарий 2: Защитная проверка NaN ATR (страховочная ветка)

В коде перед каждым входом в позицию стоит проверка:

```python
a = atr_stop[i - 1]
if isnan(a):
    continue   # нет валидного стопа — пропускаем вход
```

(src/backtest/atr_breakout_runner.py:201–203)

**Что это за ветка.** Если значение ATR-стопа оказалось бы NaN — позиция просто не открывается. Нет валидного стопа — нет сделки. Открывать позицию без заранее рассчитанной точки выхода по стопу опасно: риск становится неограниченным.

**Почему она не срабатывает в нормальной работе.** Warmup-гейт (строка 183) пропускает первые `max(atr_period, atr_stop_period) + 3` баров. Wilder ATR выдаёт первое ненулевое значение на индексе `atr_stop_period − 1` (src/backtest/indicators.py:48). Для любого реального набора параметров warmup уже гарантирует, что к моменту первой проверки `atr_stop[i−1]` является валидным числом — математически невозможно попасть в NaN при нормальном входе в цикл.

Пример: `atr_stop_period = 21` → seed-бар на индексе 20 → warmup = max(ap, 21) + 3 ≥ 24 → первое `i` в цикле ≥ 24, проверяется `atr_stop[23]` — это на 3 бара позже seed, значение уже посчитано.

**Зачем тогда она существует.** Это защитный контракт: если в будущем warmup-логика изменится или датафрейм придёт с пропусками в данных, ветка `isnan` не позволит войти в позицию с неопределённым стопом. Это намеренная страховка, а не рабочий путь выполнения.

Запускаем ATR Breakout на BTCUSDT 4H за период 2023–2026. WFA не запускался.

### Сценарий 4: Volume Breakout — вход требует двух условий

На баре `i = 50`:
- `close[49] = 67 200$`, `roll_high[48] = 66 800$` → пробой канала: **выполнен**
- `volume[49] = 1 500 BTC`, `vol_mean[49] = 900 BTC`, `vol_mult = 1.4563` → порог = 900 × 1.4563 = 1 311 BTC
- Объём 1 500 > 1 311 → подтверждение объёмом: **выполнено**
- Оба условия выполнены → вход открывается

На баре `i = 60`:
- Стоп не сработал
- `close[59] = 65 100$`, `roll_low[58] = 65 400$` → close < roll_low → **выход по каналу**

## Подводные камни / что важно понимать

**1. RAW-цифры — НЕ прогноз будущего.**
Когда дашборд показывает «Total PnL +122.66%» для Volume Breakout, это результат за весь период **с теми же параметрами, на которых эти параметры и были подобраны**. Это верхняя граница, не ожидаемый результат. Только после WFA-прогона и получения [[verdict-and-warnings|вердикта PASS (а не RAW)]] цифры приобретают смысл независимой проверки.

**2. Приоритет стопа — строгий.**
В обеих стратегиях ATR-стоп проверяется **до** обратного сигнала. Если в один и тот же бар и стоп «сработал бы», и обратный сигнал появился — выход происходит только по стопу. Это точная копия исследовательской логики, изменять порядок нельзя.
(src/backtest/atr_breakout_runner.py:209–221)

**3. Индексы [i-1] и [i-2] — это намеренная защита от смотрения в будущее.**
В financial backtesting «look-ahead bias» (утечка данных из будущего в прошлое) — главная ловушка. Если сигнал вычисляется на баре i, а условие использует данные бара i, это и есть утечка. Research-ядро использует `i−2` для ценовых окон и `i−1` для цены закрытия сигнала. Заполнение сделки происходит только по `open[i]`. Страница [[06-бэктест-и-валидация/what-is-backtest-overview]] объясняет этот принцип подробнее.

**4. Sharpe здесь может быть значительно выше «нормального».**
Потому что нормировка идёт по среднему времени удержания, а не по всем барам. Это корректно для per-trade сравнения, но нельзя напрямую сравнивать с Sharpe из отчётов других систем, где нормировка другая.

**5. Нет квотной прибыли (в долларах).**
В `_TradeRecord` нет суммы прибыли в USD. Поля `total_pnl_quote`, `avg_win_quote` и прочие в дашборде отображаются как «—». Это не ошибка — research-ядро работает без реального капитала.
(src/backtest/research_runner_envelope.py:179–183)

**6. NaN-стоп = нет сделки (страховочный принцип).**
Это не ошибка обработки, а осознанное решение безопасности: открывать позицию без заранее определённой точки выхода по стопу — значит рисковать без меры. Ветка `isnan → continue` (src/backtest/atr_breakout_runner.py:202–203) в нормальной работе не достигается — warmup-гейт уже гарантирует, что ATR посчитан к моменту первого входа. Ветка существует как явный контракт: даже если данные придут с пропусками или warmup-параметры изменятся, бот не войдёт в позицию без валидного стопа.

**7. Mark-to-market — это не реальный выход.**
Последняя сделка в тесте (принудительное закрытие по `close[-1]`) может создавать искусственно прибыльную или убыточную запись, которой в живой торговле не было бы. Она включается для того, чтобы кривая капитала не «обрывалась» на незакрытой позиции.
