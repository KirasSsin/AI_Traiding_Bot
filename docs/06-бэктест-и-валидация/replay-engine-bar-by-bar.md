# Движок проигрывания истории (replay_engine): как сделки исполняются бар за баром

**TL;DR:** `run_replay` — это «машина времени» бэктеста: она проходит по историческим барам один за другим, открывает и закрывает сделки строго по правилам, считает деньги и формирует итоговую кривую капитала. Ключевое свойство — честность: бот никогда не «видит» цену следующего бара до его появления.

## Простыми словами

Представьте, что вы хотите проверить торговую идею на прошлых данных: «А что если бы я покупал каждый раз, когда стратегия говорит "сигнал", и продавал по стоп-лоссу или тейк-профиту?». Именно это и делает `replay_engine`.

Он берёт таблицу исторических свечей (баров — каждая свеча = один промежуток времени: час, четыре часа и т.д.) и «прокручивает» их слева направо. На каждой свече движок задаёт себе два вопроса:

1. **Есть ли открытая позиция?** Если да — проверяем, не пора ли её закрыть (сработал стоп-лосс, достигнут тейк-профит или другая причина).
2. **Есть ли сигнал на вход?** Если да — планируем покупку на следующей свече.

После прохода по всей истории движок возвращает:
- список всех совершённых сделок с деталями,
- кривую капитала (как рос или падал счёт во времени),
- итоговые метрики качества торговли.

**Аналогия:** это как сыграть в монополию «назад» — вы листаете старый дневник игры и точно воспроизводите каждый ход, соблюдая правила. Результат показывает, насколько хорошей была стратегия — при условии, что вы не «подглядывали» вперёд.

## Как это работает у нас

### Шаг 0: Загрузка настроек (строки 127–141)

Перед стартом цикла `run_replay` читает конфигурацию и устанавливает параметры симуляции:

| Параметр | По умолчанию | Что означает |
|---|---|---|
| `initial_balance` | 10 000 USDT | Стартовый капитал симуляции |
| `commission_taker` | 0.1% (0.001) | Комиссия биржи за каждую сделку |
| `slippage` | 0.05% (0.0005) | Проскальзывание — цена исполнения хуже желаемой |
| `position_size_pct` | 10% | Доля капитала на одну сделку |
| `max_drawdown_pct` | 20% | Порог аварийного стопа (kill-switch) |
| `sl_atr_mult` | 1.5 | Множитель ATR для стоп-лосса |
| `tp_atr_mult` | 3.0 | Множитель ATR для тейк-профита |
| `long_only` | False | Если True — только покупки, короткие сигналы игнорируются |

`(src/backtest/replay_engine.py:131–139)`

После чтения настроек вызывается `calculate_indicators(df, config)` — функция добавляет к таблице баров рассчитанные индикаторы ([[ema-rsi-indicators|EMA, RSI]], [[atr-indicator|ATR]]) и колонку `signal` с торговым сигналом (`+1` = вход в покупку, `−1` = вход в продажу, `0` = нет сигнала). Как именно из индикаторов получается сигнал — см. [[indicators-and-signals]]. `(src/backtest/replay_engine.py:141)`

### Шаг 1: Основной цикл бар за баром (строка 150)

```python
for i in range(len(data)):
    row = data.iloc[i]
    ...
```

Цикл идёт от бара `0` (самый ранний) до бара `N-1` (самый поздний). На каждой итерации доступны значения текущей свечи: `close` (цена закрытия), `low` (минимум), `high` (максимум), `signal` (торговый сигнал). `(src/backtest/replay_engine.py:150–156)`

### Шаг 2: Активация отложенного входа (pending_entry)

Это самый важный механизм — защита от look-ahead (подглядывания в будущее).

**Проблема:** Стратегия формирует сигнал на основе цены закрытия бара `i`. Но в момент закрытия этого бара цена открытия следующего бара `i+1` ещё неизвестна — она появится только когда начнётся следующий бар.

**Решение (pending_entry):** Вход не исполняется мгновенно. Движок создаёт «заявку на вход» (`pending_entry`) с меткой времени следующего бара. Когда следующий бар наступает и его `timestamp` совпадает с меткой заявки — заявка активируется и становится реальной позицией.

```python
if position is None and pending_entry is not None and pending_entry["timestamp_open"] == ts:
    position = pending_entry
    pending_entry = None
```
`(src/backtest/replay_engine.py:158–160)`

Таким образом вход всегда происходит по цене `open[i+1]` — первой цене следующей свечи. Это самая ранняя честная цена: она стала известна только после окончания бара `i`, где был получен сигнал.

### Шаг 3: Проверка условий выхода из позиции

Если позиция открыта, движок проверяет четыре причины выхода в строгом порядке приоритета. `(src/backtest/replay_engine.py:162–190)`

**Порядок приоритета для BUY-позиции (покупки):**

1. **SL (стоп-лосс):** `low_price <= position["sl"]` → выход по цене стоп-лосса. Стоп-лосс — это как страховка: заранее решаем, при какой цене выходим, чтобы не потерять больше задуманного.
2. **TP (тейк-профит):** `high_price >= position["tp"]` → выход по цене тейк-профита. Тейк-профит — это «карман для фиксации прибыли»: выходим, когда цена достигла нашей цели.
3. **SIGNAL_FLIP (разворот сигнала):** если сигнал стал `−1` и режим не `long_only` → выход по цене закрытия бара. Стратегия говорит «теперь продавай» — это сигнал, что тренд развернулся.
4. **EOD (конец данных):** если это последний бар в истории и выхода ещё не было → принудительное закрытие по `close`. Нельзя держать позицию «в воздухе» после последней известной свечи.

Для SELL-позиции (продажи) логика зеркальная: SL срабатывает когда цена пошла вверх (`high >= sl`), TP — когда цена упала до цели (`low <= tp`).

### Шаг 4: Расчёт прибыли/убытка сделки

Когда выход найден:

```
slippage_factor = (1 − slippage) для продажи (BUY-exit)
exit_price = raw_exit_price × slippage_factor
gross_pnl = (exit_price − entry_price) × qty    # для BUY
net_pnl = gross_pnl − entry_fee − exit_fee
```
`(src/backtest/replay_engine.py:192–202)`

**Проскальзывание (slippage)** — это моделирование реальности: на реальной бирже исполнение происходит чуть хуже желаемой цены. При покупке платим чуть больше (`× 1.005`), при продаже получаем чуть меньше (`× 0.9995`). По умолчанию 0.05%.

**Комиссия taker** — плата бирже за каждую сделку. Считается от суммы сделки: `fee = exit_price × qty × 0.001` (0.1%). Входная комиссия (`entry_fee`) рассчитывается в момент создания `pending_entry` и хранится в позиции до выхода. `(src/backtest/replay_engine.py:249, 201)`

### Шаг 5: Условие и параметры входа в позицию

После проверки выходов движок проверяет, можно ли войти в новую позицию: `(src/backtest/replay_engine.py:227–259)`

```python
entry_allowed = signal in (1, -1) and not (long_only and signal == -1)
if position is None and pending_entry is None and entry_allowed and i < len(data) - 1:
    ...
```

Вход разрешён, если:
- есть сигнал (`1` или `−1`),
- позиции нет,
- ожидающего входа нет,
- текущий бар не последний (`i < len(data) - 1`) — иначе некуда входить, следующего бара не существует.

Размер позиции здесь — простой фиксированный процент баланса (по умолчанию 10%). Это упрощение симуляции: в live-риск-менеджере размер считается сложнее — по [[position-sizing-kelly|формуле Келли по фазам]].
```
spend = balance × position_size_pct / 100   # по умолчанию 10% баланса
qty = spend / entry_price
```
`(src/backtest/replay_engine.py:229, 239)`

Уровни стоп-лосса и тейк-профита рассчитываются от ATR (мера волатильности рынка — подробнее см. [[wilder-atr-and-stops]]). Если ATR не рассчитан (NaN в прогревочных барах) — используется запасное значение `close × 0.01`, то есть 1% от текущей цены. `(src/backtest/replay_engine.py:240)`

### Шаг 6: Kill-switch (аварийный стоп)

В конце каждого бара движок обновляет «пик капитала» (high-water mark — максимум, которого когда-либо достигал баланс) и считает текущую просадку:

```python
high_water_mark = max(high_water_mark, balance)
drawdown = (high_water_mark - balance) / high_water_mark
```
`(src/backtest/replay_engine.py:261–262)`

Если просадка достигла или превысила 20% (`max_drawdown_pct`):
1. Открытая позиция немедленно закрывается по цене `close` с учётом проскальзывания и комиссии.
2. Причина закрытия — `"KILL_SWITCH"`.
3. Цикл прерывается `break` — дальнейшие бары не обрабатываются.
4. Итоговая точка кривой капитала записывается, и функция завершает работу.

`(src/backtest/replay_engine.py:264–299)`

Kill-switch защищает от полного опустошения счёта при затяжном неблагоприятном движении рынка. Это симуляционный аналог живых защитных механизмов: в реальной торговле похожую роль играют [[circuit-breakers-drawdown-flash|автоматические предохранители по просадке]] и [[kill-switch-emergency-stop|аварийный стоп-файл оператора]].

### Шаг 7: Mark-to-market — переоценка капитала

На каждом баре (если kill-switch не сработал) в кривую капитала записывается не просто баланс, а **переоценённый** балансс учётом открытой позиции:

```python
mark_to_market = balance
if position is not None:
    mark_to_market += (close_price - entry_price) × qty   # для BUY
equity_rows.append({"timestamp": ts, "balance": mark_to_market})
```
`(src/backtest/replay_engine.py:301–307)`

Это как оценить стоимость акций, которые у вас есть, по текущей цене — даже если вы их ещё не продали. Кривая капитала отражает реальное «богатство» на каждый момент времени, включая незакрытые позиции.

### Шаг 8: Расчёт длительности удержания

После закрытия позиции вычисляется время, сколько бот «держал» сделку, через `_holding_time_seconds`. `(src/backtest/replay_engine.py:15–28)`

Функция понимает два формата меток времени:
- **Объекты timedelta** (стандартный Python/pandas формат) → вызывается `.total_seconds()`.
- **Числа в миллисекундах** (некоторые источники данных хранят время именно так): если `|delta| > 1 000 000` — делится на 1000 для перевода в секунды.

Итоговое время в часах записывается в таблицу сделок как `holding_hours`.

## Формулы и расчёты

### Размер позиции

```
spend = balance × (position_size_pct / 100)
qty   = spend / entry_price
```

**Простыми словами:** если у вас 10 000 USDT и `position_size_pct = 10`, то на одну сделку тратится 1 000 USDT. Если цена входа 50 000 — покупаем `1000 / 50000 = 0.02 BTC`.

`(src/backtest/replay_engine.py:229, 239)`

### Цена входа и выхода со скольжением

```
entry BUY:  entry_price = open[i+1] × (1 + slippage)     # платим чуть дороже
exit  BUY:  exit_price  = raw_exit  × (1 − slippage)     # получаем чуть меньше
entry SELL: entry_price = open[i+1] × (1 − slippage)     # заходим чуть дешевле
exit  SELL: exit_price  = raw_exit  × (1 + slippage)     # закрываем чуть дороже
```

`(src/backtest/replay_engine.py:234–237, 194–197)`

### PnL (прибыль/убыток) сделки

```
gross_pnl BUY  = (exit_price − entry_price) × qty
gross_pnl SELL = (entry_price − exit_price) × qty

entry_fee = entry_price × qty × commission
exit_fee  = exit_price  × qty × commission

net_pnl = gross_pnl − entry_fee − exit_fee
```

**Простыми словами:** валовая прибыль — это сколько вы заработали «до вычета расходов». Чистая прибыль — после оплаты двух комиссий (при входе и при выходе).

`(src/backtest/replay_engine.py:195–202)`

### Уровни SL и TP

```
BUY:   sl = entry_price − sl_atr_mult × ATR    (по умолчанию: −1.5 × ATR)
BUY:   tp = entry_price + tp_atr_mult × ATR    (по умолчанию: +3.0 × ATR)
SELL:  sl = entry_price + sl_atr_mult × ATR
SELL:  tp = entry_price − tp_atr_mult × ATR
```

**Простыми словами:** ATR — средний дневной диапазон движения цены (подробнее: [[wilder-atr-and-stops]]). Стоп-лосс ставится на расстоянии 1.5 ATR, тейк-профит — на 3.0 ATR. Соотношение риска к прибыли 1:2.

`(src/backtest/replay_engine.py:243–247)`

### Просадка (drawdown)

```
high_water_mark = max(high_water_mark, balance)   # исторический пик капитала
drawdown        = (high_water_mark − balance) / high_water_mark
```

**Простыми словами:** просадка — это насколько глубоко вы упали от своего лучшего результата. Если баланс был 12 000 и упал до 9 000 — просадка 25%. Kill-switch срабатывает при просадке ≥ 20%. Как максимальная просадка используется в качестве метрики качества — см. [[max-drawdown-winrate-rr]].

`(src/backtest/replay_engine.py:261–264)`

## Примеры / сценарии

### Сценарий A: Успешная сделка с тейк-профитом

**Исходные данные:** баланс 10 000 USDT, цена входа 50 000 USDT, ATR = 1 000 USDT.

1. **Бар i = 100:** стратегия выдаёт `signal = 1`. Последний бар? Нет (`i < N-1`). Создаём `pending_entry`:
   - `next_open = 50 500` (цена открытия бара 101)
   - `entry_price = 50 500 × 1.0005 = 50 525.25` (со скольжением)
   - `spend = 10 000 × 10% = 1 000 USDT`
   - `qty = 1 000 / 50 525.25 = 0.01979 BTC`
   - `sl = 50 525.25 − 1.5 × 1 000 = 49 025.25`
   - `tp = 50 525.25 + 3.0 × 1 000 = 53 525.25`
   - `entry_fee = 50 525.25 × 0.01979 × 0.001 = 0.9999 USDT`

2. **Бар i = 101:** `timestamp == pending_entry["timestamp_open"]` → позиция активирована. На этом баре `high = 54 000 ≥ tp (53 525.25)`:
   - `exit_price = 53 525.25 × (1 − 0.0005) = 53 498.52`
   - `gross_pnl = (53 498.52 − 50 525.25) × 0.01979 = 58.84 USDT`
   - `exit_fee = 53 498.52 × 0.01979 × 0.001 = 1.0587 USDT`
   - `net_pnl = 58.84 − 1.00 − 1.06 = 56.78 USDT`
   - Причина: `"TP"`

### Сценарий B: Kill-switch в действии

**Начало:** баланс 10 000 USDT. После серии убыточных сделок баланс упал до 8 200 USDT. `high_water_mark = 10 000`.

На очередном баре:
```
drawdown = (10 000 − 8 200) / 10 000 = 0.18   → 18%  (ниже 20%)
```

Торговля продолжается. Ещё одна убыточная сделка: баланс → 7 900.
```
drawdown = (10 000 − 7 900) / 10 000 = 0.21   → 21% ≥ 20%
```

Kill-switch: открытая позиция закрывается по `close` с комиссией и скольжением, сделка помечается `"KILL_SWITCH"`, цикл прерывается. Кривая капитала обрывается на этом баре.

### Сценарий C: Последний бар — принудительный EOD-выход

Если бот достиг последней свечи в истории с открытой позицией и ни SL, ни TP не сработали — позиция закрывается по цене `close` последнего бара. Причина: `"EOD"` (End of Data). `(src/backtest/replay_engine.py:188–190)`

## Подводные камни / что важно понимать

**1. Anti-look-ahead — это не просто «хорошая практика», это критично.**
Если бы движок использовал цену закрытия бара `i` для входа (а не `open[i+1]`), результаты бэктеста были бы нечестными: стратегия «знала бы» цену, которая в реальности стала известна только в следующий момент. Все прибыльные результаты были бы завышены, а бот в реальной торговле работал бы иначе. Механизм `pending_entry` — техническая гарантия того, что этого не происходит. `(src/backtest/replay_engine.py:158–160, 228, 252)`

**2. SL имеет приоритет над TP.**
Если за один бар и `low <= sl`, и `high >= tp` — срабатывает SL. В реальности на таком баре это могло произойти в любом порядке, но движок консервативно выбирает худший сценарий — SL. `(src/backtest/replay_engine.py:167–173)`

**3. На последнем баре вход запрещён.**
Условие `i < len(data) - 1` гарантирует, что если сигнал появился на последней свече — вход не будет создан, поскольку нет следующей свечи для исполнения. `(src/backtest/replay_engine.py:228)`

**4. Запрет двух позиций одновременно.**
Условие `position is None and pending_entry is None` гарантирует: пока есть открытая позиция или ожидающий вход — новый сигнал игнорируется. Бот торгует строго один инструмент в один момент. `(src/backtest/replay_engine.py:228)`

**5. Kill-switch — это обрыв, а не пауза.**
После срабатывания kill-switch цикл прерывается `break`. Бот не продолжает торговать после восстановления. Кривая капитала становится короче, чем вся история. Это влияет на все последующие метрики — они считаются только по «живой» части истории.

**6. ATR из `indicators.py` — это EWM-вариант, не Wilder-рекурсия.**
В `replay_engine` ATR берётся из колонки `atr`, которую заполняет `calculate_indicators`. Там используется pandas `.ewm()` — экспоненциально взвешенное скользящее среднее. Это отличается от Wilder-рекурсии, применяемой в других раннерах (например, в [[research-kernel-execution-model|research-ядре для стратегий-пробоев]]). Подробнее: [[wilder-atr-and-stops]]. `(src/backtest/indicators.py:102–109)`

**7. Метрики считаются отдельной функцией, не внутри цикла.**
После завершения цикла `run_replay` вызывает `_compute_metrics(equity_df, trades_df, ...)`. Sharpe, Sortino, Win Rate и остальные показатели — это пост-обработка результатов, а не расчёты в реальном времени. Подробнее о метриках: [[replay-engine-metrics]].

**8. Аннуализация Sharpe зависит от таймфрейма.**
Параметр `bars_per_year` (по умолчанию 8760 для 1-часовых баров) задаёт множитель `√bars_per_year` для [[sharpe-sortino-metrics|Sharpe Ratio]]. Для 4-часовых баров должно быть 2190, для 15-минутных — 35040. Неверное значение искажает Sharpe в несколько раз. `(src/backtest/replay_engine.py:35–43, 137)`

- [[end-to-end-overview]] — где симуляция стоит в общей картине бота (данные → сигнал → риск → ордер)

Что движок использует на входе:
- [[indicators-and-signals]] — как формируется колонка `signal`, по которой движок принимает решения
- [[ema-rsi-indicators]] — EMA и RSI: индикаторы, которые `calculate_indicators` добавляет к барам
- [[atr-indicator]] — ATR как мера волатильности; здесь берётся EWM-вариант, а не Wilder
- [[wilder-atr-and-stops]] — расчёт ATR и логика уровней стоп-лосса / тейк-профита
- [[bar-model]] — структура свечи OHLCV, по которой движок итерирует бар за баром

Что движок выдаёт на выходе:
- [[replay-engine-metrics]] — что значат Sharpe, Sortino, Profit Factor и остальные метрики, которые `run_replay` возвращает
- [[sharpe-sortino-metrics]] — как считается Sharpe/Sortino и роль `bars_per_year` при аннуализации
- [[max-drawdown-winrate-rr]] — метрика максимальной просадки по equity-кривой, которую строит движок
- [[trade-extractor-and-records]] — как таблица сделок из replay превращается в `TradeRecord` для статистики (DSR)
- [[reporter-and-artifacts]] — как результаты прогона (сделки, метрики, equity) сохраняются в файлы
- [[equity-chart-and-drawdown]] — как кривая капитала и просадка из движка визуализируются в дашборде

Применение в валидации:
- [[walk-forward-analysis]] — как `run_replay` используется внутри WFA: функция `replay_fn` передаётся в `WalkForwardRunner`
- [[acceptance-gates-t1-t6]] — пороги Sharpe/Sortino/просадки, которые применяются к метрикам, возвращённым движком
- [[deflated-sharpe-ratio]] — поправка Sharpe на множественные попытки, считается по сделкам из replay-пути
- [[donchian-runner-and-reference-run]] — канонический пример полного WFA-прогона через `replay_engine`
- [[single-symbol-wfa-and-data-loading]] — откуда движок получает OHLCV (загрузка Parquet + WFA для одного символа)
- [[run-backtest-form]] — форма дашборда, которая запускает прогон через движок

Альтернативные / контрастные модели исполнения:
- [[research-kernel-execution-model]] — ВТОРАЯ система исполнения (`_backtest_single`) для стратегий-пробоев: аддитивный PnL вместо процентного, намеренно обходит `replay_engine`
- [[vector-backtest-fast-approximation]] — быстрый безцикловый движок для грубой оценки: без SL/TP, контраст к честному бар-за-баром
- [[kronos-exploratory-runner]] — разведочный прогон Kronos через кэш предсказаний (без ворот T1-T6)

Анти-look-ahead и защита капитала (смежные механизмы):
- [[bar-source-live]] — та же защита от look-ahead, но в live-режиме (дедупликация, только закрытые свечи)
- [[position-sizing-kelly]] — как размер позиции считается в live (формула Келли) против фиксированного % в симуляции
- [[circuit-breakers-drawdown-flash]] — живые предохранители по просадке, аналог симуляционного kill-switch
- [[kill-switch-emergency-stop]] — реальный аварийный стоп оператора (контраст с внутренним kill-switch движка)
