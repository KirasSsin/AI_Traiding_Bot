# Извлечение сделок (TradeRecord): мост между прогоном и DSR

**TL;DR:** Бэктест-прогон выдаёт таблицу сделок в формате DataFrame (строки в памяти). Чтобы статистический модуль [[06-бэктест-и-валидация/deflated-sharpe-ratio|DSR]] смог эти данные считать, функция `extract_trade_records` превращает каждую строку в типизированный объект `TradeRecord` — с точными числами, временными метками в UTC и каноническим кодом причины выхода.

## Простыми словами

Представьте, что бот сыграл 200 партий в карты (прогнал бэктест). После каждой партии крупье записал результат на обычной бумажке: «купил в 10:00 по цене 50 000, продал в 11:00 по цене 50 300, заработал 1.5 USDT». Проблема: статистик, который должен проверить — стоит ли доверять этому боту — читает данные в строго определённом формате с точными числами и метками времени. Бумажки крупье он не понимает.

Функция `extract_trade_records` — это переводчик. Она берёт каждую «бумажку» (строку таблицы из бэктеста) и переводит её в стандартный «протокол» (`TradeRecord`), который статистический модуль уже умеет читать.

Зачем это нужно? Два отдельных слоя — бэктест и аналитика — создавались независимо, с разными форматами данных. Переводчик позволяет их соединить, не ломая ни один из слоёв.

## Как это работает у нас

### Шаг 1. Когда вызывается extract_trade_records

После того как бэктест-прогон заканчивается ([[06-бэктест-и-валидация/walk-forward-analysis|WFA]] — Walk-Forward Analysis, обход исторических данных по окнам), система извлекает из каждого окна таблицу закрытых сделок в виде DataFrame. Именно в этот момент вызывается `extract_trade_records`.

Вызывается функция в двух местах:
- `donchian_runner.py:166` — для Donchian-стратегии (см. [[06-бэктест-и-валидация/donchian-runner-and-reference-run|Donchian runner]])
- `data_loading.py:204` — для основного WFA-пути (см. [[06-бэктест-и-валидация/single-symbol-wfa-and-data-loading|загрузка данных и WFA]])

В обоих случаях перед вызовом таблица нормализуется: колонки `timestamp_open` / `timestamp_close` переименовываются в `entry_ts` / `exit_ts`, а времена без часового пояса принудительно помечаются UTC (`tz_localize(UTC)`). Если в таблице нет колонки `fees_paid` (комиссия), она вычисляется как сумма `entry_fee + exit_fee` (donchian_runner.py:162–165, data_loading.py:200–203).

### Шаг 2. Проверка на пустую таблицу

```python
if df.empty:
    return []
```

Если прогон не дал ни одной сделки (бывает, если рынок не давал входных сигналов), функция немедленно возвращает пустой список — никаких ошибок (src/backtest/trade_extractor.py:60–61).

### Шаг 3. Обход строк и конвертация чисел в Decimal

Для каждой строки:

```python
qty = Decimal(str(row["qty"]))
entry_price = Decimal(str(row["entry_price"]))
pnl_quote = Decimal(str(row["net_pnl"]))
fees_paid = Decimal(str(row.get("fees_paid", 0)))
```

Почему `Decimal`? Обычные числа с плавающей точкой (float) накапливают крошечные погрешности при умножении и делении. Для денежных расчётов это недопустимо: 0.1 + 0.2 в float равно 0.30000000000000004, а не 0.3. `Decimal` — это точная арифметика без таких сюрпризов.

Все числа сначала преобразуются в строку (`str(...)`), а потом в Decimal — чтобы избежать потери точности при промежуточном float-представлении (src/backtest/trade_extractor.py:67–70).

### Шаг 4. Расчёт pnl_pct (доходность в долях)

```python
notional = qty * entry_price
pnl_pct = (pnl_quote / notional) if notional > 0 else Decimal("0")
```

Подробнее — в разделе «Формулы и расчёты» ниже (src/backtest/trade_extractor.py:72–73).

### Шаг 5. Нормализация временных меток

```python
entry_ts = row["entry_ts"]
if hasattr(entry_ts, "to_pydatetime"):
    entry_ts = entry_ts.to_pydatetime()
```

Pandas хранит временны́е метки в собственном формате `Timestamp`. Python-объект `TradeRecord` требует стандартный `datetime`. Метод `to_pydatetime()` делает конвертацию. Проверка `hasattr(...)` защищает на случай, если кто-то уже передал обычный `datetime` — тогда конвертация пропускается (src/backtest/trade_extractor.py:75–81).

### Шаг 6. Маппинг кода причины выхода

Это ключевой шаг. Бэктест-движок ([[06-бэктест-и-валидация/replay-engine-bar-by-bar|replay_engine]]) пишет причины выхода как свободные строки: `'SL'`, `'TP'`, `'SIGNAL_FLIP'`, `'EOD'`, `'KILL_SWITCH'`. DSR и аналитические отчёты работают только с каноническими кодами из перечисления [[04-риск-менеджмент/reason-codes-assessment-output|`ReasonCode`]]. Без маппинга система не знала бы, что `'SL'` — это стоп-лосс.

Маппинг задан жёстко в таблице `_EXIT_REASON_MAP` (src/backtest/trade_extractor.py:29–35):

| Строка из бэктеста | Канонический код | Что означает |
|---|---|---|
| `SL` | `EXIT_SL_HIT` | Стоп-лосс сработал — вышли с убытком по заранее заданному уровню |
| `TP` | `EXIT_TP_HIT` | Тейк-профит сработал — взяли прибыль |
| `SIGNAL_FLIP` | `EXIT_SIGNAL_FLIP` | Стратегия дала обратный сигнал — вышли досрочно |
| `EOD` | `EXIT_TIME_STOP` | Конец дня — вышли по времени |
| `KILL_SWITCH` | `EXIT_CIRCUIT_BREAKER` | Аварийная остановка бота ([[04-риск-менеджмент/circuit-breakers-drawdown-flash\|предохранитель]] / [[04-риск-менеджмент/kill-switch-emergency-stop\|kill-switch]]) |

Функция `_map_exit_reason` берёт строку и ищет её в таблице. Если строка не найдена или отсутствует — возвращает `EXIT_TP_HIT` как запасной вариант для обратной совместимости (src/backtest/trade_extractor.py:38–46).

> **Исторический контекст (S27 T4):** до исправления функция всегда возвращала `EXIT_TP_HIT` для всех сделок — включая убыточные. В результате аналитический файл `formulas_audit_v1.json` показывал стоп-лоссы как тейк-профиты, что делало диагностику невозможной. Исправлено в Sprint 27, задача T4.

### Шаг 7. Сборка объекта TradeRecord

```python
records.append(
    TradeRecord(
        symbol=symbol,
        entry_signal_id=uuid4(),
        entry_ts=entry_ts,
        exit_ts=exit_ts,
        qty=qty,
        entry_price=entry_price,
        exit_price=Decimal(str(row["exit_price"])),
        pnl_quote=pnl_quote,
        pnl_pct=pnl_pct,
        fees_paid=fees_paid,
        reason_code=reason_code,
        kelly_phase=1,
        recorded_at=now_utc,
    )
)
```

Два поля требуют отдельного объяснения (src/backtest/trade_extractor.py:86–102):

**`entry_signal_id = uuid4()`** — уникальный идентификатор сделки. UUID (Universally Unique Identifier) — это случайный 128-битный номер вида `3f6c4a28-e217-4b2a-9f3a-000123456789`, гарантированно не совпадающий с другими. В бэктесте он синтезируется заново для каждой строки — бэктест не имеет реальных сигналов, поэтому нужен суррогатный идентификатор. DSR требует от него одного: уникальности — и только.

**`kelly_phase = 1`** — фаза алгоритма Келли ([[04-риск-менеджмент/position-sizing-kelly|метода определения размера позиции]]). В бэктесте всегда ставится 1 — допущение, что мы ещё в начальной фазе, без реальной истории сделок. Это константа, жёстко зашитая для всех бэктест-сделок.

## Формулы и расчёты

### Доходность в долях (pnl_pct)

```
pnl_pct = pnl_quote / notional
где:
  notional = qty × entry_price
  pnl_quote = net_pnl сделки (знаковый: положительный = прибыль, отрицательный = убыток)
```

**Что считает:** какую долю от вложенных денег составил результат сделки. Знак сохраняется: прибыль — положительное число, убыток — отрицательное.

**Пример из теста** (tests/unit/test_trade_extractor.py:36–37):
- `qty = 0.001` BTC
- `entry_price = 50 000` USDT
- `net_pnl = 1.0` USDT
- `notional = 0.001 × 50 000 = 50` USDT
- `pnl_pct = 1.0 / 50 = 0.02` → это +2%

**Пример убыточной сделки** (tests/unit/test_trade_extractor.py:56–69):
- `net_pnl = -0.5` USDT
- `pnl_pct = -0.5 / 50 = -0.01` → это -1%

**Важно:** результат — дробь, не процент. Число `0.02` означает «+2%», а не «+0.02%». DSR и другие метрики работают именно с дробями (fractional returns).

**Тип данных:** в бэктесте `pnl_pct` — тип `Decimal` (точная арифметика). В исследовательском ядре (research/) — обычный `float`. Единицы одинаковы (дробь), но в бэктесте точность выше (src/backtest/trade_extractor.py:73).

**Защита от деления на ноль:** если `notional == 0` (что невозможно при нормальных данных, но подстраховано кодом), `pnl_pct` устанавливается в `Decimal("0")` (src/backtest/trade_extractor.py:73).

### Источник реализации

```python
# src/backtest/trade_extractor.py:72–73
notional = qty * entry_price
pnl_pct = (pnl_quote / notional) if notional > 0 else Decimal("0")
```

## Примеры / сценарии

### Сценарий: три сделки, разные причины выхода

Допустим, WFA-прогон по одному окну дал три закрытые сделки:

| # | Вход | Выход | qty | entry_price | net_pnl | reason_code (строка) |
|---|---|---|---|---|---|---|
| 1 | 10:00 | 11:00 | 0.001 | 50 000 | +1.0 USDT | `TP` |
| 2 | 12:00 | 13:00 | 0.001 | 50 100 | -0.5 USDT | `SL` |
| 3 | 14:00 | 15:00 | 0.001 | 50 200 | +0.3 USDT | `SIGNAL_FLIP` |

После `extract_trade_records(df, symbol="BTCUSDT")` получаем список из трёх `TradeRecord`:

| # | pnl_quote | notional | pnl_pct | reason_code (канон) | entry_signal_id |
|---|---|---|---|---|---|
| 1 | +1.0 | 50.0 | +0.020 (+2%) | `EXIT_TP_HIT` | `uuid-A` |
| 2 | -0.5 | 50.1 | -0.00998 (≈-1%) | `EXIT_SL_HIT` | `uuid-B` |
| 3 | +0.3 | 50.2 | +0.00598 (≈+0.6%) | `EXIT_SIGNAL_FLIP` | `uuid-C` |

Все три UUID разные — функция `uuid4()` гарантирует уникальность. Список передаётся дальше в DSR-вычисление, где анализируются распределение доходностей и вероятность случайной удачи.

### Сценарий: старые данные без reason_code в таблице

Если бэктест-таблица не содержит колонки `reason_code` (старый формат до S27), функция обращается к `row.get("reason_code")`, получает `None` и через `_map_exit_reason(None)` возвращает `EXIT_TP_HIT` — безопасный запасной вариант. Прогон не падает (src/backtest/trade_extractor.py:43–44).

## Подводные камни / что важно понимать

**1. pnl_pct — дробь, не процент.**
Значение `0.02` в поле `pnl_pct` = 2%, а не 0.02%. Если смотреть на числа напрямую, не зная это правило, можно решить, что бот зарабатывает сотые доли процента. На самом деле шкала другая.

**2. kelly_phase всегда 1 в бэктесте — это допущение, не факт.**
В живой торговле `kelly_phase` реально может быть 2, 3 или 4 — зависит от накопленной истории. В бэктесте история не накапливается (каждый прогон независим), поэтому всегда ставится 1. Это означает, что расчёты Kelly в бэктесте консервативны — бот не «включает» более агрессивные фазы.

**3. UUID синтезируется заново при каждом запуске бэктеста.**
Каждый запуск `extract_trade_records` генерирует новые UUID. Если один и тот же бэктест запустить дважды — UUID будут разными. Это нормально: идентификаторы используются только для дедупликации внутри одного запуска, не между запусками.

**4. Fallback `EXIT_TP_HIT` маскирует неизвестные причины.**
Если бэктест-движок вернул незнакомую строку (например, новый тип выхода, ещё не добавленный в `_EXIT_REASON_MAP`), она тихо превращается в `EXIT_TP_HIT`. Это не ошибка — не падает, работает. Но аналитика будет некорректно классифицировать такие сделки. Если добавляется новый тип выхода в replay_engine — нужно синхронно обновить `_EXIT_REASON_MAP` в `trade_extractor.py`.

**5. Нормализация времени — в вызывающем коде, не в extractor.**
Сам `extract_trade_records` не добавляет часовой пояс к временны́м меткам — он только вызывает `to_pydatetime()` если нужна конвертация типа. Приведение к UTC (`tz_localize`) происходит раньше, в `donchian_runner.py:156–161` и `data_loading.py:194–199`. Если кто-то вызовет `extract_trade_records` напрямую с временны́ми метками без часового пояса, `TradeRecord` не примет их (поле `entry_ts` требует `AwareDatetime` — datetime с явным часовым поясом).

**6. TradeHistoryRepository в бэктесте не используется.**
`TradeRecord` — это структура данных, а [[04-риск-менеджмент/trade-fill-history|`TradeHistoryRepository`]] — это отдельный класс для записи в SQLite-базу (src/risk/trade_history.py:38–180). В бэктесте сделки не сохраняются в базу — они живут только в памяти как список объектов. База данных ([[01-как-работает-бот/storage-and-database|хранилище]]) используется только в живой торговле. Методы `consecutive_losses` и `last_trade_ts` (src/risk/trade_history.py:132–161) кормят [[04-риск-менеджмент/halt-gate-precommitted-criteria|`HaltGate`]] в живом режиме — в бэктест они не вовлечены.
