# Архитектура сигналов: как стратегия говорит боту «торговать»

**TL;DR:** Каждая стратегия общается с остальным ботом через единый конверт — объект `Signal`. Конверт содержит «команду» (купить или выйти), снимок показателей рынка и метку времени. Бот гарантирует: сигнал рождается только ПОСЛЕ закрытия свечи и исполняется на следующей — никакого «взгляда в будущее».

---

## Простыми словами

Представьте, что стратегия — это аналитик, который смотрит на графики и решает, что делать. Но аналитик не может сам позвонить брокеру: у него нет прямого провода. Вместо этого он заполняет стандартный бланк (это и есть `Signal`) и кладёт его в общий ящик. Дальше другие части бота — риск-менеджер и исполнитель — берут этот бланк, проверяют его и при необходимости отправляют реальный ордер на биржу.

Почему нужен стандартный бланк? Потому что у нас несколько стратегий ([[ema-crossover-strategy|EMA-кроссовер]], [[donchian-breakout-strategy|пробой Donchian]], [[mean-reversion-strategy|Mean Reversion]], [[supertrend-strategy|Supertrend]], [[kronos-ml-strategy|Kronos]] и другие). Все они разные внутри, но все обязаны заполнять один и тот же бланк. Риск-менеджер не знает, какая именно стратегия его прислала — он читает бланк и принимает решение по единым правилам.

Аналогия: любая посылка в курьерской службе, независимо от содержимого, сопровождается накладной единого образца. Содержимое разное — накладная одна.

---

## Как это работает у нас

### 1. Объект Signal — «стандартный бланк»

`Signal` — это неизменяемый объект данных (Pydantic-модель с флагом `frozen=True`), который стратегия создаёт ровно один раз и больше не трогает. Поле `extra="forbid"` означает: нельзя добавить ни одного лишнего поля, не предусмотренного схемой. Это защита от случайных опечаток и от попыток «протащить» какие-то данные в обход схемы.

```python
# src/signalgen/models.py:17-43
class Signal(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")

    signal_id: UUID          # уникальный идентификатор этого конкретного сигнала
    symbol: str              # тикер, например "BTCUSDT" (только пары к USDT)
    side: SignalSide         # LONG (открыть) или FLAT (выйти)
    bar_close_time: datetime # когда закрылась свеча, по которой принято решение
    generated_at: datetime   # когда стратегия создала объект Signal

    # Снимок индикаторов в момент принятия решения:
    ema_fast: Decimal
    ema_slow: Decimal
    adx_14: Decimal          # от 0 до 100 (сила тренда)
    plus_di_14: Decimal      # от 0 до 100 (+DI)
    minus_di_14: Decimal     # от 0 до 100 (-DI)
    rsi_14: Decimal          # от 0 до 100 (перекупленность/перепроданность)
    atr_14: Decimal          # >= 0 (средний диапазон свечи, волатильность)

    reason: str              # код причины, не длиннее 128 символов
```

Поля индикаторов ([[ema-rsi-indicators|`ema_fast`]], [[adx-indicator|`adx_14`]], [[atr-indicator|`atr_14`]] и т.д.) имеют диапазонные ограничения, проверяемые автоматически при создании объекта. Если стратегия попытается передать `adx_14 = 150`, Pydantic сразу выбросит ошибку — некорректный сигнал не попадёт дальше по цепочке. `(src/signalgen/models.py:31-35)`

### 2. SignalSide — только два состояния

```python
# src/signalgen/models.py:11-14
class SignalSide(StrEnum):
    LONG = "LONG"   # «открыть позицию» — купить
    FLAT = "FLAT"   # «выйти из позиции» — закрыть
    # SHORT не используется в v0.1 (spot only)
```

Почему только LONG и FLAT, но не SHORT? Бот торгует на споте Bybit — это значит, он торгует реальной криптовалютой, которую держит в кошельке. Продать в минус (открыть короткую позицию) без заёмных средств невозможно. Поэтому сокращение SHORT намеренно исключено из v0.1.

### 3. Инвариант look-ahead — запрет «заглядывать в будущее»

Это одно из фундаментальных правил честного бэктеста и корректной торговли. «Заглядывание вперёд» (look-ahead) — это когда стратегия использует данные, которые в реальности ещё не были бы известны на момент принятия решения. Например, если на закрытии свечи в 10:00 стратегия «видит» цену открытия свечи в 10:01 — это нечестно: в 10:00 эта цена ещё неизвестна.

В коде это защищено валидатором модели:

```python
# src/signalgen/models.py:39-43
@model_validator(mode="after")
def _generated_after_close(self) -> "Signal":
    if self.generated_at < self.bar_close_time:
        raise ValueError("generated_at must be >= bar_close_time (look-ahead invariant)")
    return self
```

Правило буквально: время создания сигнала (`generated_at`) обязано быть равно или позже времени закрытия свечи (`bar_close_time`). Если кто-то попытается создать сигнал с `generated_at` в прошлом относительно свечи — Pydantic немедленно выбросит ошибку.

### 4. Контракт on_bar — как стратегия «живёт»

Каждая стратегия реализует один метод `on_bar(bar: Bar) -> Signal | None` (на вход — одна закрытая свеча [[bar-model|`Bar`]]). Его вызывает рантайм (живой трейдинговый движок) ровно один раз на каждую закрытую свечу:

```python
# src/runtime/manager.py:346
signal = self._strategy.on_bar(bar)
```

Логика простая: если стратегия считает, что нужно действовать — возвращает заполненный `Signal`. Если ничего делать не надо — возвращает `None`. Рантайм проверяет результат и, если это не `None`, передаёт сигнал дальше: сначала в [[risk-overview-decision-pipeline|риск-менеджер]], потом в [[order-lifecycle-overview|исполнитель]]. `(src/runtime/manager.py:319-410)`

Временной инвариант жёстко задокументирован в стратегии EMA-кроссовера:

```
# src/signalgen/strategy.py:5-6
Invariant: signal on close(T) → execution at open(T+1)
```

Другими словами: сигнал рождается на закрытии свечи T, а реальный ордер отправляется на открытии следующей свечи T+1. Это честная модель — как в реальном трейдинге.

### 5. FSM — стратегия помнит, «в позиции она или нет»

FSM расшифровывается как Finite State Machine — «конечный автомат состояний». Для трейдинга это просто означает: стратегия запоминает, есть у неё открытая позиция или нет.

У каждой стратегии есть внутренняя переменная `_current_side`, инициализированная как `SignalSide.FLAT` (нет позиции). Это защита от двух опасных ошибок:

- **Двойной вход** — стратегия не может послать сигнал LONG, если уже в позиции LONG. Вход разрешён только из состояния FLAT.
- **Выход из пустоты** — стратегия не пошлёт сигнал FLAT, если и так никакой позиции нет.

Вот как это выглядит в EMA-кроссовер стратегии:

```python
# src/signalgen/strategy.py:60
self._current_side: SignalSide = SignalSide.FLAT

# src/signalgen/strategy.py:131-144 — вход только из FLAT:
if (cross_up and trend_strong and bullish_dir and not_overbought
        and self._current_side == SignalSide.FLAT):
    self._current_side = SignalSide.LONG
    return self._build_signal(bar, SignalSide.LONG, ...)

# src/signalgen/strategy.py:147-157 — выход только из LONG:
if self._current_side == SignalSide.LONG:
    if flip_down and bearish_dir:
        self._current_side = SignalSide.FLAT
        return self._build_signal(bar, SignalSide.FLAT, ...)
```

### 6. warmup — «прогрев» без торговли

Когда бот запускается, ему нужны исторические данные, чтобы правильно вычислить индикаторы (например, EMA за последние 200 свечей). Но эти исторические бары нельзя обрабатывать через `on_bar` — иначе бот попытается торговать на прошлых данных.

Для этого существует отдельный метод `warmup(bar: Bar)`:

```python
# src/signalgen/strategy.py:76-83
def warmup(self, bar: Bar) -> None:
    """Feed historical bar to rolling buffer WITHOUT signal emission.

    ADR 0022 sub-decision 2 — catch-up на startup защищает от look-ahead
    trade events на bars из прошлого.
    """
    self._append_bar(bar)
```

`warmup` делает то же самое, что `on_bar` внутри — кладёт бар в буфер, — но пропускает шаг оценки и никогда не возвращает `Signal`. Это честный прогрев: индикаторы насыщаются данными, но торговые решения не принимаются. `(src/signalgen/strategy.py:76-83)`

### 7. Zero-placeholder поля

`Signal` — общий тип для всех стратегий, но разные стратегии вычисляют разные индикаторы. Стратегия Mean Reversion, например, не считает EMA и ADX — она работает только с RSI и [[bollinger-bands-indicator|полосами Боллинджера]]. Что делать с полями `ema_fast`, `adx_14` и другими, которые эта стратегия не использует?

Соглашение: заполнять их нулями (`Decimal("0")`). Это называется zero-placeholder — «заполнитель нулём».

```python
# src/signalgen/mean_reversion_strategy.py:8
# Unused EMA/ADX/DI fields в Signal populated с zero placeholders
# (mean-reversion не computes those indicators).

# src/signalgen/mean_reversion_strategy.py:203-207
ema_fast=Decimal("0"),
ema_slow=Decimal("0"),
adx_14=Decimal("0"),
plus_di_14=Decimal("0"),
minus_di_14=Decimal("0"),
```

Аналогично Donchian-стратегия заполняет нулями поля, которые не вычисляет:
`(src/signalgen/donchian_strategy.py:152-166)`

Важно: потребитель сигнала (риск-менеджер, аудит-лог) должен понимать, что нули в индикаторных полях — это «не вычислялось», а не «индикатор равен нулю». Правило: если в аудит-логе видите стратегию Mean Reversion с `adx_14=0` — это норма, не ошибка.

### 8. ReasonCode — «причина» каждого сигнала

Каждый `Signal` несёт строку `reason` — код причины из перечня `ReasonCode`. Это позволяет потом в логах и аудите понять, почему именно был выпущен сигнал.

Важный нюанс: на уровне Pydantic-модели поле объявлено как `reason: str = Field(..., max_length=128)` — то есть принимается любая строка длиной до 128 символов, проверки принадлежности к `ReasonCode` нет. Это **соглашение**, а не схемное ограничение: если стратегия передаст произвольную строку, Pydantic её примет без ошибки. Следование перечню — договорённость команды, а не барьер кода. `(src/signalgen/models.py:37)`

```python
# src/risk/reason_codes.py:45 — начало перечня
class ReasonCode(StrEnum):
    # Входы в позицию:
    ENTRY_LONG_EMA_CROSS_UP          # EMA быстрая пересекла медленную вверх
    ENTRY_LONG_DONCHIAN_BREAKOUT     # пробой верхней границы канала Donchian
    ENTRY_LONG_MEANREV_RSI_BB        # RSI перепродан + цена ниже нижней полосы BB
    ENTRY_LONG_SUPERTREND            # Supertrend переключился в бычью сторону
    ENTRY_LONG_KRONOS                # ML-модель предсказала рост выше порога
    # ... и другие

    # Выходы из позиции:
    EXIT_FLAT_SIGNAL_FLIP            # EMA перевернулась вниз
    EXIT_FLAT_ATR_STOP               # ATR-стоп сработал
    EXIT_FLAT_SUPERTREND_FLIP        # Supertrend переключился в медвежью сторону
    EXIT_FLAT_KRONOS                 # ML-модель предсказала падение
    # ...

    # Отклонения риск-менеджером:
    REJECT_RISK_EXCEEDED             # превышен допустимый риск
    REJECT_INSUFFICIENT_BALANCE      # недостаточно баланса
    REJECT_STALE_DATA                # данные устарели
    # ...

    # Экстренные остановки:
    HALT_DRAWDOWN_L1 / L2 / L3      # просадка превысила порог уровня 1/2/3
    HALT_KILL_SWITCH                 # оператор нажал аварийную кнопку
    HALT_FLASH_CRASH                 # обнаружен flash crash
    # ... и другие
```

В `reason_codes.py` можно выделить несколько семейств по префиксу. Но картина неоднородная — важно знать точную границу, иначе аудит-лог будет вводить в заблуждение.

**Входы в позицию** — стратегийные коды начинаются на `ENTRY_LONG_*` (шесть штук: EMA, Donchian, Mean Reversion, Supertrend, [[kronos-signal-rule|Kronos]], [[volume-breakout-strategy|Volume Breakout]]) и `ENTRY_LONG_ATR_BREAKOUT` ([[atr-breakout-strategy|ATR-пробой]]). Параллельно существуют `ENTRY_SHORT_*` (два кода для коротких позиций, зарезервированы на будущее) и `SCALE_IN_LONG/SHORT` (доливки). `(src/risk/reason_codes.py:47-52)`

**Выходы из позиции** — здесь нет единого префикса. Стратегийные коды выходов действительно используют `EXIT_FLAT_*` (кроссовер, Mean Reversion, Donchian, Supertrend, Kronos, VolumeBreakout, ATR-breakout). Однако системные выходы, которые встречаются в логах не реже стратегийных, используют другие имена: `EXIT_SL_HIT` (стоп-лосс сработал), `EXIT_TP_HIT` (тейк-профит), `EXIT_TRAILING_STOP` (трейлинг-стоп), `EXIT_SIGNAL_FLIP` (разворот сигнала, общий), `EXIT_TIME_STOP`, `EXIT_CIRCUIT_BREAKER`, `EXIT_RECONCILE_DETECTED` и ещё несколько. `(src/risk/reason_codes.py:56-64, 101)` Итого из 20 «выходных» кодов ровно 10 не имеют префикса `EXIT_FLAT_`.

Практическое правило для чтения аудит-лога: `EXIT_SL_HIT` и `EXIT_TP_HIT` — самые частые коды закрытия позиций при работе стоп/тейк-ордеров. Видеть их в логе — норма, а не аномалия.

**Отклонения риск-менеджером** (`REJECT_*`) и **экстренные остановки** (`HALT_*`) — здесь префикс действительно универсален для всех кодов своего класса. `(src/risk/reason_codes.py:66-116)`

Коды **неизменяемы**: их нельзя переименовывать без поправки к ADR (архитектурному решению). Аудит-лог хранит строковые значения, и переименование кода сделало бы старые записи нечитаемыми. `(src/risk/reason_codes.py:7-8)`

Всего в перечне на момент v0.1 (Sprint 52): **67 кодов**. `(src/risk/reason_codes.py:38-153)`

## Формулы и расчёты

Сама по себе архитектура сигналов формул не содержит — `Signal` это структура данных, а не вычислительный алгоритм. Формулы живут внутри конкретных стратегий, которые этот `Signal` создают.

Единственное «вычисление» уровня модели — проверка временного инварианта:

```
generated_at >= bar_close_time
```

Расшифровка простыми словами: «момент создания сигнала» должен быть не раньше «момента закрытия свечи». Это физически и логически очевидно: сигнал не может появиться раньше, чем закроется свеча, по которой он принят. `(src/signalgen/models.py:40-42)`

За формулами индикаторов — см. [[technical-indicators|технические индикаторы]] и страницы конкретных стратегий.

## Примеры / сценарии

### Сценарий 1: Нормальный вход EMA-кроссовер

Допустим, в 10:00 UTC закрылась часовая свеча BTCUSDT. EMA(12) пересекла EMA(26) снизу вверх, ADX = 28 (выше порога 25), +DI > -DI, RSI = 58 (не перекуплен). Стратегия `EmaCrossoverAdxRsiStrategy` вызывает `on_bar()`. (Числа периодов EMA взяты из дефолтных параметров: `strategy_ema_fast=12`, `strategy_ema_slow=26` — `src/platform/config.py:92-93`.)

1. Бар принят в буфер через `_append_bar()`.
2. Индикаторы пересчитаны на всём буфере.
3. Условие входа выполнено, `_current_side == FLAT` → генерируется `Signal`.
4. `_current_side` меняется на `LONG`.
5. Объект `Signal` создаётся: `side=LONG`, `bar_close_time=2026-01-01T10:00:00Z`, `generated_at=2026-01-01T10:00:00.012Z`, `reason="ENTRY_LONG_EMA_CROSS_UP"`, `ema_fast=42150.5`, `ema_slow=41900.2`, `adx_14=28.3`, `rsi_14=58.1`, `atr_14=430.0`.
6. Валидатор `_generated_after_close` проверяет: 10:00:00.012 >= 10:00:00 — OK.
7. Сигнал уходит в рантайм, а там — в риск-менеджер.

На следующей свече (T+1, открытие в 11:00:00) ордер будет отправлен на биржу.

### Сценарий 2: Нормальный выход

Через несколько свечей EMA(12) опустилась ниже EMA(26), -DI > +DI. `_current_side == LONG` → стратегия выпускает `Signal(side=FLAT, reason="EXIT_FLAT_SIGNAL_FLIP")`. Бот закрывает позицию на следующем открытии.

### Сценарий 3: Игнорирование сигнала двойного входа

В позиции LONG приходит ещё одна свеча с идеальными условиями для входа. `_current_side == LONG` → условие `self._current_side == SignalSide.FLAT` в блоке входа не выполнено → `on_bar` возвращает `None`. Никакого действия не происходит, двойного входа нет.

### Сценарий 4: Zero-placeholder в Mean Reversion

RSI(14) упал до 27 (ниже порога 30), цена пробила нижнюю полосу Боллинджера. (Дефолтный порог перепроданности: `strategy_rsi_oversold=30` — `src/platform/config.py:97`.) Mean Reversion генерирует `Signal(side=LONG, reason="ENTRY_LONG_MEANREV_RSI_BB", ema_fast=0, ema_slow=0, adx_14=0, plus_di_14=0, minus_di_14=0, rsi_14=27.0, atr_14=510.0)`. Поля EMA и ADX — нули, это норма: данная стратегия их не считает.

## Подводные камни / что важно понимать

**1. «Нули» — это не «показатель равен нулю».**
Если в аудит-логе у сигнала `adx_14=0`, `ema_fast=0` — это zero-placeholder, а не факт об индикаторе. Нужно смотреть на `reason`, чтобы понять, какая стратегия выпустила сигнал. Коды `ENTRY_LONG_MEANREV_*` или `ENTRY_LONG_DONCHIAN_*` означают, что EMA и ADX этой стратегией не вычислялись.

**2. ReasonCode нельзя переименовывать без ADR.**
Коды хранятся как строки в базе данных аудит-лога. Если переименовать `ENTRY_LONG_EMA_CROSS_UP` в `ENTRY_EMA_BULL`, все прошлые записи лога будут ссылаться на несуществующий код. ADR-ограничение защищает от этого. `(src/risk/reason_codes.py:7-8)`

**3. `_current_side` — только в памяти стратегии, не на бирже.**
После перезапуска бота `_current_side` сбрасывается в `FLAT`. Это значит: если бот был в позиции до рестарта, стратегия после рестарта «думает», что позиции нет. Реальную позицию бот восстанавливает через механизм реконсиляции (`HALT_RECONCILE_DIVERGENCE`, `EXIT_RECONCILE_DETECTED`), а не через внутренний FSM стратегии. `(src/risk/reason_codes.py:85, 101)`

**4. `warmup` не генерирует сигналов, но наполняет буфер.**
Важно подавать в `warmup` ровно столько исторических баров, сколько нужно для прогрева самого «голодного» индикатора. Если баров меньше, чем `max(ema_slow, 2 * adx_period) + 1`, первые реальные вызовы `on_bar` всё равно вернут `None` — индикаторы ещё не насытились. `(src/signalgen/strategy.py:90-94)`

**5. `Signal` — неизменяем после создания.**
Флаг `frozen=True` означает, что объект нельзя изменить после создания. Попытка написать `signal.side = SignalSide.FLAT` вызовет ошибку. Это намеренно: аудит-лог должен хранить именно то решение, которое приняла стратегия, без возможности его тихо переписать.

**6. Счётчик ReasonCode постепенно растёт вместе со стратегиями.**
На старте проекта было 28 кодов, к Sprint 52 стало 67. Новые коды добавляются через ADR-поправку — это не просто добавление строчки в enum, а архитектурное решение с обоснованием. История роста отражена в комментариях файла: `(src/risk/reason_codes.py:23-39)`
