# Как работает офлайн-прогноз: кэш и воспроизведение

**TL;DR:** Kronos — тяжёлая нейросеть, которую нельзя запускать «на лету» при каждой свече. Поэтому мы запускаем её заранее (офлайн) на мощном MacBook, сохраняем прогнозы в файлы и в процессе работы бота просто достаём готовый ответ из файла — так же, как берут заранее приготовленное блюдо из холодильника вместо того, чтобы готовить с нуля каждый раз.

---

## Простыми словами

Представьте повара, который готовит завтраки на неделю вперёд в воскресенье, раскладывает их по контейнерам и убирает в холодильник. Когда наступает утро понедельника — он не стоит у плиты, а просто достаёт нужный контейнер. Это быстро, предсказуемо и экономит ресурсы.

У нас то же самое:

- **Нейросеть Kronos** — это «повар». Она умеет предсказывать, какой будет цена биткоина (или другой монеты) через одну свечу. Но она тяжёлая: один прогноз требует десятки мегабайт памяти GPU и несколько секунд времени.
- **Офлайн-инференс** (офлайн-вывод прогноза) — запуск нейросети заранее, не в момент торговли, а накануне на отдельной машине (Mac M4 Pro с нужными библиотеками).
- **Кэш прогнозов** — «холодильник», папка `data/kronos_cache/` с файлами, в которых лежат готовые прогнозы. Каждый файл привязан к конкретной свече: символ, таймфрейм, момент времени.
- **Воспроизведение (replay)** — когда бот торгует и видит новую свечу, он идёт в кэш, находит нужный прогноз по «адресу» этой свечи и принимает решение.

Ключевое следствие: во время реальной торговли **torch (библиотека нейросетей) вообще не импортируется** в торговой части кода. Стратегия работает как обычный справочник: спрашивает — получает ответ — решает.

---

## Как это работает у нас

### Три фазы pipeline

```text
ФАЗА 1: ОФЛАЙН — запуск нейросети (scripts/run_kronos_s53.py)
   ↓ прогнозы для каждого бара
ФАЗА 2: ЗАПИСЬ В КЭШ (src/ml/prediction_cache.py — метод put)
   ↓ файлы в data/kronos_cache/
ФАЗА 3: ВОСПРОИЗВЕДЕНИЕ В ТОРГОВЛЕ (src/signalgen/kronos_strategy.py — on_bar)
```

Фазы 1 и 2 выполняются один раз на мощном компьютере. Фаза 3 — при каждой новой свече во время работы бота, уже без нейросети.

---

### Фаза 1 — Офлайн-инференс: запуск нейросети заранее

Запускается скрипт `scripts/run_kronos_s53.py` (подробная инструкция оператору — в [[kronos-cache-build-script]]) с переменной окружения `RUN_ML=1`. Без этой переменной скрипт только печатает инструкции и выходит — это защита от случайного запуска нейросети в CI/CD или тестах (`scripts/run_kronos_s53.py:484-507`).

Для каждого из 11 торговых наборов (символ + таймфрейм: BTCUSDT/5m, BTCUSDT/1h, ETHUSDT/1h и т.д.) скрипт проходит по историческим данным бар за баром и для каждого бара:

1. **Строит «адрес» кэша** (`CacheKey`) — семь полей, однозначно идентифицирующих этот прогноз.
2. **Проверяет, есть ли уже прогноз** — если да, пропускает (идемпотентный rebuild).
3. **Запускает нейросеть 20 раз** (`SAMPLE_COUNT = 20`, `scripts/run_kronos_s53.py:70`) — это называется ансамблем: нейросеть стохастична, каждый запуск даёт чуть другой ответ.
4. **Берёт медиану из 20 ответов** — `median_ensemble()` — и записывает один стабильный прогноз в кэш.

Параметры запуска (`scripts/run_kronos_s53.py:67-72`):

| Параметр | Значение |
|---|---|
| `DEVICE` | `"mps"` (GPU Mac M4 Pro) |
| `TEMPERATURE` | `1.0` |
| `TOP_P` | `0.9` |
| `SAMPLE_COUNT` | `20` |
| `HORIZON` | `1` (прогноз на одну свечу вперёд) |
| `SEED` | `42` |

### Структура «адреса» кэша: класс CacheKey

Каждый прогноз хранится под уникальным «адресом» — объектом `CacheKey`. Несовпадение **хотя бы одного** из семи полей означает промах (нужный прогноз не найден), и стратегия просто не торгует по этой свече (`src/ml/prediction_cache.py:34`):

```python
@dataclass(frozen=True)
class CacheKey:
    model_id: str       # идентификатор модели (например, "NeoQuasar/Kronos-base")
    weights_hash: str   # SHA-256 хэш весов модели на диске
    symbol: str         # торговая пара ("BTCUSDT")
    timeframe: str      # таймфрейм ("1h", "5m", ...)
    bar_close_ts: int   # момент закрытия свечи в секундах (Unix-время)
    params_hash: str    # SHA-256 хэш параметров запуска (T, top_p, sample_count, ...)
    device: str         # устройство ("mps", "cuda", "cpu")
```
`(src/ml/prediction_cache.py:33-47)`

**Почему именно 7 полей?** Каждое поле закрывает свой класс ошибок:
- `model_id` + `weights_hash` — «это тот же самый вес модели, что я обучал?» (как SHA-256 весов защищает от подмены модели — в [[kronos-security-weights-hash]])
- `symbol` + `timeframe` — «это тот же рынок?»
- `bar_close_ts` — «это та же конкретная свеча?»
- `params_hash` — «использовались те же настройки (температура, top_p и т.д.)?»
- `device` — «прогноз получен с того же GPU/CPU?»

#### bar_close_ts — временная метка закрытия свечи

`bar_close_ts` — это целое число: сколько секунд прошло с 1 января 1970 года до момента **закрытия** данной свечи. Формула:

```text
bar_close_ts = int((open_time + timeframe_delta).timestamp())
```

Например, свеча BTCUSDT/1h, открытая в 12:00 UTC, закрывается в 13:00 UTC. В числах: `int(datetime(2024,1,1,13,0,0, utc).timestamp())`.

Эта же формула используется и в скрипте кэш-билда (`scripts/run_kronos_s53.py:219`), и в стратегии (`src/signalgen/kronos_strategy.py:138`). Точное совпадение формулы — принципиально: любое расхождение означает промах и потерю всех прогнозов для этой свечи.

#### hash_params() — зачем хэшировать параметры

Если мы изменим хотя бы один параметр нейросети (например, `sample_count` с 20 на 10), получатся другие прогнозы. Старый кэш неприменим. `hash_params()` превращает словарь параметров в 64-символьный SHA-256 хэш — и этот хэш становится частью «адреса» кэша. Порядок ключей в словаре не важен: `{"a":1,"b":2}` и `{"b":2,"a":1}` дадут одинаковый хэш (`src/ml/prediction_cache.py:50-58`).

### Фаза 2 — Запись в кэш: класс PredictionCache

`PredictionCache` — это директория-хранилище (`data/kronos_cache/`, `scripts/run_kronos_s53.py:108`). Каждый прогноз хранится как пара файлов:

- `<ключ-sha256>.json` — сам прогноз: список чисел в текстовом виде
- `<ключ-sha256>.json.sha256` — контрольная сумма (sidecar)

#### Почему Decimal, а не float?

`Decimal` — это тип точной десятичной арифметики. Обычный `float` в Python не может хранить `0.1` точно (попробуйте: `0.1 + 0.2 != 0.3`). Для цен это критично: прогноз `40000.10` нельзя потерять в округлении. Прогнозы записываются строками (`"40000.10"`), а при чтении восстанавливаются как `Decimal("40000.10")` — без потери точности (`src/ml/prediction_cache.py:127-130`, `175`).

#### Атомарная запись (put): защита от сбоя

Метод `put()` никогда не пишет прямо в финальный файл. Сначала создаются временные файлы с суффиксом `.tmp`, потом они переименовываются атомарно через `os.replace()` — это POSIX-операция, которая либо выполняется целиком, либо не выполняется вовсе (`src/ml/prediction_cache.py:138-150`).

Порядок записи принципиален:
1. Сначала — sidecar (контрольная сумма).
2. Последним — тело прогноза.

Это гарантия: если компьютер выключится в середине записи, может остаться только «осиротевший» sidecar. При следующем чтении `get()` не найдёт оба файла и вернёт промах — **но никогда не вернёт неполный прогноз** (`src/ml/prediction_cache.py:132-137`).

#### SHA-256 sidecar — проверка целостности

Для каждого JSON-файла прогноза существует файл-напарник с контрольной суммой (SHA-256). При чтении (`get()`) сумма пересчитывается заново и сравнивается с сохранённой. Расхождение (файл повреждён, подменён или скопирован с чужой машины) трактуется как промах, и бот **не торгует**, а только выдаёт предупреждение — без исключения и остановки (`src/ml/prediction_cache.py:165-171`).

**SHA-256** (произносится «ша-256») — математический алгоритм «отпечатка пальца» для файла. Любое изменение хотя бы одного байта даёт совершенно другой 64-символьный хэш.

### Метод get() — чтение из кэша во время торговли

```python
def get(self, key: CacheKey) -> list[Decimal] | None:
```
`(src/ml/prediction_cache.py:152-175)`

Возвращает список `Decimal`-значений (прогнозы на каждый шаг горизонта) или `None` при промахе. `None` означает «прогноза нет» — не ошибку. Три условия промаха:

1. Файла с таким ключом нет (никогда не строился или ключ изменился).
2. Отсутствует sidecar-файл.
3. Контрольная сумма не совпадает (файл повреждён или подменён).

---

### median_ensemble() — зачем 20 прогонов и медиана

Нейросеть Kronos стохастична: при одинаковых данных она выдаёт чуть разные числа каждый раз. Чтобы получить стабильный, воспроизводимый прогноз, мы запускаем её 20 раз (`SAMPLE_COUNT = 20`) и берём **медиану** — среднее значение из отсортированного ряда.

Медиана устойчивее среднего арифметического: один «выброс» (случайно большое или маленькое число) не сдвигает результат. Формально для нечётного числа прогонов медиана — это ровно центральный элемент; для чётного (наш случай: 20 — чётное) — нижний из двух центральных, чтобы не делить Decimal (т.к. деление нарушило бы точность) (`src/ml/prediction_cache.py:84-89`):

```python
lower_mid = (n - 1) // 2   # для n=20: lower_mid = 9 (10-й по счёту из 20)
result.append(column[lower_mid])
```

Это называется **ансамбль по медиане** (median ensemble) — стандартная техника снижения шума нейросетевых прогнозов.

### Фаза 3 — Воспроизведение: on_bar() в KronosStrategy

Когда бот получает новую закрытую свечу, метод `on_bar()` выполняет три шага:

1. **Строит CacheKey** из параметров свечи: `bar_close_ts = int(bar.close_time.timestamp())` (`src/signalgen/kronos_strategy.py:133-141`).
2. **Запрашивает кэш**: `prediction = self._cache.get(key)` (`src/signalgen/kronos_strategy.py:142`).
3. **Принимает решение** по правилу V3 (подробнее — в [[kronos-signal-rule]]; как прогноз превращается в торговый сигнал — в [[kronos-ml-strategy]]):
   - Если `prediction` — `None` (промах): не торгует, возвращает `None`.
   - Если прогнозируемая цена выше текущей закрытой на порог (`DEFAULT_THRESHOLD = Decimal("0.006")` = 0.6%): сигнал на вход в лонг (`src/signalgen/kronos_strategy.py:151-159`).
   - Если прогнозируемая цена ниже текущей закрытой: сигнал на выход (`src/signalgen/kronos_strategy.py:161-165`).

Torch и Kronos не упоминаются в `kronos_strategy.py` совсем. Изоляция полная.

## Формулы и расчёты

### Адрес кэша (digest ключа)

```text
digest(key) = SHA-256(JSON(key, sort_keys=True))
```

Простыми словами: все 7 полей ключа собираются в строку JSON (в алфавитном порядке ключей — чтобы результат был всегда одинаковый), и эта строка пропускается через SHA-256. Результат — 64-символьный hex-код, который становится именем файла: `<этот-код>.json`.
`(src/ml/prediction_cache.py:44-47)`

### bar_close_ts — формула

```text
bar_close_ts = int((open_time + timeframe_delta).timestamp())
```

- `open_time` — момент открытия свечи (UTC datetime)
- `timeframe_delta` — длина свечи в секундах (5 мин = 300 сек, 1 час = 3600 сек)
- `.timestamp()` — перевод в количество секунд с эпохи Unix (1 января 1970 00:00 UTC)
- `int(...)` — отбрасываем дробную часть

`(scripts/run_kronos_s53.py:219, src/signalgen/kronos_strategy.py:138)`

### Медиана ансамбля

```text
sorted_column = sorted([sample[step] for sample in samples])
result[step] = sorted_column[(n - 1) // 2]
```

Для n=20 прогонов: берём элемент с индексом 9 (10-й из 20, если считать с единицы). Decimal-деление не производится — точность сохраняется.
`(src/ml/prediction_cache.py:84-89)`

## Примеры / сценарии

### Пример 1 — удачное попадание в кэш (HIT)

**Сценарий:** торгует пара BTCUSDT/1h. Бот получает свечу, закрытую в 13:00 UTC 1 января 2024.

1. Скрипт офлайн-инференса ранее уже обработал эту свечу:
   - Запустил Kronos 20 раз с параметрами T=1.0, top_p=0.9, horizon=1.
   - Получил 20 прогнозов закрытия следующей свечи.
   - Взял медиану: `Decimal("42153.77")`.
   - Записал файл `data/kronos_cache/<хэш-ключа>.json` и sidecar.

2. В `on_bar()` стратегия строит ключ:
   - `model_id = "NeoQuasar/Kronos-base"`, `symbol = "BTCUSDT"`, `timeframe = "1h"`
   - `bar_close_ts = int(datetime(2024,1,1,13,0,0,tzinfo=UTC).timestamp())` = `1704114000`
   - `params_hash = SHA-256({"T":1.0,"top_p":0.9,"sample_count":20,"horizon":1,"seed":42})`

3. `get(key)` → файл найден, sidecar совпадает → возвращает `[Decimal("42153.77")]`.

4. Текущая закрытая цена свечи: `Decimal("41900.00")`.
   - Условие входа: `42153.77 > 41900.00 * (1 + 0.006) = 42151.40`? Да!
   - Стратегия выдаёт сигнал `ENTRY_LONG_KRONOS`.

### Пример 2 — промах (MISS): изменили параметры

Оператор перезапустил скрипт с `--sample-count 10` вместо 20. Это изменяет `params_hash`. Все ключи в кэше теперь ссылаются на старый `params_hash` — стратегия с новым `params_hash` не найдёт ни одного прогноза. Бот просто не торгует, пока не будет проведён полный rebuild кэша с новыми параметрами.

### Пример 3 — промах: повреждённый файл

Кто-то вручную отредактировал JSON-файл прогноза. SHA-256 пересчитывается при чтении и не совпадает с sidecar. `get()` выдаёт предупреждение `UserWarning` и возвращает `None` — бот не торгует этой свечой, но не падает.

## Подводные камни / что важно понимать

**1. Кэш не в репозитории.** `data/kronos_cache/` прописан в `.gitignore`. Если склонировать проект на новую машину — кэша нет. Нужен полный rebuild офлайн-инференса (`scripts/run_kronos_s53.py`).

**2. Смена параметров = обязательный rebuild.** Изменение любого поля, входящего в `CacheKey`, делает старые записи невидимыми для новой конфигурации. Особенно важно: смена весов модели (обновление вариanta Kronos) меняет `weights_hash` — весь кэш становится «мёртвым» и место на диске занимает зря (`scripts/run_kronos_s53.py:495-496`).

**3. Промах — не ошибка, а тихое пропускание.** При промахе `on_bar()` возвращает `None`. Бот не торгует этой свечой и не сигнализирует проблему. Если прогнозы не были построены для части истории — бот просто пропустит эти свечи. Это может создать иллюзию, что «бот работает», тогда как на самом деле он не торгует из-за пустого кэша.

**4. bar_close_ts и `is_closed`.** Стратегия проверяет `bar.is_closed` (одно из полей [[bar-model|свечи Bar]]) перед чтением кэша (`src/signalgen/kronos_strategy.py:120-121`). Незакрытые свечи игнорируются — это защита от look-ahead bias (заглядывания в будущее); в live-режиме этой же ловушкой занимается отдельный страж — см. [[bar-source-live]].

**5. Скорость: ~801 мс на бар при `sample_count=20`.** Полный rebuild 29 000 баров BTC/1h с 20 прогонами занял бы ~6,5 часов. Поэтому в скрипте есть параметр `--max-bars N` — строить кэш только для последних N баров (`scripts/run_kronos_s53.py:413-418`).

**6. FAST-режим vs V4-точный.** Флаг `--fast` меняет метод: вместо 20 отдельных запусков + медиана — один запрос с внутренним усреднением (mean). Это в ~4 раза быстрее, но менее точно методологически (`scripts/run_kronos_s53.py:462-466`).

**7. Претрейн-утечка (data leakage).** BTC/USDT подтверждённо входит в обучающую выборку нейросети Kronos. Все бэктест-результаты несут пометку `VERDICT_RAW_PRETRAIN_LEAKAGE_SUSPECTED` и считаются исследовательскими, не боевыми. Подробнее — в [[kronos-data-leakage]].

- [[kronos-mock-adapter]] — заглушка `MockKronosAdapter`, которой заменяют нейросеть в тестах (проверка, что кэш и стратегия правильно принимают прогноз)
- [[bar-model]] — структура свечи `Bar` и поле `is_closed`/`close_time`, из которого строится `bar_close_ts` в ключе кэша
- [[bar-source-live]] — тот же look-ahead-барьер (отбрасывание незакрытых свечей) в live-источнике данных
