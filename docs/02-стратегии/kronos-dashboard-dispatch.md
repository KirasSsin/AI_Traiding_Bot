# Kronos в дэшборде: как работает dispatch и покрытие кэша

**TL;DR:** Когда вы нажимаете «Запустить бэктест» для стратегии Kronos, дэшборд НЕ запускает нейросеть — он читает заранее записанные ответы из файла-кэша. Этот модуль отвечает за три вещи: понять, есть ли кэш, взять из него правильные данные (по «паспорту» модели), и честно сказать пользователю, если кэша нет.

---

## Простыми словами

Представьте, что вы заказываете в ресторане фирменное блюдо, которое готовится заранее и лежит в холодильнике. Официант (дэшборд) принимает ваш заказ, идёт на кухню и ищет именно ваш контейнер. Но чтобы взять **правильный** контейнер, он должен знать: какой шеф-повар готовил, какой рецепт использовал и для какого зала. Эта информация записана на «ярлыке» контейнера — в нашем случае это файл `_manifest.json`.

Если холодильник пуст (кэш не собран) — официант не говорит «система упала», а честно отвечает: «Это блюдо нужно заказать заранее — вот инструкция».

Если холодильник есть, но ваш заказ не совпадает с тем, что там лежит (вы хотите вариант `mini`, а кэш собран для `base`) — тоже честный ответ без аварии.

Такой подход называется **«dispatch»** — маршрутизация запроса к нужному источнику данных. В нашем случае это `src/dashboard/_kronos_dispatch.py`.

## Как это работает у нас

### Шаг 1 — откуда вызывается dispatch

Когда фронтенд дэшборда отправляет запрос на бэктест, сервер смотрит на поле `type` в описании стратегии. Если `type == "kronos"` — вся логика передаётся в функцию `run_kronos_dispatch()`. Это единственная точка входа для всей Kronos-ветки.

```python
# src/dashboard/backtest_runner.py:1104-1114
if preset.get("type") == "kronos":
    from src.dashboard._kronos_dispatch import run_kronos_dispatch
    return run_kronos_dispatch(
        req,
        preset=preset,
        run_id=run_id,
        cache_path=cache_path,
        runs_dir=_RUNS_DIR,
        cache_dir=_KRONOS_CACHE_DIR,
    )
```

Важная деталь: в этом модуле **torch (библиотека нейросетей) не импортируется вообще**. Никакого запуска нейросети — только чтение готовых файлов. Это сделано намеренно: нейросеть тяжёлая и требует специального оборудования, её работа происходит отдельно (см. [[kronos-offline-predict-cache]]).

### Шаг 2 — список разрешённых пар (11 комбо)

Прежде чем делать что-либо ещё, функция проверяет, поддерживается ли запрошенная комбинация «монета + таймфрейм». В коде жёстко прописаны 11 разрешённых комбо (`_KRONOS_PARQUET_BY_COMBO`, `src/dashboard/_kronos_dispatch.py:29-41`):

| Монета | Таймфреймы |
|--------|------------|
| BTCUSDT | 5m, 15m, 1h, 4h, 1d |
| ETHUSDT | 15m, 1h, 4h |
| SOLUSDT | 15m, 1h, 4h |

Если запрошена другая пара — `run_kronos_dispatch()` выбрасывает ошибку с понятным сообщением, что запрошенная комбинация не поддерживается (`src/dashboard/_kronos_dispatch.py:222-226`).

### Шаг 3 — чтение манифеста (`_read_kronos_manifest`)

**Манифест** — это небольшой файл `data/kronos_cache/_manifest.json`, который скрипт построения кэша записывает рядом с предсказаниями. В манифесте хранится «паспорт» модели: какой именно вариант нейросети создал кэш, по какому рецепту (хэш параметров), с каких устройств (CPU / MPS) и какие свечи покрыты.

Функция `_read_kronos_manifest()` (`src/dashboard/_kronos_dispatch.py:58-77`) делает одно простое действие — читает этот JSON-файл. Если файла нет или он повреждён — возвращает `None`.

Это принципиальное различие:
- Манифест **отсутствует** → кэш вообще не построен → честный ответ «запусти скрипт».
- Манифест **есть**, но предсказание для конкретной свечи не нашлось → легитимный «промах» (0 сделок), а не «кэш не готов».

### Шаг 4 — конвертация таймфрейма (`_INTERVAL_TO_TIMEFRAME`)

Дэшборд говорит с пользователем на языке чисел: «60» означает 60 минут. Стратегия Kronos говорит на другом языке: «1h». Словарь `_INTERVAL_TO_TIMEFRAME` (`src/dashboard/_kronos_dispatch.py:160-166`) переводит между системами:

```text
"5"   → "5m"
"15"  → "15m"
"60"  → "1h"
"240" → "4h"
"D"   → "1d"
```

Без этого перевода ключ поиска в кэше не совпал бы — запрашивали бы «60», а кэш хранит «1h».

### Шаг 5 — сборка ключа кэша из манифеста

Это самая важная часть — и здесь есть история. До Sprint 52 дэшборд использовал жёстко прошитые заглушки: `model_id="kronos"`, `weights_hash="unknown"`, `device="cpu"`. Кэш при этом реально собирался с настоящими значениями (например, `model_id="NeoQuasar/Kronos-base"`, реальный [[kronos-security-weights-hash|хэш весов]], `device="mps"` на MacBook). Результат: **100% промахов** — дэшборд искал не то, что там лежало.

Теперь значения берутся из манифеста (`src/dashboard/_kronos_dispatch.py:248-257`):

```python
params_kr = {
    "model_id":    combo_entry.get("model_id",    manifest_kr.get("model_id", "kronos")),
    "weights_hash": combo_entry.get("weights_hash", manifest_kr.get("weights_hash", "unknown")),
    "params_hash":  combo_entry.get("params_hash",  manifest_kr.get("params_hash", "unknown")),
    "device":      combo_entry.get("device",       manifest_kr.get("device", "cpu")),
}
```

Приоритет: сначала смотрим в запись для конкретного комбо (schema v2), потом — в верхнеуровневые поля манифеста (schema v1, fallback). Это позволяет хранить в одном кэше разные варианты модели и разные настройки одновременно.

### Шаг 6 — поиск комбо-записи для schema v2 (`_find_combo_entry`)

Schema v2 — это усовершенствованный формат манифеста (введён в Sprint 54). В нём каждое комбо «монета + таймфрейм» несёт **собственный** набор параметров. Это важно, если вы строили кэш сначала для `base`, потом для `mini` — они могут мирно сосуществовать в одном манифесте с разными `model_id`.

Функция `_find_combo_entry()` (`src/dashboard/_kronos_dispatch.py:80-94`) просто проходит по массиву `combos[]` в манифесте и ищет запись, где `symbol` и `timeframe` совпадают с запрошенными.

### Шаг 7 — проверка варианта модели (variant-mismatch guard)

**Вариант модели** — это `base` или `mini` (см. [[kronos-what-is-it]] про разницу). После чтения манифеста дэшборд проверяет: `model_id` из манифеста совпадает ли с `model_id` запрошенного варианта?

Например:
- Вы нажали «mini» в UI → `requested_variant.model_id = "NeoQuasar/Kronos-mini"`
- В манифесте написано `model_id = "NeoQuasar/Kronos-base"`
- Несовпадение → кэш собран под другой вариант

В этом случае `run_kronos_dispatch()` возвращает структурированный ответ `kronos_variant_not_cached` с понятным сообщением без аварии (`src/dashboard/_kronos_dispatch.py:316-349`). Бот не падает, не запускает стратегию с чужими данными — просто честно сообщает о проблеме.

### Шаг 8 — ветка «кэш не построен»

Если `_read_kronos_manifest()` вернул `None` — кэша нет совсем. Функция возвращает структурированный результат `kronos_cache_absent` (`src/dashboard/_kronos_dispatch.py:272-309`) с [[verdict-and-warnings|предупреждением]]:

```text
"Kronos predictions not cached yet — run
 `RUN_ML=1 scripts/run_kronos_s53.py` on M4 first."
```

Результат всё равно записывается на диск (атомарная запись через `atomic_write_text`) — чтобы следующий одинаковый запрос взял ответ из кэша, не повторяя проверку.

### Шаг 9 — ветка «кэш есть, запускаем replay»

Если манифест прочитан и вариант совпал — наконец загружаем исторические данные и запускаем воспроизведение предсказаний:

1. `_load_kronos_df()` читает parquet-файл с ценовыми свечами для нужной пары и обрезает по датам (`src/dashboard/_kronos_dispatch.py:97-152`).
2. `run_kronos_exploratory()` из `src/backtest/kronos_runner.py` прогоняет [[kronos-signal-rule|торговую логику]] (порог роста 0.6%), доставая готовые предсказания из кэша бар за баром (см. [[kronos-backtest-runner]]).
3. Результат упаковывается в стандартный конверт и записывается на диск.

Вердикт (`verdict`) жёстко зафиксирован как `RAW_PRETRAIN_LEAKAGE_SUSPECTED` (ADR 0068) — независимо от числа сделок или качества прогнозов. Это не ошибка, а честная пометка: данные BTC присутствуют в предобучающей выборке Kronos, поэтому любой backtest на этих данных может быть «загрязнён» (см. [[kronos-data-leakage]]).

## Coverage API: как дэшборд знает, что закрашивать серым

### Что это такое

**Coverage API** (API покрытия кэша) — это специальный эндпоинт, который фронтенд вызывает при открытии страницы стратегии Kronos. Он возвращает список: для каких комбо (монета + таймфрейм) в кэше есть данные и за какой период.

На практике это означает: кнопки комбо, для которых кэш не собран, автоматически блокируются в UI. Поля «Начало» и «Конец» автозаполняются реальными датами из кэша (чтобы пользователь не вводил период, которого там нет).

### Эндпоинт

```text
GET /api/kronos/coverage
```

Ответ (`src/dashboard/app.py:206-208`):
```json
{"coverage": [
  {"symbol": "BTCUSDT", "timeframe": "1h", "start_iso": "2022-01-01", "end_iso": "2023-12-31", "n_entries": 8760},
  ...
]}
```

### Функция `kronos_coverage()`

`src/dashboard/_kronos_dispatch.py:394-432`. Читает тот же `_manifest.json` через `_read_kronos_manifest()`. Если манифеста нет — возвращает пустой список (`[]`), и UI покажет все комбо как «не готово».

Для каждой записи в `combos[]` манифеста функция:
1. Читает `first_bar_ts` и `last_bar_ts` — Unix-временные метки первой и последней свечи в кэше (секунды UTC).
2. Переводит их в строки формата `YYYY-MM-DD`.
3. Возвращает также `n_entries` — сколько предсказаний записано для этого комбо.

Комбо, у которых нет временных меток (например, кэш собирался по старой schema v1 без этих полей) — возвращают пустые строки `""`, что UI интерпретирует как «не готово».

## Примеры / сценарии

### Сценарий 1: всё хорошо

1. Оператор заранее запустил [[kronos-cache-build-script|`RUN_ML=1 scripts/run_kronos_s53.py`]] → в `data/kronos_cache/` появился `_manifest.json` и файлы предсказаний.
2. Пользователь открывает дэшборд → вызывается `/api/kronos/coverage` → фронтенд видит список доступных комбо и автозаполняет даты.
3. Пользователь выбирает BTCUSDT / 1h / base, нажимает «Запустить» → `run_kronos_dispatch()` читает манифест, собирает правильные ключи, загружает OHLCV, запускает replay → получает результаты.

### Сценарий 2: кэш не построен

1. Кэш ещё не собирался → `data/kronos_cache/_manifest.json` отсутствует.
2. Вызов `/api/kronos/coverage` → `kronos_coverage()` возвращает `[]` → все комбо заблокированы в UI.
3. Если пользователь всё же как-то запустил бэктест → `run_kronos_dispatch()` видит `manifest_kr is None` → возвращает результат с предупреждением `kronos_cache_absent`. Никакой аварии.

### Сценарий 3: вариант не совпадает

1. Кэш собран для варианта `base` → в манифесте `model_id = "NeoQuasar/Kronos-base"`.
2. Пользователь выбирает вариант `mini` → `requested_variant.model_id = "NeoQuasar/Kronos-mini"`.
3. Проверка: `"NeoQuasar/Kronos-base" != "NeoQuasar/Kronos-mini"` → возвращается предупреждение `kronos_variant_not_cached`. Никакой аварии, понятное сообщение.

### Сценарий 4: запрошена неподдерживаемая пара

1. Пользователь запрашивает XRPUSDT / 1h.
2. `run_kronos_dispatch()` проверяет `preset["supported_combos"]` — такой комбинации нет.
3. Выбрасывается `ValueError` с сообщением: «Kronos не поддерживает эту комбинацию. Поддерживаемые: [...11 комбо...]».

## Подводные камни / что важно понимать

**Кэш и manifest неразделимы.** Если вы вручную скопировали файлы предсказаний без манифеста — дэшборд не будет их видеть и скажет «кэш не построен». Манифест — это обязательный «ярлык», без него содержимое холодильника считается пустым.

**Отсутствие предсказания ≠ отсутствие кэша.** Если кэш собран, но для конкретной свечи не нашлось предсказания (например, вы просили данные за 2020 год, а кэш собран за 2022–2023) — это нормальный промах, не «кэш не построен». Функция вернёт 0 сделок за этот период, не ошибку.

**100% промах без манифеста — историческая проблема.** До Sprint 52 дэшборд использовал жёстко вшитые заглушки как ключи поиска. Поскольку они никогда не совпадали с реальными ключами кэша, пользователь всегда видел 0 сделок, даже если кэш был корректно собран. Сейчас ключи берутся из манифеста — промахи только по реальным несовпадениям.

**Schema v1 vs v2.** Старые кэши, собранные до Sprint 54, содержат манифест формата v1 (без `combos[]`). Dispatch умеет работать с обоими форматами: сначала ищет per-combo запись (v2), при её отсутствии использует верхнеуровневые поля (v1). Если вы обновили скрипт построения кэша, но не пересобрали сам кэш — работа идёт по старому манифесту.

**Вердикт всегда `RAW_PRETRAIN_LEAKAGE_SUSPECTED`.** Это не ошибка кода и не плохой результат стратегии — это предупреждение исследователя. Kronos претренировалась на данных, которые включают BTC. Доверять бэктесту на этих же данных нельзя. Подробнее — в [[kronos-data-leakage]].

**Torch не загружается в этом модуле.** Если вы видите ошибку импорта torch при запуске бэктеста Kronos через дэшборд — это ошибка приходит из другого места (не из этого файла). `_kronos_dispatch.py` принципиально не импортирует torch.
