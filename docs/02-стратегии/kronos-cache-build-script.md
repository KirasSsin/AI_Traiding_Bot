# Как запустить построение кэша прогнозов (run_kronos_s53.py)

**TL;DR:** `run_kronos_s53.py` — это скрипт для ручного запуска. Он заставляет нейросетевую модель [[kronos-ml-strategy|Kronos]] «просмотреть» всю историю 11 пар символ + таймфрейм и заранее записать прогнозы в папку-кэш. Затем торговый бот берёт готовые прогнозы оттуда — быстро и без запуска тяжёлой нейросети в реальном времени. Это средняя часть [[kronos-offline-predict-cache|трёхэтапного pipeline «офлайн-прогноз → кэш → воспроизведение»]].

## Простыми словами

Представьте, что у вас есть аналитик, который умеет читать графики и давать прогнозы, но работает очень медленно — один прогноз занимает секунду. Если бот будет спрашивать его каждые несколько секунд в реальном времени, это нереально.

Решение: **заранее**, до начала торговли, усадить аналитика прочитать всю историю цен с самого начала и записать каждый прогноз в блокнот. Во время торговли бот просто достаёт нужный лист из блокнота — это занимает миллисекунды.

`run_kronos_s53.py` — это и есть «сессия работы аналитика». Вы запускаете его вручную на мощном компьютере (Mac M4 Pro), он идёт по каждому историческому бару, просит Kronos сделать прогноз, и сохраняет результат в файл. Потом скрипт запускает быстрый пробный бэктест, чтобы сразу увидеть, как бот торговал бы на этих прогнозах.

**Важное честное предупреждение.** BTC/USDT подтверждённо входит в обучающий набор данных нейросети Kronos. Это значит, что результаты бэктеста по BTC могут выглядеть лучше, чем они будут в реальности — модель уже «видела» эти данные раньше. Поэтому все результаты помечаются вердиктом `VERDICT_RAW_PRETRAIN_LEAKAGE_SUSPECTED` («подозрение на [[kronos-data-leakage|утечку]]»). Скрипт носит **исследовательский** характер. Единственная честная проверка — реальное или бумажное форвард-тестирование (ADR 0068, `scripts/run_kronos_s53.py:17-21`).

## Как это работает у нас

### Шаг 0. Защитный замок — RUN_ML

Без специального флага скрипт не делает ничего тяжёлого. При запуске без флага:

```bash
.venv/bin/python scripts/run_kronos_s53.py
```

он просто напечатает инструкцию и завершится. Нейросеть (`torch`) вообще не загружается. Это сделано намеренно: загрузка модели занимает время и оперативную память, поэтому запуск должен быть явно разрешён оператором (`scripts/run_kronos_s53.py:64`):

```python
RUN_ML: bool = os.environ.get("RUN_ML") == "1"
```

Правильный запуск:

```bash
RUN_ML=1 .venv/bin/python scripts/run_kronos_s53.py --variant base
```

### Шаг 1. Выбор варианта модели

Kronos существует в двух вариантах — `base` и `mini` (`scripts/run_kronos_s53.py:404-408`):

| Вариант | Модель HuggingFace | Контекст (баров) |
|---|---|---|
| `base` (по умолчанию) | `NeoQuasar/Kronos-base` | 512 |
| `mini` | `NeoQuasar/Kronos-mini` | 2048 |

«Контекст» — это сколько предыдущих баров модель видит, делая прогноз. `mini` видит дальше, но использует другой токенизатор и другие веса, поэтому его кэш несовместим с кэшем `base`. При смене варианта нужно полностью перестраивать кэш (подробнее — в разделе «Подводные камни»).

Параметры вариантов определены в `src/ml/kronos_variant.py:33-49`.

### Шаг 2. Вычисление хешей — «отпечатки» параметров

До начала работы скрипт вычисляет два «отпечатка» (хеша). Хеш — это способ закодировать большой набор данных в короткую строку так, чтобы при любом изменении строка менялась.

**`weights_hash`** — SHA-256 отпечаток фактических файлов весов модели и токенизатора на диске (`src/ml/weights_hash.py:47-112`). Тот же хеш служит защитой от подмены модели — подробно в [[kronos-security-weights-hash]]. Если модель обновится, хеш изменится, и старый кэш станет недействительным. Если файлы ещё не скачаны, используется запасной вариант: хеш от строки вида `model_id@revision|tokenizer_id@revision`, чтобы разные версии модели никогда не смешивались.

**`params_hash`** — SHA-256 отпечаток параметров сэмплирования: температуры, top_p, sample_count, горизонта прогноза, seed (`src/ml/prediction_cache.py:50-58`). Если изменить любой из этих параметров, старый кэш не подойдёт — нужно строить новый.

Значения по умолчанию, прошитые в скрипте (`scripts/run_kronos_s53.py:67-72`):

| Параметр | Значение | Что означает |
|---|---|---|
| `DEVICE` | `"mps"` | Процессор Apple (M-серия) |
| `TEMPERATURE` | `1.0` | Степень «случайности» модели |
| `TOP_P` | `0.9` | Ограничение выборки токенов |
| `SAMPLE_COUNT` | `20` | Число прогонов модели на один бар |
| `HORIZON` | `1` | Прогноз на 1 бар вперёд |
| `SEED` | `42` | Зерно воспроизводимости (случайность фиксирована) |

**Зерно воспроизводимости (seed)** — это как выбор стартовой точки для генератора случайных чисел. При одинаковом seed и одинаковых параметрах модель всегда даёт одинаковый результат. Это важно: один и тот же ключ кэша должен всегда давать один и тот же прогноз (`scripts/run_kronos_s53.py:529`).

### Шаг 3. 11 комбо — какие пары и таймфреймы строятся

Скрипт обходит 11 комбинаций символ + таймфрейм (ADR 0068 scope, `scripts/run_kronos_s53.py:83-95`):

| Символ | Таймфреймы |
|---|---|
| BTCUSDT | 5m, 15m, 1h, 4h, 1d |
| ETHUSDT | 15m, 1h, 4h |
| SOLUSDT | 15m, 1h, 4h |

BTC получает больше всего таймфреймов как наиболее ликвидный актив. ETH и SOL — по три среднесрочных таймфрейма. Очень короткие (1m) и очень длинные интервалы не включены: 1m — слишком много баров и шума, а дневной (1d) есть только у BTC.

Данные читаются из файлов формата **[[parquet-storage|parquet]]** (`data/BTCUSDT_1h.parquet` и т.д.). Parquet — это эффективный колоночный формат хранения таблиц, который занимает меньше места, чем CSV, и читается значительно быстрее.

Перед обработкой функция `_normalize_df()` (`scripts/run_kronos_s53.py:136-154`) приводит данные к единому виду: находит столбец с временной меткой (может называться `ts`, `time` или `timestamp`), конвертирует в UTC-время и оставляет только нужные колонки: `_ts, open, high, low, close, volume`.

Если файла нет или в нём меньше 50 баров, комбо пропускается с предупреждением (`scripts/run_kronos_s53.py:612`).

### Шаг 4. Построение кэша — функция `_build_cache_for_combo()`

Это главный цикл скрипта (`scripts/run_kronos_s53.py:172-263`). Для каждого бара из истории:

**4.1. Вычисляем ключ кэша (CacheKey)**

Ключ — это «адрес» прогноза. Он состоит из 7 полей (`src/ml/prediction_cache.py:33-47`):

```python
CacheKey(
    model_id=...,        # какая модель
    weights_hash=...,    # какие веса
    symbol=...,          # BTCUSDT / ETHUSDT / SOLUSDT
    timeframe=...,       # 5m / 15m / 1h / 4h / 1d
    bar_close_ts=...,    # временная метка закрытия бара (секунды UTC)
    params_hash=...,     # параметры сэмплирования
    device=...,          # mps
)
```

`bar_close_ts` вычисляется как (`scripts/run_kronos_s53.py:218-219`):

```python
bar_close_ts = int((open_time + td).timestamp())
```

Где `open_time` — время открытия бара (из столбца `_ts`), `td` — длительность таймфрейма (например, 1 час). Это целое число секунд с начала эпохи Unix — уникальный идентификатор конкретного момента.

**Эта же формула** используется в `KronosStrategy.on_bar()` при живой торговле, что гарантирует совпадение ключей кэша со стороны построения и со стороны чтения (`src/backtest/kronos_runner.py:119-120`).

**4.2. Проверяем: уже в кэше?**

Если прогноз для этого ключа уже записан — пропускаем. Это делает скрипт **идемпотентным**: если прервать и перезапустить, уже готовая работа не будет переделана (`scripts/run_kronos_s53.py:239-240`).

**4.3. Запускаем модель 20 раз**

Модель запрашивается `SAMPLE_COUNT = 20` раз для одного и того же бара. Зачем? Языковые модели имеют элемент случайности — каждый вызов может дать немного разный результат. Двадцать прогонов позволяют получить стабильную оценку (`scripts/run_kronos_s53.py:250-254`).

**4.4. Берём медиану — функция `median_ensemble()`**

Из 20 прогнозов берётся медиана — среднее значение после сортировки, которое отфильтровывает крайние выбросы лучше, чем среднее арифметическое. При чётном числе выборок берётся нижний из двух средних элементов (без усреднения, чтобы сохранить точное десятичное значение — V4 determinism, `src/ml/prediction_cache.py:61-90`).

**4.5. Записываем в кэш**

Результат сохраняется как JSON-файл с именем `<SHA-256 от ключа>.json` и рядом файл-контрольная-сумма `.json.sha256`. При чтении сумма проверяется — если файл повреждён, кэш вернёт «промах» (miss) вместо ошибки (`src/ml/prediction_cache.py:118-151`).

### Шаг 5. Ограничитель --max-bars

Полная история BTC по таймфрейму 1h — около 29 000 баров. При 20 прогонах на каждый это **580 000 обращений к нейросети**. При скорости 801 мс/бар (на M4 MPS при 20 образцах) это заняло бы около 6.5 часов только для одного комбо. Для исследовательских запусков разумнее строить только последние N баров:

```bash
RUN_ML=1 .venv/bin/python scripts/run_kronos_s53.py --max-bars 500
```

При `--max-bars 500` скрипт строит кэш только для последних 500 баров, но при этом передаёт модели **всю предыдущую историю как контекст** — ранние бары нужны модели, чтобы «вспомнить» рыночный контекст, но их прогнозы не сохраняются (`scripts/run_kronos_s53.py:213`).

### Шаг 6. Режим --fast

По умолчанию: 20 **отдельных** вызовов модели → медиана результатов. Это V4-точный режим.

С флагом `--fast`: **один** вызов модели, но внутри него Kronos делает 20 внутренних путей и усредняет их (mean, а не median). Итог примерно в 4 раза быстрее, но есть небольшое методологическое отклонение от стандартного режима (`scripts/run_kronos_s53.py:551-552`):

```python
internal_paths = sample_count if args.fast else 1
n_draws = 1 if args.fast else sample_count
```

Для исследовательских запусков `--fast` приемлем. Для «официального» кэша, который будет использоваться в торговле, рекомендуется стандартный режим (median).

Ориентиры скорости на M4 MPS при разных `--sample-count` (`scripts/run_kronos_s53.py:444`):

| sample_count | Время/бар |
|---|---|
| 20 (по умолчанию) | ~801 мс |
| 10 | ~390 мс |
| 5 | ~196 мс |
| 1 | ~47 мс |

### Шаг 7. Фильтры --symbols и --timeframes

Вместо всех 11 комбо можно запустить одно:

```bash
RUN_ML=1 .venv/bin/python scripts/run_kronos_s53.py --symbols BTCUSDT --timeframes 1h --max-bars 200
```

Фильтры работают как пересечение: из списка `COMBOS` остаются только те, что одновременно входят в оба фильтра (`scripts/run_kronos_s53.py:578-584`).

### Шаг 8. Пробный бэктест

После построения кэша для каждого комбо скрипт сразу запускает `run_kronos_exploratory()` — это быстрый [[kronos-exploratory-runner|разведочный прогон]] торговой стратегии по уже записанным прогнозам (без нейросети). Порог входа в сделку — `threshold = "0.006"` (0.6% прогнозируемого движения, `scripts/run_kronos_s53.py:665`) — само правило входа/выхода описано в [[kronos-signal-rule]].

Результаты печатаются на экран и сохраняются в `data/kronos_s53_results/kronos_s53_{symbol}_{timeframe}.json`. Детали бэктеста описаны в [[kronos-backtest-runner]].

### Шаг 9. Манифест — «паспорт кэша»

После обхода всех комбо записывается файл `data/kronos_cache/_manifest.json` — сводный документ, описывающий содержимое кэша (`scripts/run_kronos_s53.py:266-314`).

Манифест версии 2 (schema_version = 2, `scripts/run_kronos_s53.py:118`) содержит:

- Верхнеуровневые поля: `model_id`, `weights_hash`, `params_hash`, `device` — для совместимости со старыми читателями (v1).
- Список `combos`: каждое комбо самоописывает себя — свой `model_id`, `weights_hash`, `params_hash`, `device`, `first_bar_ts`, `last_bar_ts`, `n_entries`. Это важно: разные комбо могут быть построены с разными параметрами и спокойно сосуществуют в одном манифесте.

Манифест **объединяется** с существующим: если запустить скрипт для одного комбо, уже записанные комбо не исчезают из манифеста (`scripts/run_kronos_s53.py:291-298`).

Дэшборд читает манифест, чтобы знать, какие комбо покрыты кэшем, и строить ключи для поиска прогнозов. Подробнее — в [[kronos-dashboard-dispatch]].

### Шаг 10 (опциональный). Обновление манифеста --rebuild-manifest

Если манифест был создан старой версией скрипта (v1, без `first_bar_ts`/`last_bar_ts` на комбо), его можно обновить **без запуска нейросети**:

```bash
.venv/bin/python scripts/run_kronos_s53.py --rebuild-manifest
```

Обратите внимание: `RUN_ML=1` не нужен — скрипт только читает существующий манифест и parquet-файлы и вычисляет временные метки по той же формуле `bar_close_ts` (`scripts/run_kronos_s53.py:317-393`).

## Формулы и расчёты

### Ключ кэша: bar_close_ts

```
bar_close_ts = int((open_time + timeframe_delta).timestamp())
```

**Расшифровка простыми словами:** берём момент открытия бара (например, 01 июня 2024 15:00:00 UTC), прибавляем длительность таймфрейма (1 час → получаем 16:00:00), конвертируем в количество секунд с начала Unix-эпохи (1 января 1970). Результат — целое число, например `1717250400`. Это и есть уникальный «адрес» бара во времени.

Реализация: `scripts/run_kronos_s53.py:219`, зеркально — `src/backtest/kronos_runner.py:119-120`.

### Медиана из N образцов

```
prediction = median_ensemble([pred_1, pred_2, ..., pred_20])
```

Для каждой позиции горизонта прогноза (у нас horizon=1, то есть 1 шаг): берём 20 значений от 20 прогонов, сортируем, берём элемент с индексом `(20 - 1) // 2 = 9` (нижний из двух средних). Медиана устойчива к выбросам — если одна из 20 попыток дала аномальный результат, общий прогноз не испортится.

При чётном числе образцов берётся нижний средний — без усреднения двух соседних элементов, чтобы хранить точное десятичное число (`src/ml/prediction_cache.py:85`).

## Примеры / сценарии

### Исследовательский запуск: последние 200 баров BTC 1h

```bash
# Установка зависимостей (один раз)
pip install -e ".[ml]"

# Запуск: только BTC 1h, последние 200 баров, быстрый режим
RUN_ML=1 .venv/bin/python scripts/run_kronos_s53.py \
    --variant base \
    --symbols BTCUSDT \
    --timeframes 1h \
    --max-bars 200 \
    --fast
```

Что происходит:
1. Скрипт загружает `data/BTCUSDT_1h.parquet` — допустим, 29 000 баров.
2. Берёт только последние 200 для построения кэша.
3. Для каждого из 200 баров: проверяет кэш → если MISS → 1 вызов модели с 20 внутренними путями (fast-режим) → записывает прогноз.
4. Запускает пробный бэктест на этих 200 барах.
5. Пишет манифест в `data/kronos_cache/_manifest.json`.

На M4 MPS в fast-режиме: ~200 мс/бар × 200 баров ≈ примерно 40 секунд на построение (без накладных расходов загрузки модели). Откуда 200 мс? В таблице скоростей строка `sample_count=1` даёт 47 мс — но это один внутренний путь. В `--fast`-режиме адаптер строится с `sample_count=20` внутренних путей (`scripts/run_kronos_s53.py:551,561`), то есть один вызов делает ровно столько же работы, сколько 20 путей, но передаёт их векторизованно. Это и даёт «примерно в 4 раза быстрее» стандартного режима: 801 мс ÷ 4 ≈ 200 мс/бар (`scripts/run_kronos_s53.py:444,551`).

### Полный запуск: все 11 комбо

```bash
RUN_ML=1 .venv/bin/python scripts/run_kronos_s53.py \
    --variant base \
    --max-bars 500
```

Скрипт обходит все 11 комбо по очереди, строит кэш для последних 500 баров каждого, запускает 11 пробных бэктестов, пишет сводный JSON в `data/kronos_s53_results/kronos_s53_summary.json`.

### Обновление манифеста без нейросети

```bash
# RUN_ML не нужен
.venv/bin/python scripts/run_kronos_s53.py --rebuild-manifest
```

Полезно после обновления скрипта, если старый манифест версии v1 не содержит `first_bar_ts`/`last_bar_ts`.

## Подводные камни / что важно понимать

**1. Смена варианта = полная перестройка кэша.**
Если переключить `--variant mini` после `--variant base`, все существующие записи кэша станут промахами (MISS). Причина: `weights_hash` отличается (другие файлы весов), и ключ кэша не совпадает. Дашборд будет видеть пустой кэш. Хранить два кэша одновременно — нельзя (они пишутся в одну директорию `data/kronos_cache/`). Подробнее: `scripts/run_kronos_s53.py:492-495`.

**2. Данные никогда не публикуются в репозитории.**
Оба выходных каталога — `data/kronos_cache/` и `data/kronos_s53_results/` — находятся в `.gitignore`. Прогнозы могут содержать информацию о весах модели (через `weights_hash`), и они специфичны для конкретного железа. Передавать кэш между машинами нужно вручную.

**3. Результаты бэктеста — только исследование.**
Вердикт `VERDICT_RAW_PRETRAIN_LEAKAGE_SUSPECTED` означает: BTC/USDT был в обучающей выборке Kronos. Хороший Sharpe на истории BTC может быть иллюзией — модель могла «запомнить», а не «научиться». Единственная чистая проверка — форвард-тест на незнакомых данных (ADR 0068).

**4. Безопасность: версии модели зафиксированы.**
HuggingFace-репозитории загружаются по конкретным commit SHA, прошитым прямо в код (`src/ml/kronos_variant.py:38-39, 46-47`). Это защита от незаметного обновления весов на стороне публичного репозитория — потенциально небезопасная операция (загрузка `torch.load` выполняет произвольный код). Менять SHA без проверки нельзя.

**5. --sample-count меняет params_hash.**
Если уменьшить `--sample-count` (скажем, до 5) для ускорения исследования, это изменит `params_hash`, и весь прежний кэш (со значением 20) станет недействительным. Нужно либо использовать отдельную директорию, либо принять, что придётся перестраивать.

**6. Скрипт не запускается в CI.**
`RUN_ML=1` — это намеренный барьер. Скрипт предназначен для ручного запуска оператором на M4 Pro с MPS-ускорением. В автоматических тестах torch не загружается — юнит-тесты работают с заглушкой (`KronosMockAdapter`). Описание заглушки: [[kronos-mock-adapter]].
