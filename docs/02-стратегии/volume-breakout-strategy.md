# Стратегия прорыва с подтверждением объёма

**TL;DR:** По замыслу стратегия должна покупать биткоин, когда цена пробивает верхний предел коридора последних 9 четырёхчасовых свечей и торговый объём значимо выше обычного (в 1.46 раза). Продаёт по стоп-лоссу через ATR или когда цена ныряет ниже нижней границы коридора выхода. **Внимание: в live-коде есть известный дефект (описан в разделе «Подводные камни»), из-за которого сигнал входа никогда не срабатывает. Описание ниже — задокументированный замысел стратегии, не её текущее поведение в production.**

## Простыми словами

Представьте, что вы наблюдаете за ценой биткоина на графике четырёхчасовых свечей. Несколько дней цена болтается в одном коридоре — не особо растёт, не особо падает. А потом вдруг одна свеча закрывается выше, чем все предыдущие 9 свечей. Это и называется **пробоем [[03-индикаторы-и-расчёты/donchian-channel-indicator|канала]]** (breakout).

Но пробои бывают ложными: цена вышла вверх, а потом сразу же вернулась обратно. Чтобы не попасть в такую ловушку, стратегия добавляет второй фильтр — **подтверждение объёмом** (volume confirmation). Объём — это сколько биткоина было куплено и продано за этот период. Если пробой настоящий, обычно много людей одновременно хотят купить, и объём резко вырастает. Если же пробой ложный — объём остаётся обычным, как в спокойный день.

Аналогия: представьте очередь за новым iPhone. Если в магазин пришли 5 человек — это просто случайность. Но если пришли 200 — это настоящий спрос, пробой в народном сознании. Стратегия ждёт именно «очередь из 200 человек».

**Что делает стратегия у нас:**
- Работает только на покупку (Long-only) — бот не умеет зарабатывать на падении.
- Таймфрейм: 4-часовые свечи (4H), символ BTCUSDT.
- Параметры зафиксированы навсегда по результатам автоматического перебора 4510 комбинаций (autoresearch sweep #1644) и не меняются без отдельного архитектурного решения.

## Как это работает у нас

### Шаг 0. Инициализация — создаём «окно памяти»

При запуске создаётся объект `VolumeBreakoutStrategy` для конкретного символа. Внутри него — четыре «скользящих контейнера» (deque) для хранения последних баров: максимумы (high), минимумы (low), цены закрытия (close) и объёмы (volume). Каждый контейнер хранит не более `buffer_size = 15` баров — старые данные вытесняются новыми автоматически. (`src/signalgen/volume_breakout_strategy.py:87–97`)

### Шаг 1. Приходит новая закрытая свеча — `on_bar(bar)`

Метод `on_bar(bar)` вызывается каждый раз, когда закрывается очередная 4-часовая свеча. Он возвращает либо [[02-стратегии/signal-architecture|сигнал]] (`Signal`), либо `None` (ничего не делать).

Первая проверка: свеча должна быть **закрытой**. Незакрытые (живые) свечи игнорируются — по незакрытой свече нельзя принять решение, ведь цена ещё может измениться. (`src/signalgen/volume_breakout_strategy.py:114`)

Данные новой свечи добавляются в контейнеры. (`src/signalgen/volume_breakout_strategy.py:117–121`)

### Шаг 2. Прогрев — warmup gate

Чтобы рассчитать все индикаторы (канал Дончиана, среднее объёма, ATR), нужен минимальный набор исторических баров. Бот «молчит» первые **12 баров** (warmup = max(9, 8, 9, 10) + 2 = 12). При 4-часовых свечах это 2 полных дня. (`src/signalgen/volume_breakout_strategy.py:87–89, 123–125`)

### Шаг 3. Вычисление индикаторов

Из накопленных данных рассчитываются:

**Канал Дончиана (Donchian channel)** — это просто максимум и минимум цены за последние N баров. Он определяет «коридор» для входа и выхода.

Все три окна используют срез `arr[-(N+1):-1]`, что означает: исключается только текущий бар T (индекс `-1`), но включается предыдущий бар T-1 (индекс `-2`). Иначе говоря, окно охватывает бары T-1, T-2, ..., T-N.

- `ref_high` = максимум из `high` за 9 баров T-1..T-9 (исключая только текущий бар T) — верхняя граница канала входа. (`src/signalgen/volume_breakout_strategy.py:139`)
- `ref_low` = минимум из `low` за 8 баров T-1..T-8 (исключая только текущий бар T) — нижняя граница канала выхода. (`src/signalgen/volume_breakout_strategy.py:140`)

**Среднее объёма** — `vol_mean` = среднее из объёмов за 10 баров T-1..T-10 (исключая только текущий бар T). Показывает, насколько «обычный» сейчас торговый день. (`src/signalgen/volume_breakout_strategy.py:141`)

**[[03-индикаторы-и-расчёты/atr-indicator|ATR]] (Average True Range)** — мера волатильности, показывает «средний размах» свечи за последние 9 баров. Используется для расчёта стоп-лосса. Считается по методу Уайлдера через `talib.ATR` и включает текущий бар T (в отличие от бэктест-ранера, который использует ATR(T-1) — это задокументированное расхождение G3, ADR 0059). (`src/signalgen/volume_breakout_strategy.py:150; src/signalgen/indicators.py:67–81`)

### Шаг 4. Условия входа в позицию (FLAT → LONG)

Бот входит в покупку только если сейчас нет открытой позиции и **оба условия выполнены одновременно**:

**Условие 1 — пробой канала:**
```
close[-2] > ref_high  (максимум из high[-(lookback_n+1):-1])
```

**Условие 2 — подтверждение объёмом:**
```
volume[-2] > vol_mean * vol_mult
          = vol_mean * 1.4563
```

(`src/signalgen/volume_breakout_strategy.py:155–166`)

**Почему `[-2]` а не `[-1]`?** Это ключевой момент для честности стратегии. Индекс `[-1]` — это текущая, только что закрывшаяся свеча T. Индекс `[-2]` — это свеча T-1, предыдущая. Бот смотрит на свечу T-1 и принимает решение, не «заглядывая в будущее» (look-ahead). Если бы бот использовал `[-1]` — он фактически «знал» бы данные текущей свечи до исполнения ордера, что невозможно в реальной торговле. Сигнал генерируется по закрытию T, ордер исполняется на открытии T+1. (`src/signalgen/volume_breakout_strategy.py:128–129`)

При срабатывании обоих условий бот запоминает `entry_price = close[-2]` (цену входа), меняет статус на LONG и формирует сигнал с [[04-риск-менеджмент/reason-codes-assessment-output|кодом причины]] `ENTRY_LONG_VOLUME_BREAKOUT`. (`src/signalgen/volume_breakout_strategy.py:159–166`)

### Шаг 5. Условия выхода из позиции (LONG → FLAT)

Когда есть открытая позиция, на каждой новой свече проверяются два условия выхода. Порядок проверки важен — он совпадает с тем, как устроен бэктест-движок, иначе результаты расходились бы.

**Приоритет 1 — ATR-стоп (внутрибаровый стоп, intrabar stop):**
```
bar.low <= entry_price - atr_stop_mult * ATR
         = entry_price - 2.9663 * ATR
```

Если минимум текущей свечи касается уровня стоп-лосса — позиция закрывается немедленно. Это происходит **«внутри» свечи** (intrabar): даже если свеча закроется выше стопа, позиция уже закрыта по достижению уровня низом. Сигнал: `EXIT_FLAT_ATR_STOP_VB`. (`src/signalgen/volume_breakout_strategy.py:178–190`)

**Приоритет 2 — выход по каналу:**
```
close[-2] < ref_low  (минимум из low за exit_lookback_n=8 баров)
```

Если предыдущая свеча закрылась ниже нижней границы канала выхода — позиция закрывается. Сигнал: `EXIT_FLAT_VOLUME_CHANNEL`. (`src/signalgen/volume_breakout_strategy.py:191–200`)

Стоп-лосс по ATR всегда проверяется **первым**. Это критично: на одной и той же свече теоретически могут сработать оба условия. Приоритет ATR-стопа выбран, чтобы точно совпасть с результатами бэктеста (где тот же приоритет в `_backtest_single` строка 128). (`src/backtest/volume_breakout_runner.py:128`)

### Три задокументированных расхождения с бэктестом

[[06-бэктест-и-валидация/volume-breakout-strategy|Бэктест-ранер]] и live-стратегия не совпадают числово по трём причинам (ADR 0059, G2-G4). Ранер работает не на основной системе исполнения, а на отдельном [[06-бэктест-и-валидация/research-kernel-execution-model|research-ядре]]. Расхождение не означает ошибку — оно намеренное и задокументировано:

1. **Окно Дончиана:** live-код использует `arr[-(N+1):-1]` (включая T-1), бэктест-ранер использует `roll_high[i-2]` (исключая T-1). Разные окна → разный `ref_high`/`ref_low`. (`src/signalgen/volume_breakout_strategy.py:139–140` vs `src/backtest/volume_breakout_runner.py:112`)

2. **ATR(T) против ATR(T-1):** live-стратегия вычисляет ATR по буферу включая текущий бар T; бэктест использует `atr[i-1]` (ATR на момент свечи сигнала). Формула Уайлдера: ATR(T) = 8/9 × ATR(T-1) + 1/9 × TR(T) — числовое расхождение небольшое, но не нулевое. (ADR 0059 G3, `src/backtest/volume_breakout_runner.py:122`)

3. **Цена заполнения ATR-стопа:** бэктест заполняет по `stop_price` (внутри свечи), live FSM заполнит по `open(T+1)` (открытие следующей свечи). На 4H-гэпах расхождение существенное. (ADR 0059 G4, `src/signalgen/volume_breakout_strategy.py:178–190`)

## Формулы и расчёты

### Условие входа (замысел)

```
Пробой:   close[T-1] > max( high[T-1 : T-10] )   ← включает high(T-1)
Объём:    volume[T-1] > mean( volume[T-1 : T-11] ) × 1.4563
```

**Расшифровка простыми словами:**
- Берём цену закрытия предпоследней свечи (T-1).
- Сравниваем с наибольшей точкой, которой достигала цена за 9 свечей T-1..T-9.
- Если цена эту точку превысила — первое условие выполнено.
- Берём объём торгов свечи T-1 и сравниваем со средним за 10 свечей T-1..T-10.
- Если объём больше среднего в 1.46 раза — второе условие выполнено.
- Оба условия истинны одновременно → сигнал покупки.

### Стоп-лосс

```
stop_level = entry_price - 2.9663 × ATR(period=9)
```

**ATR (Average True Range)** — средний дневной размах свечи за последние 9 четырёхчасовых периодов. Считается по формуле Уайлдера: истинный диапазон каждой свечи = max(high−low, |high−prev_close|, |low−prev_close|), затем усредняется с экспоненциальным затуханием. (`src/signalgen/indicators.py:67–81`)

**Пример:** если ATR = 500 USDT (типичный размах за 4 часа), а мы вошли по цене 40 000 USDT, то стоп-лосс = 40 000 − 2.9663 × 500 = **38 517 USDT**. Это примерно 3.7% ниже цены входа — достаточно далеко, чтобы обычный шум не выбил нас раньше времени.

### ATR: talib vs ручная реализация

В `VolumeBreakoutStrategy` используется `talib.ATR` (через обёртку `atr()` из `indicators.py`). Для бэктеста есть отдельная [[06-бэктест-и-валидация/wilder-atr-and-stops|ручная реализация Уайлдера]] (`wilder_atr()` из `indicators.py` и `_wilder_atr` из `backtest/indicators.py`). Оба метода — Уайлдер, но дают небольшое расхождение (~1.4%) из-за разного seed-значения. Параметры заперты из autoresearch, который использовал именно ручную реализацию — поэтому в бэктест-ранере тоже ручная, а в live-стратегии talib. Это задокументированное расхождение, зафиксированное в ADR 0059. (`src/signalgen/indicators.py:98–100`)

## Примеры / сценарии

> **Важно перед чтением сценариев:** сценарии A, B, C описывают **задуманное поведение** стратегии. Из-за дефекта окна (описан в «Подводных камнях», пункт 8) сценарий A в live-коде не срабатывает. Сценарий B описывает выход по ATR-стопу — он работает как задумано, если позиция уже открыта. Сценарий C (отклонение ложного пробоя) технически недостижим в live-коде по той же причине.

### Сценарий A: успешный вход и выход по каналу (задуманное поведение)

**Ситуация:** BTCUSDT, 4H. Среди 9 последних свечей T-1..T-9 максимальная цена закрытия — 41 200 USDT. Среднее объёма за 10 свечей — 850 BTC за 4 часа.

1. **Свеча T-1** закрывается по 41 500 USDT (выше 41 200 — пробой). Объём = 1 320 BTC > 850 × 1.4563 = 1 238 BTC. **Оба условия выполнены.**
2. **Свеча T** закрылась. Метод `on_bar()` видит пробой + объём. Отправляет сигнал `ENTRY_LONG_VOLUME_BREAKOUT`. `entry_price = 41 500`.
3. **Ордер исполняется** на открытии следующей 4H свечи (T+1) по рыночной цене ~41 550.
4. Через 3 дня (18 свечей) цена падает ниже нижней границы 8-барного канала выхода. `close[-2] = 39 800 < ref_low = 40 100`. Сигнал `EXIT_FLAT_VOLUME_CHANNEL`.

### Сценарий B: ATR-стоп срабатывает внутри свечи

**Ситуация:** Позиция открыта, `entry_price = 41 500`, ATR = 550, стоп = 41 500 − 2.9663 × 550 = **39 869 USDT**.

1. Пришла новая свеча. Её `high = 42 000`, `close = 41 300`, но `low = 39 700`.
2. Несмотря на то что свеча закрылась выше стопа, `low = 39 700 ≤ 39 869`.
3. `on_bar()` фиксирует: `bar.low <= stop_level`. Немедленный сигнал `EXIT_FLAT_ATR_STOP_VB`.
4. Бот вышел из позиции, хотя свеча «выглядела» нормально.

Обратите внимание: в production FSM заполнение ордера произойдёт по `open(T+1)`, а не по точной цене стопа — это задокументированное расхождение с бэктестом (ADR 0059 G4).

### Сценарий C: ложный пробой — объём не подтвердил (задуманное поведение)

**Ситуация:** Цена пробила предыдущий максимум (41 500 USDT), но объём свечи T-1 — всего 900 BTC.

1. Условие 1: 41 500 > 41 200 — **выполнено**.
2. Условие 2: 900 < 1 238 (850 × 1.4563) — **не выполнено**.
3. `on_bar()` возвращает `None`. Сигнала нет. Бот ждёт следующей свечи.

## Подводные камни / что важно понимать

**1. Параметры заперты — это намеренно.**
Числа 1.4563 и 2.9663 выглядят странно, они не круглые — и это не случайно. Они получены автоматическим перебором (autoresearch sweep #1644), а не «на глаз». Любое округление уже было бы подгонкой задним числом (post-observation tuning). Эти параметры зафиксированы в коде и в ADR 0059, и их изменение требует нового архитектурного решения. (`src/signalgen/volume_breakout_strategy.py:49–59`)

**2. Long-only — нет защиты от медвежьего рынка.**
Стратегия принципиально покупает только вверх. На сильно падающем рынке она просто не войдёт в позицию — но если уже в позиции — может получить убыток. На исторических данных 8 месяцев медвежьего рынка бэктест показал +20.42% при «держи и не продавай» = -30.14% за тот же период. Но это единственное чистое out-of-sample свидетельство (17 сделок — малая выборка), и в общем зачёте стратегия получила вердикт WFA_FAIL — см. [[00-обзор/strategies-and-50-sprint-results|итоги 50+ спринтов]]. (ADR 0059, строки ~66–70)

**3. Только 4H BTCUSDT — ограничение в интерфейсе.**
[[08-дашборд/breakout-strategies|Dashboard]] (legacy-интерфейс) принудительно скрывает опции других таймфреймов и символов: при выборе стратегии `volume_breakout` все выпадающие меню, кроме BTCUSDT/240, становятся серыми и недоступными для нажатия. Это сделано на уровне браузера (frontend lock). Сам backend-код не проверяет, совпадают ли переданные символ/таймфрейм с «замороженными» значениями: `_run_backtest_locked` проверяет только то, известна ли стратегия и поддерживается ли таймфрейм как таковой (`src/dashboard/backtest_runner.py:950–958`), но не блокирует по несоответствию символа/таймфрейма — бэктест просто запустится с другими данными, если они есть. Параметры оптимизированы под конкретную пару и таймфрейм, перенос на другие активы потребует повторного поиска. (Frontend lock: `src/dashboard_legacy/static/dashboard.js:182–193`)

**4. Прогрев 12 баров (2 дня) — бот «молчит» при старте.**
Если запустить бота с нуля, первые 12 закрытых свечей он будет собирать историю и не выдаст ни одного сигнала. Это нормально — без достаточного количества данных индикаторы просто не считаются. (`src/signalgen/volume_breakout_strategy.py:87–89, 123–125`)

**5. Приоритет ATR-стопа критичен для совпадения с бэктестом.**
Если поменять порядок (сначала канальный выход, потом ATR) — результаты live-торговли будут расходиться с тем, что показывает бэктест. Это была намеренная инженерная задача Sprint 55 (TL-04): дословно перенести порядок проверок из исследовательского кода в production. Выход по каналу в live-коде возможен только как второй приоритет (после ATR-стопа). (`src/signalgen/volume_breakout_strategy.py:173–177; src/backtest/volume_breakout_runner.py:128`)

**6. Объект не потокобезопасен.**
Один экземпляр `VolumeBreakoutStrategy` обслуживает ровно один символ, в одном потоке. Параллельное использование из нескольких потоков недопустимо (ADR 0023). (`src/signalgen/volume_breakout_strategy.py:28–29`)

**7. ATR-стоп не определён при отсутствии ATR.**
Если в буфере недостаточно данных для вычисления ATR (`atr_val is None`) — сигнал входа всё равно может быть выдан (бот войдёт), но ATR-стоп работать не будет. Выход будет только по каналу. На практике после прогрева ATR всегда доступен. (`src/signalgen/volume_breakout_strategy.py:178–180`)

**8. КРИТИЧЕСКИЙ ДЕФЕКТ: сигнал входа в live-коде никогда не срабатывает.**

Это самое важное, что нужно понять читателю: **в текущем production-коде стратегия не генерирует сигналы на покупку.** Это математически доказуемо.

Причина — в том, как вычисляется окно для `ref_high`. Код:

```python
ref_high_window = highs_arr[-(self._lookback_n + 1) : -1]   # arr[-10:-1]
```

Этот срез охватывает 9 элементов с индексами `-10, -9, ..., -2`. Последний из них (индекс `-2`) — это `high(T-1)`, максимум предыдущего бара.

Проверка входа:
```python
breakout = prev_close > ref_high   # prev_close = closes_arr[-2] = close(T-1)
```

То есть бот проверяет: `close(T-1) > max(окна, которое включает high(T-1))`.

Но по правилам OHLC: цена закрытия свечи **всегда не превышает** её максимума: `close(T-1) ≤ high(T-1)`. А `ref_high = max(окна)` и окно включает `high(T-1)`, значит `ref_high ≥ high(T-1) ≥ close(T-1)`. Условие `close(T-1) > ref_high` **математически невозможно**.

Точно та же проблема делает выход по каналу недостижимым через естественный путь (хотя для уже открытых позиций теоретически возможна при внешнем засеве состояния). Окно `ref_low` тоже включает `low(T-1)`, а проверка `close(T-1) < min(окна включая low(T-1))` нарушает инвариант `close(T-1) ≥ low(T-1)`. (`src/signalgen/volume_breakout_strategy.py:139–140, 157, 192`)

Это **известный дефект**, зафиксированный в тест-файле как «out of TL-04 scope» (`tests/unit/test_volume_breakout_parity.py:17–22`). Бэктест-ранер использует другое окно (`roll_high[i-2]`, исключающее T-1) и дефекта не имеет — поэтому исторические результаты в ADR 0059 корректны.

**Для исправления** нужно изменить срез в live-коде: `arr[-(N+2):-2]` (исключить и T, и T-1). Это вернёт логику к замыслу. До исправления стратегия не торгует.
