# Безопасность: как бот проверяет подлинность весов нейросети

**TL;DR:** Перед тем как бот начнёт использовать прогнозы нейросети [[kronos-what-is-it|Kronos]], он проверяет, что загруженные файлы модели именно те, которым мы доверяем. Это делается двумя способами: пинованием конкретного коммита на HuggingFace и SHA-256 хэшем фактических файлов весов. Вместе они закрывают угрозу тихой подмены модели — ситуации, когда бот начинает делать прогнозы на основе чужого или изменённого файла.

## Простыми словами

Представьте, что вы наняли советника, который даёт вам рекомендации по инвестициям. Прежде чем следовать его советам, вы хотите убедиться: это тот самый человек, которому вы доверяете, а не самозванец с похожим именем.

С нейросетью та же история. Kronos — это не программа-инструкция, а **набор числовых весов** (то есть миллионы коэффициентов, которые были «выучены» во время обучения). Эти веса хранятся в файлах на серверах HuggingFace Hub — открытой платформы для публикации ML-моделей. Когда бот скачивает Kronos, он фактически скачивает эти файлы.

Проблема: **что если файл на сервере изменился?** Или что если мы случайно используем старую версию весов вместо новой? Советы тогда будут от «не того советника» — и мы об этом не узнаем.

Решение — **цифровой паспорт** в двух частях:

1. **Пин ревизии (SHA git-коммита)** — как номер паспорта. Мы жёстко фиксируем в коде, какой именно «снимок» репозитория считается доверенным. HuggingFace проверяет этот номер при скачивании.

2. **SHA-256 хэш файлов** — как контрольная сумма. После того как файлы скачаны, мы перечитываем их и считаем «отпечаток» (хэш) по содержимому. Если хоть один байт изменился — отпечаток будет другим.

**SHA-256** («алгоритм безопасного хэширования», SHA = Secure Hash Algorithm) — это математическая функция, которая превращает любой файл (хоть гигабайт весов, хоть текстовый документ) в строку из 64 шестнадцатеричных символов. Изменение одного байта в исходном файле полностью меняет результат. Именно это свойство делает SHA-256 инструментом проверки целостности.

## Как это работает у нас

### Уровень 1 — пин ревизии в коде (`KronosVariant`)

Каждый вариант Kronos — `base` и `mini` — описывается объектом `KronosVariant` (неизменяемым датаклассом). Внутри обязательно есть два поля ревизии:

```python
@dataclass(frozen=True)
class KronosVariant:
    model_revision: str      # SHA-коммит репозитория модели
    tokenizer_revision: str  # SHA-коммит репозитория токенизатора
```

(src/ml/kronos_variant.py:14-30)

Конкретные значения, закреплённые в коде:

| Вариант | `model_revision` | `tokenizer_revision` |
|---------|-----------------|----------------------|
| `KRONOS_BASE` | `2b554741eca47781b64468546e77fef3e85130e6` | `0e0117387f39004a9016484a186a908917e22426` |
| `KRONOS_MINI` | `f4e68697d9d5aed55cef5c96aabc3376bcad9f81` | `26966d0035065a0cae0ebad7af8ece35bc1fb51c` |

(src/ml/kronos_variant.py:38-48)

**Почему модель и токенизатор — разные репозитории с разными SHA?** Потому что на HuggingFace они опубликованы отдельно. `NeoQuasar/Kronos-mini` и `NeoQuasar/Kronos-Tokenizer-2k` — это два разных репозитория, каждый со своей историей коммитов. Единый SHA на оба не работает: у них нет общей точки истории. Поэтому в `KronosVariant` — два отдельных поля, по одному на каждый репозиторий. (src/ml/kronos_variant.py:18-22)

Пины зафиксированы **в коде, а не в переменных окружения** — это принципиальное решение. Так они проходят через git-историю и code review: любое изменение ревизии видно в PR и требует осознанного действия. Обоснование прямо в докстринге класса: «Pinned in-code (version-controlled) rather than via env var.» (src/ml/kronos_variant.py:18-23)

Когда `KronosModelAdapter` загружает модель, он передаёт эти SHA напрямую в `from_pretrained`:

```python
model = Kronos.from_pretrained(variant.model_id, revision=variant.model_revision)
tokenizer = KronosTokenizer.from_pretrained(
    variant.tokenizer_id, revision=variant.tokenizer_revision
)
```

(src/ml/kronos_adapter.py:124-127)

HuggingFace проверяет коммит на своей стороне — если файл в репозитории изменился после нашего пина, скачивание завершится ошибкой.

### Почему это важно: угроза ACE

**ACE (Arbitrary Code Execution — выполнение произвольного кода)** — это атака, при которой злоумышленник заставляет программу выполнить произвольный код, замаскированный под легитимные данные.

`from_pretrained` внутри вызывает `torch.load`, который десериализует файлы чекпоинта через pickle — стандартный Python-механизм сериализации объектов. Принципиальная проблема pickle: **сериализованный файл может содержать исполняемый код**. Это задокументированная уязвимость PyTorch. Проще говоря, скачать «чекпоинт» модели с чужого сервера без пина = запустить чужой exe-файл с полными правами текущего пользователя.

Именно поэтому в комментарии к `KronosModelAdapter.__init__` явно написано:

> "torch.load pickle = ACE. Separate repos → separate pins. `weights_hash` is post-download provenance, NOT ACE prevention."

(src/ml/kronos_adapter.py:83-87)

Пин ревизии — это первый рубеж защиты. `weights_hash` — второй, более тонкий.

### Уровень 2 — хэш фактических файлов (`compute_weights_hash`)

После того как файлы скачаны, функция `compute_weights_hash()` вычисляет SHA-256 по фактическому содержимому весовых файлов. Это уже не «проверка по имени», а «проверка по содержимому».

```python
def compute_weights_hash(
    variant: _VariantLike,
    *,
    hf_cache: Path | None = None,
) -> str:
```

(src/ml/weights_hash.py:47-51)

**Шаг 1 — поиск файлов.** Функция ищет файлы в кэше HuggingFace (`~/.cache/huggingface/hub` по умолчанию). Для каждого из двух репозиториев — модели и токенизатора — строится путь к директории по схеме `models--{org}--{name}`. Внутри рекурсивно ищутся файлы с расширениями: `.bin`, `.safetensors`, `.ckpt`, `.pt` — все форматы, которые бывают у весов PyTorch-моделей. (src/ml/weights_hash.py:25, 76-83)

**Шаг 2 — хэширование всех найденных файлов скопом.** Все найденные файлы сортируются по пути (чтобы порядок был детерминирован) и читаются блоками по 65 536 байт (`_CHUNK_SIZE = 65536`), которые последовательно «подаются» в один SHA-256 хэшер. Результат — единая строка из 64 шестнадцатеричных символов. (src/ml/weights_hash.py:103-112)

```python
weight_files.sort()
h = hashlib.sha256()
for wf in weight_files:
    with wf.open("rb") as fh:
        while chunk := fh.read(_CHUNK_SIZE):
            h.update(chunk)
digest = h.hexdigest()
```

(src/ml/weights_hash.py:103-111)

**Шаг 3 — fallback при отсутствии файлов.** Если файлы весов ещё не скачаны (например, при первом запуске до `from_pretrained`), функция не паникует. Вместо этого она строит хэш из строки-идентификатора, включающей все четыре координаты: model_id, model_revision, tokenizer_id, tokenizer_revision:

```python
fallback_seed = (
    f"{variant.model_id}@{variant.model_revision}"
    f"|{variant.tokenizer_id}@{variant.tokenizer_revision}"
)
return hashlib.sha256(fallback_seed.encode("utf-8")).hexdigest()
```

(src/ml/weights_hash.py:88-101)

**Почему fallback включает revision?** Это критично. Если хэшировать только `model_id|tokenizer_id` (без ревизии) — два разных пина на один и тот же репозиторий дадут одинаковый хэш. Кэш предсказаний от старой версии будет считаться валидным для новой. Именно такой баг был найден и зафиксирован тестом `test_compute_weights_hash_fallback_distinct_revisions_differ` (tests/unit/test_weights_hash.py:114-141). Текущая реализация включает ревизии в seed, поэтому разные пины всегда дают разные хэши.

### Роль `weights_hash` в ключе кэша

Вычисленный хэш становится полем `CacheKey` — ключа, по которому хранятся и читаются прогнозы из [[kronos-offline-predict-cache|офлайн-кэша]]:

```python
@dataclass(frozen=True)
class CacheKey:
    model_id: str
    weights_hash: str      # <-- здесь
    symbol: str
    timeframe: str
    bar_close_ts: int
    params_hash: str
    device: str
```

(src/ml/prediction_cache.py:33-42)

Несовпадение хэша весов = промах кэша (MISS). Прогноз, сделанный со «старыми» весами, не будет переиспользован после смены весов — даже если всё остальное (символ, таймфрейм, временная метка бара) осталось прежним. Это контракт C4 по ADR 0068.

**Что происходит при смене варианта.** Переключение с `base` на `mini` (или обновление пина ревизии) даёт другой `weights_hash` — все записи в кэше становятся промахами. Кэш нужно перестраивать полностью. Это важная операционная особенность, о которой предупреждает ADR 0069.

## Формулы и расчёты

### SHA-256 по файлам весов

Когда файлы найдены, вычисляется единый SHA-256 по конкатенации всех файлов в отсортированном порядке:

```text
digest = SHA-256( bytes(file_1) ++ bytes(file_2) ++ ... ++ bytes(file_N) )
```

Что это считает простыми словами: функция SHA-256 принимает весь поток байт (все файлы весов подряд) и выдаёт «отпечаток» — строку из 64 символов. Изменение любого байта в любом файле полностью меняет этот отпечаток. Порядок файлов фиксирован сортировкой.

Реализация: `hashlib.sha256()` + последовательные вызовы `.update(chunk)` для каждого блока в 65 536 байт. (src/ml/weights_hash.py:104-110)

### SHA-256 fallback (без файлов на диске)

```text
fallback_seed = "{model_id}@{model_revision}|{tokenizer_id}@{tokenizer_revision}"
digest = SHA-256( UTF-8(fallback_seed) )
```

Что это считает: хэш строки, которая уникально описывает конкретную версию каждого из двух репозиториев. Два разных пина = два разных seed = два разных хэша. Это гарантирует, что кэш-ключи не пересекаются, даже когда файлы ещё не скачаны.

Реализация: src/ml/weights_hash.py:88-101.

## Примеры / сценарии

### Сценарий 1 — нормальный запуск с файлами на диске

Модель `KRONOS_MINI` уже скачана в `~/.cache/huggingface/hub/`.

1. `compute_weights_hash(KRONOS_MINI)` вызывается при инициализации.
2. Функция строит путь `~/.cache/huggingface/hub/models--NeoQuasar--Kronos-mini/` — директория существует.
3. Рекурсивно находит, например, `model.safetensors` и `tokenizer.model.bin`.
4. Сортирует: `['...Kronos-mini/.../model.safetensors', '...Kronos-Tokenizer-2k/.../tokenizer.model.bin']`.
5. Читает оба файла блоками по 65 536 байт, подаёт в SHA-256 хэшер.
6. Возвращает 64-символьный хэш: например, `a3f7c2...` (64 символа).
7. Этот хэш попадает в поле `CacheKey.weights_hash` — все прогнозы маркируются им.

### Сценарий 2 — первый запуск, файлы ещё не скачаны

1. `compute_weights_hash(KRONOS_MINI, hf_cache=пустая_директория)` — файлов нет.
2. `weight_files` пустой список → переходим к fallback.
3. В лог пишется предупреждение: «No weight files found for NeoQuasar/Kronos-mini@f4e68... / NeoQuasar/Kronos-Tokenizer-2k@26966... under ...; using revision-pinned ids as hash seed.»
4. Строим seed: `"NeoQuasar/Kronos-mini@f4e68697d9d5aed55cef5c96aabc3376bcad9f81|NeoQuasar/Kronos-Tokenizer-2k@26966d0035065a0cae0ebad7af8ece35bc1fb51c"`.
5. Возвращаем SHA-256 этой строки — детерминированный хэш, уникальный для этой пары ревизий.

### Сценарий 3 — обновление пина ревизии

Представим, что вышла новая версия `KRONOS_MINI` и мы обновили `model_revision` в коде.

- **Старый пин:** `model_revision = "f4e68697..."`
- **Новый пин:** `model_revision = "a1b2c3d4..."`

Оба пина дают разные `weights_hash` — как в fallback-режиме (разные seed строки), так и при наличии файлов (другие байты в загруженных весах). Все записи в кэше прогнозов становятся промахами — кэш перестраивается с нуля. Это нормальное ожидаемое поведение при обновлении модели.

### Сценарий 4 — тест: баг TQ-05 не воспроизводится

Тест `test_compute_weights_hash_fallback_distinct_revisions_differ` создаёт два варианта с одинаковыми `model_id` / `tokenizer_id`, но разными ревизиями, и проверяет, что хэши отличаются (tests/unit/test_weights_hash.py:114-141). Тест документирует конкретный баг: старая версия кода хэшировала только `"{model_id}|{tokenizer_id}"` без ревизий — два разных пина на один репозиторий давали одинаковый хэш, и кэш от старой версии модели мог переиспользоваться для новой.

## Подводные камни / что важно понимать

**`weights_hash` — это НЕ защита от ACE.** Это постфактумная проверка целостности уже скачанного файла. ACE-атака происходит при самом скачивании (`torch.load` на этапе `from_pretrained`). Защита от ACE — пин ревизии, который передаётся в `from_pretrained(revision=...)`. Если вредоносный файл уже скачан с «правильным» SHA коммита — он пройдёт на первом рубеже. Именно поэтому оба механизма нужны вместе. (src/ml/kronos_adapter.py:59-60)

**Два репозитория — два SHA.** Нельзя использовать один и тот же `model_revision` для модели и токенизатора: это разные репозитории с разными историями коммитов. Каждый пинируется отдельно. (src/ml/kronos_variant.py:18-22, 29-30)

**Смена варианта = инвалидация всего кэша.** Переключение между `base` и `mini` (или обновление SHA ревизии) меняет `weights_hash`, что делает все существующие кэш-записи промахами. Перед сменой варианта нужно запланировать перестройку кэша прогнозов. (Зафиксировано в разделе «Ограничения» ADR 0069, строка 116: «Смена variant или токенизатора invalidates `weights_hash` → полный rebuild кэша».)

**Fallback-хэш — не значит «небезопасно».** Если файлы ещё не скачаны, функция не падает с ошибкой. Она возвращает детерминированный хэш на основе ревизий — достаточно уникальный для кэш-ключа. Однако он не проверяет содержимое файлов (их ещё нет). Настоящая проверка целостности файлов возможна только после скачивания.

**Модуль `weights_hash.py` намеренно не импортирует torch.** Это позволяет запускать юнит-тесты проверки хэша в CI без установки PyTorch — тесты проходят с одним `hashlib`. (src/ml/weights_hash.py:1-14 — модульный docstring: «NEVER imports torch».)

**Файлы с расширением `.safetensors` не уязвимы к ACE через pickle.** `.safetensors` — более новый формат, специально разработанный как безопасная альтернатива pickle. Тем не менее пин ревизии важен и для них: злоумышленник может подменить файл с корректными весами на файл с другими весами того же формата.
