# Реализация и лучшие практики (MVP Bybit Bot)

Этот документ фиксирует, что уже реализовано в проекте и какие практики использованы, чтобы бот был стабильным, наблюдаемым и безопасным для MVP.

## 1. Интеграция с Bybit (pybit)
- Используется официальный клиент `pybit` для HTTP/REST и WebSocket.
- Поддержаны режимы:
  - `testnet=True`
  - `demo=True` (Demo Trading, актуально для Testnet ключей)
- Реальные сделки включаются флагом `LIVE_TRADING = True`.

## 2. Источник данных и устойчивость
- **REST seed:** при запуске бот скачивает историю свечей и заполняет буфер (по умолчанию 1000 свечей) — это исключает "сырые" индикаторы.
- **WebSocket → REST fallback:** если WS недоступен (Demo часто возвращает 503), бот автоматически переходит на REST‑поллинг.
- **Реактивный REST‑поллинг:** частые запросы (по умолчанию 1 секунда) и генерация "живых" свечей, чтобы стратегия работала похоже на WS.

## 3. Стратегия (MVP)
Используется базовый набор индикаторов:
- EMA 12/26 (кросс)
- RSI фильтр (не входить в перегрев)
- ATR для динамического стоп‑лосса и тейк‑профита

Это соответствует лучшим практикам MVP: простая и проверяемая логика + риск‑фильтр.

## 4. Риск‑менеджмент
- **Risk‑first gate:** сигнал проверяется перед отправкой ордера.
- **Fixed fractional risk:** размер позиции рассчитывается как доля капитала.
- **Kill‑switch:** если просадка превышает лимит — торговля блокируется.
- **One‑signal‑per‑candle:** стратегия не будет повторять сигналы на одной и той же закрытой свече (важно при REST‑поллинге).

## 5. Исполнение ордеров
- Перед отправкой **нормализуем количество** под `qtyStep` и `minOrderQty` из `get_instruments_info`.
- Каждое исполнение добавляется в локальный `execution_log` (до 50 записей).
- Поддержан **тестовый buy/sell** при запуске (`STARTUP_TEST_USD=100`) для быстрой проверки.

## 6. Синхронизация истории сделок
- При запуске бот запрашивает историю исполнений через `get_executions`.
- Далее синхронизация выполняется **каждую минуту**.
- История из API объединяется с локальными сделками бота и отображается в UI.

Это решает рассинхрон: сделки, совершённые вручную, теперь отображаются в дашборде.

## 7. UI / Dashboard
В UI отображается:
- Цена и состояние свечи
- Источник данных (`WS`/`REST`)
- Время последней свечи
- История исполнений (BUY/SELL)
- Статус risk‑gatekeeper и equity
- Интервал теперь в **секундах** (например, `1` минутный таймфрейм показывает `60`)

Также:
- UI‑сервер автоматически выбирает свободный порт (8000 → 8001 → 8002 → 8003).

## 8. Основные конфиги (main.py)
- `LIVE_TRADING = True` — включает реальные сделки в Demo Testnet
- `DEMO_TRADING = True` — для Demo ключей
- `REST_POLL_INTERVAL = 1` — частота REST‑поллинга в секундах
- `STARTUP_TEST_USD = 100` — тестовая покупка+продажа при старте
- `UI_PORT` — опционально через переменные окружения

## 9. Ограничения MVP
- Demo WS может быть нестабильным (503 от CloudFront) → REST‑fallback.
- Индикаторы рассчитаны на одном таймфрейме и одной паре.
- Нет полноценного управления позицией (частичные выходы, трейлинг, лимитные ордера) — можно добавить дальше.

## 10. Следующие логичные улучшения
- Полный backfill истории (например, 30 дней 1m) с пагинацией.
- MTF‑логика (HTF фильтр + LTF вход).
- Автоматический режим "one‑position‑at‑a‑time" и контроль экспозиции.
- WebSocket приватные стримы для подтверждения исполнения в real‑time.
