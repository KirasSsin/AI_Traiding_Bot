# AI Trading Bot: Полная Техническая и Архитектурная Документация Проекта

Этот документ — основной ориентир по архитектуре и эксплуатации AI Trading Bot. Он обновляется вместе с кодом; при расхождении приоритет у фактического поведения репозитория (`src/`, `config.yaml`).

---

## РАЗДЕЛ 1: ОПИСАНИЕ ПРОЕКТА

### 1.1 Название, назначение и контекст
**Проект:** AI Trading Bot — высокопроизводительный локальный криптовалютный торговый бот, изначально спроектированный для двух взаимодополняющих режимов: исторического тестирования на исторических рыночных данных (backtesting) и симуляционной торговли в реальном времени (paper trading / testnet). 

**Назначение:** Главная бизнес-задача проекта заключается в проверке математической гипотезы: _«Могут ли простые, классические алгоритмические правила, основанные на пересечениях и фильтрации статических технических индикаторов, генерировать стабильную положительную доходность (альфу) на строго заданном историческом периоде конкретного финансового актива, при условии безусловного и полного учета всех транзакционных издержек, включая торговые комиссии биржи и рыночное проскальзывание (slippage)?»_. Проект должен доказать или опровергнуть эффективность базовых паттернов технического анализа (таких как пересечение Экспоненциальных и Простых Скользящих Средних, осцилляторы Индекса Относительной Силы и Схождение/Расхождение Скользящих Средних) перед тем, как переходить к использованию сложных моделей машинного обучения или HFT-инфраструктуры.

### 1.2 Стек технологий с версиями
Для обеспечения оптимального баланса между скоростью разработки, производительностью вычислений и богатством экосистемы анализа данных был выбран следующий технологический стек:
- **Язык программирования:** Python 3.9+ (совместимо с текущим локальным окружением проекта).
- **Визуализация и Пользовательский Интерфейс:** Streamlit (версии 1.30+). Позволяет декларативно и быстро создавать веб-приложения для визуализации результатов бэктестинга без необходимости разрабатывать отдельный frontend на React или Vue.
- **Хранение данных:** CSV (`data/BTCUSDT_1h.csv`) как основной источник в MVP; артефакты работы сериализуются в `output/*.csv|json|html`.
- **Математика и Индикаторы:** 
  - `pandas` и `numpy` для фундаментальных операций над временными рядами.
  - Расчет EMA/RSI/ATR реализован непосредственно в коде (`src/backtest/replay_engine.py` и `src/strategy/strategy.py`) без обязательной внешней зависимости на `ta-lib`.
- **Графики и отчеты:** `Plotly` для интерактивных, масштабируемых свечных графиков и кривых капитала (equity curves). Поддерживает экспорт в автономные HTML-файлы для оффлайн репорта.
- **Интеграция с Биржами:** `pybit` (официальный SDK) для взаимодействия с WebSocket и REST API экосистемы Bybit V5.

### 1.3 Принципы архитектуры (5 замороженных решений)
Проект строится на пяти безоговорочных архитектурных принципах:
1. **Отсутствие баз данных (Zero-DB Architecture):** В MVP запрещено использование традиционных РСУБД или NoSQL решений. Все состояние (state), логи сделок и результаты тестов, конфигурации — сериализуются исключительно в плоские файлы (`.csv`, `.json`, `.parquet`, `.html`). Это избавляет от проблемы миграций схем БД, серверов баз данных и позволяет легко переносить результаты на любую машину путем копирования папки `output/`.
2. **Модульность и Изолированность:** Каждый процесс — загрузка данных, расчет индикаторов, генерация сигналов, симуляция исполнения ордеров, управление рисками и метриками — строго разделен на независимые модули. Модули общаются друг с другом исключительно через контракты данных (словари и pd.DataFrame).
3. **Единый Источник Истины для Конфигураций:** Файл `config.yaml` является абсолютным диктатором. Ни в одном из .py файлов не допускаются хардкод-значения таймфреймов, пар, ограничений риска или параметров индикаторов. Все модули обязаны получать настройки из парсера конфига и безоговорочно следовать им.
4. **Безоговорочный Учет Транзакционных Издержек:** Любой расчет прибыли и убытков (PnL) обязан включать списание maker/taker комиссий и проскальзывание цены. Тесты стратегий, не учитывающие эти параметры, считаются невалидными, так как стратегия не может быть оценена справедливо в идеальных математических условиях без рыночного трения.
5. **Human-Readable Output:** Артефакты, производимые движком бэктестирования, не могут быть скрыты внутри бинарников. Они обязаны выгружаться наружу в виде легко интерпретируемых аналитиком файлов (`trade_log.csv` для просмотра сделок в Excel, `report.html` для обмена отчетами через мессенджеры).

### 1.4 Текущий статус
- **Что работает превосходно:** `config.yaml` как единая точка конфигурации, CLI-бэктест через `run_backtest.py`, CSV-загрузчик, bar-by-bar replay с комиссиями/slippage/Kill-Switch, генерация артефактов в `output/`, Streamlit UI (`app.py`), live-движок на `pybit` (`main.py` + `src/controller.py`), unit/integration тесты (`tests/`).
- **Что не работает / ограничения:** Полноценный parquet-loader не внедрен в backtest pipeline (приоритет остается у CSV). Часть HFT-метрик есть в realtime-контуре, но не весь расширенный институциональный набор KPI из дорожной карты Stage 3-5.
- **Что важно по безопасности:** API-ключи больше не хардкодятся; live-режим читает ключи из env (`BYBIT_API_KEY`, `BYBIT_API_SECRET`) и по умолчанию выключен (`live.enabled: false`).

## РАЗДЕЛ 4: МОДУЛИ — ПОЛНОЕ ОПИСАНИЕ

### 4.1 Модуль `src/backtest/data_collector.py`
**Назначение:** загрузка и нормализация OHLCV из CSV, фильтрация по датам из `config.yaml`, валидация структуры данных.  
**Ключевой интерфейс:** `load_market_data(config: dict) -> pd.DataFrame` (для совместимости с текстом старых версий доступен алиас `load_data` → тот же вызов).  
**На выходе:** подготовленный DataFrame с колонками `timestamp/open/high/low/close/volume` для бэктест-ядра.  
**Статус:** ✅ реализован.

### 4.2 Модуль `src/backtest/replay_engine.py`
**Назначение:** bar-by-bar симуляция стратегии MVP (EMA fast/slow по `config` + RSI + ATR), включая комиссии, slippage, SL/TP и kill-switch по просадке.  
**Ключевой интерфейс:** `run_replay(df: pd.DataFrame, config: dict) -> dict` (`equity_df`, `trades_df`, `metrics`).  
**Особенности текущей реализации:**
- индикаторы считаются внутри `_calculate_indicators` (отдельного `indicators.py` в проекте нет);
- флаги `strategy.indicators.*.enabled` в конфиге **пока не отключают** расчёт индикаторов в бэктесте (всегда считаются EMA/RSI/ATR при наличии данных);
- вход и выход в позиции обрабатываются в одном детерминированном цикле;
- результаты KPI считаются внутри `_compute_metrics`.
**Статус:** ✅ реализован.

### 4.3 Модуль `src/backtest/reporter.py`
**Назначение:** экспорт артефактов бэктеста в `output/` (`trade_log.csv`, `equity_curve.csv`, `metrics_summary.json`, `report.html`).  
**Ключевой интерфейс:** функции сохранения отчетов и таблиц, вызываемые из `run_backtest.py` и `app.py`.  
**Статус:** ✅ реализован.

### 4.4 Модуль `src/strategy/strategy.py`
**Назначение:** live-логика сигналов `BUY/SELL` на основе EMA/RSI/ATR с дополнительной ML/режимной фильтрацией (XGB/HMM).  
**Ключевой интерфейс:** `AdvancedStrategy.on_kline(df, current_price) -> Optional[Signal]`.  
**Важно:** сигнал формируется только при валидном кроссе и фильтрах, а финальное решение об исполнении принимает `RiskManager` и `Controller`.  
**Статус:** ✅ реализован.

### 4.5 Модуль `src/risk/risk_manager.py`
**Назначение:** risk-first gate перед исполнением сигналов.  
**Ключевые функции:**

- динамический размер позиции (`calculate_position_size`) с ограничением риска на сделку;
- оценка сигнала перед исполнением (`evaluate_signal`);

**Статус:** ✅ реализован.

### 4.6 Модуль `src/execution/executor.py`
**Назначение:** интеграция с Bybit через `pybit` (REST/HTTP), mock/live исполнение ордеров.

### 4.7 Модули `src/data/consumer.py`, `src/data/event_bus.py`, `src/data/orderbook.py`

### 4.8 Модули `src/core/metrics_engine.py` и `src/controller.py`

## РАЗДЕЛ 5: DATA FLOW (Архитектура Потока Данных)

### 5.1 Backtest Flow (`run_backtest.py` / `app.py`)
1. `config_loader.load_config()` читает `config.yaml`.
2. `src/backtest/data_collector.load_market_data()` загружает и валидирует CSV.
3. `src/backtest/replay_engine.run_replay()` выполняет полный симуляционный цикл:
   - расчет EMA/RSI/ATR;
   - генерация сигнала;
   - вход/выход позиции;
   - учет комиссий/slippage;
   - kill-switch по drawdown.
4. `src/backtest/reporter` сохраняет артефакты в `output/`.
5. `app.py` визуализирует метрики, equity и таблицу сделок.

### 5.2 Live Flow (`main.py`)
1. `main.py` загружает конфиг и env-секреты Bybit.
2. `TradingController` поднимает:
   - `BybitDataConsumer` (WS + REST fallback),
   - `AdvancedStrategy`,
   - `RiskManager`,
   - `BybitExecutor`,
   - `MetricsEngine`.
3. На каждом событии/снимке:
   - обновляются буферы/метрики;
   - стратегия генерирует сигнал;
   - риск-блок подтверждает или отклоняет;
   - executor выполняет mock/live ордер;
   - UI/REST состояние синхронизируется через `web/data.json` и HTTP endpoints.

## РАЗДЕЛ 6: ИНДИКАТОРЫ — МАТЕМАТИЧЕСКАЯ БАЗА И ТЕОРИЯ

Этот раздел формализует индикаторы для понимания логики решений. **MVP-бэктест (`replay_engine`) реализует только кросс EMA fast/slow, RSI-фильтр и ATR для SL/TP.** Ниже также приведены SMA и MACD как теоретическая база и возможное расширение (live-стратегия или будущие версии бэктеста), если они появятся в `config` и коде.

### 6.1 Simple Moving Average (SMA - Простая Скользящая Средняя)
**Формула (полная):** 
SMA(Period) = $\frac{1}{n} \sum_{i=0}^{n-1} \text{Close}_{current-i}$
где `n` = период усреднения (например, 20 или 50).

**Псевдокод:**
```python
def calculate_sma(close_prices, timeperiod):
    возвращает массив средних арифметических окон длиной timeperiod (например 20).
    для i от timeperiod до длины:
       sum = сумма цен от i-timeperiod до i
       sma[i] = sum / timeperiod
```

**Параметры из config (roadmap / не в текущем `replay_engine`):** например `strategy.indicators.sma` с периодами fast/slow — при появлении в конфиге и коде.
**Как может использоваться в стратегии:** кроссовер fast/slow SMA — классический трендовый сигнал (в текущем бэктесте вместо этого используется EMA).
**Edge cases (нулевые движения и NaN):** 
Выдает NaN для первых `timeperiod - 1` свечей (там не хватает данных). При нулевых смещениях просто копирует цену закрытия.

### 6.2 Exponential Moving Average (EMA - Экспоненциальная Скользящая Средняя)
**Формула (полная):**
$EMA_{today} = (Price_{today} \times \alpha) + (EMA_{yesterday} \times (1 - \alpha))$
$\alpha = \frac{2}{Period + 1}$

**Псевдокод:**
```python
def calculate_ema(close_prices, timeperiod):
    k = 2 / (timeperiod + 1)
    ema[0] = close_prices[0]
    для i от 1 до длины:
        ema[i] = (close_prices[i] - ema[i-1]) * k + ema[i-1]
```

**Параметры из config:** `strategy.indicators.ema.fast_period` (часто 12), `slow_period` (часто 26) — см. `config.yaml`.
**Как используется в стратегии:** В `replay_engine` кросс `ema_fast`/`ema_slow` даёт сигнал ±1; RSI фильтрует вход (не покупать при RSI ≥ overbought при бычьем кроссе и т.д.). В силу экспоненциального сглаживания EMA быстрее реагирует на недавние шоки, чем SMA с теми же периодами.
**Edge cases:** при короткой истории первые значения EMA нестабильны из-за прогрева окна. В текущем коде используется `pandas.DataFrame.ewm(..., adjust=False)`, поэтому важно учитывать warm-up период перед торговыми решениями.

### 6.3 Relative Strength Index (RSI - Индекс Относительной Силы)
**Формула:**
$RS = \frac{SMMA(U, n)}{SMMA(D, n)}$
$RSI = 100 - \frac{100}{1 + RS}$
Где $U$ - повышающиеся изменения, $D$ - понижающиеся изменения по модулю. $SMMA$ - сглаженная скользящая средняя (обычно Wilder's Smoothing).

**Параметры из config:** `period` (дефолт 14), `overbought` (дефолт 70), `oversold` (дефолт 30).
**Как используется в стратегии:** В бэктесте при бычьем кроссе EMA вход разрешён, если RSI < `overbought`; при медвежьем — если RSI > `oversold` (см. `_calculate_indicators` в `replay_engine.py`). Поле `filter_direction` в конфиге в текущем MVP бэктеста не читается.
**Edge cases:** если цена застыла (штиль, $U=0$ и $D=0$), формула дает неопределенность $0/0$. В текущей реализации такие участки нормализуются в нейтральное значение RSI около `50`.

### 6.4 Moving Average Convergence Divergence (MACD)
**Формула:**
$MACD_{Line} = EMA(Fast) - EMA(Slow)$
$Signal_{Line} = EMA(MACD_{Line}, Signal\_Period)$
$MACD_{Hist} = MACD_{Line} - Signal_{Line}$

**Параметры из config:** типично `fast`, `slow`, `signal` (12, 26, 9).
**Статус в коде:** в текущем `replay_engine` MACD **не** считается и **не** используется для сигналов; раздел сохранён как справка и для возможных расширений.

## РАЗДЕЛ 7: МЕТРИКИ — ПРОДУКТОВЫЕ KPI И ТЕКУЩИЙ СТАТУС

В проекте используются два слоя KPI:

### 7.1 Backtest KPI (из `src/backtest/replay_engine.py`)
Текущий бэктест возвращает и сохраняет в `metrics_summary.json`:
- `Total Return (%)`
- `Max Drawdown (%)`
- `Sharpe Ratio`
- `Win Rate (%)`
- `Profit Factor`
- `Total Trades`
- `Gross Profit`
- `Gross Loss`

Это базовый валидный MVP-набор для сравнения конфигураций.

### 7.2 Realtime Product KPI (из `src/core/metrics_engine.py` / `MetricsSnapshot`)
Реализована инфраструктура и поля под расширенный продуктовый набор метрик (включая HFT-направление):
- OBI micro/macro, mid, spread;
- Kyle’s Lambda (volume-bucket);
- VWAP 1h, VWAP deviation, Anchored VWAP (+ OI bonus-flag);
- Hurst exponent;
- ATR (1m, с заделом под 5m/15m);
- CVaR;
- OI delta, Funding cumulative;
- latency fields (`latency_us`, `latency_gate_blocked`);
- поля под regime/stat-arb/risk extensions (`hmm_regime`, `zscore_eth_btc`, `fractional_kelly`, `risk_of_ruin`, `mtf_alignment`).

Итог по состоянию MVP:
- базовые продуктовые KPI и контур метрик в коде присутствуют;
- часть advanced-полей уже задекларирована и используется как этап расширения Stage 2/3.

## РАЗДЕЛ 9: АРТЕФАКТЫ ВЫВОДА (OUTPUT)

Артефакты создаются модулем `reporter.py` после полного пробега скрипта `run_backtest.py`. Если `output.directory` не существует, она создается принудительно (чаще всего `output/`).

### 9.1 Файл `trade_log.csv`
- Исходный Формат: CSV
- Содержимое: `timestamp_open`, `timestamp_close`, `direction`, `entry_price`, `exit_price`, `qty`, `spend`, `net_pnl`, `exit_reason`, `holding_time`.
- Назначение: Пост-трейдинговый дебаг. Передаётся квантам (Quants) или аналитикам данных (Data Scientists) в Excel/Tableau.
- Пример: `2023-01-01 12:00:00, 2023-01-02 14:00:00, BUY, 39000, 42000, ...`

### 9.2 Файл `equity_curve.csv`
- Исходный Формат: CSV **с заголовком**, колонки `timestamp`, `balance` (как в `equity_df` репортера).
- Содержимое: Оценка капитала по барам (mark-to-market с учётом открытой позиции в конце шага).

### 9.3 Файл `metrics_summary.json`
- Исходный Формат: JSON
- Содержимое: Ключ-значение с KPI из Раздела 7.1 (в текущей версии — 8 основных полей).
- Назначение: Парсеры автоматизированного пайплайна (CI/CD Optimization), которые запускают мульти-тест гиперпараметров (Grid Search) и программно фильтруют лучшие конфиги.
- Пример: `{"Win Rate (%)": 45.2, "Profit Factor": 1.25, ...}`

### 9.4 Файл `report.html` 
- Исходный Формат: HTML/JS разметка (через Plotly).
- Назначение: Не требует подключения к интернету, может быть открыт в любом оффлайн-браузере. Отличный способ хранить портфолио тестов.

## РАЗДЕЛ 10: ИНСТРУКЦИЯ ПО ЗАПУСКУ БОТА

Этот раздел необходим, чтобы человек, скачавший проект с GitHub или получивший архив, смог запустить код в течение 3 минут.

### Шаг 1. Предварительные требования
1. **Python 3.9+**. Проверка версии: `python3 --version`.
2. Скаченные исторические данные. В корневой папке должна существовать директория `data/`, а внутри нее `BTCUSDT_1h.csv`.

### Шаг 2. Создание виртуального окружения и Установка Зависимостей
Откройте терминал на Mac/Linux и выполните (каждая строчка — отдельная команда):
```bash
# Переход в папку проекта (укажите свой путь)
cd /path/to/AI_Traiding_Bot

# Создание чистой песочницы
python3 -m venv venv

# Активация среды
source venv/bin/activate

# Установка всех зависимостей проекта (это критично!)
pip install -r requirements.txt
```
*Примечание:* пакет `pybit` подключается локально editable из каталога `pybit-master` в корне проекта (`-e ./pybit-master` в `requirements.txt`). Установка выполняется из корня репозитория, чтобы относительный путь был валиден.

### Шаг 3. Запуск Тестера через CLI
Если вам не нужен интерфейс, и вы хотите прогнать 10 конфигураций подряд, используйте базовый CLI интерфейс (Command Line Interface).
```bash
python run_backtest.py --config config.yaml
```
**Что ожидать (Results):** скрипт загрузит CSV, прогонит replay и создаст артефакты в `output/`:
- `trade_log.csv`
- `equity_curve.csv`
- `metrics_summary.json`
- `report.html`

### Шаг 4. Запуск визуального дашборда (MVP Backtester)
Веб-приложение запускается командой `streamlit`:
```bash
streamlit run app.py
```
Ожидание: Терминал выдаст локальную ссылку (`http://localhost:8501`), браузер откроется сам на странице UI. В левой панели нажмите "Начать симуляцию".

### Шаг 5. Запуск Live Engine (Bybit Testnet/Demo)
```bash
export BYBIT_API_KEY=your_key
export BYBIT_API_SECRET=your_secret
python main.py
```
По умолчанию live-торговля выключена в `config.yaml` (`live.enabled: false`).  
Для включения нужно явно изменить конфиг.

### Типичные ошибки и способы их разрешения
1. **`FileNotFoundError: CSV file not found ...`**: проверьте `data.csv_path` в `config.yaml`.
2. **`Missing BYBIT_API_KEY/BYBIT_API_SECRET`**: для live-режима не заданы env-переменные.
3. **Пустые сделки в backtest**: фильтр сигналов слишком строгий или период данных слишком короткий.
4. **`NotOpenSSLWarning` в urllib3**: предупреждение среды macOS LibreSSL; не блокирует backtest.
